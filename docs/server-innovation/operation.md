# 既存の週次運用へ接続する

## 作業を始める場所

既存の「サーバー構築ポートフォリオの週次改善」を一つだけ使います。
現在の週次監査、career、growthの正本と保存先を維持し、その出力を改善実験へ渡します。
月曜09:00 JSTの登録があっても、端末・アプリ・権限・利用可能枠等の実行条件に左右されます。
実際に動いたかは最新の実行記録で確認します。

GitHub Actionsには今回、判定ロジックのテストだけを追加しました。
別の定期収集workflowを作って二重に起動する構成にはしません。

## 週次処理の順番

以下の 1〜10 は[自律型ポートフォリオ改善イノベーションループ](../portfolio-loop/operation.md)の `run` が一括で行います。手動で進める場合の順序として残します。

1. 前回のlatest、pending、採否記録と既存の本人計画を読む。未公開の変更を消さない。
2. 既存 `cycle.mjs` に `tools/server-innovation/discovery.config.json` を渡し、3リポジトリ17ファイルを再取得する。収集失敗なら、その情報に依存する修正を進めない。
3. 既存careerとgrowthで計画・未達・再説明を確認する。今回の追加で本人の時間を増やさない。
4. 既存監査の緊急修正、レビュー待ち、実行中の改善実験があれば `occupied=true` とする。
5. 採否記録を照合し、候補除外IDと確認時刻をcontextへ記入する。`discovery.mjs cycle` で能動プローブ・新仮説の補充・既存planへの接続を実行する。
6. 上位の候補について最新の本文、後続記録、コード、既存PRを読む。終わった課題を再作成しない。
7. 空いている共通枠で一件だけ、実施カードまたはローカルのコード変更を作り、必要な既存検査を行う。
8. 実測結果がある場合は、登録計画と原本を `discovery.mjs feedback` へ渡す。evaluateの再実行、原本コピー、重複学習防止、追試と探索配分への反映を行う。
9. 出典・変更差分・PR原稿・検証・NOT RUN・次の判断を揃える。許可された範囲で公開へ進む。
10. 変化がある場合だけ、何が進み、次に誰の何の判断が必要かを既存タスクで伝える。

探索の実行仕様・独自提案の追加・却下・原本の再検証は[発火点の探索と学習](discovery.md)を参照します。
RESEARCH_REQUIREDでは、既存の収集範囲外の記録や別の前提を調べる問いを処理し、出典を確認した独自提案を追加できます。
新しい仮説が必要なときは、根拠のある複数案を比較し、古い候補を言い換えただけの登録は避けます。

既存の作業が実機待ちなら、その待ち状態を残して、独立してできるローカル準備を比較します。
ただし、レビュー待ちの変更を増やすために占有をfalseへ変えません。
45分以内に完了しない場合は、実装や検証を省略せず残件を保存し、次回の同じ一件として続けます。

## 私用の状態

| 保存物 | 更新方法 |
| --- | --- |
| `context.json` | 既存pending・時間枠・採否記録を読んで更新。本人の技能を入れない |
| `latest.json` | planが原子的に更新。意味が同じならnotify=false |
| `runs/<ID>/plan.json`、`report.md` | 観測ごとに追記保存 |
| `protocol.draft.json` | 新しい準備候補があるときだけ生成。条件を埋める前はDRAFT |
| `protocol.registered.json` | 実験開始前にregisterで新規保存。既存ファイルへの上書き拒否 |
| `context.json`と試行の原本 | 実験専用ディレクトリ。登録時の環境条件と各試行の証拠 |
| `results.json`と判定結果 | 測定値を入力し、evaluateの出力を別ファイルへ保存 |
| `decisions.md` | 採用・見直し・保留の理由、対象計画、根拠、担当、再開条件を記録 |

上表は既存planの保存形式です。追加したdiscoveryは別の保存先を使い、`latest.json`からhash付きの`runs/<ID>/state.json`・`result.json`・`report.md`を参照します。
feedbackの原本は同じ私用保存先の`feedback/<ID>/`にコピーし、次の読込時に再検証します。
新旧のlatestを同じディレクトリへ混在させません。最新参照が消え、履歴だけ残る場合も初期化せず復旧を要求します。

作業枠用contextと環境条件用contextは別のディレクトリで管理します。
環境条件のcontextは登録後に編集しません。条件が変われば別の実験計画へ分けます。
CLIは実測原本や本人の台帳を自動更新しません。

`closed` にIDを入れるのは、採用・却下・長期保留の記録を確認できる場合です。
保留解除や新しい版での再検討は理由を残してIDを除外対象から外します。
新CLI自体はdecisions.mdの文章を解釈しません。これらの状態対応は週次Codexが確認します。

## 採否記録のテンプレート

```text
候補ID:
実験計画ID・SHA-256:
判断日時・判断者:
判断: ADOPT / ITERATE / REJECT / PARK
根拠: 判定結果、全試行、原ログ、機能確認、制約
旧版・新版SHAと環境:
採用または見送る理由:
本人の時間と運用負担:
公開対象と許可の範囲:
関連PRと最終SHA:
公開後・別日再確認の結果:
再開条件・次に確認する日:
```

実験の `PROMISING` と人の `ADOPT` は異なります。
数値がよくても、未解決の依存関係、実施者の負担、保守の難しさを含めて判断します。

## 公開のために揃えるもの

タイトル、問題と変更後の動き、対象repoとbranch、変更ファイル、差分、必要な検証、NOT RUN、戻し方を揃えます。
公開済みの実測や本人の理解を広げる表現がないか、日付・環境・試験対象版を再照合します。
既存の公開許可があればその範囲で進め、今回と異なる変更の許可を流用しません。
マージは別の判断です。マージ後は当該SHAのCIと、公開先が変わる場合の表示・導線を確認します。

原ログにはホスト名・ユーザー・IP・秘密値が含まれる可能性があります。
私用の採録をそのまま公開用outputsへコピーせず、必要な範囲を確認して根拠と制約を残します。
今回の実装に秘密値を網羅的に検出して除去する機能はありません。

## 最初の4週間の進め方

| 週 | 共通枠で進めること | 完了を判断するもの |
| --- | --- | --- |
| 1 | 最新情報を読みINV-001の結果検査と比較条件を準備 | 差分、試験、登録前の実験票 |
| 2 | 既存計画に収まる測定を実施、または入力・実機前提を整える | 実施した全試行の記録。未実施なら理由 |
| 3 | 結果を評価し、別日確認または次の仮説を決める | PROMISING/ITERATE/REJECT等の根拠 |
| 4 | 採否と運用負担を見直す。次に進む候補を一件決める | 採否記録と次の計画 |

週数は目安です。本人の時間・就職活動・案件・実機条件に合わせて既存計画内で変更します。
実施していない週を埋めるために架空の測定や学習記録を作りません。

## 止める・戻す・再開する

同じ自動化を停止すると、次回の自律実行を止められます。稼働サーバーを停止する処理ではありません。
ロックが残ればPIDと実行中プロセスを確認し、停止した当該実行のロックだけを処理します。
state破損では最新の正常runと原本を照合して復元し、以前の実験票や結果を上書きしません。

公開後の不具合は、その変更のrevertと必要な再検証で戻します。
自動化の拡張を外す場合は、今回追加した運用段落を同じ自動化から外し、既存の監査・career・growthを保持します。
本人の計画や原記録を戻す操作は行いません。

再開時には最新SHA、open PR、保留事項、計画条件、作業枠を再取得します。
古い実験結果は歴史的記録として残し、新しいSHAの成功へ自動昇格させません。

## 毎月の問い

「何を何回作ったか」より、「困り事が一つ減ったか」「測る負担が重すぎないか」「誤検知を減らせたか」を見ます。
同じ原因の再発、採用後の不具合、本人の説明、受け手の質問から次の一件を選びます。
改善しなかった方法を保留にし、根拠のない提案を取り下げることも正常な結果です。
