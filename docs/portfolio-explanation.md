# 主作品を自分の言葉で説明する練習

このページは、[やさしい用語・見方ガイド](./beginner-guide.md)で読んだ仕組みを、声に出して説明し、自分の操作記録につなげる練習帳です。教材は [server](https://github.com/ns7jp/server) です。既存の実装や証跡を読んだことと、自分で構築・復旧したことを分けて話します。

最初は **目的 → 構成 → 確認 → 根拠 → 次の課題** の五つで話します。全文暗記よりも、この順番と各項目の意味を覚えます。

## 1. まず 30 秒で作品を紹介する

以下は**作品の内容を紹介する例**です。本人が操作したという主張は含みません。

> この作品は、Linux 上でアプリと監視を動かし、正常確認から障害対応まで学ぶ個人のラボです。数値は Prometheus が集め、Grafana が表示し、ログは Alloy と Loki で扱います。実装だけでなく、試験の記録と未実施の範囲を分けています。私は今、【自分の学習段階】を学んでいます。

【自分の学習段階】には、「構成を読んで説明する段階」「自分の VM で起動を試している段階」など、現在の事実を入れます。読む前から「構築しました」「復旧できました」に置き換えません。

練習は、文章を一度読む → 閉じて話す → 録音を聞く、の順です。30 秒を超えても、最初は意味を保つことを優先します。言いにくい用語は[入門ガイド](./beginner-guide.md)に戻って、自分の短い言葉に直します。

## 2. 次に 3 分で、根拠を添えて説明する

時間配分は練習用の目安です。以下の内容を一度に丸暗記せず、五つの項目を一つずつ話します。

| 時間の目安 | 項目 | 話す内容 |
| --- | --- | --- |
| 0:00〜0:25 | 目的 | 作って終わらせず、正常確認・異常の切り分け・復旧を学ぶ個人のラボである |
| 0:25〜1:10 | 構成 | Linux が土台、Compose が複数サービスを起動、Ansible が設定をそろえる。人の要求は Nginx からアプリへ届く |
| 1:10〜1:50 | 確認 | Prometheus が数値を取得し、Grafana が問い合わせて表示する。異常条件は Prometheus、通知の整理・配送は Alertmanager。ログは Alloy → Loki、検索は Grafana から行う |
| 1:50〜2:30 | 根拠 | 証跡台帳から一件だけ選び、日付・環境・対象の版・確認内容・未確認範囲を示す。本人の操作は下の記録がある範囲だけ話す |
| 2:30〜3:00 | 次の課題 | 今の未実施事項を一つ示し、何を見て完了とするかを話す |

構成を説明するときは[構成図](./architecture-diagram.md)、実測を説明するときは[主作品の証跡台帳](https://github.com/ns7jp/server/blob/main/docs/evidence/README.md)を開きます。たくさんの技術名を並べるより、**一つの経路を図と設定ファイルで指せること**を優先します。

### 記録済みの証跡を読む例

主作品の[2026-08-22 の E2E 記録](https://github.com/ns7jp/server/blob/main/docs/evidence/2026-08-22-full-stack-e2e.md)には、使い捨て Ubuntu 環境での一括構築や 2 回目の Ansible 適用などの結果があります。E2E は、複数の部品を組み合わせて端から端まで確認する試験です。

説明は「その日、その環境、その版で確認した記録があります」とします。現在の版も自分の端末でも同じ結果になることや、本人が内容を習得したことは、別の確認が必要です。ローカル webhook（HTTP で通知を受ける仕組み）への到達と Slack への実配信も区別します。

### 自分の担当・理解を問われたときの空欄台本

```text
目的: 私は【学びたいこと】を確かめるために取り組んでいます。
読んだ範囲: 【文書・設定ファイル】を読み、【役割・理由】を説明できます。
自分で行った操作: 【記録がある操作。未実施なら NOT RUN】です。
判定の根拠: 【出力の該当箇所】が【期待値】だったため、【範囲】を確認しました。
詰まったこと: 【実際の症状。経験がなければ未記入】です。
確認と対処: 【自分が行った確認・変更・再確認】です。
まだ言えないこと: 【未実施・未確認・未理解の内容】です。
次の一歩: 【一つの操作】を行い、【出力・状態】を残します。
```

コードや手順の作成で支援を受けた場合は、その範囲も説明します。「作成を支援された」「設定の意味を説明できる」「自分で変更して試験した」は、それぞれ別の事実です。

## 3. 自分の操作記録を一つ作る

最初の課題は、主作品の[初心者向け学習ガイド](https://github.com/ns7jp/server/blob/main/docs/beginner-learning-guide.md)から、今の段階に合う操作を一つ選ぶことです。前提確認から始め、app と Nginx の最小構成を動かします。環境がない場合は、先に[開始前診断](./learning-plan/00-start-here.md)へ進みます。下記は記入用であり、実行結果ではありません。

```text
題名: 【何を確認したか】
状態: NOT RUN
実施日時: 【記入待ち】
実行者・支援を受けた範囲: 【記入待ち】
環境: 【OS、VM / WSL / その他、確認対象。公開時は秘密情報を除く】
対象の版: 【git rev-parse HEAD の結果など】
参照した手順と番号: 【記入待ち】
目的: 【何を確かめたいか】
前提・中止条件: 【手順の前提がそろわなければ進めない】
戻し方: 【変更をする前に記入。読み取りだけなら変更なし】
実行したコマンド: 【記入待ち】
期待する結果: 【実行前に記入】
実際の結果: 【実行後、出力を保存して記入】
判定: 【期待値との一致 / 不一致、根拠となる行】
今回分かったこと: 【一文】
この結果だけでは分からないこと: 【一文】
次に確かめること: 【一つ】
証跡の保存先: 【秘密値を除いたログや画面の保存場所】
```

状態は、未実施なら `NOT RUN`、前提不足で進めないなら `BLOCKED`、実行結果が期待と不一致なら `FAIL`、決めた確認範囲で一致したなら `PASS` にします。失敗を正確に記録できた場合も学習は進んでいますが、試験結果を `PASS` に書き換えません。

パスワード、トークン、個人情報を証跡へ入れず、公開前に確認します。記録を残す詳しい観点は[証跡採録チェックリスト](./evidence-capture-checklist.md)、動画の構成は[デモ台本](./demo-script.md)を使います。記録のない成功談を、台本から補って書くことはしません。

## 4. 説明でよく聞かれること

以下は**仕組みの回答例**です。自分の経験を聞かれた場合は、前の記録欄を根拠に答えます。

| 質問 | 回答の組み立て方 |
| --- | --- |
| 何を作った作品ですか | 個人の Linux 監視ラボです。アプリの応答、数値、ログを確認し、構築から復旧まで学ぶためのものです |
| なぜ監視が必要ですか | 起動した瞬間の成功だけでは、その後の状態が分からないからです。継続して観測し、異常が起きた時刻と状態を追えるようにします |
| Docker Compose と Ansible は同じですか | Compose はコンテナ群の構成と起動、Ansible はホストの設定や配備をそろえる役割です。この作品では組み合わせて使います |
| Grafana が落ちると収集も止まりますか | Grafana は表示側なので、それだけでは Prometheus の収集停止を意味しません。同じホスト自体が落ちた場合は両方に影響します |
| アラートは誰が検知して知らせますか | この作品では Prometheus が数値とルールで条件を判定し、Alertmanager が届いたアラートを整理して配送します。通知先での受信は別途確認します |
| `up=0` ならアプリ停止が原因ですか | Prometheus が対象の数値を取得できていない状態です。停止以外にも通信、認証、取得先設定などを調べます |
| `changed=0` なら全部正常ですか | その実行で Ansible が変更しなかったという結果です。対象・失敗の有無に加え、サービスの応答試験も確認します |
| DB はどこにありますか | 主作品の基本構成には業務データ用の DB を置いていません。監視データの保存先はあり、Web / AP / DB の練習は別の発展ラボです |
| AWS や Slack は経験済みですか | 実装と、実際の構築・配信記録を分けて答えます。記録がない実操作は `NOT RUN` です。関連コードを読んだ場合は読んだ範囲を述べます |
| 何が一番難しかったですか | 自分の記録から「症状 → 確認 → 原因または仮説 → 変更 → 再確認」を一件話します。記録がなければ、実体験として語らず次に試す内容を述べます |

知らない質問には「そこは未確認です。今分かっているのは【範囲】で、【文書・設定・試験】を確認します」と答えます。未確認を言えることも、確認範囲を正確に説明する練習です。

## 5. 見ずに答える確認問題

先に紙やメモへ答えを書き、その後で下の解答と比べます。文章の一致ではなく、役割と判断範囲が合っているかを確認します。

1. サーバーとクライアントの違いを、ブラウザーの例で説明してください。
2. Nginx、Gunicorn、Flask は、それぞれ何を担当していますか。
3. アプリの `/metrics` に要求を出すのは Prometheus と Grafana のどちらですか。
4. Grafana がグラフを表示するために問い合わせる相手は誰ですか。ログの場合は誰ですか。
5. この作品で数値の異常条件を判定する役と、通知を整理・配送する役は誰ですか。
6. `docker compose ps` の `Up` だけを見て「利用者から正常に使える」と言えますか。
7. CI の記録に復旧成功があれば「自分の端末で復旧を確認した」と言えますか。
8. アプリに接続できないとき、変更前に何を残し、変更後に何をしますか。

### 解答と、迷ったときの戻り先

| 問題 | 解答の要点 | 戻り先 |
| --- | --- | --- |
| 1 | ブラウザーは要求するクライアント、Web サーバーは要求に応答する側。固定した機器の種類だけを表す言葉ではない | [入門ガイド 1](./beginner-guide.md#1-この作品は何を作っているのか) |
| 2 | Nginx は入口で中継、Gunicorn は Flask アプリを動かし、Flask アプリが応答を作る | [入門ガイド 3](./beginner-guide.md#3-通信と監視を三つの経路で覚える) |
| 3 | Prometheus が定期取得する。取得先の設定は `scrape_configs` にある | [入門ガイド 3](./beginner-guide.md#3-通信と監視を三つの経路で覚える) |
| 4 | 数値は Prometheus、ログは Loki に問い合わせる。Grafana 自体がこの収集の正本ではない | [入門ガイド 3](./beginner-guide.md#3-通信と監視を三つの経路で覚える) |
| 5 | Prometheus がルールで判定し、Alertmanager が通知を整理・配送する。受信先で届いたことも確認する | [入門ガイド 3](./beginner-guide.md#3-通信と監視を三つの経路で覚える) |
| 6 | 言えない。コンテナの稼働に加え、期待した経路から応答・内容などを確認する | [入門ガイド 4](./beginner-guide.md#4-コマンドを目的から選ぶ) |
| 7 | 言えない。記録の日時・環境・版の結果であり、本人の再現は自分の操作記録が必要 | [入門ガイド 6](./beginner-guide.md#6-作品の証跡と自分の習得を分ける) |
| 8 | 対象・時刻・症状・直前の変更・状態・ログを保存する。戻し方を決めて一つ変更し、同じ試験で期待値と再比較する | [入門ガイド 5](./beginner-guide.md#5-構築と障害対応を一巡する) |

## 6. 説明と操作を別々に確かめる

| 段階 | 自分で確認する条件 | 記録するもの |
| --- | --- | --- |
| 説明の練習 | 目的を一文で話し、通信・数値・ログの経路を描き、上の 8 問を自分の言葉で答える | 回答と、説明できなかった点 |
| 操作の練習 | 現在の学習段階の操作を行い、期待値と実際の出力を比較する | 自分の操作記録一件 |
| 第三者への説明 | 相手に「何のため・どう確認・どこまで実施」を言い直してもらい、伝わらなかった点を直す | 指摘と修正した説明 |

これは学習を進めるための自己確認です。読了だけで実機の構築・復旧や、採用での評価が保証されるものではありません。教材が初心者に再現できるかを確認した場合は、別途[第三者再現テスト記録](./learning-plan/beginner-usability-test.md)へ残します。

次は[主作品の初心者向け学習ガイド](https://github.com/ns7jp/server/blob/main/docs/beginner-learning-guide.md)で操作を一つ進め、記録を使って 30 秒と 3 分の説明を更新します。最小構成を確認できたら、[一本道ラーニングパス](https://github.com/ns7jp/server/blob/main/docs/learning-path.md)で監視・自動化・復旧へ範囲を広げます。
