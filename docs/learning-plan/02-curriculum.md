## Phase 1: Linux 基礎（W1-W4）

**フェーズの目的**: 1 台の Linux サーバーを、渡された条件どおりに初期構築できるようになる。

### W1 OS インストールと基本操作

- **学習項目**: シェルとコマンドの基本 / ディレクトリ構造（FHS）と主要ディレクトリの役割 / 絶対パスと相対パス / ファイル操作（`cp` `mv` `rm` `mkdir`）/ 閲覧（`cat` `less` `head` `tail`）/ 検索（`find` `grep`）/ リダイレクトとパイプ / `man` の読み方 / `vi` の最低限（挿入・保存・終了・検索・置換）/ アーカイブと圧縮（`tar` `gzip`）
- **ハンズオン**:
  - VM を 1 台作成し、[初期設定チェックリスト](./01-environment.md)を最後まで実施する
  - `/etc` `/var` `/usr` を探索し、それぞれ何が置かれているかを 1 行ずつメモする
  - 端末を 2 つ開き、片方で `tail -f /var/log/auth.log`（RHEL 系は `/var/log/secure`）を表示したまま、もう片方から SSH ログインしてログの変化を観察する
  - `find` と `grep` を組み合わせ、特定の文字列を含む設定ファイルを探す
- **到達確認**:
  - `/var/log` 配下で直近 1 時間以内に更新されたファイルを列挙できる
  - `vi` で設定ファイルを開き、指定行を書き換えて保存・終了できる
  - コマンドの出力をファイルへ保存し、エラー出力だけを別ファイルへ分けられる
- **つまずきやすい点**: `vi` から抜けられない（`Esc` → `:q!`）/ `rm -rf` の実行事故（`ls` で対象を確認してから実行する習慣をつける）/ カレントディレクトリの取り違え

### W2 ユーザー・グループ・パーミッション

- **学習項目**: ユーザーとグループの管理 / `/etc/passwd` `/etc/shadow` `/etc/group` の内容 / パーミッションの読み方と数値表記 / 所有者・所有グループの変更 / `umask` / SUID・SGID・スティッキービット / `sudo` と `sudoers` / SSH 公開鍵認証の仕組み
- **ハンズオン**:
  - 一般ユーザー 3 つと共有グループ 1 つを作り、共有ディレクトリを SGID 付きで作成する
  - `sudo` で特定コマンドだけを許可する設定を書き、許可外のコマンドが拒否されることを確認する
  - 公開鍵認証を設定し、鍵ファイルのパーミッションをわざと `644` にして接続失敗を再現する
  - アプリ用ユーザーがログファイルへ書き込めない状況を作り、原因を `ls -l` と `id` の出力から説明する
- **到達確認**:
  - ディレクトリの実行権（`x`）が何を意味するかを説明できる
  - 「読めるのに書けない」「入れるのに一覧できない」状態を意図的に作れる
  - 鍵認証が失敗したとき、サーバー側ログのどこを見るか分かる
- **つまずきやすい点**: ディレクトリの `x` とファイルの `x` の違い / `~/.ssh` は `700`、`authorized_keys` は `600` / `sudo su -` を癖にしない

### W3 プロセス・サービス・ログ

- **学習項目**: プロセスとシグナル（`ps` `top` `kill`）/ 親子関係と PID / systemd の考え方 / unit ファイルの構造 / `systemctl`（起動・停止・自動起動・状態確認）/ `journalctl` の絞り込み / rsyslog と `/var/log` / `logrotate` / `cron` と systemd timer
- **ハンズオン**:
  - 5 行程度のシェルスクリプトを書き、systemd サービスとして登録して自動起動を有効にする
  - スクリプト内のパスをわざと相対パスにして起動失敗させ、`journalctl -u` で原因を特定する
  - `Restart=on-failure` を設定し、プロセスを `kill` して自動復帰することを確認する
  - 自作ログに `logrotate` を設定し、強制実行してローテーションを確認する
  - `cron` と systemd timer の両方で同じ定期処理を組み、実行痕跡をログで確認する
- **到達確認**:
  - サービスが起動しないとき、状態確認 → ログ確認 → 設定確認の順で追える
  - `systemctl restart` と `reload` の違いを説明できる
  - 特定サービスの直近 30 分のログだけを抽出できる
- **つまずきやすい点**: unit の `Type` 指定 / systemd 配下では対話的な環境変数が使えない / unit を書き換えたら `daemon-reload` が必要

### W4 ディスク・ファイルシステム・シェルスクリプト

- **学習項目**: パーティションとファイルシステム / `mount` と `/etc/fstab` / LVM の概念（PV・VG・LV）と拡張 / `df` `du` `lsblk` `findmnt` / inode / スワップ / シェルスクリプト（変数・条件分岐・ループ・終了ステータス・`set -euo pipefail`・引数処理）
- **ハンズオン**:
  - 仮想ディスクを 1 本追加し、LVM で構成して `/data` にマウントし、`/etc/fstab` へ永続設定する
  - LV を後から拡張し、ファイルシステムを online で拡張する
  - `/data` を意図的に 100% まで埋め、原因ファイルを特定して復旧する
  - `/etc/fstab` をわざと誤記して起動失敗させ、レスキューモードから復旧する（**スナップショット必須**）
  - 指定ディレクトリを日付付きで固めて保存し、7 世代より古いものを削除するバックアップスクリプトを書く
- **到達確認**:
  - `df` では空きがあるのに書き込めない状況（inode 枯渇、削除済みファイルをプロセスが保持）を説明できる
  - `fstab` の誤記が起動に与える影響を理解し、復旧できる
  - 自作スクリプトが異常時に非ゼロで終了し、ログを残す
- **つまずきやすい点**: `fstab` の記述ミスは起動不能に直結する（`mount -a` で検証してから再起動）/ ファイル削除後も容量が戻らないケース

**Phase 1 の成果物**: 初期構築手順書 v1（[01 学習環境](./01-environment.md)のチェックリストに、コマンドと想定結果を追記したもの）

## Phase 2: ネットワーク基礎（W5-W8）

**フェーズの目的**: 「つながらない」を、勘ではなく順番で切り分けられるようになる。

### W5 TCP/IP とアドレス設計

- **学習項目**: OSI 参照モデルと TCP/IP モデル / Ethernet と MAC アドレス / ARP / IP アドレスとサブネットマスク / CIDR とサブネット計算 / ルーティングテーブルとデフォルトゲートウェイ / `ip` コマンド（`ip a` `ip r` `ip n`）/ 設定の永続化（netplan / NetworkManager）
- **ハンズオン**:
  - サブネット計算を 20 問解く（ネットワークアドレス・ブロードキャスト・利用可能ホスト数）
  - ラボ VM の `ip a` `ip r` の出力を読み、どの経路でホスト PC と通信しているか図にする
  - 静的ルートを追加・削除し、`ip r get <宛先>` で選択される経路を確認する
  - デフォルトゲートウェイをわざと誤設定し、通信できなくなることと復旧手順を確認する
- **到達確認**:
  - `/24` `/26` `/27` の利用可能ホスト数を暗算できる
  - 自分のラボの通信経路をホワイトボード 1 枚で説明できる
  - 一時設定と永続設定の違いを理解し、再起動後も設定が残ることを確認できる
- **つまずきやすい点**: 一時設定（`ip` コマンド）は再起動で消える / 古い教材の `ifconfig` `route` は非推奨環境がある

### W6 名前解決とアドレス配布

- **学習項目**: DNS の階層構造（ルート・権威・キャッシュ）/ 再帰問い合わせと反復問い合わせ / レコード種別（A / AAAA / CNAME / MX / NS / TXT / PTR）/ TTL / `/etc/hosts` と `/etc/resolv.conf` の優先順位 / systemd-resolved / DHCP の流れ / 内部 DNS の役割
- **ハンズオン**:
  - `dig +trace` でルートから権威サーバーまでの解決過程を追い、各段階を説明する
  - 権威サーバーへ直接問い合わせ、キャッシュ経由の結果と TTL の減り方を比較する
  - `/etc/hosts` で名前を別 IP に向け、アプリの接続先が変わることを確認する
  - ラボ内に簡易 DNS を立て、`lab-web01.lab.local` などの内部名で解決できるようにする
  - DNS 設定だけを壊し、「IP では通るが名前では通らない」状態を再現する
- **到達確認**:
  - 名前解決の流れを、`dig` の出力を指しながら説明できる
  - 名前解決の失敗とサービス断を区別できる
  - TTL がキャッシュと切り替え作業に与える影響を説明できる
- **つまずきやすい点**: 手元のキャッシュに惑わされる / `resolv.conf` が自動生成で上書きされる環境がある

### W7 ポート・ファイアウォール・SSH の実務

- **学習項目**: TCP と UDP / 3 ウェイハンドシェイク / ポートと待ち受け / `ss` の読み方 / firewalld のゾーンとサービス / ufw / nftables の考え方 / SSH の設定（`sshd_config`、鍵、`~/.ssh/config`、`ProxyJump` による踏み台経由、ポートフォワード）/ SELinux の基本（Enforcing / Permissive、ポートラベル、denial ログ）
- **ハンズオン**:
  - Web サーバーのポートを開閉し、`ss -tlnp` と外部からの接続結果の対応を確認する
  - 踏み台ホスト経由で DB ホストへ接続する設定を `~/.ssh/config` に書く
  - ローカルポートフォワードで、外部公開していない管理画面をホスト PC のブラウザから開く
  - RHEL 系で標準外ポート（例: 8080）を使い、SELinux による拒否を発生させてから許可設定を入れる
- **到達確認**:
  - 「ファイアウォールで閉じている」「サービスが起動していない」「別 IP で待ち受けている」を区別できる
  - 踏み台経由の接続を、鍵をコピーせずに実現できる
  - SELinux の拒否ログを見つけ、対処方針を説明できる（無効化は最後の手段と理解している）
- **つまずきやすい点**: firewalld は `--permanent` と `--reload` の組み合わせ / `127.0.0.1` にしか待ち受けていない設定 / SELinux を反射的に無効化しない

### W8 パケットキャプチャと切り分け演習

- **学習項目**: `tcpdump` の基本フィルタと出力の読み方 / Wireshark での可視化 / TLS ハンドシェイクの流れ / HTTP リクエストとレスポンスの観察 / `curl -v` `nc` `traceroute` `mtr` / 切り分けの順序（物理 → リンク → ネットワーク → トランスポート → アプリケーション）
- **ハンズオン**:
  - ホスト PC → Nginx → アプリケーションの通信を `tcpdump` で観察し、パケットの流れを図にする
  - HTTPS 通信をキャプチャし、ハンドシェイクと暗号化後の区間を区別する
  - 次の 5 種の障害を 1 つずつ仕込み、**原因を知らない状態で**切り分ける（仕込みは前日に行い、翌日に自分で解く）
    - NIC のリンクダウン相当（インターフェース停止）
    - デフォルトゲートウェイの誤設定
    - DNS の誤設定
    - ファイアウォールによるポート閉塞
    - バックエンドサービスの停止
  - 各障害について「どのコマンドで・何が見えて・何が分かったか」を一次メモに残す
- **到達確認**:
  - 「ping は通るが HTTP が返らない」状態の原因を 5 分以内に特定できる
  - 切り分けを下位層から順に実施し、飛ばした層がないことを説明できる
  - 一次メモが、後から自分以外にも読める形で残っている
- **つまずきやすい点**: `tcpdump` の実行権限 / 名前解決で出力が止まる（`-n` を付ける）/ フィルタを盛りすぎて必要なパケットを落とす

**Phase 2 の成果物**: ネットワーク切り分けの一次メモ（本リポジトリの[証跡採録チェックリスト 優先 4](../evidence-capture-checklist.md) に対応）

## Phase 3: ミドルウェア構築（W9-W12）

**フェーズの目的**: Web / AP / DB の 3 層構成を、TLS 込みで構築できるようになる。

### W9 Web サーバーの構築

- **学習項目**: Nginx と Apache の特徴と使い分け / 設定ファイルの構造と読み込み順 / バーチャルホスト / 静的コンテンツの配信 / アクセスログとエラーログ / ログフォーマットの設計 / ドキュメントルートの権限設計 / 主要ステータスコードの意味
- **ハンズオン**:
  - Nginx を導入し、2 つのバーチャルホストを名前ベースで構成する
  - アクセスログのフォーマットに応答時間と上流サーバーを追加する
  - `403` `404` `502` を意図的に発生させ、それぞれエラーログにどう記録されるかを比較する
  - 設定ミスを入れた状態で構文チェックを実行し、反映前に検知できることを確認する
- **到達確認**:
  - `403` の原因を 3 種類挙げ、それぞれ再現できる
  - 設定変更を無停止で反映する方法と、再起動が必要な場面を区別できる
  - ログから特定 IP のアクセスだけを抽出できる
- **つまずきやすい点**: 権限や SELinux によるアクセス拒否 / 構文チェックせずに再起動して落とす / 設定の include 順による上書き

### W10 TLS とリバースプロキシ

- **学習項目**: HTTPS の仕組み / 秘密鍵・CSR・証明書・中間証明書・証明書チェーン / 自己署名証明書と公的証明書 / Let's Encrypt の自動更新 / 有効期限の監視 / リバースプロキシの役割 / `X-Forwarded-For` と `X-Forwarded-Proto` / タイムアウト設定 / アプリケーションサーバーとの連携と systemd 化
- **ハンズオン**:
  - 自己署名証明書を作成して HTTPS 化し、`openssl s_client` で発行者・有効期限・チェーンを確認する
  - 有効期限を数分後に設定した証明書を作り、期限切れ時のブラウザとコマンドの挙動を確認する
  - アプリケーションサーバーを背後に置き、Nginx からリバースプロキシする
  - バックエンドを停止して `502`、応答を遅延させて `504` を再現し、ログの違いを比較する
  - クライアント IP がアプリ側のログに正しく記録されるようヘッダを設定する
- **到達確認**:
  - `openssl s_client` の出力から証明書の問題を指摘できる
  - `502` と `504` の切り分け手順を説明できる
  - 証明書の期限切れを事前に検知する仕組みを 1 つ実装できる
- **つまずきやすい点**: 中間証明書の設定漏れ（ブラウザでは通るが `curl` で失敗する）/ 秘密鍵と証明書の不一致 / プロキシ配下でリダイレクト先が `http` に戻る

### W11 データベースの構築とリストア試験

- **学習項目**: RDBMS の基本 / インストールと初期設定 / データベースとユーザーの作成 / 権限の最小化 / 接続方式（TCP とローカルソケット）/ 文字コードと照合順序 / 主要な設定パラメータ / 論理バックアップと物理バックアップ / リストア手順 / スロークエリログ
- **ハンズオン**:
  - DB サーバーを構築し、アプリ用ユーザーに必要最小限の権限だけを付与する
  - 別ホストのアプリから接続できるよう待ち受けアドレスとファイアウォールを設定する
  - テストデータを投入し、論理バックアップを取得する
  - **別の空のデータベースへリストアし、件数とデータ内容を照合する**
  - 接続失敗を 3 パターン（権限・待ち受けアドレス・ファイアウォール）作り、エラーメッセージの違いを記録する
- **到達確認**:
  - **リストア試験まで完了している**（取得しただけのバックアップは成果物として数えない）
  - 接続エラーのメッセージから、原因の当たりを付けられる
  - バックアップの取得時刻と復旧可能な時点の関係を説明できる
- **つまずきやすい点**: 待ち受けアドレスが `localhost` のまま / ユーザーのホスト指定 / 文字コード不一致による文字化け

### W12 3 層統合と共通設定

- **学習項目**: 3 層構成の統合 / 名前解決の設計（hosts か内部 DNS か）/ 時刻同期の重要性 / ログの時刻とタイムゾーン / 起動順序と依存関係 / リソース監視の初歩（`top` `vmstat` `iostat`）/ 再起動試験 / 構成図の書き方
- **ハンズオン**:
  - Web / AP / DB を 3 台に分離し、内部名で相互接続する
  - 全台を同時に再起動し、**手作業なしでサービスが復帰する**ことを確認する
  - DB を停止した状態でアプリを起動し、依存関係の問題を再現してから対策を入れる
  - 負荷をかけた状態でリソースを観察し、どの指標が先に頭打ちになるかを記録する
  - 1 台の時刻を意図的にずらし、ログの突き合わせが困難になることを体験する
- **到達確認**:
  - 全台再起動後に、人手を介さずサービスが復帰する
  - 構成図（台数・IP・ポート・通信方向）を 1 枚で説明できる
  - 「どこが遅いか」を切り分ける最初の 3 コマンドを挙げられる
- **つまずきやすい点**: 起動順序への依存を放置する / 時刻ずれによる調査難航 / 単体では動くのに結合すると通らない

**Phase 3 の成果物**: 3 層構成ラボ一式と構成図

## Phase 4: 構築工程の実務（W13-W16）

**フェーズの目的**: 技術ではなく**仕事の進め方**を身につける。構築エンジニアの評価軸が最も集中する 4 週間です。
各週の詳細なテンプレートは [03 構築工程の実務ドキュメント](./03-build-process.md) にあります。

### W13 設計書とパラメータシート

- **学習項目**: 要件定義・基本設計・詳細設計の役割分担 / 機能要件と非機能要件 / パラメータシートの構成 / 命名規則とアドレス設計 / 設計の前提と制約の書き方 / 決定理由を残す意味
- **ハンズオン**:
  - Phase 3 で構築したラボを「案件」に見立て、**後追いでパラメータシートを作成する**
  - ホスト・OS・ネットワーク・ディスク・ユーザー・ミドルウェア・ログ・バックアップ・監視の各項目を埋める
  - 実機の設定値とシートの値を突き合わせ、差分をすべて解消する
  - 選定理由を 3 件（OS・Web サーバー・DB）について、選ばなかった候補と比較して書く
- **到達確認**:
  - シートだけを渡された人が、同じ環境を作れる粒度になっている
  - 実機とシートに差分がない
  - 「なぜこの値にしたか」を説明できない項目が残っていない
- **つまずきやすい点**: 実機に合わせてシートを直すのではなく、**シートに合わせて実機を直す**場面がある / 既定値を書かずに省略してしまう

### W14 構築手順書

- **学習項目**: 手順書の構成（前提・準備・作業手順・確認・切り戻し）/ コマンドと想定結果の書き方 / 作業前後の確認項目 / 想定外が起きたときの中断条件 / 作業ログの取得方法
- **ハンズオン**:
  - パラメータシートをもとに、**まっさらな VM から Phase 3 の構成を再現する手順書**を書く
  - 手順書だけを見て、実際に新しい VM へ構築する（記憶に頼らない）
  - 詰まった箇所・不足した記述をすべて手順書へ反映し、第 2 版を作る
  - 作業中の端末ログを取得し、実行内容が後から追える形で保存する
- **到達確認**:
  - 手順書のみで、初期状態から 1 日以内に環境を再現できる
  - すべての手順に「想定結果」が書かれている
  - 切り戻し手順が、作業手順と同じ粒度で書かれている
- **つまずきやすい点**: 自分だけが分かる省略 / 想定結果の欠落 / 切り戻しを「元に戻す」の 1 行で済ませてしまう

### W15 試験項目書とエビデンス

- **学習項目**: 単体試験・結合試験・総合試験の違い / 正常系と異常系 / 試験項目の粒度 / 期待結果の書き方 / エビデンスの取得と保管 / 秘密情報のマスキング / 不具合の記録と再試験
- **ハンズオン**:
  - 3 層構成に対する試験項目書を作成する（**異常系を全体の 3 割以上**含める）
  - 全項目を実施し、実測結果とエビデンスを残す
  - 意図的に 1 件を失敗させ、不具合票を書いてから修正・再試験する
  - エビデンスに実行日時・対象ホスト・コマンド・出力が揃っているか点検する
- **到達確認**:
  - 試験項目書のすべての行に、実施日と実測結果が入っている
  - 異常系の項目に「期待するエラーの内容」が具体的に書かれている
  - エビデンスから秘密値・個人情報がマスクされている
- **つまずきやすい点**: 正常系だけの試験になる / 「問題なし」だけのエビデンス / 再試験の記録が残らない

### W16 移行・切り戻し・運用引き継ぎ

- **学習項目**: 移行方式の考え方 / リハーサルの必要性 / 当日手順とタイムテーブル / 切り戻しの判断基準と期限 / 関係者への連絡 / 運用引き継ぎ資料（運用手順書・監視設計・連絡体制）/ 引き継ぎ後の問い合わせ対応
- **ハンズオン**:
  - 既存ラボから新環境へ「移行する」想定で、当日タイムテーブルを作る（分単位）
  - 切り戻しの判断基準を数値で決める（例: 開始 60 分で確認項目 A が通らなければ切り戻す）
  - リハーサルを 1 回実施し、想定と実測の所要時間の差を記録する
  - 運用引き継ぎ資料として、日常運用・障害時の一次対応・エスカレーション基準を 1 枚にまとめる
- **到達確認**:
  - 切り戻し判断が、感覚ではなく基準で説明できる
  - リハーサル結果を反映して当日手順を修正している
  - 引き継ぎ資料だけで、構築に関わっていない人が一次対応を開始できる
- **つまずきやすい点**: 切り戻し期限を決めずに作業を続けてしまう / 引き継ぎ資料が構築者視点のままで、運用者に伝わらない

**Phase 4 の成果物**: パラメータシート / 構築手順書 / 試験項目書 / 移行手順・切り戻し手順 / 運用引き継ぎ資料

## Phase 5: 自動化・IaC（W17-W20）

**フェーズの目的**: Phase 4 までの手作業を、再実行できる形へ変換する。

### W17 Git とバージョン管理・変更管理

- **学習項目**: Git の基本操作（`clone` `add` `commit` `push` `pull`）/ ブランチとマージ / コンフリクトの解消 / `.gitignore` / コミットメッセージの書き方 / プルリクエストによるレビュー / 変更管理の考え方（変更理由・影響範囲・確認結果・切り戻し）
- **ハンズオン**:
  - 設定ファイル・手順書・スクリプトをリポジトリで管理する
  - 変更ごとにブランチを切り、変更理由が分かるコミットメッセージを書く
  - **秘密情報を誤ってコミットしない仕組み**（`.gitignore` と設定値の分離）を入れる
  - プルリクエストの本文に、変更理由・確認結果・切り戻し手順を書く運用を始める
- **到達確認**:
  - 半年後の自分が読んで、変更理由が分かるコミット履歴になっている
  - 秘密値がリポジトリに含まれていないことを確認できる
- **つまずきやすい点**: 秘密情報の誤コミット（履歴に残るため取り消しが困難）/ コミット粒度が大きすぎて追えない

### W18 シェルスクリプトによる定型化

- **学習項目**: 実務で使うスクリプトの設計（引数・終了ステータス・ログ出力・冪等性の意識）/ エラーハンドリング / ロックによる多重起動防止 / systemd timer との組み合わせ / 実行結果の通知
- **ハンズオン**:
  - 日次バックアップと世代管理を行うスクリプトを実務水準で書き直す（ログ・エラー処理・多重起動防止つき）
  - 環境チェックスクリプトを書く（サービス稼働・ディスク使用率・証明書残日数・時刻同期を一括確認）
  - 失敗時に通知が飛ぶよう組み込み、**わざと失敗させて通知を確認する**
- **到達確認**:
  - スクリプトが失敗したことに、人が気付ける仕組みになっている
  - 同じスクリプトを 2 回実行しても問題が起きない
- **つまずきやすい点**: 成功時しかテストしない / cron 環境ではパスや環境変数が対話シェルと異なる

### W19 Ansible による構成管理

- **学習項目**: 構成管理の目的 / インベントリ / playbook とタスク / モジュールの選び方 / 変数と `group_vars` / テンプレート / role への分割 / 冪等性 / `--check` と `--diff` / 機密情報の取り扱い / 構文チェックと Lint
- **ハンズオン**:
  - Phase 4 の構築手順書を、そのまま playbook へ書き換える
  - **2 回実行して変更が発生しない**（冪等）ことを確認する
  - 共通設定を role として切り出し、新しい VM へ適用して同じ環境が再現できることを確認する
  - `--check` で事前差分を確認してから適用する運用にする
- **到達確認**:
  - 手順書と playbook の内容が一致している
  - 2 回目の実行で変更ゼロになる
  - 新規ホストへ適用して、同一構成が再現できる
- **つまずきやすい点**: `command` モジュールの多用で冪等性が壊れる / 変数の優先順位 / 手順書と playbook が乖離していく

### W20 コンテナによる構成再現

- **学習項目**: コンテナと仮想マシンの違い / イメージとレイヤ / Dockerfile の書き方 / ボリュームと永続化 / ネットワーク / Docker Compose による複数サービス構成 / ログの扱い / 本番利用時の注意点（権限・イメージの更新）
- **ハンズオン**:
  - 3 層構成を Docker Compose で再現し、`docker compose up` で起動できるようにする
  - 非 root ユーザーで動くイメージを作る
  - データを永続化し、コンテナを削除してもデータが残ることを確認する
  - VM 構成とコンテナ構成の**それぞれの利点と限界**を、自分の言葉で 5 行にまとめる
- **到達確認**:
  - 1 コマンドで 3 層構成が起動する
  - コンテナを作り直してもデータが失われない
  - 「コンテナでよい場面」と「VM が適する場面」を説明できる
- **つまずきやすい点**: 永続化の設計漏れ / コンテナ内で `systemd` を使おうとする / ログの出力先が変わることへの未対応

**Phase 5 の成果物**: Ansible role 一式とコンテナ構成、変更履歴の残ったリポジトリ

## Phase 6: クラウド・監視・仕上げ（W21-W24）

**フェーズの目的**: クラウド上に再構築し、監視・バックアップ・復旧まで通して「運用に渡せる状態」にする。

### W21 クラウド基礎

- **学習項目**: クラウドの責任共有モデル / リージョンとアベイラビリティゾーン / 仮想ネットワークとサブネット / ルートテーブルとゲートウェイ / セキュリティグループ / 仮想サーバー / オブジェクトストレージ / マネージド DB / IAM と権限設計 / 課金の仕組み
- **ハンズオン**:
  - [01 学習環境](./01-environment.md)の課金ガード 6 項目を先に設定する
  - 仮想ネットワークとサブネットを作り、仮想サーバーを 1 台起動して SSH 接続する
  - セキュリティグループでアクセス元を自分の IP のみに限定する
  - **同日中にすべて削除**し、翌日に請求額を確認して記録する
- **到達確認**:
  - オンプレのラボ構成と、クラウド上の構成要素を対応付けて説明できる
  - 作成したリソースを、消し漏れなく削除できる
  - 想定外課金を防ぐ仕組みを説明できる
- **つまずきやすい点**: 削除漏れによる課金（未使用の固定 IP・ロードバランサー・スナップショット）/ ルートユーザーでの作業

### W22 Terraform によるコード化

- **学習項目**: IaC の目的 / `plan` と `apply` の違い / state の役割と保管 / 変数と出力 / モジュール化 / `destroy` / コードレビューと変更管理の接続
- **ハンズオン**:
  - W21 で手作業した構成を、そのまま Terraform で書き直す
  - `plan` の出力を読み、**適用前に何が変わるか**を説明できる状態で `apply` する
  - 設定値を変更して再適用し、差分だけが反映されることを確認する
  - `destroy` で完全に削除し、コンソールで残骸がないことを確認する
- **到達確認**:
  - `plan` の差分を読んで、意図しない変更に気付ける
  - 同じコードから同じ環境が再現できる
  - state を安全に扱う必要性を説明できる
- **つまずきやすい点**: state の紛失・共有 / 手作業の変更とコードの乖離 / `destroy` 漏れ

### W23 監視・バックアップ・復旧演習

- **学習項目**: 監視の 4 分類（死活・リソース・ログ・外形）/ 監視項目としきい値の決め方 / 通知設計とアラート疲れ / ダッシュボードの構成 / バックアップ方式と保管世代 / 目標復旧時間と目標復旧時点の考え方 / 復旧演習の進め方
- **ハンズオン**:
  - 監視ツールを導入し、CPU・メモリ・ディスク・プロセス死活・HTTP 応答を可視化する
  - しきい値超過で通知が飛ぶよう設定し、**負荷をかけて実際に発報させる**
  - 復旧後に「復旧しました」の通知が届くことも確認する
  - バックアップから復旧する演習を 1 回実施し、**検知から復旧までの所要時間を実測**する
  - 演習結果を記録し、手順書の不足を修正する
- **到達確認**:
  - 実際に発報した通知の記録がある（設定しただけでは数えない）
  - 復旧演習の所要時間が実測値で記録されている
  - しきい値を決めた理由を説明できる
- **つまずきやすい点**: 通知が多すぎて無視されるようになる / バックアップの取得だけで復旧を試さない / 演習を「成功させる」ことが目的化する

### W24 総仕上げとポートフォリオ化

- **学習項目**: 成果物の棚卸し / 公開時の秘密情報の点検 / 読み手に合わせた説明の順序 / 面接での説明の組み立て / 学習の継続計画
- **ハンズオン**:
  - Phase 1-6 の成果物を 1 つのリポジトリへ集約し、README から辿れるようにする
  - 秘密値・個人情報・実 IP・ホスト名がマスクされているか全ファイルを点検する
  - **「やったこと」と「コードは書いたが実行していないこと」を書き分ける**
  - 3 分・10 分の 2 パターンで、構成と設計判断を口頭説明する練習をする
  - 次の 3 か月の学習計画を作る（資格・未着手領域・実務で必要になる領域）
- **到達確認**:
  - 第三者が README から 5 分で全体像を把握できる
  - 公開物に秘密情報が含まれていない
  - 設計判断の理由を、選ばなかった選択肢と比較して説明できる
  - 「できていないこと」を正確に言える
- **つまずきやすい点**: 完成させてから公開しようとして機を逃す / 誇張した表現が深掘りで崩れる

**Phase 6 の成果物**: クラウド上の再構築コード、監視ダッシュボード、復旧演習の実測ログ、公開用ポートフォリオ
