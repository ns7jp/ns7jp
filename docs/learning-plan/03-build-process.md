# 03 構築工程の実務ドキュメント

> **本ドキュメントの位置付け**
>
> [学習プラン](./README.md) Phase 4（W13-W16）で使うテンプレート集です。
> 未経験者の学習は技術習得に偏りがちですが、**構築エンジニアの評価は「正確に作れるか」と同じ重みで「正確に残せるか」で決まります**。
> ここに載せているのは特定企業の様式ではなく、**どの現場でも共通する最小限の項目**です。実際の案件では会社の様式に従ってください。

最終更新: 2026-08-11

## 1. 工程と成果物の対応

| 工程 | 決めること | 主な成果物 | 未経験者の関与度 |
| --- | --- | --- | --- |
| 要件定義 | 何を・いつまでに・どこまでの品質で | 要件一覧、非機能要件 | 低い（読む側） |
| 基本設計 | 全体構成、方式、冗長性、監視方針 | 基本設計書、構成図 | 低い（読む側） |
| 詳細設計 | 設定値そのもの | **パラメータシート** | 中（作成補助） |
| 構築 | 作業手順と順序 | **構築手順書**、作業ログ | **高い（主担当）** |
| 試験 | 何をもって完成とするか | **試験項目書**、エビデンス | **高い（主担当）** |
| 移行 | 切り替え方法と切り戻し | 移行手順書、当日タイムテーブル | 中（作業担当） |
| 引き継ぎ | 運用の進め方 | 運用手順書、監視設計、連絡体制 | 中（作成補助） |

**太字が本ドキュメントで扱う 3 点**です。未経験者が最初に任される範囲と一致します。

## 2. パラメータシート

### 目的

「実機の設定値を、実機を見ずに把握できる状態」を作ります。
構築時の指示書であり、運用時の参照資料であり、障害時の比較対象にもなります。

### 記載項目

| 項目 | 記入例 | 備考 |
| --- | --- | --- |
| ホスト名 | `lab-web01` | 命名規則に従う |
| 役割 | Web / リバースプロキシ | |
| 環境区分 | 検証 | 本番 / ステージング / 検証 |
| 設置場所 | ローカル仮想環境 | オンプレ / クラウド / 仮想基盤 |
| 用途・備考 | 学習用 3 層構成の入口 | |

#### ログ・バックアップ・監視

| 項目 | 記入例 |
| --- | --- |

| バックアップ方式・世代 | 日次フル、7 世代 |
| 保管先 | 別ホストの `/backup` |
| 監視項目 | プロセス死活、HTTP 応答、CPU、メモリ、ディスク使用率 |
| しきい値 | ディスク 80% 警告 / 90% 重大 |

### 書くときの原則

1. **既定値も書く**。「既定のまま」と書かれていないと、設定漏れなのか意図なのか判別できません
2. **バージョンは正確に書く**。マイナーバージョンの差が挙動差になることがあります
3. **決めた理由を残す**。特に既定値から変えた項目は、理由を 1 行添えます
4. **実機と一致させる**。ずれたまま放置されたシートは、あるだけで害になります

## 3. 構築手順書

### 構成

```text
1. 概要
   1.1 目的
   1.2 対象ホスト
   1.3 前提条件（完了済みの作業、必要な権限、必要な資材）
   1.4 想定所要時間
2. 作業前確認
   2.1 現状確認コマンドと想定結果
   2.2 バックアップ・スナップショットの取得
3. 作業手順
   3.1 手順 1  … コマンド / 想定結果 / 判定
   3.2 手順 2  …
4. 作業後確認
   4.1 サービス稼働確認
   4.2 疎通確認
   4.3 ログ確認
5. 切り戻し手順
   5.1 切り戻しの判断基準
   5.2 切り戻し手順（作業手順と同じ粒度）
6. 記録
   6.1 実施者・実施日時
   6.2 作業ログの保管先
```

### 1 手順の書き方

| 項目 | 内容 |
| --- | --- |
| No | 手順番号 |
| 作業内容 | 何をするかを 1 行で |
| コマンド | 実行するコマンドをそのまま（変数部分は明示） |
| 想定結果 | 出力例、終了ステータス、画面表示 |
| 判定 | OK / NG の基準 |
| 備考 | 注意点、失敗時の対応 |

記入例：

| No | 作業内容 | コマンド | 想定結果 | 判定 |
| --- | --- | --- | --- | --- |
| 3-1 | Nginx の導入 | `sudo apt install -y nginx` | エラーなく完了し、パッケージが導入される | 終了ステータス 0 |
| 3-2 | 構文チェック | `sudo nginx -t` | `syntax is ok` と `test is successful` が表示される | 両方が表示される |
| 3-3 | 設定反映 | `sudo systemctl reload nginx` | 出力なし | 3-4 が active |
| 3-4 | 稼働確認 | `systemctl is-active nginx` | `active` | 一致 |

### 原則

1. **想定結果のない手順は書かない**。確認できない手順は、成功したかどうか判定できません
2. **「適宜」「必要に応じて」を使わない**。判断が必要なら、判断基準を書きます
3. **コピー＆ペーストで実行できる粒度**にする。環境依存の値は先頭にまとめて定義します
4. **切り戻し手順を同時に書く**。作業手順を書いた直後が、最も正確に書けるタイミングです
5. **手順書は「読んだ人が再現できたか」で評価する**。自分で試すのではなく、間を空けて自分に試させます

### 作業ログの取得

作業内容を後から追えるようにします。

```bash
# 端末のやり取りを丸ごと記録する
script -a /var/tmp/work_20260811_lab-web01.log

# 記録を終了する
exit
```

- ファイル名に**日付・対象ホスト・作業名**を含めます
- 保存前にパスワード・トークン・実 IP などをマスクします
- 学習ラボでも同じ運用にしておくと、そのまま現場の作法になります

## 4. 試験項目書

### 目的

「完成した」を、主観ではなく**合否判定**で示します。
試験項目書がないと、動いているように見えるだけの環境を納品してしまいます。

### 項目の書式

| No | 試験分類 | 観点 | 前提条件 | 手順 | 期待結果 | 実測結果 | 判定 | エビデンス | 実施日 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| T-01 | 単体 | Nginx 稼働 | サーバー起動済み | `systemctl is-active nginx` | `active` | `active` | OK | `t01.log` | 2026-08-11 |
| T-02 | 単体 | 自動起動 | OS 再起動後 | `systemctl is-enabled nginx` | `enabled` | | | | |
| T-03 | 結合 | HTTPS 応答 | 証明書設定済み | `curl -I https://lab-web01/` | `200` が返る | | | | |
| T-04 | 異常系 | バックエンド停止時 | AP 停止 | `curl -I https://lab-web01/app` | `502` が返り、エラーログに記録される | | | | |
| T-05 | 異常系 | 不正な接続元 | 別セグメントから | `ssh lab-web01` | 接続が拒否される | | | | |
| T-06 | 総合 | 再起動後の復帰 | 全台再起動 | 一連の疎通確認 | 人手を介さず復帰する | | | | |

### 試験分類

| 分類 | 対象 | 例 |
| --- | --- | --- |
| 単体試験 | 1 台・1 機能 | サービス稼働、設定値、権限、自動起動 |
| 結合試験 | 複数台をまたぐ動作 | Web から AP、AP から DB への疎通、ログ連携 |
| 総合試験 | 利用者視点の一連の流れ | ブラウザから操作して結果が返る、再起動後の復帰 |
| 異常系 | 想定外への振る舞い | 依存先の停止、権限不足、不正な入力、容量枯渇 |

### 異常系を必ず入れる理由

正常系だけの試験は「うまくいく場合しか確認していない」ことを意味します。
現場で発生する障害の多くは異常系にあり、**異常系の試験項目を書けることが構築者の実力の目安**になります。
本プランでは**異常系を全体の 3 割以上**にすることを条件にしています。

### エビデンスの要件

| 要件 | 内容 |
| --- | --- |
| 再現性 | 実行コマンド、対象ホスト、実行日時、対象バージョンが分かる |
| 結果 | 出力全文またはスクリーンショット。「OK」だけの記録は不可 |
| 安全性 | パスワード、トークン、実 IP、個人名、URL のマスク済み |
| 命名 | `<試験No>_<対象>_<日付>.<拡張子>` の形式で統一 |
| 保管 | 試験項目書から辿れる場所に置く |

本リポジトリでの実運用ルールは[証跡採録チェックリスト](../evidence-capture-checklist.md)に定義しています。

### 不具合が出たときの記録

| 項目 | 内容 |
| --- | --- |
| 発生日時 | いつ |
| 事象 | 何が起きたか（エラー全文） |
| 再現手順 | どうすれば再現するか |
| 原因 | 調査で判明した原因 |
| 対処 | どう直したか |
| 再試験 | 再試験の実施日と結果 |
| 横展開 | 同じ原因が他ホストにないかの確認結果 |

**横展開の確認**まで書けると、1 件の不具合対応が品質改善につながります。

## 5. 移行と切り戻し

### 当日タイムテーブル

分単位で作ります。時間の見積もりはリハーサルの実測値を使います。

| 時刻 | 作業 | 担当 | 判定ポイント |
| --- | --- | --- | --- |
| 21:00 | 作業開始連絡、現行状態の確認 | 作業者 | 現行が正常であること |
| 21:10 | バックアップ取得 | 作業者 | 取得完了、サイズ確認 |
| 21:30 | 切り替え作業 | 作業者 | 手順書 3 章の全項目 OK |
| 22:00 | 動作確認 | 確認者 | 試験項目書の総合試験が全件 OK |
| 22:30 | **切り戻し判断** | 責任者 | 未完了があれば切り戻しを開始 |
| 23:00 | 完了連絡 | 作業者 | 関係者への報告 |

### 切り戻しの判断基準

```text
次のいずれかに該当した場合、切り戻しを開始する。

1. 22:30 の時点で、総合試験の必須項目が 1 件でも NG である
2. 原因不明の事象が発生し、30 分以内に原因の特定ができない
3. 現行環境に影響が及ぶ可能性が判明した
4. 作業者が単独で判断できない事象が発生した

切り戻し完了の期限は 23:30 とし、これを超える見込みになった時点で責任者へ即時報告する。
```

- **判断基準は作業前に決めます**。作業中に決めると、必ず楽観側へ倒れます
- **時刻を入れます**。「うまくいかなければ戻す」は基準ではありません
- **切り戻しにも所要時間があります**。切り戻し開始の期限は、作業完了期限から逆算します

### 学習ラボでの実施方法

「移行」は個人ラボでも演習できます。

1. Phase 3 の 3 層構成を「現行環境」とする
2. Phase 5 の Ansible / コンテナ構成で「新環境」を作る
3. 参照先を新環境へ切り替える作業を、当日手順に沿って実施する
4. 意図的に 1 つ失敗させ、**実際に切り戻しを実行して所要時間を測る**

切り戻しを一度も実行したことがない手順書は、机上の想定にすぎません。

## 6. 本番作業の作法

技術以前に、事故を起こさないための行動様式です。**学習ラボの段階から習慣にしておきます。**

| # | 作法 | 具体的な行動 |
| --- | --- | --- |
| 1 | 作業前に対象を確認する | プロンプトのホスト名を毎回読む。複数端末を開いているときは特に |
| 2 | 破壊的コマンドは対象を先に確認する | `rm` の前に `ls`、`DELETE` の前に `SELECT` |
| 3 | 声に出して確認する | 対象ホスト・コマンド・想定結果を読み上げてから実行する |
| 4 | 重要作業は 2 人で確認する | 実行者と確認者を分ける。1 人しかいない場合は時間を空けて再確認する |
| 5 | 作業ログを取る | `script` などで端末の記録を残す |
| 6 | 手順外の操作をしない | 手順にない事象が起きたら、実行を止めて報告する |
| 7 | 想定と違ったら止める | 「たぶん大丈夫」で続行しない |
| 8 | 報告を先延ばししない | 失敗は早く報告するほど影響が小さい |

> 未経験者に最も期待されているのは高度な技術ではなく、**この 8 項目を確実に守れること**です。
> 面接で「作業前に何を確認しますか」と聞かれたときに、具体的に答えられる状態を目指します。

## 7. Phase 4 の演習課題

Phase 3 で作ったラボを「案件」に見立て、次を作成します。完成条件を満たすまで繰り返します。

| 課題 | 完成条件 |
| --- | --- |
| パラメータシート | 実機との差分がゼロ。第三者が同じ環境を作れる粒度 |
| 構築手順書 | 手順書のみで、まっさらな VM から 1 日以内に再現できる |
| 試験項目書 | 全項目に実測結果とエビデンスがあり、異常系が 3 割以上 |
| 移行・切り戻し手順 | 切り戻しを実際に 1 回実行し、所要時間を実測している |
| 運用引き継ぎ資料 | 構築に関わっていない人が、一次対応を開始できる |

> **判定のコツ**: 作成から 1 週間空けて、自分で手順書だけを見ながら再構築します。
> 1 週間後の自分は、ほぼ他人です。ここで詰まった箇所が、そのまま手順書の欠陥です。
