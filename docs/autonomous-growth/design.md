# 自律型成長の詳細設計

[入口](README.md) / [実践](practice.md) / [操作仕様](tool-guide.md)

## 1. 二つの循環をつなぐ

本人の循環は、目的・予想・実践・観測・説明・改善です。
Codexの循環は、記録収集・不整合検出・候補選択・準備・ローカル改善・検証・結果の再読込です。
本人の観測が次の候補を変え、Codexが作る確認方法を本人が試します。
本人の理解や実技をAIが代行した実績として残す設計ではありません。

## 2. 正本と補助記録

| 情報 | 保存先・正本 | 成長機能での扱い |
| --- | --- | --- |
| 32条件と段階の要求 | 既存curriculum.json | 条件・番号・前提をそのまま使う |
| 本人の試行・出力・支援量・人の評価 | 既存SE progress.json | 元の検証とevaluateで確認し、読み取りだけ行う |
| 週の時間と約束 | 既存career profile.json | 配分を変えず、指定した技術枠の内訳にする |
| 成長に使う行動 | growth settings.json | 明示した行動IDと意味の署名で固定する |
| 本人の再説明・実際の評価依頼 | growth followups.json | 元の試行ID、日時、本人記録とハッシュを参照する |
| 原因の仮説・試し方・本人の言葉 | 私用のMarkdown | AIが確認済みの原因や本人理解へ自動変換しない |
| 生成された候補と通知状態 | growth plans/latest | 予定として保存し、技能合否へ書き戻さない |

`learningSnapshot()` は既存SEの検証を再利用し、必要なメタデータだけを返します。
target、自由記述note、評価者の識別情報、添付本文は成長計画の既定出力へ含めません。
ハッシュは同一性の確認で、記録内容や本人の技能を認証するものではありません。

## 3. 候補を選ぶ規則

| 入力の状態 | 選ぶ次の一手 | 保持する境界 |
| --- | --- | --- |
| 本人台帳が未接続 | 既存IDと記録場所の確認 | 能力不足を推測しない |
| 参照不全・証跡改変・教材版不一致 | 取得・整合性確認を停止 | 古い記録を成功に読み替えない |
| 最初の未合格段階に未実施条件 | 正本の1条件の予想・実践・判定の準備 | 先の段階へ飛ばない |
| 直近のFAIL | 事実と仮説を分け、識別する確認を一つ選ぶ | 原因を自動で決め付けない |
| 同条件で2つ以上の別セッションが連続FAIL | 方法変更か相談を準備 | 二重登録を別の失敗試行として数えない |
| BLOCKED | 前提不足の整理 | 同じ実機操作を繰り返さない |
| PASSでも要求環境・独力条件が不一致 | 適切な環境や別の独力試行の準備 | 記録のPASSと条件充足を混同しない |
| 提出済み・評価待ち | 実際の依頼の有無と次回確認を整理 | 依頼や承認を作らない |
| 人の評価が再提出 | 原本の指摘を読み、補習を絞る | 指摘内容を推測して書かない |
| 全SE段階がPASS | 既存BXから次の課題を選ぶ | 独自の資格・実務権限を付与しない |

最新試行は、既存SEと同じく配列で最後に追記されたものです。実施日時で並べ替えて過去の成功を優先しません。
新しい試行がある場合は、それ以前の試行への再説明・評価依頼を現在の試行へ流用しません。
古い記録は履歴として残します。

## 4. 再説明の選択

既存の1日・7日・28日後の再確認を運用上の初期値に使います。学習効果や記憶の保持を保証する期間ではありません。
各条件の最新PASS試行を基点に、最初の未完の間隔だけを候補にします。
完了は、本人記録のある `EXPLAINED` かつ `independent` の最新観察で判断します。
guidedやaiの説明、GAP、BLOCKEDは練習として残し、独力再説明の完了にしません。

期限だけで過去のSE PASSを失効させません。再説明でGAPが出ても、SE履歴はそのままです。
必要な補習・新しい試行は本人が正本に記録します。

遅れて1日後の再説明を実施しても、同じUTC日に7日後・28日後まで独力完了としません。
次回可能時刻は、**元の期日と次UTC日の開始のうち遅い方**です。
例：9月1日の試行を9月2日に1日後確認した場合、7日後確認は9月8日より前になりません。
8月1日の試行の1日後確認が9月8日まで遅れた場合、次の間隔は最短でも9月9日UTC以降です。
実施日時を条件に合わせて書き換えません。

## 5. 評価待ちの扱い

READY FOR REVIEWは提出物が揃った状態です。送信済み・評価済みを意味しません。
評価依頼の補助記録は、当該段階の4つの試行ID、実際の依頼日時、次回確認日時、本人の依頼記録に対応させます。
確認期限前なら待機事項として表示し、期限に達したら状況確認を候補にします。
AIが依頼を送信したり、評価者を名乗ったり、承認を作ったりしません。

評価待ちでも過去の再説明や、他の実行可能なキャリア行動は進められます。
技能の前提を満たしていない次段階の実技を、自動で割り当てることはありません。

## 6. 時間と行動の接続

週10時間、20%の余白、既約束、レビュー、最大3主行動は既存career.mjsで計算します。
成長機能は、`bind-slot` で明示した行動がその週に選択され、目的・時間・完了条件等の署名が一致するときだけ、その枠を使います。
別の技術行動を自動で学習時間へ置き換えません。

一回の成長候補は原則、主課題1件と短い再説明1件です。
実践の準備60分、方法変更や相談30分、前提整理20分、短い再説明15分などの提案値を使い、枠に入らない候補は保留します。
時間だけを削って実施済みにしたり、必須確認を省いたりしません。
成長の内訳を作っても、career計画の合計時間と行動の完了状態は変わりません。

学習枠を変更したら再接続を確認します。縮小・休止・期限優先でその行動が選ばれなければ、新しい成長時間は0分です。
その場合も候補と保留理由を残し、本人が今週の配分を判断します。

## 7. Codexの準備と改善

Codexは、課題の目的を明確にする質問、期待結果・実出力の比較欄、原因を識別する観測案、実施カードを準備します。
必要な文書やコードの改善は、既存の週次枠（原則1件・45分）で実装・検証します。
実機操作・新しい依頼送信・公開は、それぞれの許可範囲に従います。

同じ提案で進まない場合、足りないものが対象、環境、教材、理解、観測、評価者、時間のどれかを確認します。
予想した原因と違う結果が出たら、その違いを次の試行の入力にします。
本人の自省、確認済みの原因、実際に得たフィードバックは本人が記録します。

## 8. システム自体の改善

月次に、役に立たなかった提案、期限の誤り、同じ内容の再通知、見積差、読み違いを確認します。
提案規則に欠陥があれば、実例を秘匿化した再現テストを作り、規則と説明を直します。
テストを減らす、SEの合格条件を弱める、本人記録を修正して結果を良く見せる方法は使いません。

改善を評価する材料は、次の課題が一つに絞れたか、実際に判断材料が増えたか、本人の説明と再現が改善したか、
余計な再実行や負荷が減ったかです。これらは本人の継続利用で確かめる項目で、今回達成した効果ではありません。

## 9. 初期範囲

機械選択はSE00〜SE07と再説明・評価依頼を対象にします。
BXの合格判定、原因ラベルの自動分類、学習モデルの再学習、本人の技能認定は実装していません。
BXは既存の資料を使い、本人と評価者の実際の記録を参照します。
新しい自動化を作らず、既存の月曜09:00 JSTのタスクへ組み込みます。
