# 本人の実践から次の改善を決める

[記入テンプレート](templates.md) / [既存の週次運用](../engineer-career/operation.md)

サーバー構築職への就職・定着につながる不足を一つ選び、**実践 → 観測 → 本人の説明 → 原因の仮説 → 改善 → 別日の再確認**を回します。
新しい技能合格体系は作りません。SEの評価は [評価仕様](../server-engineer/assessment.md)、BXの記録・評価は [発展課題のテンプレート](../server-engineer/advanced/templates.md)を正本にします。
ここに残すのは、正本への参照、不足の仮説、次に変える一手、本人の記入と再確認予定です。

## 1. 今回の不足を一つに絞る

| 入口 | 練習へ変える例 | 先に確かめること |
| --- | --- | --- |
| 求人の必須要件 | Linuxの権限設定を説明・再現する | 実際の求人要件と、対応する既存SE条件 |
| 面接で答えられなかった問い | 設定値の理由を出力と一緒に話す | 本人が実際に問われた内容と回答 |
| 前の試験のFAIL | 期待値との差を識別する確認を一つ選ぶ | 失敗した対象・版・操作・出力 |
| 手順の使いにくさ | 不足していた前提を追記して追試する | 本人または他者が実際に止まった位置 |
| 職場のフィードバック | 報告・相談を架空ラボで練習する | 相手が述べた事実と、自分の解釈の区別 |

目的を「技術力を上げる」で終えず、「何を見て何を判断できればよいか」を一文にします。
対応するSE/BX条件が不明なら対応待ちとし、似た名前の条件を推測して合格へ結び付けません。
新しい教材を増やす前に、既存の一構成、一試験、一説明で不足を確かめます。

## 2. 1回の練習を進める

次は60分の配分例です。準備と記録を含め、[キャリア計画](../engineer-career/operation.md)の週10時間に収めます。
週次レビュー、余白、既約束を差し引いた枠に入らなければ、練習を分割するか予定を見直します。

| 時間の例 | 本人が行うこと | 残すもの |
| --- | --- | --- |
| 5分 | 前の記録を見て目的と既存条件を選ぶ | 前回試行、今回の目的、完了条件 |
| 10分 | 対象、版、権限、予想、戻し方、支援量を確かめる | 実行前の記録と中止条件 |
| 25分 | 許可されたラボで操作し、期待値と出力を比較する | 操作、時刻、出力、試験ごとの結果 |
| 10分 | 元の安全な状態と利用者側の状態を確認する | 復旧・終了の確認、残った影響 |
| 10分 | 記録を見て本人が説明し、次の一手を選ぶ | 説明、未理解、仮説、再確認の予定 |

対象・影響・復旧経路が不明なら変更を始めません。必要な確認を時間に合わせて省かず、復旧の時間が不足しそうなら新しい変更を止めます。
実環境の停止・連絡・復旧は、その対象の許可と手順に従います。個人の練習計画を本番作業の許可にしません。
最後に「目的／予想／実際／判定理由／まだ言えないこと」を、本人が自分の言葉で短く説明します。
生成された説明を読めたことと、本人が説明できたことを別に記録します。

## 3. 支援を使う回と独力試行を分ける

| 支援量 | この回の扱い | 次に確かめること |
| --- | --- | --- |
| `guided` | 手順例や人の助言を使う。新しい操作を学ぶ回 | 助言が必要だった位置と理由 |
| `ai` | AIから原因の答えや操作手順を得た回 | 実際に行った操作と、本人が分からない点 |
| `independent` | 公式資料、自分の手順、man/helpを使い、自分で判断する回 | 選択理由、期待値、出力、相談の判断 |

定義は [既存の評価仕様](../server-engineer/assessment.md)に合わせます。独力は完全な暗記を意味しません。
途中で答えやコマンドの助言を受けたら、その区間と内容を残し、その回を独力評価に使いません。
支援のある試行を削除・改名して独力に変えず、別ID・別の実施記録で再確認します。
AIはヒント、仮説候補、記録の矛盾確認を支援できますが、本人の操作・理解・人の観察結果を代筆して確定しません。

## 4. 失敗を分類して次の確認を選ぶ

分類は原因候補を整理するメモで、採点や本人の資質判定ではありません。複数選択と `原因不明` を使えます。

| 分類 | 観測の例 | 次の確認・改善 |
| --- | --- | --- |
| 前提・環境 | 手順のOSや権限と実環境が違う | 差を確認し、成立する前提からやり直す |
| 対象・手順 | 違う設定を見た、操作を一段飛ばした | 対象の識別と手順の区切りを改善する |
| 知識・判断 | 出力は読めたが次の確認を選べない | 設定の役割と結果の違いを一つ調べる |
| 観測・判定 | ログ不足、期待値不明、判定範囲が広い | 測る対象と期待値を先に決める |
| 説明 | 結果はあるが理由や限界を話せない | 図・設定・出力を一つずつ対応させる |
| 連絡・計画 | 相談が遅れた、時間や確認者が足りない | 相談する条件、期限、作業量を見直す |
| 原因不明 | 証拠が複数の仮説に当てはまる | 仮説を分けられる追加確認を選ぶ |

「接続できない」だけでDNSやFWの問題と決めず、事実と仮説を別欄にします。
仮説には「正しければ何が観測されるか」「違えば何が観測されるか」を添え、一度に変える要因を一つ選びます。
改善後は同じ判定条件で確かめ、関係する既存試験も確認します。結果が変わらなければ仮説を保留・修正します。
古いFAIL、欠測、NOT RUNを消さず、新しい試行を関連付けます。改善の記述だけで効果ありとしません。

## 5. 繰り返し失敗したら相談する

同じ確認を2回繰り返して新しい事実が増えない場合は、方法を見直す初期の目安です。成功するまで同じ操作を繰り返しません。
失敗の数だけで能力不足と決めず、前提、観測、仮説、支援の必要性を確認します。

| 状況 | 次の一手 |
| --- | --- |
| 同じ結果のまま仮説を区別できない | 操作追加を止め、試行ID、事実、仮説、質問を相談メモへまとめる |
| 相談相手が未定・不在 | 質問案を作り、実施可能な読み取り確認や別の既存課題を選ぶ |
| 前提となる知識が不足 | 既存の補習先へ戻り、支援を使ってから別日に独力試行する |
| 対象誤り・影響拡大・復旧不能のおそれ | 回数を待たず、決めた中止と連絡・復旧の手順へ移る |

相談の下書きは自動で送信しません。実際の連絡、返答、観察は本人と相手の記録に対応させます。
人の評価が必要な条件は、相手が不在なら評価待ちのままにし、練習や自己確認を続けます。

## 6. 別日に確かめる

実施後 **1日・7日・28日**は、この自律運用で使う初期の再確認目安です。学習効果を保証する日数ではありません。
既存の月曜9時の週次運用で期日を確認して本人の予定へ配分し、新しい定期実行や通知を登録しません。

| 目安 | 本人が確かめること | 記録 |
| --- | --- | --- |
| 1日後 | 前の答えを見る前に目的・判断理由・限界を説明する | 自分の回答と、確認後に修正した点 |
| 7日後 | 同じ確認を別の試行として実施する | 新しい実日時・環境・版・支援量・出力 |
| 28日後 | 求人や担当業務への対応、版・条件変更、残る不足を見直す | 維持できた範囲、再試験が必要な範囲 |

すべての実機試験を毎回繰り返す意味ではありません。影響する条件を正本に照らして選びます。
予定を過ぎたら未実施と元の予定を残し、次の枠を決めます。日付の到来や延期だけで確認済みにしません。
SE07などで別日・新規VM・条件変更を求める場合は正本を優先し、1/7/28日の記録で代用しません。

## 7. 学習を仕事へつなぐ

求人には [要求と証拠の対応](../engineer-career/job-search.md)、職場には [担当範囲の相談](../engineer-career/onboarding.md)を使います。
練習結果から「どの条件で何を実施・説明できたか」「次に必要な支援」を短く取り出します。
実務への適用では規模、製品、データ、権限、承認、利用者影響の違いを先に確認します。
社内記録は許可された場所へ置き、個人GitHubには独立したラボの記録を使います。ラボを実務経験に置き換えません。
