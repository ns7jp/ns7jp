# Linux コマンド集(初心者向け)

このページは、未経験からサーバー構築エンジニアを目指す人が、Linux のコマンドを**目的から逆引きする**ための保存版リファレンスです。[やさしい用語・見方ガイド](./beginner-guide.md)で「なぜ動くか」の役割を押さえたあと、実際に手を動かして確かめるときに、このページを開いてください。

## 使い方

全部を暗記する必要はありません。「困りごと → 打つコマンド → 何を見て判断するか」の3点セットで覚え、細かいオプションは必要になったときに `man <コマンド名>` や `<コマンド名> --help` で調べる習慣をつけます。見出しから目的に近いセクションを探し、そこだけ読めば使える構成にしています。

## 安全に練習するための注意

- 本番環境ではなく、壊しても困らない VM やコンテナで練習してください
- `rm`、`chmod -R`、`kill -9`、`mkfs`、`dd`、Firewall(通信の許可・拒否を制御する仕組み)の変更などは元に戻せない、または他のプロセスやサービスに影響する操作です。実行前に `ls` や `--dry-run` などで対象を確認してから実行してください
- 各セクションには、破壊的な操作に対して同様の注意書き(⚠️)を添えています。見出しだけ拾い読みせず、実行前に必ず目を通してください

もっと基本的な用語(Nginx や systemd など、コマンド以外の役割)から知りたい場合は[やさしい用語・見方ガイド](./beginner-guide.md)へ、24 週間で体系立てて学びたい場合は[24 週の学習プラン](./learning-plan/README.md)へ進んでください。

## 基本操作・移動・自分の状況を知る

ターミナルを開いて最初にやることは、難しい設定ではなく「今どこにいるか」「誰としてログインしているか」「このマシンで何ができるか」を確認することです。このカテゴリでは、ディレクトリの移動と一覧表示、自分の状況確認、困ったときの調べ方という、これ以降すべての作業の土台になるコマンドをまとめます。

| やりたいこと | コマンド | 例 | 確認・判断のポイント |
| --- | --- | --- | --- |
| 今いる場所を知りたい | `pwd` | `pwd` | 表示された絶対パスが想定している場所かどうか |
| 別のディレクトリへ移動したい | `cd` | `cd /var/log` / `cd ~` / `cd -` | 移動後に `pwd` で確認する。存在しない場所を指定するとエラーで気づける |
| ディレクトリの中身を見たい | `ls` | `ls -lah` | 先頭が `d`(ディレクトリ)か `-`(ファイル)か、サイズが `0` のままでないか |
| 全体の構造を見取り図で見たい | `tree` | `tree -L 2` | 深さを指定して出力量を抑える(未インストールならまず導入する) |
| 画面を整理したい | `clear` | `clear` | 消えるのは画面表示だけで、それまでの操作結果は消えない |
| 過去に打ったコマンドを振り返りたい | `history` | `history` | 番号付きで一覧される。`!番号` で再実行できる |
| コマンドの使い方を自分で調べたい | `man` / `--help` | `man ls` / `ls --help` | `man` は `q` で終了、`/` で検索。`--help` は要点だけを短く見る |
| 自分が誰か確認したい | `whoami` | `whoami` | 表示が `root` なら管理者権限で操作している状態 |
| 今どのサーバーにいるか確認したい | `hostname` | `hostname` | 想定しているホスト名と一致しているか |
| 今の日時を確認したい | `date` | `date` | タイムゾーンとログの時刻表示がずれていないか |
| サーバーの稼働状況を確認したい | `uptime` | `uptime` | `up` の時間が極端に短くないか(再起動の痕跡)、負荷(ロードアベレージ)が高すぎないか |
| 文字列や設定値の中身を確認したい | `echo` | `echo $PATH` | 期待した値がそのまま表示されるか |

### pwd --- 今いる場所を確認する

`pwd`(print working directory の略で、今いるディレクトリを表示するコマンド)を実行すると、シェル(入力したコマンドを解釈して実行するプログラム)が今どのディレクトリにいるかを、ルート `/` からの完全な道順である絶対パスで表示します。ターミナルを開いたら、まずこれで自分の位置を確認する習慣をつけます。

```bash
pwd
```

出力例です。

```text
/home/ubuntu
```

**つまずきやすい点**: プロンプト(`$` の手前に表示されている文字列)にディレクトリ名が省略されて出ていることがあり、思っている場所と違うことがあります。ファイルを操作する前に `pwd` で正確なパスを確認しておくと、意図しない場所での誤操作を防げます。

### cd --- 別の場所へ移動する

`cd`(change directory の略)は、いま作業しているディレクトリを切り替えるコマンドです。指定の仕方には、ルートからの完全な道順を書く**絶対パス**と、今いる場所を基準にした道順を書く**相対パス**があります。

```bash
# 絶対パス: ルートからの完全な道順を指定する
cd /var/log

# 相対パス: 今いる場所を基準にした道順を指定する(1つ上の階層にある etc へ)
cd ../etc

# 直前にいたディレクトリへ戻る
cd -

# 自分のホームディレクトリ(ログイン直後にいる自分専用の作業場所)へ戻る
cd ~
# 引数なしの cd も同じ意味です
cd
```

**確認・判断のポイント**: `cd` は成功しても何も表示せず、静かに移動するだけです。移動できたかどうかは `pwd` で確認します。存在しないディレクトリを指定すると、次のようなエラーが出ます。

```text
bash: cd: no_such_dir: No such file or directory
```

**つまずきやすい点**: `cd -` は「直前にいた 1 つ前の場所」に戻るだけで、何度も押して履歴をさかのぼれるわけではありません。`~` は自分のホームディレクトリを指しますが、`~ubuntu` のようにユーザー名を続けると、そのユーザーのホームディレクトリを指定できます。

### ls --- ディレクトリの中身を確認する

`ls`(list の略)は、指定したディレクトリの中にあるファイルやディレクトリを一覧表示します。オプションを付けると見え方が変わります。

```bash
# 基本形: 今いる場所の中身を表示する
ls

# -l: 権限・所有者・サイズ・更新日時を含めた詳細形式で表示する
ls -l

# -a: . から始まる隠しファイル(通常は一覧に出てこない設定ファイルなど)も表示する
ls -a

# -h: -l と組み合わせて、サイズを 4096 のような数字ではなく 4.0K のように読みやすくする
ls -lh

# -lt: 更新日時が新しい順に並べ替えて表示する
ls -lt
```

出力例(`ls -lh`)です。

```text
total 12K
drwxr-xr-x 2 ubuntu ubuntu 4.0K Sep  4 10:15 Documents
-rw-r--r-- 1 ubuntu ubuntu  220 Sep  4 09:50 memo.txt
```

**確認・判断のポイント**: 行の先頭が `d` ならディレクトリ、`-` なら通常のファイルです。所有者・グループ(2 列目・3 列目)が想定通りか、サイズが `0` のまま増えていないかは、トラブル調査でもよく見る箇所です。

**つまずきやすい点**: オプションは `ls -lah` のようにまとめて 1 つに書けます。`-a` を付けないと `.`(自分自身)や `..`(1 つ上のディレクトリ)、`.bashrc` のような隠しファイルが見えず、「設定ファイルが無い」と勘違いすることがあります。

### tree --- ディレクトリ構造をひと目で見る

`tree` は、ディレクトリの中身を親子関係のまま木の形で表示するコマンドです。`ls` を何度も繰り返さなくても、フォルダ全体の見取り図が一度に分かります。

Ubuntu には標準で入っていないことが多いので、まずインストールします。

```bash
sudo apt update
sudo apt install -y tree
```

RHEL 系(AlmaLinux や Rocky Linux など)では、パッケージ管理ツール(ソフトの導入・更新・削除をまとめて扱う仕組み)として `dnf` を使います。

```bash
sudo dnf install -y tree
```

使用例です。

```bash
tree -L 2 ~/project
```

出力例です。

```text
/home/ubuntu/project
├── docs
│   └── README.md
└── src
    └── main.py

3 directories, 2 files
```

**確認・判断のポイント**: `-L 2` は「深さ 2 階層まで」表示する意味です。指定しないと、ファイル数の多いプロジェクトでは出力が大量になり、かえって読みにくくなります。末尾の集計行(`3 directories, 2 files`)には、表示しているディレクトリ自身(`~/project`)も 1 件として数えられている点に注意してください。

### clear と history --- 画面を整理する・打ったコマンドを振り返る

この 2 つは組み合わせて使うことが多い、作業の見通しをよくするコマンドです。

```bash
# 画面に表示されている内容を消して見やすくする(実行結果そのものは消えない)
clear

# 過去に実行したコマンドを番号付きで一覧表示する
history
```

出力例(`history`)です。

```text
  501  pwd
  502  ls -la
  503  cd /var/log
  504  history
```

**確認・判断のポイント**: `!503` のように番号を指定すると、その番号のコマンドを再実行できます。`history` はシェル(bash など)が今のセッション中に実行したコマンドをメモリ上の履歴として記録し、それを一覧表示するコマンドです。この履歴は通常、シェルを終了するときに `~/.bash_history` というファイルへ書き足されるため、次にログインしたときも過去のコマンドを振り返れます。`clear` は画面表示を消すだけの操作なので、`history` の記録には影響しません。

**つまずきやすい点**: `clear` は「画面表示」を消すだけで、それまでに実行した操作の結果(作成・削除したファイルなど)には一切影響しません。焦って `clear` を押しても、失敗した操作が元に戻るわけではない点に注意してください。また `!番号` での再実行は、番号を確認せずに使うと意図しないコマンドを再実行してしまうことがあるため、慣れるまでは表示された内容を確認してから使います。

### man と --help --- コマンドの使い方を自分で調べる

すべてのオプションを暗記する必要はありません。困ったときにその場で調べる方法を知っていれば十分です。`man`(manual の略で、コマンドの説明書を表示する仕組み)と、多くのコマンドに用意されている簡易ヘルプの `--help` を使い分けます。

```bash
# コマンドの詳しい説明書(マニュアル)を表示する
man ls

# 手短なオプション一覧だけを見る
ls --help
```

**確認・判断のポイント**: `man` は 1 画面ずつ表示され、`space` キーで次のページ、`q` キーで終了、`/` に続けてキーワードを入力すると文中を検索できます。`--help` は `man` より短く、オプションだけをさっと確認したいときに向いています。

**つまずきやすい点**: `cd` のようにシェル自体に組み込まれたコマンド(ビルトインコマンド)は、独立した `man` ページを持たないことがあります。その場合は `help cd`(bash 自体が持つヘルプ機能)を使うか、`man bash` の中から該当箇所を検索します。

### whoami と hostname --- 誰が、どのマシンにいるかを確認する

複数のサーバーを SSH(ネットワーク越しに別のマシンを安全に操作する仕組み)で行き来していると、「今どのユーザーで、どのマシンにログインしているか」を見失いがちです。作業を始める前にこの 2 つで確認する習慣をつけます。

```bash
# 今のユーザー名を表示する
whoami

# 今ログインしているマシンのホスト名(ネットワーク上の名前)を表示する
hostname
```

出力例です。

```text
$ whoami
ubuntu
$ hostname
web01
```

**確認・判断のポイント**: `whoami` の結果が `root` なら、管理者権限で操作している状態です。設定変更やパッケージのインストールが `sudo` なしでできてしまうため、意図せず `root` のままになっていないかを確認します。`hostname` は、複数のサーバーを開いているときに「想定と違うサーバーで作業していないか」を確かめる最初の一歩です。

### date と uptime --- 今の時刻とサーバーの稼働状況を確認する

`date`(現在の日時を表示する)と `uptime`(システムがどれくらい連続稼働しているかを表示する)は、障害対応やログの読み合わせで必ず使う基本コマンドです。

```bash
# 現在の日時とタイムゾーン(標準時からのずれ)を表示する
date

# システムの稼働時間、ログイン中のユーザー数、負荷(ロードアベレージ)を表示する
uptime
```

出力例です。

```text
$ date
Fri Sep  4 10:32:01 JST 2026
$ uptime
 10:32:05 up 3 days,  2:14,  1 user,  load average: 0.15, 0.10, 0.05
```

**確認・判断のポイント**: `date` はログの時刻表示と自分の感覚がずれていないかの確認に使います。`uptime` の `up 3 days` の部分が `up 2 min` のように極端に短い場合は、サーバーが最近再起動していたことが分かり、障害調査の重要な手がかりになります。ロードアベレージ(直近 1 分・5 分・15 分の平均負荷)は、CPU のコア数と比べて極端に高くないかを見ます。

**つまずきやすい点**: `date` が表示するタイムゾーンはサーバーの設定に依存します。自分のいる地域と違うタイムゾーンになっていると、ログの時刻とずれて見えるため、障害調査の前に確認しておくと混乱を防げます。

### echo --- 文字列や設定値を画面に表示する

`echo` は、指定した文字列やシェル変数(値を一時的に入れておく箱)の中身をそのまま画面に表示するコマンドです。単純に見えますが、動作確認やデバッグでよく使います。

```bash
# 文字列をそのまま表示する
echo "Hello, Linux"

# 環境変数(シェルやプログラムが参照する設定値)の中身を確認する
echo $HOME
echo $PATH

# 直前に実行したコマンドの終了コード(成功なら 0、失敗なら 0 以外)を確認する
echo $?
```

出力例です。

```text
$ echo "Hello, Linux"
Hello, Linux
$ echo $HOME
/home/ubuntu
$ echo $?
0
```

**確認・判断のポイント**: `echo $?` は「直前のコマンドが成功したか」を数字で確認する方法です。**覚え方は「0 なら成功、0 以外なら失敗」です。** シェルスクリプトを書くようになると、この確認方法を必ず使うことになります。

**つまずきやすい点**: `$` を付け忘れて `echo HOME` と打つと、変数の中身ではなく文字列 `HOME` がそのまま表示されてしまいます。変数の中身を見たいときは `$変数名` の形を忘れないようにします。

## ファイル・ディレクトリの操作と中身の確認

サーバー構築の作業は、設定ファイルを作る・バックアップとしてコピーする・不要になったものを消す・ログの中身を確認する、の繰り返しです。このセクションでは、その一番基礎になる「作る・移す・消す・見る」の操作を扱います。特に削除系のコマンドは元に戻せないため、操作前の確認方法までセットで覚えます。

| やりたいこと | コマンド | 例 | 確認・判断のポイント |
| --- | --- | --- | --- |
| 空のファイルを作る／タイムスタンプを更新する | `touch` | `touch memo.txt` | `ls -l` でファイルが存在するか（サイズ 0 でも正常）、更新日時が変わったかを見る |
| ディレクトリを作る（親ディレクトリごと一括で） | `mkdir -p` | `mkdir -p project/app/logs` | `find project` などで、意図した階層がすべてできているかを見る |
| ファイル・ディレクトリをコピーする | `cp -r` | `cp -r ./src ./src_backup` | コピー先ができているか、`diff -r` で元と中身が一致するかを見る |
| ファイル・ディレクトリを移動する／名前を変える | `mv` | `mv report_draft.txt report_final.txt` | 移動先に現れ、元の場所から消えたかを `ls` で両方確認する |
| 空のディレクトリだけを安全に消す | `rmdir` | `rmdir empty_folder` | 中身が残っているとエラーになる（壊れにくい削除） |
| ファイル・ディレクトリを削除する（**⚠️最重要注意**） | `rm` / `rm -r` / `rm -i` | `rm -ri old_logs/` | 実行前に `ls` で対象を確認したか、確認プロンプトで 1 件ずつ y/n を選べたかを見る |
| 既存のパスへの別名（近道）を作る | `ln -s` | `ln -s /etc/nginx/sites-available/app /etc/nginx/sites-enabled/app` | `ls -l` の `->` の先が、意図したパスと一致しているかを見る |
| ファイル全体を一度に表示する | `cat` | `cat /etc/os-release` | 短いファイル向き。出力が画面に収まらず流れる場合は `less` を使う |
| 長いファイルをスクロールしながら読む | `less`（簡易版は `more`） | `less /var/log/syslog` | `/` で検索、`n` で次候補、`q` で終了できるかを確認する |
| ファイルの先頭・末尾だけ見る／ログを流し読みする | `head` / `tail` / `tail -f` | `tail -f /var/log/nginx/access.log` | `tail -f` は新しい行が追記されるたびに画面に流れるか。終了は `Ctrl+C` |
| 行数・単語数・バイト数を数える | `wc` | `wc -l access.log` | 表示された行数が、ファイルサイズや想定件数と釣り合っているかを見る |
| 2 つのファイルの違いを比較する | `diff` | `diff nginx.conf.bak nginx.conf` | `<` が 1 つ目（元）のファイル、`>` が 2 つ目（新）のファイルの行。差分が意図どおりかを見る |

### touch --- 空ファイルの作成とタイムスタンプの更新

`touch` は、指定した名前のファイルが無ければ中身が空のファイルを作り、既にあれば中身はそのままでアクセス日時（atime）と更新日時（mtime）を今の時刻に更新します。`ls -l` で普段目にするのは主に更新日時（mtime）です。設定ファイルの雛形を先に用意しておきたいときや、あるファイルを「今さわった」ことにしたいときに使います。

```bash
touch memo.txt
ls -l memo.txt
```

`ls -l` の出力でファイルサイズが `0` と出ても、それは「まだ何も書き込んでいない」だけで正常です。中身が空であることに驚いて `touch` をやり直す必要はありません。既存ファイルに対して `touch` を実行しても中身は変わらない、という点が初心者がつまずきやすいポイントです。

### mkdir と mkdir -p --- ディレクトリの作成

`mkdir` はディレクトリ（フォルダ）を作るコマンドです。ただし親ディレクトリが存在しないと `mkdir: cannot create directory 'project/app': No such file or directory` のようにエラーになります。`-p`（parents、親ディレクトリの意味）を付けると、無い親ディレクトリもまとめて作り、かつ既に同じディレクトリが存在していてもエラーになりません。この「既にあっても失敗しない」性質のおかげで、構築手順を何度実行しても安全（**冪等**）になるため、手順書やスクリプトでは基本的に `mkdir -p` を使います。

```bash
mkdir -p project/app/logs
find project
```

`find project` の出力に `project`、`project/app`、`project/app/logs` の 3 行が並んでいれば、意図した階層ができています。パスの区切りを 1 か所間違えると別の場所に階層ができてしまうので、作成直後に必ず確認します。

### cp と cp -r --- ファイル・ディレクトリのコピー

`cp` はファイルをコピーします。設定ファイルを変更する前に「変更前の状態」を残しておく用途でよく使います。ディレクトリをまるごとコピーしたいときは `-r`（再帰的に、の意味）を付けます。付け忘れると `cp: -r not specified; omitting directory 'src'` のようなエラーになります。

```bash
cp app.conf app.conf.bak
cp -r ./src ./src_backup
```

`cp` はコピー先に同名のファイルがあっても、確認なしで上書きします（環境によっては `cp` が `cp -i`（上書き前に確認する版）のエイリアスになっている場合もあります）。大事なファイルを上書きしてしまわないよう、コピー先の名前は元と分かるように変えておくと安全です。コピーが正しく終わったかどうかは、後述する `diff -r` で元のディレクトリと中身を比較すると確実です。

### mv --- ファイル・ディレクトリの移動と名前変更

`mv` はファイルやディレクトリを別の場所へ移動する、または同じ場所で名前だけ変えるコマンドです。「移動」も「名前変更」も、実体は同じ操作（登録されている場所の情報を書き換えるだけ）です。ディレクトリを移動する場合も `cp` のような `-r` は不要です。

```bash
mv report_draft.txt report_final.txt
mv logs/ /var/backup/logs_2026-09-04/
```

`mv` は同じディスク内であれば実体をコピーし直さないため一瞬で終わりますが、`cp` 同様、移動先に同名のファイルがあると確認なしで上書きされる点に注意してください。移動が終わったら `ls` で「移動先にある」ことと「元の場所には無い」ことの両方を確認します。

### rm・rm -r・rm -i と rmdir --- 削除(最も注意が必要な操作)

削除系のコマンドは、Linux にはゴミ箱がないため実行すると即座に消え、原則として元に戻せません。まず、事故が起きにくい `rmdir` から覚えます。

`rmdir` は**中身が空のディレクトリしか消せません**。中身が残っていると失敗するので、意図せず大事なファイルごと消してしまう事故が起きにくいコマンドです。

```bash
rmdir empty_folder
```

中身が残っている状態で実行すると `rmdir: failed to remove 'empty_folder': Directory not empty` と表示され、削除は行われません。これはエラーではなく「安全装置が働いた」状態です。

一方 `rm` はファイルを削除するコマンドで、`-r`（再帰的に）を付けるとディレクトリも中身ごと削除できます。`-i` を付けると、1 件ずつ「本当に消しますか」の確認(`rm: remove regular file 'old_logs/access.log'?` のようなプロンプトに `y` か `n` で答える)が入ります。

```bash
# まず対象を目で確認してから消す
ls old_logs/
rm -ri old_logs/
```

> ⚠️ **元に戻せない操作です。** 対象を `ls` などで必ず確認してから実行してください。特に `-r` と `-f`（確認なしで強制的に削除）を組み合わせた `rm -rf` は、パスを 1 文字打ち間違えただけでも意図しない場所を丸ごと消してしまう事故につながります。
>
> 覚え方は **「まず ls、迷ったら -i、`-f` は自動化スクリプトの動作確認が済んでから」** です。ワイルドカード（`*` など）を使うときは、`rm` の前に同じパターンで `ls` を実行し、消える対象の一覧を先に目で見てから `rm` に置き換える習慣をつけると事故を防げます。

### ln -s --- シンボリックリンク(近道)を作る

シンボリックリンクとは、実体ではなく「このパスを見てね」という参照先の情報だけを持つ、いわば近道(ショートカット)です。`ln` に `-s`（symbolic、シンボリックの意味）を付けて作ります。Nginx の設定を `sites-available`（設定の置き場所）から `sites-enabled`（有効化した設定だけを集める場所）へ「有効化」する際など、実体は 1 つのまま複数の場所から参照したいときに使います。

```bash
ln -s /etc/nginx/sites-available/app /etc/nginx/sites-enabled/app
ls -l /etc/nginx/sites-enabled/app
```

`ls -l` の出力は `lrwxrwxrwx ... app -> /etc/nginx/sites-available/app` のようになり、先頭が `l`（link の意味）であること、`->` の先が意図したパスであることを確認します。リンク先の実体を消してしまうと、リンクだけが残った「参照先の無いリンク」になり、`ls -l` で赤く表示されたり `cat` で `No such file or directory` になったりする環境が多いので、リンク先を消すときは特に注意します。逆に、リンク自身を `rm` で消しても実体(リンク先のファイル)は消えません。

### cat --- ファイルの中身を一気に表示する

`cat` はファイルの中身を画面にそのまま流し込むコマンドです。短い設定ファイルの中身を素早く確認するときに向いています。

```bash
cat /etc/os-release
```

`NAME="Ubuntu"` や `VERSION="24.04 LTS (Noble Numbat)"` のような行がそのまま表示されます(実際の値には細かいポイントリリース番号が付くこともあります)。ログファイルのように行数が多いファイルに `cat` を使うと、画面の上に流れて過ぎて読めなくなるのが初心者がつまずきやすい点です。長いファイルは次の `less` を使います。

### less と more --- 長いファイルをスクロールしながら読む

`less` は、長いファイルを 1 画面ずつ表示しながら、上下にスクロールしたり検索したりできる**ページャ（1 画面ずつめくって表示する仕組み）**です。`more` はより古くて機能が少ないページャで、最小構成の環境では `less` が入っておらず `more` しか使えないことがあるため、名前だけ覚えておきます。

```bash
less /var/log/syslog
```

代表的な操作は、`Space` または `f` で次の画面、`b` で前の画面、`/検索したい文字列` で検索して `n` で次の候補へ移動、そして `q` で終了です。**`Ctrl+C` ではなく `q` で終了する**点を忘れて画面が固まったと勘違いする初心者が多いので、最初に覚えておくとつまずきません。

### head と tail、tail -f --- 先頭・末尾だけ見る、ログを流し読みする

`head` はファイルの**先頭**、`tail` はファイルの**末尾**を、それぞれデフォルトで 10 行だけ表示します。行数を変えたいときは `-n` を付けます。

```bash
head -n 20 access.log
tail -n 50 /var/log/nginx/error.log
```

さらに `tail -f`（follow、追いかける、の意味）を使うと、ファイルに新しい行が追記されるたびに画面へ流れ続けます。アプリケーションを操作しながら、別の端末でログをリアルタイムに眺めたいときの定番コマンドです。

```bash
tail -f /var/log/nginx/access.log
```

終了は `Ctrl+C` です。押し忘れると端末を占有したままになるので注意します。認証ログを見るときは、Ubuntu では `/var/log/auth.log`、RHEL 系では `/var/log/secure` とファイル名が違う点も合わせて覚えておくと、現場で戸惑いません。

### wc --- 行数・単語数・バイト数を数える

`wc`（word count）は、ファイルの行数・単語数・バイト数を数えるコマンドです。最初は行数を数える `-l` から覚えれば十分です。

```bash
wc -l access.log
```

出力は `15234 access.log` のように「数字 + ファイル名」の形になります。行数がいつもより極端に増えている場合、同じエラーがループして大量にログへ書き出されている、といった異常に気づく手がかりになります。オプションを付けずに `wc` だけ実行すると「行数 単語数 バイト数 ファイル名」の 3 つの数字が一度に表示されます。

### diff --- 2つのファイルの違いを比較する

`diff` は 2 つのファイルを行単位で比較し、違う部分だけを表示するコマンドです。設定ファイルを編集した後、「変えたつもりの箇所だけが変わっているか」を確認するのに使います。

```bash
cp nginx.conf nginx.conf.bak
# ここで nginx.conf を編集する
diff nginx.conf.bak nginx.conf
```

出力は次のような形になります。

```text
12c12
< listen 80;
---
> listen 8080;
```

`12c12` は「1 つ目のファイルの 12 行目が、2 つ目のファイルの 12 行目に変わった（change）」という意味で、`<` が 1 つ目（`nginx.conf.bak`、元のファイル）の行、`>` が 2 つ目（`nginx.conf`、新しいファイル）の行です。**何も表示されなければ、2 つのファイルは完全に一致しています**（差分なしが正常な場合もあります）。ディレクトリ同士を比較したいときは `diff -r ディレクトリA ディレクトリB` を使います。これ以上の細かいオプション（`-u` の unified 形式など）は `man diff` や `diff --help` で必要になったときに調べれば十分です。

## 探す・見つける

「あのファイル、どこに置いたっけ」「あの文字列、どのファイルに書いたっけ」を突き止める手段を身につけます。ファイルそのものを条件で探す方法と、ファイルの中身(文字列)を探す方法を分けて整理し、目的に合わせて正しいコマンドを選べるようにします。

| やりたいこと | コマンド | 例 | 確認・判断のポイント |
| --- | --- | --- | --- |
| ファイル名・種類・更新日時で探す | `find` | `find /etc -name "*.conf"` | 見つかったパスが1行ずつ表示される。1件もヒットしなければ何も表示されない(エラーではない) |
| ファイルの中身から文字列を探す | `grep` | `grep -rn "ERROR" /var/log/` | ヒット行が `ファイル名:行番号:内容` の形式で出る。何も出なければヒットなし |
| コマンドの実体(PATH上のファイル)を調べる | `which` | `which python3` | フルパスが1行出れば使える状態。何も表示されず終了コードが `1` になれば PATH に無い |
| コマンドの実体・manページ・関連ファイルをまとめて調べる | `whereis` | `whereis nginx` | `名前: パス パス ...` の形式で複数出る。`which` より広い範囲を探せる |
| ファイル名だけを高速に探す(索引を使う) | `locate` | `locate nginx.conf` | 一瞬で結果が出るが、索引(データベース)頼みなので最新のファイルは出ないことがある |

> 覚え方は「**find は今の実態、locate は索引の鮮度**」です。find はディスクを実際にたどるので確実ですが遅く、locate は索引を検索するので速いですが情報が古いことがあります。

### find --- 条件を指定してファイルを探す

`find`(条件を指定してファイルやディレクトリを探すコマンド)は、指定したディレクトリ以下を実際にたどりながら、名前・種類・更新日時などの条件に合うファイルを探します。ディスク上の「今の状態」を確認できるのが強みです。

```bash
# /etc 以下から、拡張子が .conf のファイルを探す(-name)
find /etc -name "*.conf"

# カレントディレクトリ以下で、名前が logs の「ディレクトリだけ」を探す(-type d)
find . -type d -name "logs"

# /var/log 以下で、直近7日以内に更新された「ファイルだけ」を探す(-type f, -mtime)
find /var/log -type f -mtime -7
```

つまずきやすい点:

- `-name` に指定するパターン(`*.conf` など)は、シェルに展開されないよう必ず引用符で囲みます。囲まないと、カレントディレクトリのファイル名一覧に展開されてしまい、意図と違う結果になります。
- `-mtime` は「日単位」の相対指定です。`-mtime -7` は「直近7日以内(7日より新しい)」、`-mtime +7` は「7日より前(古い)」を意味します。符号の向きを逆に覚えやすいので注意してください。
- 一般ユーザーで `/root` など権限の無いディレクトリを検索すると、結果に混じって `Permission denied` という行が出ます。これはコマンドの失敗ではなく「見る権限が無いディレクトリがあった」という通知です。
- `find` は `-delete` や `-exec rm {} \;` と組み合わせて、条件に合うファイルを一括削除する使い方もあります。⚠️ 元に戻せない操作です。必ず削除オプションを付けずに一度実行し、`-name` などの条件で対象ファイルの一覧を目で確認してから、削除オプションを付け直してください。

### grep --- ファイルの中の文字列を探す

`grep`(ファイルの中から指定した文字列を含む行を探すコマンド)は、ログファイルや設定ファイルの中身を検索し、障害調査でエラーメッセージを探すときによく使います。

```bash
# /var/log 以下を再帰的に検索し(-r)、大文字小文字を区別せず(-i)、
# "error" を含む行を行番号付きで(-n)表示する
grep -rni "error" /var/log/

# ヒットしたファイル名「だけ」を一覧表示する(-l、中身は表示しない)
grep -rl "TODO" ./src/

# "DEBUG" を含まない行だけを表示する(-v、ノイズの多いログを絞り込むときに便利)
grep -v "DEBUG" app.log
```

SSH の認証ログから失敗を探す例では、ディストリビューションによってログファイルの場所が違う点に注意します。

```bash
# Ubuntu 24.04(Debian系)
grep -i "failed password" /var/log/auth.log

# RHEL系(dnf/yumを使うディストリビューション)ではログファイル名が異なる
grep -i "failed password" /var/log/secure
```

つまずきやすい点:

- `-r`(再帰的に検索)を付け忘れると、指定したディレクトリの直下しか検索されません。サブディレクトリの中まで探したいときは必須です。
- `-l` はファイル名だけ、`-n` は行番号だけを追加する、というように**オプションは足し算で組み合わせられます**(`-rni` のようにまとめて書けます)。
- ヒットが無いとき、`grep` は何も表示せず、コマンドの終了コード(成否を表す番号)も「失敗」を意味する `1` になります。画面に何もエラーが出ないので、まず対象のパスと綴りを見直してください。

### which / whereis --- コマンドの実体を探す

`which`(コマンド名からPATH上の実行ファイルの場所を調べるコマンド)と `whereis`(コマンドの実行ファイル・manページ・関連ファイルをまとめて調べるコマンド)は、「このコマンドは実際どこにあるファイルを実行しているのか」を確認するときに使います。複数バージョンが入っていて意図しないものが実行される、といったトラブルの切り分けに役立ちます。

```bash
which python3
which nginx
```

`which python3` はフルパス1行(例: `/usr/bin/python3`)だけを表示します。`whereis` は同じコマンドに対して実行ファイル・設定ディレクトリ・manページなど、見つかったものをまとめて1行で表示します。

```bash
whereis nginx
```

つまずきやすい点:

- `which` は環境変数 `PATH`(コマンドを探すディレクトリの一覧)に登録された場所しか探しません。ファイルが存在していても `PATH` に無ければ「見つからない」扱いになります。
- `whereis` は `PATH` に関わらず、`/usr/bin` や `/usr/sbin` などの標準的な場所を直接探すため、`which` では見つからなかったものが見つかることがあります。
- スクリプトの中で「このコマンドが入っているか」を確認したいときは、表示結果そのものより終了コードで判定するのが定番です(例: `if ! which nginx > /dev/null 2>&1; then ...`)。

### locate --- ファイル名を索引から高速に探す(updatedbの注意)

`locate`(あらかじめ作られたファイル名の索引=データベースを検索するコマンド)は、ディスク全体を毎回たどる `find` と違い、索引を検索するだけなので瞬時に結果が返ります。

```bash
locate nginx.conf
```

つまずきやすい点:

- 索引は `updatedb`(索引を作り直すコマンド)によって、通常は1日1回程度、定期的(cronなど)に更新されます。**「さっき作ったファイルが `locate` で出てこない」のは索引がまだ古いだけ**で、多くの場合は異常ではありません。
- 最新の状態を確認したいときは、索引を作り直してから検索します。ディスク全体を読み直すため多少時間がかかり、実行には管理者権限が必要です。

```bash
sudo updatedb
locate nginx.conf
```

- Ubuntu 24.04 では `locate` コマンド自体が標準で入っていないことがあります。その場合は `sudo apt install plocate` でインストールしてから使います。
- 「今まさに存在するか」を確実に確認したいときは、索引の鮮度に左右されない `find` を使う、と使い分けます。

> 覚え方は「**locate は索引、find は現地確認**」です。速さを取るか確実さを取るかで使い分けます。細かいオプションは `man find` や `find --help` などで必要なときに調べれば十分です。

## 権限・所有者・ユーザー管理

Linux では、すべてのファイルとプロセスに「誰のものか」「誰が何をしてよいか」が必ず決まっています。このセクションでは、ファイルの権限（読める・書ける・実行できる）を読み書きし、所有者やグループを変更し、ユーザーを作成・管理し、管理者権限を安全に使い分けられるようになることを目指します。

| やりたいこと | コマンド | 例 | 確認・判断のポイント |
| --- | --- | --- | --- |
| ファイルの権限を確認する | `ls -l` | `ls -l app.sh` | `-rwxr-xr-x` の並びを所有者・グループ・その他の3組に分けて読む |
| 権限を変更する | `chmod` | `chmod 644 app.conf` | 変更後に `ls -l` で意図した権限になったか必ず見る |
| 所有者を変更する | `chown` | `sudo chown web:web app.log` | `ls -l` の3列目（所有者）と4列目（グループ）が変わったか確認する |
| グループだけを変更する | `chgrp` | `sudo chgrp deploy app.log` | `ls -l` の4列目（グループ）が変わったか確認する |
| 新規作成時のデフォルト権限を決める | `umask` | `umask 022` | 新しく作ったファイルの権限が想定どおりか `ls -l` で確認する |
| ユーザーを追加・変更する | `useradd` / `usermod` | `sudo useradd -m alice` | `id alice` でユーザーが存在し、意図したグループに入っているか確認する |
| パスワードを設定する | `passwd` | `sudo passwd alice` | 対話式の入力を求められ、`passwd: password updated successfully` が出れば成功 |
| 自分やユーザーの所属を確認する | `id` / `groups` | `id alice` | UID・GID・所属グループの一覧が正しいか確認する |
| 別ユーザーに切り替える | `su` | `su - alice` | プロンプトのユーザー名が切り替わったか、`whoami` で確認する |
| 一時的に管理者権限で実行する | `sudo` | `sudo systemctl restart nginx` | エラーが出ずコマンドが実行できれば成功。権限がない場合は `is not in the sudoers file` と表示される |

### ls -l --- ファイルの権限・所有者を読む

`ls -l` は、ファイルやディレクトリの「誰が」「何を」できるかを一覧表示するコマンドです。権限のトラブル（「動くはずなのに Permission denied になる」など）を調べるときの、最初の一歩になります。

```bash
$ ls -l /var/www/app.conf
-rw-r--r-- 1 web deploy 1200 Sep  1 10:00 /var/www/app.conf
```

出力の先頭 10 文字を、次のように分解して読みます。

```text
- rw- r-- r--
| |   |   └─ その他（other）: 読める(r) だけ
| |   └───── グループ（group）: 読める(r) だけ
| └───────── 所有者（owner）: 読める(r)・書ける(w)
└─────────── ファイル種別（- は通常ファイル、d はディレクトリ）
```

- 最初の1文字はファイル種別です。`-` は通常ファイル、`d` はディレクトリ、`l` はシンボリックリンク（別ファイルへの近道）を表します。
- 残り9文字は3文字ずつ3組に分かれ、それぞれ**所有者（owner）・グループ（group）・その他（other）**の権限を表します。
- 各組は `r`（read: 読める）・`w`（write: 書ける）・`x`（execute: 実行できる、ディレクトリの場合は中に入れる）の有無を示し、権限が無い位置は `-` になります。

> 覚え方は「**種別・所有者・グループ・その他**」の4つに分けて、左から順に読むことです。

`ls -l app.conf` の3列目（`web`）が所有者、4列目（`deploy`）が所属グループです。これは後述の `chown` / `chgrp` で変更する対象と同じ列です。

### chmod --- 権限を変更する（記号形式・数値形式）

`chmod` は、`ls -l` で見た `rwx` の組み合わせを変更するコマンドです。記号形式と数値形式の2通りの書き方があります。

**記号形式**は、誰の（`u`=所有者, `g`=グループ, `o`=その他, `a`=全員）権限を、どう変える（`+`=付与, `-`=削除, `=`=指定した権限に置き換え）かを組み合わせて書きます。

```bash
# 所有者に実行権限を追加する
$ chmod u+x deploy.sh
$ ls -l deploy.sh
-rwxr--r-- 1 web deploy 350 Sep  1 10:05 deploy.sh

# その他ユーザーの書き込み権限を削除する
$ chmod o-w app.conf
```

**数値形式**は、`r=4, w=2, x=1` の値を足し算し、所有者・グループ・その他の順に3桁で指定します。

```bash
$ chmod 755 deploy.sh
$ ls -l deploy.sh
-rwxr-xr-x 1 web deploy 350 Sep  1 10:05 deploy.sh
```

`755` は次のように分解できます。

| 桁 | 対象 | 計算 | 意味 |
| --- | --- | --- | --- |
| 7 | 所有者 | 4(r) + 2(w) + 1(x) | 読める・書ける・実行できる |
| 5 | グループ | 4(r) + 0 + 1(x) | 読める・実行できる（書けない） |
| 5 | その他 | 4(r) + 0 + 1(x) | 読める・実行できる（書けない） |

初心者がよく使う組み合わせは、設定ファイルなら `644`（所有者だけ書ける、他は読むだけ）、実行スクリプトやディレクトリなら `755`（所有者だけ書ける、全員が実行・アクセス可）です。

> 覚え方は「**読める4・書ける2・実行できる1、3つ足して1桁**」です。755なら「7=4+2+1（全部）」「5=4+1（読むと実行だけ）」と分解して読みます。

⚠️ `chmod -R` （ディレクトリ配下すべてに再帰的に適用するオプション）は一度に大量のファイルの権限を変えてしまい、元に戻すのが困難です。対象ディレクトリを `ls -l` や `find` で確認してから実行してください。特に `chmod -R 777`（全員が読み書き実行できる状態）は、セキュリティ上ほぼ常に避けるべき設定です。

### chown / chgrp --- 所有者とグループを変更する

`chown` はファイルの所有者（とグループ）を、`chgrp` はグループだけを変更するコマンドです。Webサーバーやアプリの実行ユーザーに合わせてファイルの持ち主を揃えたいときに使います。

```bash
# 所有者とグループを同時に変更する
$ sudo chown web:deploy app.log
$ ls -l app.log
-rw-r--r-- 1 web deploy 0 Sep  1 10:10 app.log

# グループだけを変更する
$ sudo chgrp deploy app.log

# 所有者だけを変更する（グループは変えない）
$ sudo chown web app.log
```

`chown 所有者:グループ 対象` の形が基本です。`chown web app.log` のようにコロンを付けずに書けば所有者だけを変更でき（グループは変わりません）、`chown :deploy app.log` のようにコロンの前を空にすればグループだけを変更できます。注意したいのは `chown web: app.log` のように**所有者の後にコロンだけを付けて何も続けない場合**で、この書き方では所有者が `web` になるのに加えて、グループも `web` ユーザーのログイングループ（プライマリグループ）に変更されます。「グループはそのままにしたい」ときはコロン自体を書かないようにしてください。多くの場合、他人のファイルの所有者を変えるには `sudo`（管理者権限）が必要です。

⚠️ `chown -R` も `chmod -R` と同様、ディレクトリ配下すべての所有者を一括で変更します。意図しないファイル（他のアプリの設定など）まで巻き込まないよう、対象ディレクトリを事前に `ls -l` で確認してから実行してください。

### umask --- 新規作成時のデフォルト権限を決める

`umask` は、新しくファイルやディレクトリを作ったときに、自動的にどの権限を「引く（付けない）」かを決める設定です。`chmod` が既存ファイルの権限を後から変えるのに対し、`umask` はこれから作るファイルの初期権限を決めます。

```bash
$ umask
0022

$ touch newfile.txt
$ ls -l newfile.txt
-rw-r--r-- 1 web web 0 Sep  1 10:15 newfile.txt
```

ファイルはデフォルトで最大 `666`（実行権限を含まない）、ディレクトリは最大 `777` から始まり、そこから `umask` の値を引いた権限になります。`umask 022` の場合、ファイルは `666 - 022 = 644`、ディレクトリは `777 - 022 = 755` になります（厳密にはビット単位の演算ですが、022 のような一般的な値では引き算のイメージで問題ありません）。

> 覚え方は「**umaskは引き算、chmodは上書き**」です。umask は「新規作成時に何を引くか」、chmod は「今ある権限をこの値にする」という違いを意識すると混同しません。

一時的に値を変えるだけなら `umask 027` のようにコマンドを打つだけで構いませんが、恒久的に変えたい場合は `~/.bashrc` などのシェル設定ファイルに追記します。

### useradd / usermod --- ユーザーを作成・変更する

`useradd` は新しいユーザーアカウントを作成し、`usermod` は既存ユーザーの設定（所属グループなど）を変更するコマンドです。どちらも管理者権限（`sudo`）が必要です。

```bash
# ホームディレクトリ付きでユーザーを作成する
$ sudo useradd -m alice
$ id alice
uid=1001(alice) gid=1001(alice) groups=1001(alice)

# 既存ユーザーを別のグループにも追加する（-a で既存の所属を維持したまま追加）
$ sudo usermod -aG sudo alice
$ id alice
uid=1001(alice) gid=1001(alice) groups=1001(alice),27(sudo)
```

初心者がつまずきやすい点は、`-m`（ホームディレクトリを作成するオプション）を付け忘れると `/home/alice` が作られないことと、`usermod -G`（大文字、`-a` を付けない）を使うと既存の所属グループがすべて上書きされて消えてしまうことです。グループを**追加**したいときは必ず `-aG` とセットで使います。

Ubuntu / Debian系では `useradd` より対話的な `adduser` コマンドもよく使われます（ホームディレクトリ作成やパスワード設定を自動で聞いてくれます）。RHEL系（CentOS / Rocky Linuxなど）では `useradd` が標準です。

### passwd --- パスワードを設定・変更する

`passwd` は、ユーザーのログインパスワードを設定・変更するコマンドです。

```bash
# 自分のパスワードを変更する
$ passwd
Changing password for alice.
Current password:
New password:
Retype new password:
passwd: password updated successfully

# 管理者が他のユーザーのパスワードを設定する
$ sudo passwd alice
New password:
Retype new password:
passwd: password updated successfully
```

自分のパスワードを変更するときは現在のパスワードの入力を求められますが、`sudo passwd ユーザー名` で他人のパスワードを管理者権限で設定する場合は、現在のパスワードは不要です。入力中は画面に文字も `*` も表示されませんが、正しく入力できています。

### id / groups --- ユーザーとグループの所属を確認する

`id` と `groups` は、ユーザーがどのグループに所属しているかを確認するコマンドです。「権限が足りない」トラブルの原因調査で、まず確認する対象になります。

```bash
$ id alice
uid=1001(alice) gid=1001(alice) groups=1001(alice),27(sudo),999(docker)

$ groups alice
alice : alice sudo docker
```

`id`（引数なし）で自分自身の情報を、`id ユーザー名` で他のユーザーの情報を確認できます。`uid`（ユーザーID）と `gid`（プライマリグループID）に加え、`groups=` の欄にそのユーザーが所属する**すべての**グループが並びます。たとえば `docker` グループに入っていなければ `docker` コマンドの実行時に権限エラーになる、といった判断に使います。

### su --- 別のユーザーに切り替える

`su`（switch user）は、ログインし直すことなく別のユーザーに切り替えるコマンドです。

```bash
$ su - alice
Password:
alice@server:~$ whoami
alice
```

`su - alice` のように**ハイフンを付ける**と、alice のログインシェルとしてホームディレクトリや環境変数も切り替わります。ハイフンを省略すると、カレントディレクトリなど元のユーザーの環境が一部残ったままになるため、初心者は基本的に `su -` の形を使うことをおすすめします。ユーザー名を省略すると `root`（管理者ユーザー）への切り替えになります。

⚠️ `su` でパスワードを何度も間違えると一時的にロックされる設定のサーバーもあります。対象ユーザー名を打ち間違えていないか、実行前に確認してください。

### sudo --- 一時的に管理者権限でコマンドを実行する

`sudo`（superuser do）は、自分のパスワードだけで、一時的に管理者（root）権限でコマンドを実行できる仕組みです。`su` で root に切り替えっぱなしにするより安全で、「誰が」「いつ」「何を」実行したかがログに残ります。

```bash
$ sudo systemctl restart nginx
[sudo] password for alice:

$ sudo -l
User alice may run the following commands on server:
    (ALL : ALL) ALL
```

誰が `sudo` を使えるかは、`/etc/sudoers`（設定ファイル）と、そこに読み込まれる `/etc/sudoers.d/` 配下のファイルで管理されています。多くのディストリビューションでは、ユーザーを `sudo` グループ（RHEL系では `wheel` グループ）に所属させることで、個別に `/etc/sudoers` を書き換えなくても `sudo` を使えるようにします。

⚠️ `/etc/sudoers` は直接テキストエディタで開いて編集せず、必ず専用コマンドの `sudo visudo` を使ってください。構文エラーがあるまま保存すると `sudo` 自体が使えなくなり、復旧が難しくなります。`visudo` は保存時に構文チェックを行うため安全です。

### ディストリビューションによる違いと詳細の調べ方

Ubuntu（Debian系）では管理者グループは `sudo`、ユーザー管理は `apt` でインストールした標準ツール（`useradd` / `adduser`）で行います。RHEL系（CentOS / Rocky Linuxなど）では管理者グループが `wheel` になる、パッケージ管理が `dnf`（新しめ）や `yum`（旧来）になるといった違いがありますが、`chmod` / `chown` / `id` などのコマンド自体の使い方はほぼ共通です。

ここで紹介したオプションは最初に使う範囲に絞っています。より詳しい使い方は `man chmod` や `chmod --help` のように、コマンド名を変えて確認してください。

## プロセス・サービス管理

このカテゴリでは、サーバー上で「今何が動いているか」を確認し、必要なら止めたり再起動したりして、OS起動時に自動で立ち上がるよう設定し、うまくいかないときはログから原因を追う、という一連の流れを扱います。障害対応でまず触ることになる操作なので、コマンドどうしのつながりを意識して覚えてください。

> 覚え方は **「見る・止める・自動化する・追う」** です。ps/top で見る → kill や jobs で止める・制御する → systemctl で自動化する → journalctl で追う、という順番でつながっています。

| やりたいこと | コマンド | 例 | 確認・判断のポイント |
| --- | --- | --- | --- |
| 動いているプロセスを一覧で見る | `ps aux` / `ps -ef` | `ps aux \| grep nginx` | 目的のプロセスの行が出れば動いている。PID（プロセス番号）を控えておく |
| リアルタイムで負荷の高いプロセスを見る | `top` | `top` | `load average` が高止まりしていないか、CPU/MEMの上位に想定外のプロセスがいないか |
| プロセスを止める | `kill` / `killall` | `kill 12345` | 対象PIDが `ps` の一覧から消えたか確認する |
| ターミナル上のジョブを制御する | `jobs` / `bg` / `fg` / `&` | `sleep 300 &` | `jobs` の出力で `Running` / `Stopped` の状態を確認する |
| プロセスの優先度を調整する | `nice` / `renice` | `renice -n 5 -p 12345` | `top` の `NI` 列で意図した値になっているか確認する |
| サービスの起動・停止・自動起動を設定する | `systemctl` | `systemctl status nginx` | `Active:` が `active (running)` か、`Loaded:` が `enabled` か確認する |
| ログで原因を追う | `journalctl` | `journalctl -u nginx -f` | 時系列で **最初に出たエラー行** と、その直前の行を読む |

### ps --- 動いているプロセスを一覧表示する

`ps`（process status）は、実行した瞬間に動いているプロセスの一覧を表示するコマンドです。よく使う書き方が2種類あり、どちらも同じ情報をほぼ同じ内容で表示しますが、見た目（列の並び）が異なります。

```bash
ps aux
```

```text
USER   PID  %CPU %MEM    VSZ   RSS TTY    STAT START   TIME COMMAND
www    1234  0.1  0.5  55000  9800 ?      S    09:00   0:03 nginx: worker process
```

```bash
ps -ef
```

```text
UID    PID  PPID  C STIME TTY          TIME CMD
www   1234  1000  0 09:00 ?        00:00:03 nginx: worker process
```

- `ps aux`（BSDスタイル）は `%CPU` や `%MEM` が見やすく、負荷確認に向いています。
- `ps -ef`（UNIXスタイル）は `PPID`（親プロセスのPID）が見やすく、どのプロセスから起動されたかを追うのに向いています。上の例では `PPID` が `1000` になっていますが、これは nginx の master プロセス（設定を読み込んでworkerを管理する親玉）のPIDを表しています。
- どちらでも構わないので、まずは1つを使い慣れることが大切です。

初心者がつまずきやすい点は、`ps aux | grep nginx` のように絞り込むと、`grep` コマンド自身の行まで一緒に表示されてしまうことです。気になる場合は `ps aux | grep [n]ginx` のように正規表現で自分自身を除外するか、プロセス名から直接PIDだけを探す `pgrep nginx` を使うと簡潔です。

### top --- リアルタイムでプロセスの負荷を見る

`top` は、`ps` の「その瞬間のスナップショット」とは違い、CPUやメモリの使用率が高い順にプロセスを並べながら継続的に更新表示してくれるコマンドです。「動画のように監視できる `ps`」とイメージすると覚えやすいです。

```bash
top
```

```text
top - 10:15:32 up  3:20,  1 user,  load average: 0.15, 0.10, 0.05
Tasks:  98 total,   1 running,  97 sleeping,   0 stopped,   0 zombie
%Cpu(s):  3.0 us,  1.0 sy,  0.0 ni, 95.4 id,  0.5 wa,  0.0 hi,  0.1 si,  0.0 st
MiB Mem :   3900.0 total,   1200.0 free,    900.0 used,   1800.0 buff/cache
MiB Swap:      0.0 total,      0.0 free,      0.0 used.   2600.0 avail Mem
  PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
 1234 www       20   0   55000    9800     800 S   0.3   0.5   0:01.23 nginx
```

- 画面上部の `load average`(過去1分・5分・15分の平均負荷)が、サーバーのCPUコア数を超えて高止まりしている場合は過負荷のサインです。
- 実行中に `P` を押すとCPU使用率順、`M` を押すとメモリ使用率順に並び替えられます。
- `q` を押すと終了します。

初心者がつまずきやすい点は、`top` を実行したまま画面が固まったように見えて終了方法が分からなくなることです。`q` を押せば元のプロンプトに戻ります。また、`top` の中で `k` を押してPIDを指定するとプロセスを止められますが、対象を間違えやすいため、慣れないうちは `q` で抜けてから後述の `kill` コマンドを使う方が安全です。

### kill・killall --- プロセスを止める(SIGTERMとSIGKILLの違い)

`kill` は指定したPID（プロセス番号）に対して、`killall` は指定したプロセス名に対して、シグナル（プロセスへの指示）を送るコマンドです。名前に反して「必ず強制終了する」わけではなく、どのシグナルを送るかで動作が変わります。

```bash
kill 12345        # 何も指定しない場合はSIGTERM(15)を送る
kill -9 12345      # SIGKILL(9)を送る
killall nginx      # プロセス名を指定して一括で送る
```

| シグナル | 番号 | 意味 |
| --- | --- | --- |
| SIGTERM | 15 | 「後片付けをしてから終了してください」とお願いする信号。まずこちらを使う |
| SIGKILL | 9 | 後片付けをする間もなく即座に強制終了させる信号。最終手段 |

⚠️ `kill -9`(SIGKILL)はプロセスに終了処理をする猶予を与えないため、保存中のデータが壊れたり、ロックファイルが残って次回起動に失敗したりすることがあります。元に戻せない操作です。まず `kill`(SIGTERM)で数秒待ち、それでも終了しない場合だけ `kill -9` を使ってください。

初心者がつまずきやすい点は2つあります。1つは `killall` が名前の一致するプロセスを**全部**止めてしまうことです。同じ名前の別ユーザーのプロセスまで巻き込む可能性があるため、実行前に `ps aux | grep <名前>` で対象を確認してください。もう1つは、止めたつもりでも `ps` に同じ名前のプロセスがまた現れる場合があることです。これは多くの場合、上位のプロセス(親プロセスや、後述の `systemctl` で管理されているサービス)が自動で再起動しているサインなので、プロセス単体ではなくサービス単位で止める必要があります。

### jobs・bg・fg・& --- シェル上のジョブを管理する

ターミナルで実行したコマンドを、画面を占有せずに裏側で動かしたり、後からまた手前に戻したりする仕組みです。あくまで「今開いているシェルの中だけ」の管理番号であり、`ps` で見るPIDとは別物です。

```bash
sleep 300 &        # 末尾に & を付けるとバックグラウンドで実行され、すぐプロンプトが戻る
jobs                # 今のシェルが把握しているジョブの一覧を見る
fg %1               # ジョブ番号1をフォアグラウンド(画面の手前)に戻す
```

```text
[1]+  Running                 sleep 300 &
```

- `Ctrl+Z` は、フォアグラウンドで動いているプロセスを一時停止(サスペンド)します。
- `bg %1` は、一時停止中のジョブ1をバックグラウンドで再開させます。

初心者がつまずきやすい点は、ターミナル(SSH接続など)を閉じるとバックグラウンドジョブも一緒に終了してしまうことです。作業用の一時的なコマンドを裏で動かす分には便利ですが、本番で常時動かし続けたいサービスは `jobs`/`bg`/`fg` ではなく、後述の `systemctl` で管理するのが基本です。

### nice・renice --- プロセスの優先度を調整する

`nice` はプロセスを**起動するとき**にCPUの優先度を指定するコマンド、`renice` は**すでに動いているプロセス**の優先度を後から変更するコマンドです。優先度は -20(最優先)から 19(最も譲る)までの数値で、指定しなければ 0 になります。

```bash
nice -n 10 tar -czf backup.tar.gz /data   # 優先度を下げて起動し、他の処理を妨げないようにする
renice -n 5 -p 12345                       # 動作中のPID 12345の優先度を後から変更する
```

判断は `top` の `NI` 列(nice値)を見て、意図した数値になっているかを確認します。優先度を上げる(数値を小さくする)操作は一般ユーザーには許可されていないため、`sudo renice -n -5 -p 12345` のように管理者権限が必要です。

初心者がつまずきやすい点は、「優先度を上げれば必ず速くなる」と誤解してしまうことです。CPUの取り分を調整しているだけなので、ディスクI/Oやメモリ不足がボトルネックの場合は効果がほとんどありません。まず `top` で本当にCPUが原因かを確認してから使う道具です。

### systemctl --- サービスの起動・停止・再起動・自動起動を管理する

`systemctl` は systemd(Linuxでサービスの起動・停止・自動起動を管理する仕組み)を操作するコマンドです。サーバー運用では、プロセスを `kill` で直接止めるのではなく、`systemctl` で「サービス」という単位で管理するのが基本になります。

```bash
sudo systemctl start nginx      # 起動する
sudo systemctl stop nginx       # 停止する
sudo systemctl restart nginx    # 一度止めてから起動し直す(設定を大きく変えた時など)
sudo systemctl enable nginx     # OS起動時に自動で立ち上がるよう設定する
sudo systemctl disable nginx    # 自動起動の設定を解除する
systemctl status nginx          # 今の状態を見る(sudo不要)
```

```text
● nginx.service - A high performance web server
     Loaded: loaded (/usr/lib/systemd/system/nginx.service; enabled; preset: enabled)
     Active: active (running) since Fri 2026-09-04 09:00:00 JST; 1h 15min ago
   Main PID: 1234 (nginx)
```

- `Active:` が `active (running)` なら正常に動作中です。`failed` は異常終了、`inactive (dead)` は止まっている状態を表します。
- `Loaded:` の中の `enabled` / `disabled` で、自動起動が設定されているかを確認できます。

初心者がつまずきやすい点は、`enable` しただけでは**今すぐは起動しない**ことです。「次回のOS起動時から有効にする」設定なので、今すぐ動かしたい場合は `start` も一緒に実行するか、`sudo systemctl enable --now nginx` のように両方をまとめて指定します。

⚠️ `stop` や `restart` は、実際に通信を受けているサービスに対して行うと接続が一時的に切れます。対象のサービス名を `status` で確認してから実行してください。

### journalctl --- ログで原因を追う

`journalctl` は、systemd が集めたログ(journal)を表示するコマンドです。`systemctl status` で異常に気づいたら、次に `journalctl` で原因の手がかりを探します。

```bash
journalctl -u nginx                       # nginxサービスのログだけを表示する
journalctl -u nginx -f                    # 末尾を表示しながら、新しいログをリアルタイムで待つ(tail -f相当)
journalctl -u nginx --since "10 min ago"  # 直近10分間だけに絞り込む
```

判断のポイントは、既存の `beginner-guide.md` と同じ考え方で、時系列で**最初に出たエラー行**と、その直前の行を読むことです。後から出てくるエラーは、最初のエラーに巻き込まれた結果であることが多く、そこだけを追っても原因にたどり着けません。

初心者がつまずきやすい点は、`-f` を付けると新しいログを待ち続けて画面が戻ってこないことです。`Ctrl+C` で抜けられます。また、RHEL系(dnf/yumを使うディストリビューション。RHEL、AlmaLinux、Rocky Linuxなど)でも `journalctl` の使い方自体はUbuntuと同じですが、認証(ログイン・sudoなど)に関するログは、Ubuntu/Debian系が `/var/log/auth.log` に記録するのに対し、RHEL系は `/var/log/secure` に記録するという違いがあります。原因調査で「そのディストリのログファイルはどこか」を意識しておくと、後から慌てずに済みます。

なお、上記のオプションは最初に使う範囲に絞ったものです。より細かい絞り込み方法(優先度でのフィルタや、複数サービスの同時表示など)は `man journalctl` や `journalctl --help` で調べてください。`ps`・`top`・`systemctl` についても同様に、まずは表の範囲を使いこなし、必要になったら `man <コマンド名>` を確認する進め方をおすすめします。

## ディスク・ファイルシステム・圧縮アーカイブ

このカテゴリでは、ディスクの空き容量やファイルシステムの構成を確認する方法と、ファイルをまとめて圧縮・展開する方法を扱います。ここを押さえると、「ディスクがいっぱいで書き込みに失敗する」「バックアップを 1 つのファイルにまとめて別サーバーへ運ぶ」といった、サーバー運用でよく起きる困りごとに自分で対応できるようになります。

| やりたいこと | コマンド | 例 | 確認・判断のポイント |
| --- | --- | --- | --- |
| ディスク全体の空き容量を見る | `df -h` | `df -h` | `Use%` が 100% に近いと危険。特に `/` と `/var` を優先して見る |
| 特定フォルダの使用量を見る | `du -sh` | `du -sh /var/log` | 数字が大きいディレクトリから順に `du -sh */` で子ディレクトリを見ていくと原因を絞り込める |
| ディスク・パーティション構成を見る | `lsblk` | `lsblk` | `MOUNTPOINTS` 列が空の領域は未使用、または未マウント |
| ディスクを一時的に使えるようにする・外す | `mount` / `umount` | `sudo mount /dev/sdb1 /mnt/data` | マウント後は `df -h` や `findmnt` で反映されているか確認する |
| マウント状況を見やすく確認する | `findmnt` | `findmnt /mnt/data` | 出力が無ければマウントされていない。`TARGET` と `SOURCE` の対応を確認する |
| 起動時のマウント設定を確認する | `/etc/fstab` を見る | `cat /etc/fstab` | ここに書かれた設定は再起動のたびに自動でマウントされる |
| ファイルをまとめて圧縮・展開する | `tar` | `tar czf backup.tar.gz ./data` | `tar tzf` で中身を確認してから展開すると事故を防げる |
| 単一ファイルを圧縮・展開する | `gzip` / `gunzip` | `gzip access.log` | 元ファイルが `.gz` に置き換わる（残したい場合は `-k` を使う） |
| Windows とも共有しやすい形式で圧縮・展開する | `zip` / `unzip` | `zip -r archive.zip ./data` | 展開先に同名ファイルがあると上書き確認が出ることがある |

### df -h --- ディスク全体の空き容量を確認する

`df`（disk free、ディスクの空き容量を表示するコマンド）は、サーバー全体でどのディスク領域がどれくらい埋まっているかを一目で確認するために使います。`-h`（human-readable、人が読みやすい単位で表示するオプション）を付けると、バイト数ではなく `GB` や `MB` 単位で表示されるので、まずはこの形で覚えます。

- **目的**: ディスクの空き容量を確認し、書き込み失敗や起動不能の予兆を早めに見つける
- **コマンド**: `df -h`
- **例**:

```bash
$ df -h
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        19G   15G  3.6G   81% /
tmpfs           2.0G     0  2.0G    0% /dev/shm
/dev/sdb1       100G   40G   55G   40% /mnt/data
```

- **確認・判断のポイント**: `Use%` が高いほど危険です。特に `/`（ルート、システムの土台になる領域）と `/var`（ログやパッケージのキャッシュが置かれる領域）は、ログの肥大化などで急に埋まることがあるため、日頃から気にして見ておく価値があります。`Use%` が 100% になると、新しいログの書き込みやパッケージのインストールが失敗するようになります。

> 覚え方は「全体を見るなら df、中身を見るなら du」です。

### du -sh --- どのフォルダが容量を使っているかを確認する

`du`（disk usage、ディスクの使用量を表示するコマンド）は、`df -h` で「ディスクが埋まっている」と分かったあと、**どのディレクトリが原因か**を探るために使います。`-s`（summarize、指定したディレクトリの合計だけを表示するオプション）と `-h` を組み合わせた `du -sh` が基本形です。

- **目的**: 容量を使っている犯人のディレクトリ・ファイルを特定する
- **コマンド**: `du -sh <ディレクトリ>`
- **例**:

```bash
$ du -sh /var/log
3.2G    /var/log

$ du -sh /var/log/*
2.8G    /var/log/journal
250M    /var/log/nginx
120M    /var/log/syslog
```

- **確認・判断のポイント**: まず親ディレクトリで大きい数字が出たら、`du -sh <ディレクトリ>/*` のようにワイルドカード（`*`、任意の文字列に一致する記号）で 1 階層下を展開し、数字が大きいものへ順番に潜っていきます。ログファイルが肥大化している場合は、ログローテーション（`logrotate` などでログを定期的に圧縮・削除する仕組み）の設定を見直す、というように次の対応につなげます。

### lsblk --- ディスク・パーティションの構成を確認する

`lsblk`（list block devices、ブロックデバイス＝ディスクの一覧を表示するコマンド）は、サーバーに接続されているディスクと、それがどのパーティション（ディスクを区切った領域）に分かれ、どこにマウントされているかをツリー形式で確認できます。ディスクを追加した直後や、構成を把握したいときに最初に打つコマンドです。

- **目的**: ディスクとパーティションの物理的な構成、マウント状況を一覧で把握する
- **コマンド**: `lsblk`
- **例**:

```bash
$ lsblk
NAME   MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
sda      8:0    0   20G  0 disk
├─sda1   8:1    0   19G  0 part /
└─sda2   8:2    0    1G  0 part [SWAP]
sdb      8:16   0  100G  0 disk
└─sdb1   8:17   0  100G  0 part /mnt/data
```

- **確認・判断のポイント**: `MOUNTPOINTS` 列が空になっているパーティションは、まだどこにもマウントされていない状態です。新しいディスクを追加したのに `df -h` に出てこない場合は、`lsblk` でそもそもパーティションが作られているか、マウントされていないだけかを切り分けます。

### mount / umount / findmnt --- ディスクを使えるようにする・外す・確認する

`mount`（ディスクやパーティションをディレクトリに結びつけて使えるようにするコマンド）と `umount`（その結びつきを外すコマンド）、`findmnt`（現在のマウント状況を見やすく表示するコマンド）はセットで覚えます。`lsblk` でマウントされていないパーティションを見つけたら、`mount` で使いたいディレクトリ（マウントポイント）に結びつけます。マウント先のディレクトリが存在しないと `mount` はエラーになるため、先に `mkdir -p`（ディレクトリを作成するコマンド。途中の階層が無くてもまとめて作る）で用意しておきます。

- **目的**: 追加したディスクを使える状態にする、または安全に取り外す
- **コマンド**: `mount` / `umount` / `findmnt`
- **例**:

```bash
$ sudo mkdir -p /mnt/data
$ sudo mount /dev/sdb1 /mnt/data
$ findmnt /mnt/data
TARGET     SOURCE      FSTYPE OPTIONS
/mnt/data  /dev/sdb1   ext4   rw,relatime

$ sudo umount /mnt/data
```

- **確認・判断のポイント**: `mount` を実行したあとは、必ず `findmnt` か `df -h` で `TARGET`（マウント先）と `SOURCE`（元のディスク）が意図した組み合わせになっているかを確認します。`umount` は、対象のディレクトリを別のターミナルで開いていたり、そこでプロセスがファイルを使用中だと `target is busy`（対象が使用中）のようなエラーで失敗することがあります。その場合は `lsof +D /mnt/data` などで使用中のプロセスを確認してから外します。

> ⚠️ `umount` は、対象ディレクトリを他の場所からコピー中・書き込み中でないことを確認してから実行してください。強制的に外すオプション（`-l`、`-f`）は、データを壊す可能性があるため初心者のうちは使わないでください。

**`/etc/fstab` に軽く触れる**: `mount` で手動でマウントした設定は、サーバーを再起動すると消えてしまいます。再起動後も自動でマウントしたい場合は、`/etc/fstab`（ファイルシステムテーブル、起動時にマウントする設定を書いておくファイル）に設定を追記します。

```bash
$ cat /etc/fstab
UUID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx /               ext4    errors=remount-ro 0 1
/dev/sdb1                                  /mnt/data       ext4    defaults           0 2
```

⚠️ `/etc/fstab` の記述を間違えると、次回起動時にシステムが正常に立ち上がらなくなることがあります。編集する前に必ず `sudo cp /etc/fstab /etc/fstab.bak` などでバックアップを取り、編集後は `sudo mount -a`（`/etc/fstab` の内容を反映させて試しにマウントするコマンド）でエラーが出ないかを再起動前に確認してください。

**RHEL 系との違い**: 上の例のファイルシステム種別（3 列目）は Ubuntu 標準の `ext4` です。RHEL 系（AlmaLinux・Rocky Linux など）は `xfs` がデフォルトになっていることが多く、`/etc/fstab` や `lsblk -f`（各パーティションのファイルシステム種別を表示するオプション）で見える値が変わります。ディストリビューションが分からないときは、まず `lsblk -f` で実際の値を確認してから作業します。

### tar czf / tar xzf --- 複数ファイルをまとめて圧縮・展開する

`tar`（tape archive、複数のファイルを 1 つのファイルにまとめるコマンド）は、バックアップの取得やファイルを別サーバーへ運ぶときの定番です。`c`（create、作成）・`z`（gzip 圧縮を使う）・`f`（file、出力ファイル名を指定する）を組み合わせた `czf` で圧縮アーカイブを作成し、`x`（extract、展開）・`z`・`f` を組み合わせた `xzf` で展開します。

- **目的**: 複数のファイル・ディレクトリを 1 つの圧縮ファイルにまとめる、またはそこから元に戻す
- **コマンド**: `tar czf <出力ファイル名> <対象>` / `tar xzf <対象ファイル>`
- **例**:

```bash
$ tar czf backup.tar.gz ./data
$ ls -lh backup.tar.gz
-rw-r--r-- 1 user user 12M  9月  4 10:00 backup.tar.gz

# 展開する前に中身だけを確認する
$ tar tzf backup.tar.gz
data/
data/report.csv
data/config.yml

# カレントディレクトリに展開する
$ tar xzf backup.tar.gz
```

- **確認・判断のポイント**: 展開（`x`）はカレントディレクトリに直接ファイルを広げるため、既存の同名ファイルを上書きすることがあります。**いきなり展開せず、まず `tar tzf`（t は table、中身の一覧だけを表示するオプション）で構成を確認してから展開する**のが安全です。作成後は `ls -lh` でファイルサイズが 0 でないこと、`tar tzf` で想定したファイルが含まれていることを確認します。

> 覚え方は「作るときも展開するときも f（対象ファイル名）は最後」です。`tar czf 出力.tar.gz 対象` と `tar xzf 対象.tar.gz` の語順をセットで覚えます。

⚠️ 展開で上書きされたファイルは元に戻せません。展開先に既存ファイルがある場合は、空のディレクトリを作ってそこへ展開し、中身を確認してから移動する方が安全です。

### gzip / gunzip --- 単一ファイルを圧縮・展開する

`gzip` は、ログファイルなど単一のファイルを圧縮するコマンドです。`tar` が「複数ファイルをまとめる」のに対して、`gzip` は「1 つのファイルを小さくする」ためのコマンドという役割の違いで覚えます。展開するときは `gunzip`、または `gzip -d`（decompress、展開オプション）を使います。

- **目的**: 古いログファイルなどを圧縮してディスク容量を節約する
- **コマンド**: `gzip <ファイル>` / `gunzip <ファイル.gz>`
- **例**:

```bash
$ ls -lh access.log
-rw-r--r-- 1 user user 50M  9月  4 09:00 access.log

$ gzip access.log
$ ls -lh access.log.gz
-rw-r--r-- 1 user user 6.1M  9月  4 09:00 access.log.gz

# 元ファイルを残したまま圧縮したい場合
$ gzip -k access.log
```

- **確認・判断のポイント**: `gzip` は初期状態では元ファイルを `.gz` に**置き換えます**（コピーではなく変換）。元ファイルも残したい場合は `-k`（keep、元ファイルを残すオプション）を付けます。圧縮後は `ls -lh` でファイルサイズが小さくなったこと、`file access.log.gz` で `gzip compressed data` と表示されることを確認します。

⚠️ `gzip` した時点で元ファイルは無くなります（`-k` を付けない限り）。ログなど消してはいけないファイルには `-k` を付けるか、圧縮前に `du -sh` でサイズを確認しておくと安心です。

### zip / unzip --- 他OSとも共有しやすい形式で圧縮・展開する

`zip` / `unzip` は、Windows や macOS でも標準的に扱える圧縮形式です。サーバー間だけで完結する作業なら `tar czf` で十分ですが、**作成したファイルを Windows のメンバーに渡す**など、他 OS とのやり取りが発生する場面では `zip` を使います。`tar` や `gzip` と異なり、`zip` / `unzip` は最小構成のサーバーには入っていないことが多いコマンドです。`zip: command not found` のように出たら、Ubuntu 系は `sudo apt install zip unzip`、RHEL 系は `sudo dnf install zip unzip`（古い RHEL 系では `yum install zip unzip`）でパッケージを追加します。

- **目的**: 他 OS とも共有しやすい形式でファイルをまとめる・展開する
- **コマンド**: `zip -r <出力ファイル名> <対象>` / `unzip <対象ファイル>`
- **例**:

```bash
$ zip -r archive.zip ./data
  adding: data/ (stored 0%)
  adding: data/report.csv (deflated 62%)

# 展開する前に中身だけを確認する
$ unzip -l archive.zip
Archive:  archive.zip
  Length      Date    Time    Name
---------  ---------- -----   ----
        0  2026-09-04 10:00   data/
    45213  2026-09-04 10:00   data/report.csv

$ unzip archive.zip
```

- **確認・判断のポイント**: `zip` はディレクトリごとまとめる場合、`-r`（recursive、ディレクトリの中身を再帰的に含めるオプション）を付け忘れると中身が空のアーカイブになるので注意します。展開前に `unzip -l`（一覧表示オプション）で中身を確認する習慣は `tar tzf` と同じです。展開時に同名ファイルがあると上書き確認のプロンプトが出ることがあり、無人実行のスクリプトで使う場合は `-o`（上書きを自動で許可するオプション）などの扱いを事前に調べてから使います。

> 覚え方は「サーバー同士なら tar、人に渡すなら zip」です。

これ以上の細かいオプションは、初心者のうちは覚えきる必要はありません。困ったときは `man tar` や `tar --help` のように、コマンド名の後ろに `--help` を付ける、または `man <コマンド名>` でマニュアルを参照する習慣をつけておくと、現場で知らないオプションに出会っても自力で調べられるようになります。

## ネットワークの確認と接続

このカテゴリでは、「つながらない」「遅い」「認証で止まる」といったネットワーク周りのトラブルに出会ったとき、どのコマンドから手を付けて原因の場所を絞り込むかを身につけます。あわせて、リモートのサーバーに安全にログインし、ファイルをやり取りする基本操作も扱います。

| やりたいこと | コマンド | 例 | 確認・判断のポイント |
| --- | --- | --- | --- |
| 自分のIPアドレスを見る | `ip a` | `ip a` | 対象のNIC（ネットワークインターフェースカード。通信の出入り口となる部品）に `inet` 行でIPアドレスが出ていればOK。`state DOWN` は物理的・設定的につながっていない |
| 相手に届くか確認する | `ping` | `ping -c 4 8.8.8.8` | `0% packet loss` なら届いている。`Destination Host Unreachable` や `100% packet loss` は経路またはFirewallの問題 |
| 自分のPCが待ち受けているポートを見る | `sudo ss -lntp` | `sudo ss -lntp` | 目的のポート番号が `LISTEN` の行にあるかを見る。無ければそのポートで誰も待ち受けていない |
| HTTP/HTTPSの応答を細かく見る | `curl -v` / `-I` / `-O` | `curl -v https://example.com` | ステータス行（`HTTP/1.1 200 OK` など）とヘッダーを見る。`Connection refused` は相手が待ち受けていない |
| ファイルを1行でダウンロードする | `wget` | `wget https://example.com/file.tar.gz` | 進捗バーが100%まで進み、`saved` と出れば成功 |
| 名前解決ができるか確認する | `dig` / `nslookup` | `dig example.com` | `ANSWER SECTION` にIPアドレスが出れば解決できている。`NXDOMAIN` はその名前が存在しない |
| リモートサーバーにログインする | `ssh` | `ssh user@203.0.113.10` | パスワードや鍵の入力プロンプトが出たあと、リモート側のプロンプト（`user@remotehost:~$` など）に変われば成功 |
| 1つのファイルをコピーする | `scp` | `scp file.txt user@203.0.113.10:/tmp/` | コピー中は転送速度と進捗（%）が表示される。エラーなく戻ってくれば完了 |
| フォルダ全体を同期する | `rsync -avz` | `rsync -avz ./local/ user@203.0.113.10:/remote/` | 転送されたファイルの一覧が出る。2回目以降は変更分だけが表示される |

> 覚え方は **「自分を見る → 届くか見る → 待ち受けているか見る → 中身を見る → 名前を引けるか見る → 入って運ぶ」** です。この順に確認すると、通信のどの区間で止まっているかが1つずつ絞り込めます。

### ip a --- 自分のネットワーク設定を見る

まず自分のPCやサーバーが、どのIPアドレスを持っているかを確認します。以前は `ifconfig` というコマンドが使われていましたが、`ifconfig` は開発が止まっており、Ubuntu 24.04には標準で入っていません。現在は `ip a`（`ip address show` の短縮形）を使うのが標準です。

```bash
ip a
```

典型的な出力（一部を抜粋、実際には他のNICも表示されます）は次のようになります。

```text
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP group default qlen 1000
    link/ether 02:42:ac:11:00:02 brd ff:ff:ff:ff:ff:ff
    inet 172.17.0.2/16 brd 172.17.255.255 scope global eth0
       valid_lft forever preferred_lft forever
```

**つまずきやすい点**

- `state UP` と `inet` 行のIPアドレスの両方をセットで確認します。`state DOWN` のときは、ケーブルの抜けやNICの無効化など、通信より前の段階で止まっています。
- クラウドやコンテナ環境では、表示されるIPアドレス（多くはプライベートIPアドレス）が、外部からアクセスするIPアドレス（パブリックIPアドレス）と異なることがあります。混同しないようにします。

### ping --- 相手に届くか確認する

目的の相手（IPアドレスやホスト名）まで通信が届くかどうかを確かめる、最も基本的なコマンドです。

```bash
ping -c 4 8.8.8.8
```

```text
PING 8.8.8.8 (8.8.8.8) 56(84) bytes of data.
64 bytes from 8.8.8.8: icmp_seq=1 ttl=115 time=12.3 ms
64 bytes from 8.8.8.8: icmp_seq=2 ttl=115 time=11.9 ms
64 bytes from 8.8.8.8: icmp_seq=3 ttl=115 time=12.5 ms
64 bytes from 8.8.8.8: icmp_seq=4 ttl=115 time=12.1 ms

--- 8.8.8.8 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3005ms
```

`-c 4` は「4回送って止める」という意味で、これを付けないと `Ctrl + C` で止めるまで送り続けます。**必ず `-c` で回数を指定する癖をつけましょう**。

**つまずきやすい点**

- `ping` が失敗しても、相手のサーバー自体は動いていることがあります。多くのFirewallは、セキュリティのためにpingへの応答（ICMPというプロトコル）だけを止めている場合があるためです。ping単独で「サーバーが落ちている」と判断せず、次に説明する `curl` や `ss` も合わせて確認します。

### ss -lntp --- 自分側がポートを待ち受けているか見る

「サーバー側のアプリが、そのポートで通信を受け付ける準備ができているか」を確認するコマンドです。以前は `netstat` が使われていましたが、現在は後継の `ss`（socket statistics）を使います。

```bash
sudo ss -lntp
```

```text
State    Recv-Q  Send-Q   Local Address:Port   Peer Address:Port  Process
LISTEN   0       511      0.0.0.0:80           0.0.0.0:*          users:(("nginx",pid=1234,fd=6))
LISTEN   0       128      127.0.0.1:8000       0.0.0.0:*          users:(("gunicorn",pid=1500,fd=5))
```

各オプションの意味は、**「Listening（待ち受け）だけを・数値で・TCPで・プロセス名付きで」** と覚えます（`-l` `-n` `-t` `-p`）。`-p` でプロセス名を出すには `sudo` が必要です。

**つまずきやすい点**

- `Local Address` が `127.0.0.1` の場合、そのPC/サーバーの内部からしかアクセスできません。外部から接続させたい場合は `0.0.0.0`（すべてのアドレスで待ち受ける設定）になっているかを確認します。
- 目的のポートの行が無ければ、アプリがそもそも起動していないか、別のポートで待ち受けています。まず `systemctl status` でアプリの状態を確認します。

### curl -v / -I / -O --- HTTP/HTTPSの応答を細かく見る

Webサーバーへのリクエストを1回だけ送り、応答を細かく確認できるコマンドです。障害切り分けで最も使う場面が多いコマンドの1つです。

```bash
curl -v https://example.com
```

`-v`（verbose、詳細表示）を付けると、通信の途中経過（TLS接続の様子やヘッダー）まで表示されます。

```text
* Connected to example.com (93.184.216.34) port 443
* SSL connection using TLSv1.3 / TLS_AES_128_GCM_SHA256
> GET / HTTP/1.1
> Host: example.com
< HTTP/1.1 200 OK
< Content-Type: text/html; charset=UTF-8
```

`>` が自分から送った内容、`<` が相手から返ってきた内容です。ステータス行（`HTTP/1.1 200 OK` の部分）を見て、200番台なら正常、400番台は自分側のリクエストの問題、500番台は相手のサーバー側の問題、と切り分けます。

ヘッダーだけ確認したいときは `-I`（HEADリクエスト。本文を取得せずヘッダーだけ受け取る）、ファイルとして保存したいときは `-O`（URLのファイル名のまま保存）を使います。

```bash
curl -I https://example.com
curl -O https://example.com/sample.zip
```

**つまずきやすい点**

- `curl: (7) Failed to connect` はポートで待ち受けていない、または経路上のFirewallで止められている状態です。まず `ss -lntp`（相手側で確認できる場合）や後述の `ping` で経路を確認します。
- `curl: (6) Could not resolve host` は名前解決の失敗です。IPアドレスを直接指定して `curl` が通れば、原因は名前解決（DNS）側にあると絞り込めます。

### wget --- ファイルを1コマンドでダウンロードする

`curl -O` と似ていますが、`wget` は最初からファイル保存を主目的に作られており、進捗バーの表示やリトライ（失敗時の再試行）に強いのが特徴です。1つのファイルをそのまま保存したいときに向いています。

```bash
wget https://example.com/sample-file.tar.gz
```

```text
Saving to: 'sample-file.tar.gz'
sample-file.tar.gz  100%[===================>]  12.34M  5.67MB/s    in 2.2s
2026-09-04 10:00:00 (5.67 MB/s) - 'sample-file.tar.gz' saved [12937216/12937216]
```

**つまずきやすい点**

- Ubuntu 24.04（Debian系）には標準で入っていますが、最小構成のRHEL系（AlmaLinuxなど）では入っていないことがあります。その場合は `sudo dnf install wget` で追加します。
- `curl` と `wget` はどちらか一方しか使えないわけではありません。「詳細を見ながら調べたいときは `curl -v`」「とにかく保存したいだけなら `wget`」と目的で使い分けます。

### dig / nslookup --- 名前解決ができるか確認する

ドメイン名（`example.com` など）からIPアドレスを引けるかどうかを確認するコマンドです。Ubuntu 24.04では `dig` が標準的で、情報量も詳しく出ます。`nslookup` はより古くからあるコマンドで、Windowsにも同名のコマンドがあるため、他OSとの比較で使われることもあります。

```bash
dig example.com
```

```text
;; ANSWER SECTION:
example.com.        86400   IN      A       93.184.216.34

;; Query time: 15 msec
;; SERVER: 127.0.0.53#53(127.0.0.53)
;; WHEN: Thu Sep 04 10:00:00 JST 2026
```

`ANSWER SECTION` にIPアドレス（`A` レコード）が出ていれば名前解決は成功です。何も出ない、または `status: NXDOMAIN` と出た場合は、その名前が見つからない状態です。

```bash
nslookup example.com
```

**つまずきやすい点**

- `dig` が失敗しても、IPアドレスを直接指定した `ping` や `curl` が成功するなら、問題はサーバー本体ではなくDNS（名前解決の仕組み）側にあると分かります。「見る・絞る・変える・確かめる」の**絞る**の段階で、この切り分けが役立ちます。
- 会社や自宅のネットワークでは、独自のDNSサーバーを使っていることがあります。`dig` の出力にある `SERVER:` 行で、どのDNSサーバーに問い合わせたかを確認できます。
- RHEL系（AlmaLinuxなど）の最小構成では `dig` や `nslookup` が標準で入っておらず、`bind-utils` パッケージが必要になることがあります。その場合は `sudo dnf install bind-utils` で追加します。

### ssh --- リモートサーバーに安全にログインする

離れた場所にあるサーバーに、暗号化された通信でログインするコマンドです。サーバー構築の作業のほとんどは、このsshでのログイン後に行います。

```bash
ssh user@203.0.113.10
```

初回接続時は、相手のサーバーの正当性を確認するメッセージが出ます。

```text
The authenticity of host '203.0.113.10' can't be established.
ED25519 key fingerprint is SHA256:xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx.
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
```

見覚えのあるサーバーであれば `yes` と入力して続けます。その後パスワード、または鍵認証(秘密鍵というファイルを使って本人確認する仕組みで、パスワードより安全性が高いとされます)の場合は鍵のパスフレーズを求められます。ログインに成功すると、プロンプトが `user@remotehost:~$` のように、リモート側のものに変わります。

**つまずきやすい点**

- `Connection timed out` は、相手までパケットが届いていない状態です。まず `ping` や、後述の対応表にある経路確認を行います。
- `Connection refused` は、相手のサーバーまでは届いているものの、22番ポート（sshの標準ポート）で待ち受けていない状態です。サーバー側で `sudo ss -lntp` を確認します。
- `Permission denied (publickey)` は、鍵認証を使う設定のサーバーで、正しい秘密鍵を指定できていない状態です。`ssh -i ~/.ssh/自分の鍵ファイル user@ホスト` のように `-i` オプションで鍵ファイルを明示します。
- サーバー側でログイン失敗の原因を調べる場合は、Ubuntu系では `sudo journalctl -u ssh` や `/var/log/auth.log`、RHEL系（AlmaLinuxなど）では `/var/log/secure` を確認します。

### scp / rsync -avz --- ファイルをリモートサーバーとやり取りする

どちらもsshの仕組みを使って、暗号化された通信でファイルを転送します。使い分けの目安は、**「1つのファイルだけをコピーするなら `scp`、フォルダごと・2回目以降の差分だけを送るなら `rsync`」**です。

```bash
scp file.txt user@203.0.113.10:/tmp/
```

```bash
rsync -avz ./local-folder/ user@203.0.113.10:/remote-folder/
```

`rsync` のオプションは、**「Archive（属性を保ったまま再帰的にコピー）・Verbose（詳しく表示）・Zip（圧縮しながら転送）」**と覚えます(`-a` `-v` `-z`)。1回目はすべてのファイルを転送しますが、2回目以降は変更のあったファイルだけを転送するため、大きなフォルダの同期に向いています。

```text
sending incremental file list
local-folder/
local-folder/report.txt

sent 1,234 bytes  received 45 bytes  855.33 bytes/sec
total size is 10,240  speedup is 8.13
```

**つまずきやすい点**

- `rsync` の転送元パスの末尾に `/` を付けるかどうかで結果が変わります。`./local-folder/` （末尾に `/` あり）は「フォルダの中身」を転送しますが、`./local-folder` （末尾に `/` なし）は「フォルダ自体」を転送先の中に作ります。意図と違う場所にコピーされていないか、転送後に転送先を `ls` で確認する習慣をつけます。
- `rsync` には `--delete` という、転送先にあって転送元に無いファイルを削除するオプションがあります。**⚠️ 元に戻せない操作です。** 意図せず必要なファイルを消してしまうことがあるため、初心者のうちは使わず、まず `--dry-run`（実際には転送・削除せず、何が起きるかだけを表示するオプション）で結果を確認してから使うようにします。

なお、これ以外の細かいオプションについては、`man ssh` や `curl --help` のように、コマンド名の後に `--help` を付ける、または `man コマンド名` でマニュアルを確認する習慣をつけると、必要なときに自分で調べられるようになります。

## テキスト処理・パイプ・シェルの便利機能・自動化

このカテゴリでは、コマンドの出力を別のコマンドへつなぎ、欲しい行・欲しい列だけを取り出し、繰り返す操作を自動化する方法を学びます。1つ1つのコマンドは単純でも、**組み合わせる**ことでログ調査や集計が驚くほど楽になります。

| やりたいこと | コマンド | 例 | 確認・判断のポイント |
| --- | --- | --- | --- |
| コマンドの出力を次のコマンドへ渡す | `\|` | `journalctl -u nginx \| grep error` | 左のコマンドの標準出力が、右のコマンドの標準入力になる |
| 出力をファイルに保存する | `>` `>>` `<` `2>` | `df -h > disk.txt` | `>` は上書き、`>>` は追記。間違えると前の記録が消えるので注意 |
| 行を並び替える | `sort` | `sort -n scores.txt` | `-n` を付けないと文字列として比較され、`9` が `87` より大きい行として扱われるなど順番が崩れる |
| 重複行をまとめる・数える | `uniq` | `sort access.log \| uniq -c` | `uniq` は**隣り合う**行しか比較しないため、事前に `sort` が必須 |
| 列を取り出す | `cut` | `cut -d ',' -f 1,3 users.csv` | 区切り文字（`-d`）と欲しい列番号（`-f`）が合っているか出力で確認する |
| 列・パターンで集計する | `awk` | `awk -F',' '$3 == "sales" {print $1}' users.csv` | `$1` は1列目、`$3` は3列目。`条件 {処理}` の条件部分で行を絞り込み、区切り文字は `-F` で指定する |
| 文字列を置換する | `sed` | `sed 's/foo/bar/' file.txt` | デフォルトは画面表示のみで元ファイルは変わらない。上書きするなら `-i` |
| 環境変数を設定・確認する | `export` `env` | `export API_KEY=xxxx` | `env` の一覧に出てくるか、`echo $変数名` で中身を確認する |
| コマンドを短い名前で呼ぶ | `alias` | `alias ll='ls -alF'` | ターミナルを閉じると消える。恒久化するには `~/.bashrc` に書く |
| 定期的にコマンドを自動実行する | `crontab -e` `crontab -l` | `crontab -l` | `-e` で編集、`-l` で今の予約一覧を表示して確認する |
| パッケージを最新化・追加する | `apt`（`dnf`/`yum`） | `sudo apt update && sudo apt upgrade` | `update` は一覧の更新、`upgrade` は実際の更新。順番を守る |

### パイプ（`|`）とリダイレクト（`>` `>>` `<` `2>`）--- コマンドをつなげる・出力を保存する

パイプ（`|`）は、あるコマンドの**標準出力**（画面に表示される結果）を、そのまま次のコマンドの**標準入力**（次のコマンドへの入力データ）として渡す仕組みです。リダイレクトは、出力や入力の行き先を画面からファイルに変える仕組みです。

```bash
# 「動いているサービスの一覧」から nginx を含む行だけを見る
systemctl list-units --type=service | grep nginx

# ディスク使用量の結果をファイルに保存する（上書き）
df -h > disk-report.txt

# 同じ内容を追記する(2回目以降は末尾に追加される)
date >> disk-report.txt

# ファイルの中身を標準入力として渡す
sort < names.txt

# 標準エラー出力(エラーメッセージ)だけを別ファイルに保存する
sudo apt update > update.log 2> update-error.log
```

- `>` は**上書き**、`>>` は**追記**です。ログをためたいときに `>` を使うと、前回までの内容が消えてしまいます。
- `2>` の「2」は標準エラー出力の番号です。通常の出力（1、省略可）と分けて保存すると、エラーだけを後から探しやすくなります。
- パイプは何段でもつなげられます。**「出力 → 絞り込み → 並び替え → 件数集計」**のように、目的の形になるまで1段ずつコマンドを足していくと、失敗した箇所がわかりやすくなります。

> 覚え方は「`|` は横につなぐ、`>` は下に落とす」です。パイプは画面の結果を次の道具へ渡し、リダイレクトは結果を紙(ファイル)に落とします。

### sort / uniq --- 並び替えてから数える

`sort`は行を並び替えるコマンド、`uniq`は隣り合う重複行をまとめるコマンドです。この2つはほぼ必ずセットで使います。

```bash
# アクセスログの中で、どのIPアドレスが多いか集計する
awk '{print $1}' access.log | sort | uniq -c | sort -nr | head -5
```

```text
     342 203.0.113.10
     198 203.0.113.55
      87 198.51.100.7
      41 198.51.100.20
       9 192.0.2.1
```

- `uniq`は**ソート済み**の行しか正しく数えられません。`sort`を挟まずに`uniq -c`だけを使うと、離れた場所にある同じ行が別々に数えられてしまいます。
- `sort -nr`の`-n`は数値として並べる、`-r`は逆順(大きい順)にするという意味です。`-n`を忘れると`"9"`が`"87"`より大きい行として扱われるなど、文字列としての順番になってしまいます。
- `sort -u`はソートと重複除去を一度に行いますが、件数(何回出てきたか)は分かりません。件数も見たい場合は`sort | uniq -c`を使います。

### cut / awk --- 列を取り出す・集計する

`cut`はシンプルに列を切り出すコマンド、`awk`はもう少し柔軟に列や条件を扱えるコマンドです。まずは`cut`で十分な場面が多く、条件を付けたくなったら`awk`を使う、という順番で覚えると混乱しません。

```bash
# CSVファイルから 1列目と3列目(名前・部署)だけを取り出す
cut -d ',' -f 1,3 users.csv

# ログの1列目(IPアドレスなど、空白区切りの1番目)だけを表示する
awk '{print $1}' access.log

# CSVで、3列目(部署)が "sales" の行だけ、1列目(名前)を表示する
awk -F',' '$3 == "sales" {print $1}' users.csv
```

- `cut`の`-d`は区切り文字、`-f`は取り出したい列番号です。区切り文字が想定と違う(タブなのにカンマを指定した、など)と、意図しない列がまるごと出力されます。
- `awk`はデフォルトで**空白(スペースやタブ)区切り**として列を認識し、`$1`が1列目、`$2`が2列目、`$0`が行全体を表します。CSVのようにカンマ区切りのときは`-F','`で区切り文字を指定します。
- `awk`の基本形は`awk '条件 {処理}'`です。条件を省略すると全行が対象になり、`{print $1}`のように処理だけを書くこともよくあります。まずはこの2パターンを覚え、複雑な条件は必要になったときに`man awk`で調べれば十分です。

### sed --- 文字列を置換する

`sed`はファイルや出力の中の文字列を、指定したパターンに従って置き換えるコマンドです。基本の書き方は`s/置換前/置換後/`(sはsubstitute=置換の頭文字)です。

```bash
# 画面に表示するだけ(元ファイルは変更されない)
sed 's/localhost/127.0.0.1/' nginx.conf

# 行の中の最初の一致だけでなく、行内すべてを置換する(gはglobal=全体の意味)
sed 's/error/ERROR/g' app.log

# ファイルを直接書き換える(-i = in-place、その場で編集)
sed -i 's/8080/8443/' app.conf
```

- 何もオプションを付けない`sed 's/.../.../'`は**画面に結果を表示するだけ**で、元のファイルは変わりません。ファイルそのものを書き換えたいときだけ`-i`を付けます。
- `-i`は元に戻せない置換です。**⚠️ 実行前に`sed 's/.../.../' file`(`-i`なし)で置換結果を画面で確認するか、`cp file file.bak`でバックアップを取ってから実行してください。**
- `g`を付けないと、1行の中で**最初に一致した箇所だけ**が置換されます。行内に同じ単語が複数あるのに1つしか変わらない、という場合はこの`g`忘れが原因のことが多いです。

### export / env --- 環境変数を設定する・確認する

環境変数(かんきょうへんすう。プログラムやシェルが読み取る「設定用の値」)は、パスワードやAPIキー、動作モードなどをコマンドやスクリプトに渡すための仕組みです。`export`は変数を設定し、そのシェルから起動した他のプログラムにも見えるようにするコマンド、`env`は今設定されている環境変数の一覧を見るコマンドです。

```bash
# 環境変数を設定する
export APP_ENV=production

# 設定されているか確認する(1つだけ)
echo $APP_ENV

# すべての環境変数を一覧表示する
env

# 特定の変数だけ絞り込む
env | grep APP_ENV
```

- `export`で設定した変数は、そのターミナルを閉じると消えます。次回も使いたい場合は`~/.bashrc`(ログイン時に読み込まれる設定ファイル)に`export`の行を追記します。
- `echo $APP_ENV`のように`$`を付けて中身を確認します。`$`を付け忘れると、変数名の文字列そのもの(`APP_ENV`という文字)が表示されるだけなので注意してください。
- **⚠️ パスワードやAPIキーなどの秘密情報を環境変数に入れる場合、`env`の実行結果や証跡(スクリーンショットやログ)に含めないよう気を付けてください。**

### alias --- コマンドを短い名前で呼ぶ

`alias`は、よく使う長いコマンドに短い別名を付けるコマンドです。毎回同じオプションを打つ手間を減らせます。

```bash
# ls に色付け・詳細表示のオプションを付けて ll という名前にする
alias ll='ls -alF'

# 今登録されている alias の一覧を見る
alias

# 恒久化する場合は ~/.bashrc に追記してから読み込み直す
echo "alias ll='ls -alF'" >> ~/.bashrc
source ~/.bashrc
```

- `alias`だけで設定した場合、そのターミナルを閉じると消えます。次回以降も使いたい場合は`~/.bashrc`に書き、`source ~/.bashrc`(設定ファイルを読み込み直すコマンド)で反映させます。
- 既存のコマンド名と同じ名前で`alias`を作ると、元のコマンドの動きが変わったように見えて混乱の元になります。慣れないうちは`ll`や`gs`のような、元のコマンドにない短縮名から始めるのがおすすめです。

### crontab（-e / -l）--- コマンドを定期的に自動実行する

`crontab`は、「毎日3時にこのコマンドを実行する」のように、決まった時刻・間隔でコマンドを自動実行させる仕組み(cron)の設定を管理するコマンドです。ここでは基本の書き方だけを扱います。

```bash
# 自分の予約(crontab)を編集する
crontab -e

# 今登録されている予約の一覧を表示する
crontab -l
```

`crontab -e`で開くファイルには、次の形式で1行ずつ予約を書きます。

```text
分 時 日 月 曜日 実行するコマンド
```

```bash
# 毎日3時にバックアップスクリプトを実行する例
0 3 * * * /home/user/backup.sh >> /home/user/backup.log 2>&1
```

- `*`は「毎回」を意味します。`0 3 * * *`は「毎日3時0分」、`*/10 * * * *`は「10分ごと」です。
- `crontab -l`で一覧を確認し、意図した予約が登録されているかを必ず確認してください。編集しただけで確認を怠ると、書式ミスのまま気づかないことがあります。
- 実行結果は自動では表示されないため、上の例のように`>> ログファイル 2>&1`(標準出力と標準エラー出力の両方をログファイルに追記する書き方)を付けておくと、後から成功・失敗を確認できます。
- **⚠️ 削除や設定変更を伴うコマンドをcrontabに登録する場合、まず手動で1回実行して結果を確認してから予約に組み込んでください。**予約は忘れた頃に自動実行されるため、意図しない削除が起きても気づきにくいという特性があります。

### apt update / upgrade / install と dnf/yum の違い --- パッケージを管理する

`apt`は、Ubuntu/Debian系のOSでソフトウェア(パッケージ)を管理するコマンドです。`update`は「使えるパッケージの一覧を最新化する」、`upgrade`は「実際にインストール済みのパッケージを新しいバージョンに更新する」、`install`は「新しいパッケージを追加する」という、それぞれ別の役割を持っています。

```bash
# パッケージ一覧を最新化してから、インストール済みパッケージを更新する
sudo apt update && sudo apt upgrade

# 新しいパッケージ(例: curl)をインストールする
sudo apt install curl
```

- `update`と`upgrade`は名前が似ていますが役割が違います。**`update`だけでは何もアップグレードされません。**`update`は「一覧の更新」、`upgrade`は「実体の更新」と覚えてください。
- `&&`は「前のコマンドが成功したら次を実行する」という意味です。`update`が失敗した状態で`upgrade`を実行すると、古い一覧のまま更新してしまう恐れがあるため、この順番と`&&`はセットで覚えます。
- `sudo`(管理者権限で実行するコマンド)を付け忘れると、権限不足でパッケージ管理ができずエラーになります。

RHEL系(CentOS Stream, Rocky Linux, Alma Linuxなど)では、パッケージ管理コマンドが異なります。

| 系統 | パッケージ管理コマンド | 一覧更新 | 更新 | インストール |
| --- | --- | --- | --- | --- |
| Debian系(Ubuntu 24.04など) | `apt` | `apt update` | `apt upgrade` | `apt install <名前>` |
| RHEL系(比較的新しいバージョン) | `dnf` | 不要(`install`/`upgrade`実行時に自動確認) | `dnf upgrade` | `dnf install <名前>` |
| RHEL系(古いバージョン) | `yum` | 不要(同上) | `yum update` | `yum install <名前>` |

- `dnf`は`yum`の後継コマンドで、使い方はほとんど同じです。どちらのOSを触っているか分からないときは、`cat /etc/os-release`(OSの種類やバージョンを表示するコマンド)で確認します。
- Debian系は`update`(一覧更新)と`upgrade`(実体更新)が明確に分かれていますが、`dnf`/`yum`は`upgrade`(または`update`)を実行するときに一覧の最新化も自動で行われる点が、初心者がつまずきやすい違いです。
