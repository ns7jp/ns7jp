# 就職・定着の週次運用

[入口](README.md) / [求人・応募](job-search.md) / [入社後](onboarding.md) / [操作](tool-guide.md)

## 1. 成長を判断する5つの観点

| 観点 | 観察すること | 次の行動へ戻す例 |
| --- | --- | --- |
| 技術 | 要件から設計・構築・試験・復旧まで説明と実行が対応するか | DNSを説明できない→SE02の該当条件を練習 |
| 信頼 | 約束、報告、未確認の区別、相談、中止の判断 | 相談が遅れた→次回は相談条件と期限を先に決める |
| 機会 | 合う職務を選び、必要な証拠を伝えられているか | 面接で復元を問われた→実記録の説明と不足試験を確認 |
| 成果 | 相手が必要とする結果と受け入れ条件を満たせたか | 引継ぎで困った点→PJの手順・受領条件を改善 |
| 持続性 | 本人の時間上限と負担の範囲で続けられるか | 計画超過が続く→課題数と予定量を減らす |

学習・資格・投稿・応募の件数だけを最終成果にしません。
年収や採用確率、企業からの評価、本人の健康状態を公開GitHubから推測しません。
収入や条件を比較するときは、本人が確認した募集・提示条件と本人の希望を別々に記録します。

## 2. 月曜09:00の実行順

既存の週次自動化を拡張します。別のスケジューラを重複登録しません。

1. 本人の最新の目標、週の上限、負荷モード、既に約束した時間を確認する。
2. GitHub監査で3リポジトリの最新原本・既存PR・CI・未実測を取得する。
3. 非公開キャリア設定を読み、接続済みならSE/PJの読み取り専用reportを参照する。
4. 求人の要求、面接での問い、職場のフィードバックと、実際の証拠を結び付ける。
5. 人の計画はCLIで時間内の最大3主行動にし、Codexの実装は最重要の実行可能な改善1件に絞る。
6. Codexの改善は既存の45分・通常5ファイル250変更行の枠に収め、必要な検証を実施する。
7. 変化、修正成果、必要な本人操作だけを短く知らせ、根拠と詳細はローカルに保存する。

Codexの作業45分は本人の学習時間を自動消費した実績にしません。
本人がレビューや準備に使った時間は、週の10時間の中へ含めます。
今回のシステム初期導入は通常の小修正枠とは別の作業です。

## 3. 機会を見つける

就職前は[求人比較票](templates.md)で希望の職務、通勤・勤務・学習支援などを整理します。
本人の条件が未確認なら未確認のままにし、応募先への適合を断定しません。
自動調査は企業の公式募集ページを優先し、URLと確認日時を残します。
最初は週3件以内を目安に、要求と証拠の比較を深めます。件数はノルマではありません。

求人原本は変わるため、14日を超えた確認や必須条件がUNKNOWN/GAPの求人に結び付く応募準備は、
CLIで `OPPORTUNITY_NEEDS_CONFIRMATION` とします。14日は初期運用値で、募集継続を保証する期間ではありません。
送信直前には本人が最新の募集・送信内容・宛先を確認します。

機会の状態はDISCOVERED→REVIEWED→SUBMITTED→INTERVIEW→OFFER等を記録できますが、
この順に自動で進める機能はありません。提出・面接・提示・終了は実際の本人記録を参照します。
返信がないことを不採用と断定せず、相手が示した時期と本人の次回確認を区別します。
同一URLは追跡パラメータ等を除いて重複検出します。別URLの同一募集はCodexと本人が意味を確認します。

入社後は、実案件の困りごと・手順の不明点・担当者のフィードバックから機会を探します。
社内情報は所属先の許可された場所で扱い、個人側には公開可能な抽象的課題への参照だけを持ちます。

## 4. 時間の計算

通常時は `週の上限 − 20%の余白 − 既約束の時間 − 週次レビュー` の残枠へ行動を入れます。
週次レビューは通常60分、縮小時30分を目安に、残枠を超えない範囲で確保します。
既約束は、その週に割り当てた面接・説明会・課題等の時間です。全期間のPJ残作業を足しません。
仕事中の業務を私生活の10時間へ自動で追加せず、本人の管理対象を明確にします。

- `normal`：本人が設定した上限を使う。
- `reduced`：一時的に半分の上限で計画する。完了条件を半分にする意味ではない。
- `paused`：新しい行動を割り当てない。期限がある約束は確認事項として残す。
- 時間未設定：制限なしとせず、新しい行動を選ばない。

予定量が過剰なら自動で約束を変更せず、どの期限と作業量を見直すか表示します。
上限に収まらない大きな行動は保留し、本人が意味のある小作業に分解します。
最大3主行動は、1つの技術課題・1つの機会課題・1つの説明課題を初期の目安にします。
実際の期限がある場合はそちらを優先し、必ず3領域を埋めることは求めません。

## 5. 学習と応募を循環させる

| 起きたこと | 判断 | 次に用意するもの |
| --- | --- | --- |
| 求人の必須要件に根拠がない | 実際の条件と、未経験者の応募可否を確認 | 質問案、既存SE条件への対応 |
| 応募文が長く主作品が伝わらない | 要求に対応する証拠を一つ選ぶ | 課題→判断→実行→結果→限界の短い説明 |
| 面接で答えられなかった | 問いと自分の回答を本人が保存 | 説明練習または実測カード |
| 実測で失敗した | 失敗と切り分けを正本へ記録 | 仮説、識別方法、再試験の条件 |
| レビュー待ちで進めない | 確認役・次回確認を決める | 他の実行可能な課題1件 |
| 実務の手順が分からない | 推測で本番を変えず相談 | 対象、事実、未確認、判断期限の報告 |
| 負担が継続して大きい | 予定量と同時進行を減らす | 縮小計画と必要な相談 |

## 6. 発信と人との接点

公開候補は、新しい実測・失敗からの学び・再現手順など、読む人が使える成果から選びます。
1件の成果をREADMEの短い説明、面接の3分説明、詳細手順へ使い分けます。
AIの文章を増やすより、本人が説明・再現できる範囲をはっきりさせます。

レビューや勉強会の候補を調べる、質問の下書きを作ることはCodexができます。
誰かへ送信する、投稿する、参加登録する、所属や紹介関係を主張する行為は本人の明示的な許可に従います。
反応が少ないことだけで技術価値を否定せず、対象者、説明、根拠、導線を確認します。

## 7. 90日と四半期の見直し

| 期間 | 狙い | 見直しの材料 |
| --- | --- | --- |
| 最初の2週 | 条件・証拠・次の実測を整理 | 比較票、説明練習、既存台帳への接続 |
| 3〜6週 | 不足の実測と応募準備を循環 | 実行記録、求人の要求、本人の質問 |
| 7〜12週 | 実際の反応から配分を調整 | 応募・面接の記録、詰まった問い、負荷 |
| 入社後30/60/90日 | 期待成果と担当範囲を合意 | 上司・育成担当の実際の確認 |
| 以後の四半期 | 仕事で役立つ専門性を一つ伸ばす | SE/BX、受領者の困りごと、再発した欠陥 |

期間は計画の節目です。12週以内の採用や90日での独力担当を約束するものではありません。
就職前後の切替は本人の状況確認で行い、公開GitHubの活動から入社を推定しません。

## 8. 記録・通知・確認の境界

`profile.json` の `updated_at` は本人が計画内容を確認した時刻です。求人を再取得しただけでは更新しません。
28日を超えた計画は、通常行動の前にレビューします。本人の週10時間の希望を勝手に変更する規則ではありません。
SE/PJが未接続ならNOT_CONNECTED、接続して読めなければUNAVAILABLE。0件の合格や成功へ読み替えません。
接続不全に依存する技術計画を止めても、独立した求人比較などは進められます。

通知の比較から単なる実行日時は除きます。選ぶ行動、期限、容量、保留理由、求人状態、接続状態が変われば通知候補です。
保留中でも期限を表示し、今週の期限なら再計画を求めます。時刻は保存上UTC、本人の予定は日本時間と照合します。
生成するMarkdown/JSONは私用です。求人候補や選考・社内記録が含まれ得るため、公開成果へそのまま転記しません。

状態が壊れた場合は上書きしません。ロックが残った場合は実行中か確認し、終了した当該ロックだけを除去します。
入力・原本・履歴を保存し、原因が分からないまま再初期化で消しません。
スケジュール停止・再開・時刻変更は、このCodexタスクで既存自動化を更新します。
