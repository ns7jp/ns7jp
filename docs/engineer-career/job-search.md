# サーバー構築職へ応募し、結果から次を決める

目標はサーバー構築職への就職と、入社後に相談しながら担当を広げられる状態です。
志望領域と提示する作品の正本は [志望トラック](../target-roles.md)、説明練習は [主作品を自分の言葉で説明する練習](../portfolio-explanation.md)です。
ここでは求人を選び、記録のある能力を応募書類へ対応させ、結果を次の行動に戻します。

## 週10時間で進める

本人の回答は **学習・作品改善・就職活動を合わせて週10時間**です。自動化の成果を読む時間や面接準備もこの枠に含めます。
週次レビューに1時間、割込みの余白に20%の2時間を確保し、主行動は残りの枠内で最大3件にします。
次は初週の配分例です。実際の期限に合わせて配分を変え、使っていない枠を無理に埋めません。

| 用途 | 時間 | 今週の出口の例 |
| --- | --- | --- |
| 主行動1: 証拠対応表 | 3時間 | 求人要求、本人の実施範囲、未実施、根拠の所在を整理 |
| 主行動2: 公式求人の比較 | 1.5時間 | 求人原本で比較した候補と未確認事項 |
| 主行動3: 説明練習 | 1時間 | 3分説明1回と、答えられなかった質問 |
| 週次レビュー | 1時間 | 実績時間、結果、翌週の一手 |
| 割込みの余白 | 2時間 | 必要になった対応に使う。予定作業へ先に割り当てない |
| 未配分 | 1.5時間 | 初週は空けておき、作業数を増やすために使わない |

予定する活動は計6.5時間、余白2時間、未配分1.5時間です。実績時間は作業後に別途記録します。
面接がある週は作品の追加を減らします。予定外の対応が余白を超えるなら同じ週の作業を取り下げ、未完了を成功に数えません。
新しい学習課題は原則1件、詳細比較する求人は一度に3件程度から始めます。これは件数ノルマではありません。

## 1. 求人の事実と希望を分ける

求人原本のURL、確認日、募集識別子を非公開の台帳へ記録します。転記した条件には原文の場所を添えます。
同じ企業・同じ募集は既存行を更新し、媒体が違うだけで新規候補に数えません。
求人票で不明な条件を、企業の評判や職種名から補いません。

| 比較項目 | 記録する事実 | 自分が確認すること |
| --- | --- | --- |
| 初期担当 | OS設定、試験、手順更新など求人にある業務 | 構築へ関われる範囲と時期は説明されているか |
| 必須・歓迎要件 | 要件を分け、原文の参照箇所を残す | 必須を満たす根拠、不足、解釈が必要な点 |
| 製品・環境 | Linux系統、仮想化、クラウド等 | 本人の確認済み環境と違う部分 |
| 支援体制 | 研修、指導担当、レビューの記載 | 困った際の相談先と、単独作業への移行方法 |
| 働き方 | 勤務地、客先、勤務帯、当番等 | 通勤・生活と両立できるか。未記載は未確認 |
| 選考・期限 | 必要書類、連絡手段、募集・回答期限 | 提出前に本人確認できる時間があるか |

判定は `候補`、`確認待ち`、`応募準備`、`見送り` のいずれかとし、理由を一文添えます。
不明な必須要件は確認待ち、希望と合わない条件は見送り候補にします。採用される確率は算出しません。

## 2. 要求から証拠へつなぐ

| 求人の要求 | 対応する根拠 | 不足している場合の次の一手 |
| --- | --- | --- |
| Linux設定・構築 | 対象版、環境、実行者、手順、試験出力 | 小さな設定を本人の検証環境で再現する |
| 設計・試験書 | 要件と設計理由、期待値と結果の対応 | 既存構成の要件1件を試験に対応させる |
| 障害の切り分け | 症状、仮説、確認、対処、再確認の記録 | 許可したラボの障害1件を切り分ける |
| チームでの作業 | 実際の報告・相談・レビューの記録 | 架空場面の報告を練習し、演習と表示する |
| 引継ぎ | 操作、注意点、残事項、受領の記録 | 引継ぎ資料を作り、他者確認は確認待ちにする |

根拠ごとに「実装あり」「本人の実施記録あり」「本人が説明した」「他者が確認した」を別々に確認します。
CIの成功を本人の実施へ、ラボを実務経験へ、自己確認を第三者承認へ置き換えません。
未実施の試験は `NOT RUN`、不明な本人理解は `未確認` のままにします。
過去の証跡はその日・環境・版に限定して説明し、現在の再実施と区別します。

## 3. 応募用の下書きを作る

1. [既存の職務経歴書](../resume.md)と志望トラックを読み、求人要件に合う記録を最大3件選ぶ。
2. 主作品の目的、本人の担当、支援範囲、結果、未確認条件を短く書く。
3. 職歴・資格・期間・数値を原記録と照合する。空欄をもっともらしい経歴で補わない。
4. 応募先名、宛先、添付ファイル、共有URL、提出方法を本人確認用にまとめる。
5. 本人がその応募先・本文・添付・送信操作を承認した後に送信する。送信結果を確認してから応募済みにする。

AIは比較、下書き、矛盾検出を担当できます。応募、採用担当者への連絡、面接の日程確約、内定承諾は自動実行しません。
PR作成の承認や別企業への応募承認を、新しい応募先への送信承認として流用しません。

```text
応募準備票（初期状態: 下書き）
候補ID / 原本URL / 確認日: 未記入
この職務を希望する理由: 未記入
求人要件 → 自分の根拠: 未記入
本人の実施・AI支援・未実施の区別: 未確認
本文の版 / 添付の版 / 公開URL: 未記入
宛先 / 送信方法 / 回答期限: 未確認
本人の送信承認と対象範囲: 未取得
実際の送信日時 / 結果の確認先: 未送信
次回確認日 / 次の行動: 未記入
```

## 4. 面接を記録に戻す

作品説明の台本は [既存の30秒・3分練習](../portfolio-explanation.md)を使い、応募先の要件に関係する証拠1件を開けるようにします。
練習後は「答えた」だけでなく、目的・判断理由・根拠・限界のどこを説明できなかったかを本人が記録します。

| 問われたこと | 回答を作る順番 |
| --- | --- |
| なぜこの構成か | 要件 → 他の案 → 採用理由 → 制約 |
| 自分でどこまで実施したか | 操作記録 → 支援の範囲 → 未実施の条件 |
| 作業で詰まったとき | 実際の症状 → 確認 → 相談・対処 → 再確認 |
| 入社後に何を担当したいか | 求人の初期業務 → 根拠のある範囲 → 必要な支援 |

面接後に、実際の質問、回答の要旨、先方から明示された点、自分の改善仮説、次の期限を非公開で記録します。
不採用理由が伝えられていなければ `理由未確認` とします。「技術不足だった」などを事実扱いしません。
面接の相手による評価とAIの練習上の指摘を分け、AIの採点を採用可能性へ換算しません。

## 5. 条件を確認して本人が判断する

次は意思決定のための確認項目です。法的な適否や契約の有効性をこのシステムで判定しません。
求人票、面接説明、提示書面に違いがあれば、相違箇所と質問案を作り、本人の承認後に確認します。

| 確認項目 | 質問・記録の例 |
| --- | --- |
| 担当と配属 | 最初の仕事、構築と運用の割合、配属・勤務地変更の扱い |
| 指導と評価 | 相談担当、研修中の期待、独力で担当する前の確認方法 |
| 勤務 | 所定時間、休日、夜間・休日対応、当番、在宅・客先勤務の扱い |
| 報酬 | 基本給と手当の内訳、時間外分の扱い、支給条件、費用負担 |
| 契約と開始 | 雇用形態、期間・更新、試用期間の条件、開始日、回答期限 |

未確認事項、本人の許容条件、確認先と期限を並べ、承諾・追加確認・辞退を本人が決めます。
解釈が難しい事項は採用窓口や公的相談窓口などに本人が確認できるよう整理し、推測で埋めません。

## 6. 止まったときの分岐

| 状況 | 次の処置 |
| --- | --- |
| 求人の内容が古い・募集終了 | 原本を再確認し、終了なら候補を閉じる。古い条件で応募を進めない |
| 求人はあるが本人の根拠が不足 | 要求1件を選んで次週の再現枠へ入れ、他の学習を増やさない |
| 書類だけを直し続けて応募準備が進まない | 送信前の不足を事実・本人判断・文章修正に分け、最小の下書きを完成させる |
| 連絡がない | 先方の案内期限を確認し、問い合わせ案を作る。経過時間を送信承認としない |
| 同じ説明で繰り返し詰まる | 台本追加を止め、設定1箇所と操作1件に戻って本人が確認する |
| 週10時間を超えそう | 未着手項目を翌週へ移し、期限のある選考と既存の約束を先に配分する |

週次には、候補・準備・実送信・面接・結果を区別して数え、予定と実績時間、次の一手を残します。
母数が少ない結果を一般化せず、応募数を稼ぐために希望条件や事実確認を省きません。
入社が決まった後は [入社後の相談と担当拡張](onboarding.md)へ移り、職場側の計画とすり合わせます。
設計根拠と提案の区別は [一次資料](sources.md)を参照してください。
