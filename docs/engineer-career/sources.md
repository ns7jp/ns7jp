# 就職と定着の設計に使った一次資料

確認日: **2026-09-08**。以下の4件は公式URLを実際に開き、本文を確認しました。
公的資料に書かれた職務・能力・キャリア形成の説明と、本システムで選んだ運用方法を分けて記載します。
資料は職務理解と能力開発の参考です。特定企業の採用基準、本人の能力認定、採用確率を示すものではありません。

## 1. 厚生労働省 job tag: システムエンジニア（基盤システム）

[公式の職業詳細](https://shigoto.mhlw.go.jp/User/Occupation/Detail/318)

### 本文で確認した事実

- ITインフラの仕事として、要件定義、構成設計、構築、構築後の問題対応、引継ぎ、文書整理を説明している。
- タスク一覧には、基盤機能、データ移行、運用のテストが含まれる。
- 設計・構築、サーバー、ネットワークの知識とスキルに加え、顧客や他のエンジニアとの意思疎通を重視している。
- 就業後の学習として研修、OJT、設計書の相互レビューなどを説明している。

### 本システムでの提案

求人要件を技術名だけで対応付けず、要件、設計理由、構築手順、試験、引継ぎの証拠へ分解します。
本人が相談・報告した範囲も扱い、資料の多さだけを能力の高さへ換算しません。
適用先: [求人から証拠への対応](job-search.md)、[担当の拡張](onboarding.md)。

## 2. 厚生労働省 job tag: 運用・管理（IT）

[公式の職業詳細](https://shigoto.mhlw.go.jp/User/Occupation/Detail/319)

### 本文で確認した事実

- 定常業務として、リソース監視、ログの確認、データやシステムのバックアップを説明している。
- 障害時の保守担当への連絡と、早期復旧のための作業を非定常業務として説明している。
- 運用方法の検討、手順書の更新、情報共有、日報などを仕事内容に含めている。

### 本システムでの提案

入社後の確認に、異常の認識、事実の報告、許可された対応、結果の記録、手順の改善を含めます。
ラボでも障害対応と報告を組にし、復旧コマンドを実行しただけで業務遂行と評価しません。
適用先: [日々の相談と例外対応](onboarding.md)、[既存の案件運営](../server-projects/operations.md)。

## 3. IPA: ITスキル標準とは―ものさしとしてのスキル標準

[公式の解説](https://www.ipa.go.jp/jinzai/skill-standard/plus-it-ui/itss/itss2.html)

### 本文で確認した事実

- スキルを個別製品の知識だけでなく、業務課題を実現する実務能力として捉えている。
- 経験・実績による達成度指標と、スキル項目・知識項目を区別している。
- レベル2を上位者の指導下で要求された作業を担当する段階、レベル3を要求作業の独力遂行として説明している。
- コミュニケーションなどの能力と継続的なスキル研鑽にも言及している。

### 本システムでの提案

本人の説明、支援付きの実施、本人の再実施、他者の確認を分けて記録します。
この記録分類は独自の運用方法です。ITSSの正式な評価・認定や、本人がレベル2・3へ到達したという主張には使いません。
GitHubのコミット数、テスト数、AI生成物の量だけでは、実務能力や独力遂行を認定しません。
適用先: [応募で提示する根拠](job-search.md)、[担当範囲の合意](onboarding.md)。

## 4. 厚生労働省: ジョブ・カードを知る

[マイジョブ・カードの公式解説](https://www.job-card.mhlw.go.jp/guidance/know)

### 本文で確認した事実

- ジョブ・カードには、生涯を通じたキャリア計画と職業能力の証明を支援する役割がある。
- 学習歴、資格、職務経験、教育・訓練や職場での評価などを蓄積し、用途に応じて応募書類や相談資料へ活用する。
- 求職者と在職者の双方を対象に、強み・弱みの整理やキャリア形成に利用できると説明している。

### 本システムでの提案

本人の能力と活動の非公開台帳を原本にし、求人に合う事実だけを応募用の下書きへ取り出します。
学習歴と職務経験、自己確認と他者評価を別々に記録し、応募先や面接の記録を公開リポジトリへ置きません。
このシステムはジョブ・カードの公式様式やオンラインサービスそのものではありません。
適用先: [応募準備と結果の記録](job-search.md)、[入社後の面談メモ](onboarding.md)。

## 設計値と本人の回答を区別する

| 項目 | 根拠・扱い |
| --- | --- |
| サーバー構築職への就職・定着を最優先 | 本人の回答。公的資料から推定した希望ではない |
| 学習・作品改善・就職活動の合計が週10時間 | 本人の回答。入社後の業務外活動の義務ではない |
| 毎週月曜9時の確認 | このタスクで本人が指定した運用時刻。公的な推奨頻度ではない |
| 余白20%、週次レビュー1時間、主行動最大3件 | 初期運用の提案。主行動を残りの枠へ配分し、空きは無理に埋めない |
| 比較する求人3件、学習課題1件 | 初期運用の提案。実際の期限と負担で調整する |
| 30・60・90日の節目 | 既存の職場接続計画を使う提案。公的な習得期限ではない |
| 本人の説明・実施・他者確認の区別 | 証拠の混同を防ぐ設計。資格認定や採用判定ではない |
| 応募・連絡・条件承諾の前の本人確認 | 本人が内容と相手を確認して意思決定するための運用 |

これらの一次資料を根拠に、求人倍率、年収、転職成功率、就職までの日数を予測しません。
雇用条件の一覧は本人が確認するための質問項目です。法的な適否や権利についての個別判定を行うものではありません。

## 次回見直しの方法

月次などの見直し時に、参照URLの移転、本文の変更、職務説明と現在の候補求人の差を確認します。
確認日、変更箇所、設計への影響、修正対象を記録し、確認できない場合は古い確認日を保持します。
資料の変更だけで本人の能力記録や入社先の合意を更新せず、それぞれの原記録を再確認します。
