# 価値を確かめる小さな実験

[入口](README.md) / [設計](design.md) / [運用](operation.md) / [指標](metrics.md) / [記録票](templates.md) / [導入計画](roadmap.md) / [CLI](../../tools/prosperity/README.md)

## 1. 誰の困り事かを先に決める

価値検証は、作った仕組みを誰がどう使い、何が変わったかを確かめることです。
最初の利用者は本人で構いません。「資料が多く、次に何をすればよいか決めにくい」を、今回のreportがどこまで軽くできるかを測れます。
就職先や第三者に役立つかは別の問いです。本人だけの試行から相手の評価や採用効果を推測しません。

P系は今回の運用・導線の価値を観察する候補です。INV系は既存のサーバー技術比較です。
復旧時間、復元の不足検出、監視の品質などを測る場合は、[既存の改善実験](../server-innovation/experiments.md)へ登録します。
P系とINV系に同じ比較計画・結果・採否を二重登録せず、必要な原記録への参照を残します。

## 2. 同時進行は共通で最大一件

既存ループのレビュー待ち、緊急の改善、進行中INVがあれば、その一件を優先します。
P系の候補を用意しておくことはできますが、別枠として実施を開始しません。
P系を進めるときも既存careerの行動IDと時間内に収め、本人が一件を採用してから実施します。

候補、採用、実施、観測結果、採否は別です。
CLIが候補を表示した時点では、本人の採用日や実績を作りません。測定値が有望でも、自動的に次の実験や時間配分を採用しません。
採否待ちは、選択肢と結果を揃えた一つの判断へまとめます。

## 3. P-001：次の一手を決める負担を比べる

これは開始前の実験案です。個人の初期値・目標値・実測値は未記入で始めます。
CLIの初期雛形と意味が異なる場合は、本人が採用する前に対象と指標を一致させます。

| 項目 | 登録前に決める内容 |
| --- | --- |
| 困り事 | 複数の台帳や出力から、実行可能な一件を選ぶのに迷う |
| 対象者 | 本人。第三者の利用実験へ自動拡大しない |
| 旧方法A | 既存loopとcareerの出力を本人が順に読む |
| 新方法B | 同じ元情報に対するprosperityのreportを使う |
| 主指標 | 読み始めてから、理由・対象・終了条件付きの一件を決めるまでの実時間 |
| 品質条件 | 期限・UNKNOWN・上流の占有・週上限を見落とさない。実施済みと未実施を区別する |
| 補助観察 | 開いた資料数、迷った点、追加確認、負荷、記録のためにかかった時間 |
| 時間枠 | 本来の行動目的に合う既存career枠の内訳。準備と採録も含む |
| 中止条件 | 正本が読めない、比較条件が変わる、予定枠を超えるおそれ、判断を誤る |
| 戻し方 | 既存loop/careerの出力を使い、今回の結果と気づきを保存する |

同じ課題を二度読めば二回目が速くなる可能性があります。
比較の順をAB、BAのように入れ替え、同程度の難しさの課題を用意して、実施者・端末・情報量・支援量を記録します。
課題が完全には同じでないことや、本人がreportの狙いを知っていることは残る限界です。

初期の小さな観察は、全試行を記録し、続けて測る価値があるか判断するために使います。
固定の成功数や短縮率を達成するまでやり直す運用にはしません。何回測るか、どの条件で打ち切るか、悪化をどう扱うかを開始前に決めます。
厳密な複数試行の技術判定が必要なら、既存INVの登録・全試行検証の仕組みを使います。

## 4. 実施の順番

1. **現状を書く。** 困っている場面を一つ選び、実際の例と原本を示す。推測しかない場合は先に観察する。
2. **比較を決める。** AとB、主指標、品質条件、同じにする条件、全試行数、停止条件を登録前に決める。
3. **基準を測る。** 旧方法の実測を記録する。合成データの例を本人のbaselineへ入れない。
4. **一つだけ変える。** 新方法を使い、同じ区間を測る。途中で条件を変えたら、その試行の変更と理由を残す。
5. **全体を見る。** 良い結果、悪化、欠測、中断、追加負担を揃え、[指標](metrics.md)の定義で比較する。
6. **本人が判断する。** 続ける、条件を変える、保留する、終了する理由を残す。技術実験なら採否はINV正本へ戻す。
7. **別の機会に確認する。** 採用した方法を次回使った結果を記録し、続かなければ戻す。初回だけの成功で恒久化しない。

## 5. 判断の例

次の数値は説明用の合成例です。本人の成果ではありません。

| 観測例 | 判断材料 | 次の行動 |
| --- | --- | --- |
| 判断が12分から9分、品質条件は満たした | 条件を限定すれば有望。慣れと追加記録の影響は未解消 | 別の同程度の課題で再確認する |
| 6分で決まったが、上流のレビュー待ちを見落とした | 速さより品質条件違反が重要 | 表示・規則を直し、元の方法へ戻す |
| 変化はないが、UNKNOWNの見落としが減った | 主指標は改善せず、別の価値の仮説が出た | 元の結果を保持し、新しい仮説として検討する |
| 旧方法の時間が未記録 | 改善率を計算できない | 新方法の値を残し、次の比較条件を決める |
| 時間は短いが、運用記録の負担が大きい | 効果と維持負担の両方を見る必要がある | 記録欄を減らすか、今回の運用を保留する |

主指標が改善しなかった後に、都合のよい別指標を元の成功条件へ差し替えません。
新しい気づきは次の仮説として保存できます。棄却や保留も、次に使わない方法が分かる正常な結果です。

## 6. 仕事上の価値へつなぐ

本人の運用が安定したら、成果が使われる場面で価値を確認します。
候補例は、実際の説明練習で相手が主張範囲を理解できたか、手順を受領者が追えたか、合意した作業の手戻りが減ったかです。
相手の協力が必要な観察は、本人が実際の依頼と同意の範囲を決めます。質問案を作っただけで依頼済みにはしません。

相手を試験のために困らせず、必要なら支援し、支援した範囲を結果へ残します。
職場の観察は組織の正本と許可された場所で行い、個人側には持ち出せる範囲の抽象的な学びだけを残します。
応募や入社の変化には、募集状況、経験、相手の判断など複数の要因があるため、このシステムだけの効果とは結論付けません。

## 7. 改善の成果を使い回す

採用した方法から、本人が説明できる短い説明、再利用できる手順、対象と限界が分かる実記録を作れます。
一つの実測をREADME・面談説明・詳細手順へ展開するときも、同じ原本と実施範囲を使います。
この再利用が本当に時間を減らしたかは、次の実利用で確認します。
公開・対人送信・実機への適用は[役割と権限](design.md)に従い、今回の実験採用と別の行為として扱います。
