# 日・週・月・四半期の運用

[入口](README.md) / [設計](design.md) / [指標](metrics.md) / [実験](experiments.md) / [記録票](templates.md) / [導入計画](roadmap.md) / [CLI](../../tools/prosperity/README.md)

## 1. 運用を一つにする

既存の `github-ns7jp` 自動化を入口として扱います。今回確認した登録は09:30・ACTIVEで、新しい繁栄CLIの定期接続・発火は未実施です。
この文書の手順を追加の定期タスクとして重複登録しません。ローカルファイルを使う定期処理は、端末とアプリの稼働等の実行条件と実際の履歴を確認します。
定期接続前でも、既存ループの実行結果を用意し、繁栄CLIを手動で実行できます。

機械の実行頻度と本人の活動頻度は別です。日次に監査が動いても、本人に毎日10時間の予定や新しい実験を配りません。
本人のまとまった計画変更は週次、一巡の効果確認は月次、目的と選択肢の見直しは四半期を初期の目安にします。

## 2. 日次：次の一手を進める

本人の確認は作業開始前と終了前に短く行い、その時間も実時間へ含めます。
日次の独立した日報を必須にせず、既存の行動記録や案件の正本へ次の項目を残せば十分です。

| タイミング | 確認・実施 | 終了条件 |
| --- | --- | --- |
| 作業前 | 今日の約束、使える時間、実施中の一件、停止条件を読む | 一つの対象と終了条件が言える |
| 準備 | 手順、期待値、戻し方、必要な権限を確かめる | この時間内で進める小作業が決まる |
| 実施 | 予想を記録し、操作・観測・説明を行う | 実際の出力と未完が残る |
| 作業後 | 実時間、困った点、支援量、次の一手を原本へ残す | 完了・続行・保留が区別される |

例えば「nginxを勉強する」では終了条件が曖昧です。
「既存の演習環境でHTTP応答を確認し、期待と実出力の差を一つ説明する」まで絞り、SEの対象条件と実施カードへつなぎます。
接続できなければ、接続に失敗した事実とどこまで確認できたかを残します。HTTP成功や学習完了にはしません。

Codexは、最新資料と差分を確認し、既に許可されたローカル改善を検証まで進めます。
本人の入力が必要な部分を待つ間も、その入力に依存しない下書きや参照検査は進められます。
同じ出力で意味のある変化がなければ通知せず終了します。

## 3. 週次：時間内に一件を通す

通常は既存careerのレビュー60分を使います。この文書のために別の60分を足しません。
レビューの配分例は、約束と負荷10分、原本と変化15分、次の一手20分、記録と翌週の配分15分です。

1. **条件を読む。** 本人が確認した目的、上限、負荷モード、既約束、期限を確認する。古い確認は更新候補として扱う。
2. **上流を動かす。** [既存ループ](../portfolio-loop/operation.md)の点検・収集・計画・取り込みを実行し、latestだけでなく参照先のrunも照合する。
3. **繁栄のreviewを行う。** [CLI](../../tools/prosperity/README.md)で次の一手、欠測、負荷、実験の状態を読む。終了コードだけで結果を判断しない。
4. **優先事項を先に処理する。** 壊れた状態、未取得、期限、過負荷、レビュー待ち等があれば、その解消に必要な一件へ絞る。
5. **共通枠を照合する。** 既存の進行中INVや未完の改善があれば、それを進める。新しいP実験を別枠で始めない。
6. **実施を準備する。** 対象、目的、期待結果、実施者、支援、証拠、停止条件、所要時間を一枚にする。
7. **結果を正本へ戻す。** 本人の実践はSE・career・PJの対応先へ、サーバー技術実験はINVへ、運用価値の観察はP系へ記録する。
8. **必要な変化だけ伝える。** 進んだこと、残る制約、次に必要な一つの行動と記録先を短く示す。

全主行動が終わらなかった場合は、未完、理由、残見積、元の期限、超過期間を残して翌週へ移す判断をします。
期限を先に書き換えて遅延を消さず、元の約束と新しく合意した期限を区別します。
空き時間を埋めるために主行動を追加する必要はありません。

## 4. 月次：役立ったか、負担は見合うか

4週前後を目安に、[指標](metrics.md)と[月次記録票](templates.md)を使って一巡を振り返ります。
月次レビューもその週の既存レビュー枠で実施します。時間が足りなければ比較対象を一件に絞ります。

| 順番 | 確かめる問い | 決めること |
| --- | --- | --- |
| 1 | 今月、誰のどんな困り事が実際に減ったか | 根拠がある成果と未確認を分ける |
| 2 | 技術・説明・利用・就職活動のどこで止まったか | 現在の最重要の不足一つ |
| 3 | 予定よりかかった時間と維持費は何か | 減らす作業、残す余白 |
| 4 | 同じ改善は別の機会にも役立ったか | 継続、条件変更、保留、終了 |
| 5 | 次の時間をどこへ向けるか | 既存profile内の次期間の配分 |

例えば説明資料の探索が毎回短くなっても、更新に同じ時間がかかれば、そのまま純削減とは言えません。
探索・記録・保守を含めて比較し、余白が確認できれば休息、同じ問題の再発防止、次の要求への準備の順で検討します。
作品数や投稿数の増加だけを根拠に、就職活動や休息の時間を削りません。

## 5. 四半期：目標と選択肢を見直す

本人が採用した日から約90日ごとに、当初の目標、現状の条件、得られた事実、変わった希望を照合します。
就職前なら公式求人と実際の反応、就職後なら合意した担当と職場のフィードバックを使います。
現在の段階が未確認なら、[導入計画](roadmap.md)の該当段階を推測で進めません。

継続する主テーマは原則一つです。次の期間に広げる技術は、求人・職場・受け手の不足から既存SE/BXの課題へ結び付けます。
新しいツール導入は「どの困り事を減らすか」「今の道具で解決できないか」「導入と保守が時間内か」で比較します。
成果の薄い定型作業や使われない記録は、正本と履歴を残して新規作成を減らします。

## 6. 止める・縮小する

| 条件 | 直ちにすること | 続けられること |
| --- | --- | --- |
| 本人が休止を選んだ | 既存careerをpausedにし、新規割当を0にする | 期限のある約束と必要な確認を表示する |
| 時間超過や負担が続く | reducedを検討し、行動数と予定量を減らす | 必要な確認品質を保った小作業 |
| 元データが壊れている | 依存する評価を停止し、原本と履歴を保全する | 破損に依存しない文書確認 |
| 取得失敗・古い観測 | 新しい確認日時を付けず、失敗理由を記録する | 独立したローカル準備 |
| 実施中の一件がある | 新規実験の採用を保留する | 現在の一件の完了・見直し |
| 対象や権限が不明 | その操作を開始せず、必要条件を絞る | 実施計画、確認項目、下書き |
| 実際の障害や利用者影響 | 対象環境の既存の障害手順に従う | 許可された事実の採録と報告準備 |

reducedは上限を半分にする既存の運用です。試験項目や安全な実施条件を半分にする意味ではありません。
負担の記録は本人の自己申告で、診断や働ける量の判定に使いません。気持ちが残っていても進められる小作業を選び、一つ決めたら計画画面を閉じます。

## 7. 障害から再開する

まずエラーの元メッセージ、実行時刻、対象パス、最新の正常な履歴、途中で保存された出力を記録します。
CLIの分類と処置は[実装仕様](../../tools/prosperity/README.md)に従います。
次の表は運用上の切り分けで、自動修復されたという意味ではありません。

| 症状 | 確認するもの | 再開条件 |
| --- | --- | --- |
| ロックが残る | PID、該当処理の稼働、保存途中か | 終了した当該処理のロックだと確認できる |
| JSONを読めない | 元ファイルと変更差分、正常履歴 | 原本を保全して形式と内容を直せる |
| 証拠のhashが違う | 証拠原本、添付コピー、変更理由 | 一致する原本の復元、または訂正理由付きの別記録 |
| 時間上限が違う | 本人が最後に確認したprofileとledger | 正本の最新条件へ一致し、検査が通る |
| 上流が古い | latestの参照先、収集結果、実際の日時 | 新しい観測が成功し、対応する出力を取得できる |
| 通知が多い | 意味の差分、単なる時刻変化、重複登録 | 通知条件と既存の一つの登録を確認する |

ロックを一括削除したり、台帳を再初期化して失敗を消したりしません。
停止中の実験は元の期限と超過を残し、環境・版・計画が変わったなら比較の継続可否を判断します。
定期運用の再開は現在の登録、正本、未完の一件、時間枠を読み直し、まず一回の実行記録を確認します。

## 8. 完了の見方

日次は次に戻れる実記録、週次は時間内の一件と残件、月次は継続・見直しの判断、四半期は次の主テーマと条件が残れば運用上の一区切りです。
採用、内定、独力担当、受領、実機成功は、それぞれ当事者の実際の記録で確認します。
この運用が動いた証拠と本人の成果は、[検証記録](validation.md)に分けて残します。
