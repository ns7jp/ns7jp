# やさしい用語・見方ガイド

このページは、サーバーを初めて学ぶ人が本ポートフォリオを読むための入口です。用語を丸暗記せず、**役割と確認方法をセット**で覚えます。

読むだけで終わらせず、次に **[初心者向けスタートガイド](./learning-plan/00-start-here.md)** へ進んでください。そこでは、始める前に自分の PC・知識・使える時間が足りるかを確かめる「開始前診断」と、実際に手を動かす「最初の 30 分」を行います。PC のメモリや空き容量が少ない場合の軽い進め方や、「何ができれば合格か」の判断例も載せています。

## まず覚える 1 本の流れ

サーバー構築の仕事は、次の 6 語で整理できます。

> **設計 → 構築 → 試験 → 監視 → 復旧 → 記録**

| 工程 | やること | 身近なたとえ |
| --- | --- | --- |
| 設計 | 何を、どこに、どの設定で作るか決める | 家の設計図を作る |
| 構築 | OS、ソフト、ネットワークを設定する | 設計図どおりに建てる |
| 試験 | 想定どおり動くか確かめる | 水や電気が使えるか確認する |
| 監視 | 異常の兆候を継続して見る | 火災報知器を付ける |
| 復旧 | 壊れた状態から戻す | 故障箇所を直す |
| 記録 | 誰でも再現できるように残す | 点検記録を書く |

> **一言でいうと**：サーバーの仕事は「作って終わり」ではなく、作った後に**壊れていないことを確かめ続け、壊れたら戻し、やったことを残す**までが 1 セットです。

## 技術を「役割」で覚える

| 用語 | 役割 | このポートフォリオでの使い方 |
| --- | --- | --- |
| Linux | サーバーを動かす OS | Ubuntu 24.04 を使用 |
| Nginx | 通信の入口 | リクエストを Web アプリへ渡す |
| Flask / Gunicorn | Web アプリ本体（Flask がアプリ、Gunicorn がその Flask を動かす土台） | 監視される側のアプリとして応答を返す |
| Docker | アプリを箱に分けて動かす | 同じ構成を再現しやすくする |
| Ansible | 設定を自動化する | 手作業を playbook（設定手順を書いたファイル）に置き換える |
| Prometheus | 数値を集める | CPU やサービス状態を記録する |
| Grafana | 数値を見える化する | ダッシュボードに表示する |
| Loki / Alloy | ログを集めて運ぶ | 原因調査に使うログを集約する |
| Alertmanager | 異常を通知する | 条件を満たした警告を送る |
| Terraform | クラウドの構成を設定ファイル（コード）に書き、その通りに作らせる | AWS 構成のコードを書いて管理する。ただし `apply`（コードどおりに実際の AWS 上へ作る操作）は未実施 |
| 冪等性（べきとうせい） | 同じ操作を何度実行しても結果が変わらない性質 | 同じ手順書を3回実行しても状態が変わらない |
| OSI 参照モデルの L1 から L7 | ネットワーク通信を 7 つの階層（ケーブルなどの物理層からアプリケーション層まで）に分けた考え方 | 障害の切り分け（不具合の原因がある場所を絞り込む作業）で、「どの層まで通信が届いているか」を確認する |
| 証跡（しょうせき） | 「本当にやった」と後から他人が確認できる記録（コマンドの出力、画面の写し、ログ） | 演習ごとに出力を保存し、実測済みか未実施かを区別する根拠にする |

> **一言でいうと**：製品名を 1 つずつ覚えるのではなく、**「入口・本体・計測・表示・通知」** の 5 つの役割で覚えます。Nginx が入口で受け、Flask / Gunicorn が応答を返し、Prometheus と Loki / Alloy が数値とログを集め、Grafana が見せ、Alertmanager が知らせます。

## コマンドは「目的」で覚える

すべてのオプションを暗記する必要はありません。まず「困りごと → 打つコマンド → 何が見えたら正常か」の 3 点セットで覚え、細かいオプションは必要になったときに `--help` や公式文書で調べます。

| 知りたいこと | 最初に使うコマンド | どう判断するか |
| --- | --- | --- |
| サービスは動いているか | `systemctl status <名前>` | `active (running)` なら動いている。`failed` / `inactive` は止まっている |
| なぜ失敗したか | `journalctl -u <名前>` | 時系列で **最初に出たエラー行** と、その直前の行を読む。後から出るエラーは巻き添えのことが多い |
| ポートを待ち受けているか（外からの接続を受け付ける口が開いているか） | `ss -lntp` | 目的のポート番号が `LISTEN` の行にあれば待ち受けている。行が無ければ誰も待ち受けていない |
| 名前解決できるか（ドメイン名から IP アドレスを引けるか） | `dig <名前>` | `ANSWER SECTION` に IP アドレスが出れば引けている。`status: NXDOMAIN` はその名前が見つからない |
| HTTP が返るか | `curl -v <URL>` | `HTTP/1.1 200 OK` など 200 番台なら応答している。`Connection refused` は相手が待ち受けていない |
| ディスクに空きがあるか | `df -h` | `Use%` に余裕があれば大丈夫。`100%` は空きが無く、書き込み失敗の原因になる |
| コンテナは動いているか | `docker compose ps` | Status が `Up` なら動いている。`Exited` / `Restarting` は止まっている、または再起動を繰り返している |
| ログを確認したい | `docker compose logs <名前>` | 起動直後のログの先頭から読み、最初に出たエラー行を探す |

## 障害対応の 4 ステップ

覚え方は **「見る・絞る・変える・確かめる」** です。上のコマンド表は、この 4 ステップの中で使います。

1. **見る**：エラーの全文、発生した時刻、対象（ホスト名やサービス名）、直前に自分が変えたことをメモに書き写す
2. **絞る**：利用者の手元 → ネットワーク → 入口（Nginx） → アプリ（Flask / Gunicorn） → DB（データの保管場所）の順に、どこまで正常かを 1 つずつ確認する。`dig`（名前を引けるか）、`curl -v`（HTTP が返るか）、`systemctl status`（サービスが動いているか）、`docker compose ps`（コンテナが動いているか）と上から順に試すと、壊れている区間が 1 か所に絞れる
3. **変える**：候補が複数あっても、変えるのは一度に 1 つだけにする。2 つ同時に変えると、どちらが効いたのか説明できなくなる
4. **確かめる**：手順 2 で使ったコマンドをもう一度実行し、表示が異常から正常（`active`、状態コード 200 など）へ変わったことを記録する

いきなり再起動すると、原因の手がかり（プロセスの状態や、まだ保存されていないログ）が消えてしまうことがあります。まず状態とログを保存してから、再起動などの操作を行います。

## 安全に練習するための約束

- 本番環境ではなく、削除できる VM やコンテナで練習する
- 変更前にスナップショットまたはバックアップを取る
- コマンドの対象ホスト、ファイル、ユーザーを声に出して確認する
- 削除・Firewall・権限変更は、戻し方を決めてから実行する
- パスワード、トークン、メールアドレスなどの秘密情報を証跡に残さない
- クラウドは予算アラートを設定し、終了後にリソースを削除する

## 1 つの演習で残す 5 点

```text
目的:
実行したこと:
期待する結果:
実際の結果:
失敗時の戻し方:
```

慣れるまでは、次の記入例のように埋めます（内容は書き方の見本で、実測の記録ではありません）。

```text
目的: Nginx の設定を変更したあとも、Web の入口が動いているか確認する
実行したこと: /etc/nginx/nginx.conf を編集し、sudo nginx -t と sudo systemctl reload nginx を実行した
期待する結果: nginx -t が syntax is ok を表示し、systemctl status nginx が active (running) を表示する
実際の結果: syntax is ok と表示され、status も active (running) だった
失敗時の戻し方: 編集前に控えた nginx.conf を戻し、sudo systemctl reload nginx を実行する（実行前に決めておく）
```

「コマンドを打てた」ではなく、**何を見て成功と判断したか**まで説明できれば、知識が実務で使える形になります。
