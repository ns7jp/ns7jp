# 練習と本人用の記録票

## 15分で仕組みを理解する

この練習はコードの判断を理解するためのものです。本人のサーバー技能の実測にはしません。

1. 目的を一文にする。「作業を増やす前に、役立った成果と続けられる負荷を確認する」。
2. `node --test tools/autonomous-prosperity/tests/*.test.mjs` で判断規則のテストを実行する。
3. [状態表](design.md)を見て、古い観測、負荷の縮小、成果の悪化がどう扱われるか予想する。
4. `node tools/autonomous-prosperity/prosperity.mjs status --json` で今ある台帳を読み取る。本人台帳なしなら `CONNECT_PROFILE` が期待値。
5. 「なぜNOT RUNを0に置き換えないか」「なぜ2回の改善だけで別環境へ拡大しないか」を自分の言葉で説明する。

正しく動いた確認は、このCLIのテスト結果と状態出力です。サーバーの復旧や本人の就職結果は、この練習ではNOT RUNです。

## 比較の例

以下は説明用の架空の値です。本人の索引へ転記しません。

| 比較 | 結果の例 | 判断 |
| --- | --- | --- |
| 同じ環境・方法で別日に100秒から70秒、110秒から75秒。最小幅10秒 | 2日とも改善、品質条件も満たす | CONSIDER_REUSE。本人が同条件での再利用を検討 |
| 速くなったがデータが失われた | 品質条件不成立 | REVIEW_HARM。速度だけを成果にしない |
| 1回だけ改善した | 再現の確認不足 | MEASURE_AGAIN。別日に確認 |
| VMとCIの測定を1回ずつ混ぜた | 環境が異なる | 別グループとして扱い、2回の改善にしない |
| 元の数値が未実測 | 比較できない | 索引へ架空の値を入れず、原本にNOT RUN |

## 本人の結果を残す記録票

既存の `.local/engineer-career/records/` に、自分が実施した範囲だけを保存します。

```text
日付と既存行動ID:
誰のどんな困りごとを減らすか:
今回の完了条件:
対象版・環境・比較条件:
実施前の予想:
実際にした操作:
観測結果・比較前後の値・単位:
事前に決めた最小改善幅:
速度以外に守る品質条件と結果:
本人が説明できたこと:
未実施（NOT RUN）・助言が必要だった範囲:
実際に要した時間と負荷:
次回は続ける・方法を変える・保留のどれか、その理由:
次の確認日:
```

記録がない欄をAIの想定で埋めません。詰まったことも、次に方法を選ぶための材料です。
企業や職場の記録は所属先の規則に従い、この個人リポジトリへ持ち込む必要はありません。

## 月次の問い

- 誰かが実際に使えたか。相手の反応を直接確認したか。
- 別の日でも自分で再現し、理由を説明できたか。
- 速さの代わりに失った品質や、増えた維持作業はないか。
- 今の目標に結びつくか。次の週に入れるなら何と入れ替えるか。
- 保留するなら、何が分かったら再開するか。

答えを確認してから既存キャリアや採否台帳を本人が更新します。システムは提案と完了条件をつなぎます。
