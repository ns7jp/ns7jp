# PJ06 初期保守・運用移管

[案件の入口](../README.md) / [前工程 PJ05](05-acceptance.md) / [次工程 PJ07](07-closure.md)

初期保守では、引き渡したサービスの状態、問い合わせ、障害、変更、残課題を合意した期間で追います。そのうえで、運用担当が自分の権限と手順で対応できることを確認して移管します。

DEMO-A「研修用監視VM1台の構築・引渡し」を架空の例にします。日数、時刻、件数の記入例から実績を作りません。監視データや問い合わせ記録を取得していない期間は「欠測」「未確認」のまま残します。

## 1. 保守の境界を最初に確認する

| 項目 | 決めること | 未確認のまま進めると起きる問題 |
| --- | --- | --- |
| 開始・終了 | 日時、タイムゾーン、起点となる確認 | いつから誰の担当か分からない |
| 対応時間 | 営業時間、休日、時間外の窓口 | 24時間対応を勝手に約束する |
| 対象 | ホスト、アプリ、監視、データ、運用作業 | 対象外の作業を引き受ける |
| 除外 | 利用者操作、他社製品、追加開発等の扱い | 不具合と追加要望が混ざる |
| 受付 | 問い合わせ先、記録場所、初動と報告の目標 | 個人のDMだけに障害が残る |
| 変更 | 誰が提案し、誰が承認するか | 保守名目で未承認変更をする |
| 終了 | 必要な観測、未解決事項、移管先の確認 | 期限だけで未完了を切り捨てる |

PJ05の保守開始条件とこの表を照合します。合意した条件がなければ案件責任者と運用受領者へ確認し、空欄を都合のよい既定値で埋めません。既存の監視アラート目標も、そのまま契約上の応答保証にはなりません。

## 2. 役割と記録の準備

案件主担当は初期保守の実施と課題管理をまとめ、運用受領者`operations`は点検・受付・運用範囲・移管結果を確認します。障害の復旧判断、変更の承認、費用や期間の変更には、それぞれ合意した責任者を使います。

[保守台帳テンプレート](../templates/support-register.md)を非公開の案件記録先に作ります。点検、問い合わせ、障害、変更、残課題の記録を関連IDで結び、正本の所在を統一します。実際の顧客情報やログを公開Issueへ転記しません。

DEMO-Aでは、[日次点検スクリプト](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/scripts/ops/daily-check.sh)と[ランブック索引](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/runbooks/README.md)を参考にできます。既存スクリプトがSKIPした項目は、本案件で確認済みだったことにはしません。

## 3. PJ06-C1 合意した期間の監視・問い合わせと欠測を記録

**目的：** 見た範囲と見ていない範囲を区別し、状態と問い合わせの推移を追います。

### 実行前確認

1. 対象hostname・VM識別・配置SHA・設定版をPJ05の引き渡し記録と照合する。
2. 観測開始と終了予定、日次点検の予定時刻、許容ずれ、担当、休日の扱いを決める。
3. 点検項目、採録元、しきい値、データ保持期間、欠測判定、連絡条件を確認する。
4. 問い合わせの窓口と受付記録を確認する。個人宛の連絡を受けた場合に正本へ集約する方法も決める。
5. 自動採録を使う場合は対象・実行権限・保存先を確認し、初回の結果を手動点検と照合する。台帳CLIは実機を監視したり自動で外部通知したりしない。

### 日次の順序

1. 現在時刻、対象、稼働版、前回確認からの変更を記録する。
2. 利用者の応答、対象サービス、監視の最終サンプル、容量、直近エラー、バックアップ最終成功を確認する。
3. 通知先や監視収集自体が動いているか確認する。通知がないことだけで正常と判定しない。
4. 合意した受付先を調べ、問い合わせの新規件数・未処理・期限接近を記録する。受付先を確認できなければ件数を未確認にする。
5. 異常や懸念があればPJ06-C2の台帳へ関連付け、担当と次の確認を付ける。
6. 点検結果、実施日時、証跡先、前回との差分を保存する。変更した目標・対象・期間があれば旧条件も保存する。

| 点検項目 | 確認内容 | 未確認時の記録 |
| --- | --- | --- |
| 利用者経路 | 指定した入口の応答と内容 | 応答未測定、理由、再確認予定 |
| 監視 | 最終データ時刻、対象、発火と解消 | 監視欠測、確認できない期間 |
| 容量・ログ | 実値と増加傾向、エラーの変化 | 採録できた項目とできない項目 |
| バックアップ | 最終成功、対象、鮮度、次回予定 | ジョブ未確認または失敗 |
| 問い合わせ | 正式受付先の新規・未処理・期限 | 受付先未確認。0件と書かない |

### 7日間を選んだ場合の架空の計画例

| 観測点 | 予定の意味 | 実施時刻 | 結果 | 証跡 |
| --- | --- | --- | --- | --- |
| 開始点 | 引き渡し状態との照合 | NOT RUN | NOT RUN | NOT SET |
| D1 | 合意した日次点検 | NOT RUN | NOT RUN | NOT SET |
| D2 | 日次と問い合わせ確認 | NOT RUN | NOT RUN | NOT SET |
| D3 | 日次と傾向確認 | NOT RUN | NOT RUN | NOT SET |
| D4 | 日次と残課題期限確認 | NOT RUN | NOT RUN | NOT SET |
| D5 | 日次と移管準備 | NOT RUN | NOT RUN | NOT SET |
| D6 | 日次と運用担当の実操作 | NOT RUN | NOT RUN | NOT SET |
| D7 / 終了点 | 合意した終了条件の確認 | NOT RUN | NOT RUN | NOT SET |

7回の採録と7×24時間の観測は別です。契約や計画で期間を定義した開始・終了時刻と、実経過時間を記録します。必要な期間が14日ならその期間を観測し、教材の7日例へ縮めません。

### 欠測を見つけたとき

予定日時、気付いた日時、理由、確認不能な期間、影響、補足できる既存記録、次の確認を残します。後日の正常性を過去へさかのぼって当てはめません。再採録や期間延長が必要なら元の終了予定・新しい予定・遅延・理由を残し、責任者に確認します。

**期待結果：** 合意期間の観測と問い合わせ確認に証拠があり、欠測はそのまま識別できます。必要な観測が不足した状態を「期間経過」で完了にしません。

**中止・戻り先：** 対象版不一致、監視停止、秘密情報を含む採録、不明なアクセスを見つけたら点検結果を残して担当経路へ連絡します。運用継続の判断と追加変更の承認を分けます。

**提出物：** 日次記録、問い合わせの確認範囲、欠測履歴、期間変更の根拠、観測まとめ。

## 4. PJ06-C2 障害・変更・残課題を責任者と期限へ割り当て

**目的：** 見つけた問題を、次に誰が何を判断するかまでつなげます。

1. 受付時刻、発生時刻または不明、申告者、症状、対象、利用者影響、証跡を記録する。
2. 障害、問合せ、既知の残課題、変更提案に分ける。原因や契約上の責任が不明なら、断定せず調査中とする。
3. 合意した影響・緊急度で優先度を付ける。初動担当、判断責任者、次回報告時刻、期限を明示する。
4. 直近変更、実ログ、利用者の再現条件から調査する。仮説、確認、結果を時系列で残す。
5. 復旧操作は権限と承認の範囲に従う。設定変更が必要なら[変更・障害対応](../change-incident.md)へ関連付け、保守担当だから自由に変更できると解釈しない。
6. 復旧後は利用者操作と監視収束を確認し、暫定復旧と原因対処完了を別に記録する。
7. 再発防止と残課題には、担当、期限、受入条件、依存、必要な支援を付ける。単に「注意する」で終わらせない。
8. 初期保守期間を越えるものは、移管先が内容と期限を実際に受領した記録を得る。未受領なら未移管のまま責任者へ戻す。

| 種類 | DEMO-Aでの架空の申告例 | 担当へ渡す判断材料 |
| --- | --- | --- |
| 障害 | 指定した監視画面を開けない | 発生範囲、直近変更、入口・依存先・ログ |
| 問合せ | バックアップ日時の確認場所が分からない | 手順の該当箇所、権限、教育の不足 |
| 残課題 | 合意した資料補足が未完了 | 元の合意、影響、担当、期限、受領条件 |
| 変更提案 | 監視対象VMをもう1台追加したい | 元の対象外、工数・費用・試験・運用への影響 |

**期待結果：** 未解決の項目に責任者と次の期限があり、問い合わせの解決、障害復旧、恒久対処、変更の採否を区別できます。

**中止・戻し：** データ保全や復旧時間が不確か、対象外へ影響、権限不足の場合は操作を止めて支援を要請します。同じ障害が再発したら毎回の発生を残し、前回を消さず関連付けます。

**提出物：** 受付・課題台帳、障害時系列、変更の採否と承認経路、復旧確認、期限超過と再予定、移管先の受領記録。

## 5. PJ06-C3 運用担当の実操作と対応範囲・終了条件を確認

**目的：** 初期保守が終わった後も、運用担当が自分で確認と一次対応を行える状態にします。

1. 運用移管の対象版、文書版、残課題、アクセス一覧をPJ05以後の変更で更新する。
2. 運用担当が自分のアカウントで対象を確認し、日次点検、ログ確認、バックアップの確認を実際に行う。
3. 対応範囲に含む操作を一つ実施する。研修用の別復元先での復元結果確認など、影響と戻し方が確定した操作を選ぶ。本番障害の注入は移管のために勝手に追加しない。
4. 運用担当が、どの症状を自分で調べ、どの条件で止め、誰に引き継ぐかを説明する。
5. 手順の欠陥、権限不足、担当範囲の空白があれば直し、修正後の操作を記録する。資料を送っただけで移管済みにしない。
6. 合意期間の必須観測、未達、欠測の扱い、問い合わせ、未解決事項の受領を確認する。
7. 運用受領者が移管可否、開始日時、対応範囲、残条件、窓口を記録する。初期保守の終了判断は、合意した責任者が行う。
8. 不要となる一時権限の終了計画をPJ07へ渡す。運用担当のアクセスが機能する前に既存の復旧経路を削除しない。

**期待結果：** 運用担当の実操作と範囲の確認があり、初期保守を終える条件と未完了の受領が揃っています。

**中止・戻り先：** 操作未実施、未受領の重大課題、対応範囲不明、必須観測不足があれば完了としません。保守継続や再計画が必要な場合は、期間・費用・担当を責任者へ確認し、無償延長等を推定しません。

**提出物：** 運用担当の実操作、移管判定、対応範囲、未完了の受領、保守終了の根拠。

## 6. 見積・実績と異常分岐

点検、問合せ、障害調査、復旧、恒久対処、追加変更、教育をWBSへ分け、実作業・待機・手戻りを記録します。件数は確認した記録から数え、未測定を0件・0時間として平均に入れません。

| 状況 | 次の扱い |
| --- | --- |
| 期間中に重大障害が発生 | 合意した障害責任者へ移行、終了判断を再確認 |
| 終了日に課題の担当がいない | 案件責任者へ戻し、未移管のまま保存 |
| 観測が一部欠けた | 欠測を保存し、補足・追観測・期間変更を確認 |
| 運用担当が参加できない | 実操作はNOT RUN、日程と担当を再調整 |
| 追加要望が続く | 元の範囲と分け、採否・見積・期限を合意 |
| 保守の終了日を越える | 元期限・超過・理由・責任者判断を記録 |

## 7. 次工程へ渡す確認

- [ ] 未完了項目は移管先本人の受領と期限がある。
- [ ] 運用担当が自分の権限と手順で実操作している。
- [ ] 対応範囲、保守終了条件、アクセス終了の前提が明確になっている。
