# PJ05 検収・引き渡し

[案件の入口](../README.md) / [前工程 PJ04](04-execution.md) / [次工程 PJ06](06-support.md)

この工程では、合意した成果を受領者が確認し、次の担当者が実際に操作できる状態へ引き渡します。構築担当者の「完成しました」と、受領者の検収判断を別に記録します。

DEMO-A「研修用監視VM1台の構築・引渡し」を架空の例にします。実施・受領・承認はすべて未実施から始めます。顧客への送付、実運用アカウントの発行、契約上の検収判断を教材や台帳が代行することはありません。

## 1. 用語と開始条件

| 用語 | この手順で扱うこと |
| --- | --- |
| 技術上の完成 | 合意した必須試験が対象ホスト・対象版で成功している状態 |
| 受領確認 | 文書・アクセス・運用方法を受け取った人が確認する記録 |
| 検収 | 契約や組織の合意に従い、権限を持つ受領者が成果を判断する手続 |
| 条件付きの受領 | 対象・残条件・担当・期限を明示した受領状態。全要件の合格とは別 |
| 運用移管 | 点検・問い合わせ・障害・変更を扱う担当と範囲の移行 |

PJ04が有効なPASSで、最終稼働版、実ホスト、必須試験、残課題が一致していることが開始条件です。PJ04以後にコード・設定・対象が変わった場合は、変更影響の確認と必要な再試験・再承認を済ませます。

PJ01の合意資料から、受入条件、検収対象、判断できる人、記録方法、確認期限、保守開始条件を取り出します。期限や担当者が未確認なら先に確認し、連絡がない状態を受領と推定しません。

## 2. 役割と準備するもの

| 役割 | 行うこと |
| --- | --- |
| 案件主担当 | 成果一覧、試験結果、説明資料、残課題をまとめる |
| 技術確認者 | 設計値と実機、試験の証拠、運用手順の適合を確認する |
| 受領者`customer` | 合意範囲と受入結果を確認し、検収結果を自身で記録する |
| 運用受領者 | 手順書で点検・指定操作を行い、運用の引き受け条件を確認する |
| 契約・事務担当 | 検収様式、請求との関係、保守開始条件を契約に照らして確認する |

受領者と運用受領者が別の人なら、両方の確認を取ります。同じ人が兼ねる場合も、契約上の判断と技術上の実操作を分けて記録します。氏名やIDを台帳に書いただけでは、その人の代理権を確認したことにはなりません。

[検収・引き渡し票](../templates/acceptance-handover.md)を複製し、[既存の引き渡しチェックリスト](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/build-package/07-handover-checklist.md)を項目の参考にします。そこにある著者の実測結果はDEMO-Aの受領結果へ転記しません。

## 3. PJ05-C1 合意した受入試験を受領者と確認

**目的：** 作ったものを受入条件に照らし、受領者と同じ証拠を見て確認します。

### 実行前確認

1. 検収対象の案件ID、合意資料の版、対象ホスト、配置SHA、設定版を固定する。
2. PJ04の必須試験集計と個別結果が一致し、別ホスト・別版の証跡が混入していないか確認する。
3. 受領者の確認範囲と担当権限を、案件の連絡・承認経路から確認する。不明なら案件責任者または契約担当へ戻す。
4. 実施する受入操作、対象データ、影響、時間帯、戻し方を説明する。本番で障害を注入する試験を当日追加しない。
5. 受領者用の接続手段と、秘密値を本文へ書かない受け渡し経路を準備する。

### 実施の順序

1. 要件ごとに「要求したこと」「今回確認すること」「除外したこと」を読み合わせる。
2. 受領者が合意した方法で試験を確認する。ログによる確認、立会い、本人操作のどれだったかを記録する。
3. 利用者の入口から実際の応答・内容・権限を確認する。管理者だけが見られる画面の成功で一般利用者の受入を代替しない。
4. 結果を試験IDごとに残す。例としてDEMO-A-REQ-001、DEMO-A-TEST-001、DEMO-A-EVID-001をつなぐ。これらはPJ05-C1という工程条件とは別のIDである。
5. 不一致・新しい要望・運用上の懸念を分けて記録する。要件にあった未達は不具合、元の範囲にない追加要望は変更提案として扱う。
6. 不一致があれば再試験、変更、保留の担当と期限を決める。受領者が忙しいことを理由に、本人の確認を主担当が代筆しない。

| DEMO-Aの架空の受入対象 | 確認内容 | 実施結果 |
| --- | --- | --- |
| 監視Web画面 | 指定した利用者が合意した経路で閲覧できる | NOT RUN |
| アクセス制御 | 合意した認証・許可経路・拒否経路が機能する | NOT RUN |
| 監視と通知 | 指定対象の情報と演習用通知の証拠を確認できる | NOT RUN |
| バックアップと復元 | 合意した対象・復元先・実測範囲を説明できる | NOT RUN |
| 構成・運用文書 | 実対象と版が一致し、必要な資料へ到達できる | NOT RUN |

**期待結果：** 受領者と確認した範囲、方法、日時、結果が記録されています。文書を見る試験と実操作する試験を区別できています。

**中止・戻り先：** 必須試験がFAIL、対象版不一致、未承認の差分、データ保全不明なら検収成功へ進めません。PJ04または[変更・障害対応](../change-incident.md)へ戻し、原因対処と必要な承認を行います。

**提出物：** 要件と受入試験の対応、受領者の確認記録、不一致一覧、再試験の予定と結果。

## 4. PJ05-C2 手順・アクセス・教育・残事項を引き渡す

**目的：** 主担当が横にいなくても、次の担当者が安全に確認・操作できる状態にします。

### 引き渡し物の準備

- 構成図、パラメータ、配置版、バックアップ先、監視対象。
- 起動・停止・正常性確認・ログ確認・復元の手順と実行場所。
- 管理者と利用者のアクセス取得・失効の経路。秘密値そのものは含めない。
- 対応可能時間、一次窓口、緊急時の連絡先、変更依頼の出し方。
- 残課題・既知の制限・回避策・影響・担当・期限・終了条件。
- 文書の正本、更新者、更新の承認経路、証跡の保存場所。

### 受領者による実操作

1. 受領者または運用受領者が、自分に付与された接続手段で対象へ入る。主担当のアカウントの貸し借りで済ませない。
2. 資料から対象を確認し、日次点検、サービス状態、ログ、バックアップ最終成功の確認を行う。
3. 合意した影響の小さい操作を一つ実施する。DEMO-Aなら研修環境での指定サービスの計画停止・再開、または別の復元先での結果照合などを選ぶ。
4. 実行前に対象・期待結果・中止条件を本人に説明してもらう。危険な取り違えがあればその場で止める。
5. 操作の時刻、実行者、結果、質問、必要だった口頭補足を記録する。文書にない補足は修正候補にする。
6. 修正した箇所を受領者が再操作して確認する。「一度説明した」だけで教育完了にしない。
7. 残課題を受け持つ人に、内容・影響・回避策・期限・確認方法を示し、実際の受領記録を得る。担当者名を入れただけで移管済みにしない。

| 実操作の観察 | 問題があった場合の修正 |
| --- | --- |
| どの端末で実行するか迷う | 管理端末・対象ホスト・対象アプリを手順行に明記 |
| 正常な出力が分からない | 期待結果と異常時の判断先を追加 |
| 権限が足りない | 必要最小限の権限と取得経路を確認し、再試行 |
| 主担当の補足がないと進めない | 補足を手順へ反映して本人に再実行してもらう |
| 残課題の担当が未定 | 案件責任者が担当と期限を調整するまで未移管 |

**期待結果：** 実在する別の人が手順書で操作し、受け取った資料と権限の範囲、教育結果、残課題の受領が記録されています。

**中止・戻し：** 対象の誤認、想定外の停止、必要権限不明があれば操作を止めます。承認済みの戻し方で正常性を確認し、資料か環境の問題を直して再実施します。

**提出物：** 引き渡し物一覧、実操作ログ、質問と修正、アクセス受領の状態、残課題移管の証拠。

## 5. PJ05-C3 検収結果・範囲・日時・保守開始条件を記録

**目的：** 誰が何を受け入れ、何が残り、いつから誰が運用するかを明確にします。

1. 受領者が「合意範囲を検収」「条件を明示して受領」「保留」「受領不可」のどの判断をしたか、元の文書・記録とともに残す。
2. 判定の対象範囲、対象版、確認日時、確認した試験、除外範囲、残条件、判断者を記録する。
3. 条件付きの受領なら、条件の影響、対応担当、期限、解除の確認者を記録する。必須条件が未達のまま工程全体をPASSへ進めない。
4. 受入条件を変更する場合はPJ01の合意から見直し、変更影響・試験・承認の更新を行う。過去の失敗を消さず、改版後の結果を追加する。
5. 保守開始の起点、期間、対応時間、対象、除外、窓口、運用受領者、保守終了条件を確認する。検収日と自動的に同日と仮定しない。
6. 検収と請求・支払手続との関係は契約・事務担当へ確認する。金額、請求可能日、入金を技術担当者が推定しない。
7. PJ05の最新証跡に結び付けて受領者`customer`の工程確認を記録する。台帳操作は[ツール操作](../tracker-guide.md)に従う。

**連絡がない場合：** 未回答の日時、連絡履歴、確認期限、次回の窓口を残します。「期限を過ぎたので承諾」と推定しません。契約に記載された取扱いの適用は契約担当と権限者が確認し、その根拠を残します。台帳が黙示検収を自動判定することはありません。

**期待結果：** 技術上の完成、成果の受領、契約上の手続、保守開始が区別されています。未回答を受領済みにしていません。

**提出物：** 検収結果、根拠文書、対象版、受領者と日時、残条件、保守開始条件、事務担当への確認事項。

## 6. 異常分岐と工数差

| 状況 | 次の扱い |
| --- | --- |
| 受領者が参加できない | 未実施を残し、元期限・新予定・遅延理由を記録 |
| 追加要望が出た | 元の不具合と区別し、変更提案の採否待ちへ |
| 受入で既存不具合が判明 | PJ04の結果へ関連付け、対処・再試験・再承認 |
| 必須試験は成功、教育は未実施 | PJ05-C2を完了にせず、教育と実操作を計画 |
| 契約上の扱いが未確認 | 判断できる担当へ確認し、未確認の事務状態を残す |
| 案件自体が保留・取消 | 元の成果・未達・費用確認事項を保存して別経路へ |

説明会、受入立会い、資料修正、再試験、回答待ちをWBSへ分けます。見積との差は時間と原因を記録し、追加費用の請求可否は担当者へ照会します。待機していた期間を実作業時間として一括計上しません。

## 7. 次工程へ渡す確認

- [ ] 対象版と受入範囲、受領者の判断が一致している。
- [ ] 受領者による実操作と、資料修正後の確認が記録されている。
- [ ] 未解決事項は受領者・担当・期限・確認方法まで決まっている。
- [ ] 保守開始・期間・対応範囲・窓口が未確認のままではない。
- [ ] 未回答、保留、取消を成功検収へ読み替えていない。

PJ05が有効なPASSになったら、[PJ06 初期保守・運用移管](06-support.md)へ引き渡します。実サービスで障害が起きた場合の対応は、工程待ちを理由に放置せず、合意した責任者と障害対応経路を優先します。
