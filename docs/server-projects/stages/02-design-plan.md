# PJ02 設計・実行計画 — 要件を構成・手順・試験へつなぐ

[案件運用の入口](../README.md) / [前: 要件・見積](01-scope-estimate.md) / [要件対応表](../templates/requirements-trace.md) / [実行計画](../templates/execution-plan.md) / [次: 本番前確認](03-readiness.md)

この工程の目的は、合意した要件を「どの構成で実現し、どの順に作業し、何を見て確認するか」へ変換することです。文書を増やすことではなく、要件から実行と検証まで辿れる状態を作ります。

入力は有効なPJ01と、その合意版です。案件主担当が計画を作り、`technical`の技術確認者が設計・試験・復旧の整合を確認します。本番への変更承認は後続PJ03の`change`が扱います。

## 入力・担当・出口

| 項目 | 内容 |
| --- | --- |
| 必須入力 | 要件・対象外・前提、受入条件、WBSと見積根拠、関係者と日程 |
| 主担当 | 要件に対応する設定、手順、試験、戻し方を作る |
| 技術確認者 | 設計の妥当性、漏れ、危険な対象指定、復旧可能性を確認 |
| 関係者 | 運用受領者、データ所有者、ネットワーク担当、変更責任者 |
| 出力 | 要件対応表、設計・パラメータ、実行計画、試験計画、復元計画 |
| 出口 | 対応関係が追え、技術確認者が対象版と最新証跡を承認した |

| 条件ID | 確認すること |
| --- | --- |
| PJ02-C1 | 要件から構成・設定・試験へ対応を付ける |
| PJ02-C2 | 構築・移行・戻し・データ保護の計画を整える |
| PJ02-C3 | 作業分担・日程・レビューと実行場所を確定 |

## PJ02-C1 要件から構成・設定・試験へ対応を付ける

### 1. 参照する技術資料と対象版を固定する

既存の[基本設計](https://github.com/ns7jp/server/blob/main/docs/build-package/01-basic-design.md)、[詳細設計](https://github.com/ns7jp/server/blob/main/docs/build-package/02-detailed-design.md)、[パラメータシート](https://github.com/ns7jp/server/blob/main/docs/build-package/03-parameter-sheet.md)、[ネットワーク設計](https://github.com/ns7jp/server/blob/main/docs/build-package/04-network-ip-plan.md)を参照します。

案件の記録にはURLだけでなく、実際に確認したリポジトリの完全なGit SHA、文書版、設定の版を残します。参照URLの`main`が後で更新されても、どの内容で設計したかを追えるようにします。秘密値や実IPの差分は、許可された非公開の設定管理先で扱います。

### 2. 要件を一行ずつ対応付ける

[要件対応表](../templates/requirements-trace.md)を使い、各REQにDES、TEST、EVIDへの参照を付けます。まだ実行していない試験のEVIDは`NOT SET`、結果は`NOT RUN`です。将来使う証跡の名前を予約しても、証拠が存在することにはなりません。

| ID | 役割 | 例 |
| --- | --- | --- |
| REQ-001 | 合意した要求 | 指定管理端末から認証後に画面を使える |
| DES-001 | 実現する設計・設定 | 入口、認証、管理経路、設定項目への参照 |
| TEST-001 | 期待値を持つ試験 | 正しい経路と認証で応答することを確認 |
| EVID-001 | 実際の実行記録 | 日時、対象、版、コマンド、結果を保存した記録 |

IDは案件内で一意にし、別案件との識別には案件IDを付けます。REQとTESTが一対一とは限りません。一つの要件に正常、異常、復旧の複数試験を結び、複数要件を一つの試験で確認する場合は対象を明示します。

### 3. 正常・異常・復旧を組にする

[既存の試験仕様書](https://github.com/ns7jp/server/blob/main/docs/build-package/06-test-specification.md)の項目を、対象案件の受入条件に合わせて選びます。既存試験のPASSを新案件へ持ち込まず、何を今回実行する必要があるかを決めます。

| 観点 | 計画に含める確認 | 誤った代用品 |
| --- | --- | --- |
| 正常 | 許可された利用者が必要な操作を行える | プロセスが起動しているだけ |
| 異常 | 不正な認証・不許可の経路・依存先停止を判定できる | 確認コマンドが存在せず失敗しただけ |
| 復旧 | 別対象へ戻した内容と利用者視点の正常性 | バックアップファイルが存在するだけ |
| 継続 | 再起動後の設定、保存、監視、必要な観測期間 | 一度の応答だけ |

各試験に前提、対象、実行する場所、期待結果、時間上限、中止条件、戻し方、採録先を記載します。手順と期待結果を分け、実出力を書く場所は空のまま確保します。

### 4. 設計の空白と余分な作業を検出する

要件から右へ辿り、設計や試験がないREQを見つけます。次に設定から左へ辿り、どの要件にも必要とされていない変更を確認します。余分な監視製品や公開ポートを「便利だから」と追加せず、必要なら変更提案として扱います。

要件を廃止するときはIDを再利用せず、廃止理由と代替IDを記録します。試験が不要になった場合も、削除して未実施を隠すのではなく、どの合意変更により不要になったかを示します。

## PJ02-C2 構築・移行・戻し・データ保護の計画を整える

### 1. 手順を前提・操作・確認・中止で書く

[既存の構築手順](https://github.com/ns7jp/server/blob/main/docs/build-package/05-build-procedure.md)を、対象案件のパラメータで具体化します。対象ホストや接続先を含む実値は非公開管理先へ置きます。

| 手順の欄 | 書く内容 |
| --- | --- |
| 前提 | 直前に何が完了していれば実行できるか |
| 実行場所 | 管理端末、検証VM、本番対象、コンテナ内など |
| 対象 | inventory、対象ID、変更するサービス・データ |
| 操作 | 対象版のスクリプト・コマンド・GUI手順への参照 |
| 期待結果 | 何の出力をどの基準で判断するか |
| 中止・戻し | どんな差で止め、どの正常状態へ戻るか |
| 採録 | 日時、出力、終了コード、判定をどこへ残すか |

初心者向け手順では、失敗後に同じブロックの後続コマンドが進まないことも確認します。期待した拒否と、道具不足・接続先誤りによる失敗を分けます。秘密値を引数や差分へ出す手順は、公開例をそのまま流用しません。

### 2. 構築と移行を分ける

新しい環境を作ることと、利用者の接続先やデータを切り替えることは別の作業です。移行がある場合は、データ取得時点、書き込み停止、同期差分、切替、利用者確認、切戻し可能な期限を記載します。

データを扱わない案件でも「なし」とした理由を残します。実データがあるか未確認なのに移行なしとして計画を短縮しません。

### 3. 戻す対象をコード・設定・データに分ける

[変更・ロールバック計画](https://github.com/ns7jp/server/blob/main/docs/build-package/08-change-rollback-plan.md)を参照し、変更前後の版と正常状態を定義します。

| 対象 | 戻し計画に必要なこと |
| --- | --- |
| コード | 変更前の完全なSHA、その版を取得・実行できること |
| 設定 | 変更前の設定版、秘密値の参照先、対象へ戻す方法 |
| データ | バックアップID、取得時点、復元先、整合性確認、失う範囲 |
| 接続経路 | DNS・経路・公開先などの戻し方と反映確認 |

コードを旧版へ戻せばデータも戻るとは限りません。データ形式の変更がある場合は旧コードとの互換性を確認し、後戻りできない地点を明示します。不可逆な変更を含む場合は、組織の変更管理で専門担当と復旧方式を確定するまで実行へ進みません。

### 4. バックアップと復元先を計画する

復元元と復元先を識別し、原本を保持して別対象へ戻す手順を設計します。バックアップの日時・ハッシュ・容量と、必要な秘密値をどこから取り戻すかを記録します。復元に必要な情報を、故障する予定の同じホストだけへ置かないようにします。

検証環境ではダミーデータまたは組織が許可したデータを使い、実データを無断で個人ラボへ持ち込みません。復元先の容量、ネットワーク到達性、認証、所要時間の測定方法も計画へ含めます。

## PJ02-C3 作業分担・日程・レビューと実行場所を確定

### 1. 作業窓へ手順を並べる

[実行計画](../templates/execution-plan.md)へ、事前確認、適用、事後試験、観測、切り戻し判断、復元、終了報告を時系列に配置します。構築操作だけで作業窓を埋めません。

WBSの依存関係と予定を照合し、必要な確認者がその時間に参加できるか確認します。作業中に連絡が取れないとき、誰が中止を判断し、誰が利用者へ伝えるかも定めます。

### 2. 実行場所とデータの流れを読む

作業者以外の人が手順書だけを読み、「この操作はどの機械に作用するか」を指差し確認します。SSHで入った端末とローカル端末の区別、Ansibleの対象一覧、コンテナ内の操作、ファイル転送先を特に確認します。

ここでは本番へ接続して試す必要はありません。読み取り調査が必要なら、許可された調査として別途実施します。手順書レビューを口実に未承認の本番変更を行いません。

### 3. レビューコメントを閉じる

指摘には「修正必須」「確認待ち」「提案」を分けて記録します。提案は案件主担当や技術確認者が採用したときに要件・計画へ反映します。未採用の提案を勝手に実装して範囲を広げません。

重大な指摘が残ればPJ02は未完了です。軽微な文書改善を後回しにする場合も、担当・期限・影響と、その扱いを決めた確認者を記録します。

## 架空例 DEMO-Aの対応関係

以下は設計の書き方を示す架空例です。実施結果と証跡は未作成です。

| 要件 | 設計 | 試験計画 | 結果・証跡 |
| --- | --- | --- | --- |
| REQ-001 認証後に画面を使う | DES-001 管理経路・入口・認証 | TEST-001 正常、TEST-002 認証なし拒否 | NOT RUN / NOT SET |
| REQ-002 不要な公開をしない | DES-002 待受と到達制御 | TEST-003 許可元・拒否元から確認 | NOT RUN / NOT SET |
| REQ-003 研修データを復元する | DES-003 別復元先と保管 | TEST-004 内容比較、TEST-005 復元後利用 | NOT RUN / NOT SET |

各TESTは、既存案件パックの対応項目を参考にして詳細化します。参照先に過去のPASSがあっても、上表の結果をPASSに変えません。

## 合格・中止・やり直し

- [ ] C1: 全必須要件に設計・設定・試験が対応し、未実施と証跡なしを識別できる。
- [ ] C2: 構築・移行・戻し・データ保護が対象版と対象環境に合わせている。
- [ ] C3: 作業分担、時間、レビュー、実行場所、情報の保存先が確定している。
- [ ] technicalの実確認記録が、最新の計画版と条件記録に結び付いている。

対象が特定できない、戻し方が不明、復元先がない、受入条件に対応する試験がない、担当者が重要操作を説明できない場合は検証計画を見直します。設計済みの表示だけで本番準備完了にしません。

| よくある失敗 | 修正する行動 |
| --- | --- |
| 文書とコードのポートやOSが違う | パラメータの正本を決め、差を一覧にして同時に修正 |
| 手順が「実行する」で終わる | 期待結果、中止、採録、復旧を同じ手順へ追加 |
| バックアップを元データへ上書き復元する | 原本を保持し、別対象で内容確認してから切替を計画 |
| 既存の試験IDを並べただけ | 自案件の要件と測定条件に合っているか一行ずつ確認 |

要件そのものが変わる場合はPJ01の再合意へ戻ります。設計修正は旧版と指摘を保持し、修正後に技術確認者へ再確認を依頼します。採用変更で影響する工程では、設計の再点検・必要な試験の再実施を行い、新しい条件記録とレビューを残します。旧PASSの記録だけで後続承認を復活させません。PJ02が有効に承認されたら、[PJ03](03-readiness.md)で実機検証・復元と本番変更の可否を確認します。
