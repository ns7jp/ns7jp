# PJ04 本番作業・結果確認

[案件の入口](../README.md) / [前工程 PJ03](03-readiness.md) / [次工程 PJ05](05-acceptance.md)

この工程の目的は、承認された対象・版・時間・操作の範囲で作業し、利用者から見た結果と戻し判断を記録することです。手順を最後まで実行したことと、変更が成功したことは別に確認します。

以下のDEMO-A「研修用監視VM1台の構築・引渡し」は架空の演習例です。実施欄はすべて`NOT RUN`、承認情報は`NOT SET`から始めます。実案件は組織が許可した場所と手続で扱い、顧客の実構成・生ログ・秘密値をこの公開リポジトリへ保存しません。

## 1. 入力と役割

| 入力 | 確認する内容 | 不足したとき |
| --- | --- | --- |
| PJ03の有効な確認記録 | 承認者、対象ホスト、対象版、変更窓、条件 | 作業を開始せずPJ03へ戻す |
| 実行手順・作業分担 | 手順番号、実行場所、作業者、確認者 | 同時変更や担当不明を解消する |
| 必須事後試験 | 要件・試験ID、期待結果、実行対象 | 成功を判断できないため開始しない |
| バックアップ・戻し計画 | 読取可否、復旧対象、開始条件、残り時間 | 復旧可能性を確認してから再判断 |
| 連絡・判断経路 | 開始、異常、終了時の窓口と代替連絡 | 連絡不能時の扱いを決める |
| 見積と作業一覧 | 見積幅、依存、期限、残時間 | 元見積を残して再見積する |

案件主担当は実行と記録をまとめ、作業者は割り当てられた対象だけを操作します。技術確認者は試験結果と構成差分を確認し、変更責任者`change`が作業開始・継続・戻し・結果を判断します。CLIの工程PASSや確認者IDだけで、組織の本番権限が発行されることはありません。

[作業結果テンプレート](../templates/work-result.md)を案件の非公開記録先に複製します。既存の[作業結果報告書](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/build-package/11-work-result-report.md)は項目の参考に使えますが、他のホストや著者の過去のPASSは転記しません。

## 2. PJ04-C1 直前確認と対象版・対象ホストを照合

**目的：** 前日までの承認と、今から変更する実体を一致させます。

### 実行前確認

1. PJ03の承認対象を読み上げ、案件ID・変更ID・対象環境・hostname・資産またはVMの識別情報を確認者と照合する。
2. 管理端末と接続先を分けて記録する。踏み台や多重SSHを使っている場合は、現在のシェルがどのホストかを確認する。
3. 対象OSのhostname、実IP、VMまたは資産識別情報を読み取り、承認票と比較する。hostnameだけが一致しても同じホストと断定しない。
4. ソースの承認SHA、配置するアーカイブやイメージの識別、設定ファイル群のハッシュを比較する。Gitチェックアウトなら`git rev-parse HEAD`と未コミット差分を確認する。
5. inventory・環境変数・ローカル上書きも承認対象の設定と照合する。ソースSHAが一致しても設定値が違えば同じ変更とは扱わない。
6. バックアップと戻し先の実体、取得時刻、必要容量、読取可否、代替接続経路を確認する。バックアップジョブの成功表示だけで復元可能と判定しない。
7. 現在のサービス、利用者応答、監視、エラー、容量を採録し、作業前から存在する異常を分ける。
8. 変更窓、作業者、確認者、同時作業、連絡経路、戻し所要時間に変化がないことを確認し、変更責任者の開始判断を記録する。

| 照合項目 | 承認済みの値 | 直前の実値 | 初期判定 |
| --- | --- | --- | --- |
| 案件・変更ID | DEMO-A / DEMO-A-CHG-001という架空例 | NOT RUN | 未確認 |
| 対象hostname・VM識別 | NOT SET | NOT RUN | 未確認 |
| ソースの40桁SHA | NOT SET | NOT RUN | 未確認 |
| 設定・配置物の識別 | NOT SET | NOT RUN | 未確認 |
| 作業窓・停止上限 | NOT SET | NOT RUN | 未確認 |
| 戻し先・復元ポイント | NOT SET | NOT RUN | 未確認 |

**期待結果：** 承認票、配置物、設定、実ホストが一致し、作業前の状態が記録されています。資料を読んだだけの項目と、その場で実測した項目が区別されています。

**中止・戻り先：** SHA不一致、未承認の差分、別ホスト、権限不足、バックアップ未確認、時間窓外、変更責任者不在があれば開始しません。原因を直すか、差分と影響を示してPJ02・PJ03を再確認します。現場の都合で承認票の値を実体へ書き換えません。

**提出物：** 直前照合表、変更前状態、開始判断の根拠、作業者・確認者と時刻。ここで得た読み取り結果にも証跡IDを付けます。

## 3. PJ04-C2 承認範囲内で実行し時系列と差分を記録

**目的：** 実際に何を変更したかを、別の人が追える形で残します。

### 作業の時系列

1. 決められた連絡経路で開始を通知し、記録に発信者・宛先・時刻・内容を残す。演習で送信しない場合は「下書き・未送信」と記録する。
2. 手順番号ごとに対象、入力、期待結果を確認して実行する。担当外のホストや設定を「ついでに」変更しない。
3. 実開始・終了、操作、主要出力、終了コード、判定、証跡先をその場で記録する。秘密値は表示させず、生ログは許可された非公開保管先に置く。
4. 期待結果に合わない場合は、その手順をFAILとして後続の依存作業を止める。失敗を見つけた時刻と利用者への影響を残す。
5. 承認手順内で対処可能か、戻し条件か、追加変更が必要かを分類する。追加の設定変更は[変更・障害対応](../change-incident.md)へ回し、既存承認の範囲だと推定しない。
6. 独立した作業が進められる場合は、対象と担当を明示して継続判断を得る。依存先が失敗した作業は進めない。
7. チェックポイントごとに残り時間と戻し所要時間を再見積し、戻し開始の最終時刻を越える見込みなら変更責任者へ判断を求める。
8. 作業中に判明した設計差分、未文書化の前提、想定外の操作を差分表へ追記する。手順書を修正した時刻と版を残す。

| 記録する列 | 書き方 | 避ける書き方 |
| --- | --- | --- |
| 操作 | 承認手順番号と実行した対象・内容 | 「いろいろ調整」 |
| 実出力 | 成否を判断した出力、終了コード、証跡 | 「問題なし」だけ |
| 影響 | 利用者・監視・データのどこまで確認したか | 未確認の影響を「なし」 |
| 差分 | 計画と実行の違い、判断者、根拠 | 予定欄を実績に上書き |
| 時間 | 実作業、待機、調査、手戻りを分ける | 待ち時間を消して短縮を主張 |

### DEMO-Aの架空の計画例

対象は研修用の監視VM1台で、[既存構築パック](https://github.com/ns7jp/server/tree/44c52e733826b9b5239918c05010b8b68b60346c/docs/build-package)を選んだ場合の流れです。次の分数は計画例で、実測値ではありません。

| 相対時刻の計画 | 作業 | 次へ進む条件 | 実績 |
| --- | --- | --- | --- |
| T+0〜15分 | 対象・版・バックアップの直前確認 | PJ04-C1の証拠と開始判断 | NOT RUN |
| T+15〜45分 | 承認した構成を適用 | 適用成功、想定外差分なし | NOT RUN |
| T+45〜65分 | 利用者応答・権限・監視の事後試験 | 全必須試験の結果が揃う | NOT RUN |
| T+65分 | 継続または戻しの判断点 | 確保した戻し時間を残せる | NOT RUN |
| T+65〜90分 | 完了処理または承認済みの戻し | 最終状態と連絡を記録 | NOT RUN |

戻しに必要な時間がこの計画内に収まることは、PJ03の検証で別に確認します。「25分で戻る」という計画例を復元実績へ転記しません。

**期待結果：** 承認した範囲の実行が、時刻・対象・版・出力・差分とつながります。予定外の対処がある場合は判断経路が残ります。

**中止・戻り先：** 新しい影響、秘密値の露出、データ保全の不確実性、戻し時間不足があれば変更を重ねず停止します。緊急対応が必要なら組織の緊急変更経路に従い、権限を自己付与しません。

**提出物：** 全作業のタイムライン、手順ごとの出力、実績工数、計画との差分、変更・障害の関連ID。

## 4. PJ04-C3 必須事後試験・戻し判断・結果報告を完了

**目的：** 操作の終了ではなく、要件に対する結果を確認して閉じます。

### 事後試験から結果報告まで

1. 合意した必須試験の対象数を確定し、要件・設計・試験・証跡をたどる。DEMO-A-REQ-001からDEMO-A-TEST-001と実証跡へ対応付ける。
2. 利用者が使う経路から応答と内容を確認する。プロセス起動、構文検査、localhost応答だけで利用者経路の成功へ読み替えない。
3. 認証・アクセス拒否、依存先、監視、通知、バックアップ等、合意した必須項目を実対象・実版で実施する。通知の下書きと実受信も区別する。
4. PASS・FAIL・BLOCKED・NOT RUNを個別結果から集計する。試験数の合計が一致するかを確認する。
5. 必須試験にFAILや未実施があれば、成功報告を出さない。変更責任者と継続・戻し・保留を判断し、理由と時刻を記録する。
6. 戻す場合は承認済みの範囲で旧版・設定・データの整合を回復し、戻した後の利用者応答と監視も試験する。戻しに成功しても、新しい変更の成功とは記録しない。
7. 一時的な許可、テストデータ、監視抑止は計画に従って処理する。後続担当が必要とするアクセスを先に削除しない。
8. 最終稼働版、構成差分、停止時間、試験結果、残課題、連絡先、次の判断を報告し、変更責任者の確認を得る。

| 結果の分岐 | 記録と次の動き |
| --- | --- |
| 必須試験が全て成功し未承認差分なし | 対象版を固定し、PJ04のレビュー後にPJ05を準備 |
| 必須試験が失敗し、承認済みの戻しが成功 | 変更結果は失敗・切戻し。原因対処と再承認へ |
| 復旧できたが未承認差分が残る | 復旧状態と差分を報告し、成功完了へ進めない |
| 戻しにも失敗 | 障害対応へ移行し、影響・保全・支援要請を優先 |
| 時間切れで未実施が残る | 未実施を残して保留・再計画。成功件数へ加算しない |
| 依頼が取消になった | [日々の運営](../operations.md)の取消手順へ。成功終結とは区別 |

「変更責任者が了承した」という記録だけで、失敗した必須試験をPASSへ上書きしません。要件や受入条件を変更する場合は影響を示して上流の合意と計画を改版し、必要な検証・承認を取り直します。台帳の再記録で失効する承認も再確認します。

**期待結果：** 実施結果、戻し結果、最終状態が区別され、次の担当が現在のサービス状態を説明できます。

**提出物：** [作業結果票](../templates/work-result.md)、試験集計、戻し判断、最終構成、残課題と担当・期限、変更責任者の確認記録。

## 5. 見積と実績を比較する

WBSごとに元見積、最新見積、実作業、待機、手戻り、残時間を記録します。未測定は未測定で、0時間にしません。超過した場合は、どの前提が違ったかを「依存待ち」「環境差」「試験不足」「追加変更」等の具体的な事実で説明します。

差額の請求可否や人員契約への適合を作業者だけで判断しません。時間差と作業範囲を整理し、PJ01の費用・変更条件を確認する担当へ渡します。金額欄は確認前に埋めません。

## 6. 次工程へ渡す確認

- [ ] PJ04-C1〜C3の最新結果と根拠が揃っている。
- [ ] 必須試験の失敗・未実施、未承認差分が残る場合は成功扱いにしていない。
- [ ] 変更責任者の確認は実際の対象・版・証跡に結び付いている。
- [ ] PJ05へ渡す対象範囲、最終版、試験結果、残課題、窓口が確定している。
- [ ] 公開用教材と顧客の記録を分離している。

台帳の記録方法は[ツール操作](../tracker-guide.md)を参照します。実作業の成功を確認してPJ04が有効なPASSになったら、[PJ05 検収・引き渡し](05-acceptance.md)へ進みます。
