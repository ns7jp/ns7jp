# PJ03 検証完了・本番変更の承認 — 動かした証拠と戻れる条件で判断する

[案件運用の入口](../README.md) / [前: 設計・実行計画](02-design-plan.md) / [実行計画](../templates/execution-plan.md) / [変更・障害対応](../change-incident.md) / [次: 本番作業](04-execution.md)

PJ03は本番変更の前に必ず通る工程です。設計、スクリプト、構文検査が揃っただけでは通過できません。検証環境で必要な試験と復元を実行し、対象・版・時間・戻し・連絡を特定したうえで、実際の変更責任者の判断を得ます。

学習用の`training`では、架空の対象に対して実際に行った検証と模擬判断を記録します。実案件の`work`では、組織の変更申請・承認・本番実行手順を優先します。ローカル台帳の工程PASSは、本番作業権限や契約上の承諾を発行するものではありません。

## 入力・担当・出口

| 項目 | 内容 |
| --- | --- |
| 必須入力 | 有効なPJ02、合意した要件・設計・試験・実行計画の版 |
| 主担当 | 検証を実行し、結果、差分、残リスク、変更条件をまとめる |
| 技術確認者 | 試験結果と復元の妥当性、本番との差を確認する |
| 工程確認者 | `change`。対象範囲の変更を判断する変更責任者 |
| 関係者 | 利用者・運用窓口、データ所有者、当日の作業者・確認者 |
| 出口 | 最新の証跡と対象版について、変更責任者の有効な承認を記録した |

| 条件ID | 確認すること |
| --- | --- |
| PJ03-C1 | 検証環境で必須試験と復元を実行し差分を整理 |
| PJ03-C2 | 対象・変更窓・中止閾値・戻しと連絡を確定 |
| PJ03-C3 | 残リスクと未解決事項を示し対象版の変更承認を得る |

## PJ03-C1 検証環境で必須試験と復元を実行し差分を整理

### 1. 検証開始前の対象を確認する

検証用の対象ID、OS、構成、データ、ネットワーク、コードSHA、設定版を確認します。本番と紛らわしい名前や共用のDockerプロジェクトは避け、何を破棄・復元できるのかを明確にします。

使う手順はPJ02で確認した版です。[既存の試験仕様書](https://github.com/ns7jp/server/blob/main/docs/build-package/06-test-specification.md)、[ネットワーク検証](https://github.com/ns7jp/server/blob/main/docs/build-package/09-network-validation-procedure.md)、[変更・ロールバック計画](https://github.com/ns7jp/server/blob/main/docs/build-package/08-change-rollback-plan.md)を対象案件へ適合させた参照を用意します。

既存資料内の例示IP、ホスト名、過去の証跡、予定時刻を、そのまま本番用の対象として実行しません。対象を確定できなければ`BLOCKED`です。

### 2. 必須試験を実際に動かす

[要件対応表](../templates/requirements-trace.md)のTESTを、前提→操作→実出力→期待値との比較→後処理の順に実行します。正常、異常、復旧、永続性など、今回の要件で必須とした範囲を確認します。

| 結果 | この工程での扱い |
| --- | --- |
| PASS | 試験対象と期待値を実出力で確認した |
| FAIL | 実行したが期待値と一致しない。原因と再試験が必要 |
| BLOCKED | 道具・環境・権限などが足りず実行できない |
| NOT RUN | まだ実行していない。成功件数へ含めない |

「試験を開始した」「終了コードが0だった」だけで全要件をPASSにしません。拒否試験では、本当に対象の制御が働いたのか、コマンド不存在や接続先誤りで失敗したのかを区別します。

失敗した記録は保持し、修正後に新しい試行を追加します。同じ日付の自動生成ログが上書きされるツールでは、各試行の原本を別の識別名で保存します。秘密値を含むログは組織が許可した場所に限定します。

### 3. バックアップから別対象へ実復元する

データまたは設定を戻す必要がある案件では、バックアップを取得するだけでなく、別の復元先へ戻して確認します。[既存のバックアップ・復元手順](https://github.com/ns7jp/server/blob/main/docs/backup-restore.md)を、保管場所・対象版・データ量に合わせて使います。

実施する順番は次のとおりです。

1. 元データとバックアップの取得時点、容量、識別子、ハッシュを記録する。
2. 復元先が元データとは別で、容量と権限が足りることを確認する。
3. 復元開始前に測定の開始点と終了点を定義し、実際に復元する。
4. 復元コマンドの終了と、件数・内容・必要な設定・利用者視点の動作を確認する。
5. 戻せた時点、失うデータの範囲、実測時間、残る制約を記録する。
6. 元環境を壊していないことを確認し、採録後に計画した後処理を行う。

同一ホスト内の別volume復元は、その範囲の証跡です。ホスト全損からの復旧が要件なら、新規の別ホストへの再構築・復元を含む試験が必要です。数行のダミーDBだけを戻して、実案件の大容量データでの復旧時間を保証しません。

RTOは復旧時間の目標、RPOは戻せる時点についての目標です。実測欄には、測った区間と環境を記載します。「復元コマンドの秒数」と「検知・判断・切替・確認を含む全体時間」を別々に示します。

### 4. 検証環境と本番の差を残す

| 差分 | 比較する点 | 対応 |
| --- | --- | --- |
| OS・版 | パッケージ、カーネル、設定方式 | 未確認の差を再検証する |
| 台数・構成 | コンテナかVMか、経路、外部依存 | 同じとみなせない範囲を分ける |
| データ | 量、種類、保存期間、復元先 | 測定条件と容量の差を評価する |
| 認証・権限 | 学習ユーザーか実担当者か | 実際の権限申請と試験を確認する |
| 運用時間 | 一時起動か継続稼働か | 必要な観測期間と欠測を記録する |

差があること自体を隠さず、影響、追加検証、残リスク、担当、期限を示します。必須要件に直結する未確認を、残リスクという名前だけで合格へ変えません。必須範囲を変更するならPJ01の再合意からやり直します。

## PJ03-C2 対象・変更窓・中止閾値・戻しと連絡を確定

### 1. 当日使う対象を一つの表にまとめる

[実行計画](../templates/execution-plan.md)へ、対象環境、ホスト識別、inventory、変更前後のSHA、設定版、手順版、バックアップIDを記録します。識別情報が`NOT SET`のまま本番へ進みません。

対象確認は主担当だけでなく当日の確認者も行います。復旧用の接続経路、コンソール、秘密値の取得方法は、権限があることまで確かめます。実秘密値は計画本文へ貼りません。

### 2. 変更窓と切り戻し判断期限を逆算する

変更窓は、変更や停止を受け入れてもらえる時間帯です。開始時刻と終了時刻に日付・タイムゾーンを付けます。切り戻しは窓の終了直前に判断しても間に合わないため、復元・再確認・連絡に必要な時間を残して期限を決めます。

考え方は、`最終判断期限 = 変更窓終了 - 戻しの見込み時間 - 戻した後の確認時間 - 合意した余裕`です。見込みはPJ03-C1の実測と本番との差を根拠にします。値が未確認なら、都合のよい短い値で計算しません。

架空例DEMO-A: 同日20:00〜22:00の窓で、戻し30分、戻した後の確認15分、余裕15分を計画するなら、遅くとも21:00までに戻し開始を判断する設計です。適用30分と事後確認15分を20:45までに完了する案を置き、遅れた場合は残時間を再評価します。この時刻は実案件の承認や実測ではありません。

### 3. 中止閾値を観測可能にする

| 条件 | 判断するための記録 | 動き |
| --- | --- | --- |
| 対象・版が計画と不一致 | 対象表と直前出力の差 | 開始せず対象を再確認 |
| 必須バックアップや復元根拠がない | 取得時点、ハッシュ、実復元記録 | 開始せず前提を整備 |
| 計画外の公開・認証回避 | 待受、接続、認証の実出力 | 続行を止め変更責任者へ連絡 |
| データ整合が期待値と不一致 | 内容比較、エラー、試験結果 | 保存・隔離し戻し判断へ |
| 判断期限に達した | 現在時刻、残手順、復旧見込み | 計画した戻しへ移行するか責任者判断 |
| 影響が合意した上限を超えた | 合意した指標・しきい値・観測結果 | 中止・復旧・必要な障害連絡 |

具体的な待ち時間、許容停止、エラー数などが必要な条件では、その値と測定方法を計画へ記入します。未設定のまま「適宜判断」と書いて済ませません。

### 4. 連絡と判断者を確定する

開始、途中の判断点、異常、中止・切り戻し、終了の各場面について、誰が誰に何を伝えるかを決めます。連絡先が不通の場合の代理経路と、中止する条件も確認します。

通知設定があるだけでは連絡可能とは判定しません。組織が許可した方法で宛先・参加可能時間・代理担当を確認し、必要な連絡試験を行います。実際のメッセージ送信は担当者が許可された経路で行います。

## PJ03-C3 残リスクと未解決事項を示し対象版の変更承認を得る

### 1. 判断用の資料を揃える

変更責任者に示すものは、変更目的と対象、必須試験の集計、実復元の証跡、検証との差、作業窓、中止閾値、戻し方、連絡、残リスクです。大量のログだけを渡さず、要点から原本へ辿れるようにします。

| 残リスクの欄 | 書く内容 |
| --- | --- |
| 内容・影響 | 何が未確認で、誰にどんな影響があり得るか |
| 発生時の観測 | 何を見て気付くか |
| 対処・限界 | 何ができ、何ができないか |
| 担当・期限 | 誰がいつまでに解消または移管するか |
| 判断 | 誰がどの範囲で受け入れたか、まだ未承認か |

「大丈夫と思う」「軽微」のような主観だけで残リスクを閉じません。未解決事項を引き受ける人がいなければ、解決済みとも受容済みとも記録しません。

### 2. 実際の変更責任者の判断を記録する

承認対象には完全なSHA、設定版、手順版、対象ホスト、作業日時、最新の条件証跡を含めます。承認日時、確認者ID・役割、判断、条件、組織の申請記録への参照を残します。

変更責任者が返答していない場合は承認待ちです。AIの提案、主担当の自己チェック、過去案件の承認、台帳の入力だけで代替しません。変更責任者の権限そのものも組織で確認します。

### 3. 承認後に変わった場合の扱いを決める

承認後に対象、コード、設定、作業日時、復元条件、重要な担当が変われば、どの承認が影響を受けるかを確認します。条件を再記録すると当該工程と後続の旧承認は失効するため、[ツール操作](../tracker-guide.md)と組織手順で再確認します。影響工程の検証・実復元・直前条件の確認を新しい前提でやり直し、新しい条件記録を作ってから再承認を得ます。旧試験のPASSだけを流用して進行可能にしません。

新しい提案が来ただけなら、採否待ちとして扱います。採用する前に承認済み範囲へ混ぜず、採用後に影響と再試験・再承認を整理します。

## 最終判定と次工程

- [ ] C1: 全必須試験と必要な実復元の証跡があり、FAIL・BLOCKED・NOT RUNを残したまま合格にしていない。
- [ ] C2: 対象と版、変更窓、中止閾値、判断期限、戻し、連絡経路が確定している。
- [ ] C3: 残リスク・未解決事項を示し、実際の変更責任者が対象版を承認している。
- [ ] 承認は最新の証跡と有効な先行工程に結び付いている。

未達があれば開始しません。検証不足はPJ03-C1へ、設計不足はPJ02へ、要件や許容範囲の変更はPJ01へ戻します。延期する場合は元の作業日時・新日時・理由・影響を保持し、関係者へ実際に確認します。

| よくある失敗 | 修正 |
| --- | --- |
| CI成功で本番復元も確認済みとする | 対象環境と復元範囲の差を明記し、必要な実機試験を行う |
| 戻し時間を残さず作業窓を使う | 実測をもとに判断期限から逆算する |
| 承認後に小さな変更を混ぜる | 差分と影響を提示し、必要な再試験・再承認を行う |
| リスク欄へ書けば承認不要と考える | 引受人、範囲、日時を含む実判断を確認する |

有効なPJ03承認を得ても、当日の状態が変わっている可能性があります。[PJ04](04-execution.md)で直前に対象・版・バックアップ・連絡・時間をもう一度照合してから、組織の手順に従って作業します。
