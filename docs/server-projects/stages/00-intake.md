# PJ00 受付・担当可否 — 引き受ける前に依頼と責任の範囲を確かめる

[案件運用の入口](../README.md) / [受付票](../templates/intake.md) / [日々の運営](../operations.md) / [次: 要件・見積](01-scope-estimate.md)

この工程の目的は、曖昧な依頼をそのまま作業にせず、「何のために、誰が、どの範囲を、いつまでに判断するか」を揃えることです。相談を受けたこと、技術的に可能なこと、正式に引き受けたことは別々に記録します。

対象は小規模サーバー案件の受付です。学習修了や個人ラボの成功は、本番の作業権限や案件の受注判断を自動的に与えません。実案件は所属組織の受付・契約・情報管理の手順を優先します。

## 入力・担当・出口

| 項目 | 内容 |
| --- | --- |
| 入力 | 依頼文、相談の背景、依頼者が渡すことを許可した資料、希望時期 |
| 主担当 | 依頼を整理し、できること・不足することを説明する案件主担当 |
| 確認者 | `sponsor`。案件として扱うかを判断する案件責任者 |
| 必要に応じて参加 | 技術確認者、既存システムの所有者、運用窓口、調達・契約担当 |
| 出力 | 受付票、確認事項一覧、担当可否の理由、次の担当と期限 |
| 次へ進む条件 | 3条件の証跡を案件責任者が確認し、有効なPJ00承認を記録した |

案件責任者が未定なら、主担当が自分の判断で代わりに承認しません。まず責任者の確定を次の作業にします。CLIに名前を入力することと、その人が本当に判断したことは別です。

| 条件ID | 確認すること |
| --- | --- |
| PJ00-C1 | 依頼の目的・窓口・対象と情報区分を記録 |
| PJ00-C2 | 担当可能範囲と不足能力・権限を確認 |
| PJ00-C3 | 受ける・調査する・断る判断と次の期限を合意 |

## PJ00-C1 依頼の目的・窓口・対象と情報区分を記録

### 1. 受付記録を一件作る

組織が許可した保存先で[受付票](../templates/intake.md)を複製し、案件IDと受付日時を付けます。演習は`training`、許可された実案件は`work`で始め、途中で取り替えません。実案件の記録を公開GitHubへ直接置かないでください。

受付時には、依頼者の原文と主担当による要約を分けます。原文を読みやすく書き直した場合も、元の依頼への参照を残します。電話や口頭の依頼は、日時、相手、聞いた内容、聞き取れなかった点を短く記録します。

### 2. 依頼を五つに分けて聞く

| 観点 | 具体的に確認する内容 | 不十分な記録 | 書き直す方向 |
| --- | --- | --- | --- |
| 目的 | 現在何に困り、何ができれば解消するか | サーバーを作りたい | 誰がどの業務で使い、何が改善するか |
| 利用者 | 使う人、管理する人、影響を受ける人 | 社内の人 | 利用部門・利用時間・運用担当を分ける |
| 対象 | 新規／既存、台数、OS、データ、接続先 | Linux一式 | 変更する対象と触らない対象を列挙 |
| 希望時期 | 希望日、必要な理由、動かせない期限 | 至急 | いつ何を判断・利用できる必要があるか |
| 判定者 | 完成を確認する人、変更を許可する人 | 依頼者が見る | 案件責任者・変更責任者・受領者を分ける |

最初から全設定値を決める必要はありません。値が分からなければ`NOT SET`、事実を確かめていなければ`未確認`と記録します。確認相手と期限を付け、仮定で埋めた欄を確定値として扱いません。

### 3. 情報の持ち方を決める

実構成、顧客名、IP、アカウント、生ログ、秘密値の保存先・閲覧者・共有方法を確認します。公開教材には匿名化した事例を当然に載せてよいわけではありません。再利用・公開する場合も組織の許可範囲を確認します。

| 記録する分類 | 受付段階の扱い |
| --- | --- |
| 公開してよい情報 | 公開済みURLと公開範囲を確認して参照 |
| 案件内共有情報 | 許可された管理先に置き、閲覧対象を明記 |
| 機微な構成・データ | 必要性と取扱担当を確認してから受領 |
| パスワード・鍵・トークン | 受付票本文に貼らず、組織の秘密管理手段を使う |
| 区分が不明 | 未確認として、受領・転送を止めて確認 |

誤って秘密情報を受け取った場合は、さらに転送したり公開Issueへ貼ったりせず、組織の情報事故窓口へ連絡します。学習用の公開質問には、ダミー値と再現可能な最小構成だけを使います。

## PJ00-C2 担当可能範囲と不足能力・権限を確認

### 1. 「できる」を工程ごとに分ける

要件整理、設計、構築、試験、移行、切り戻し、引き渡し、保守の各行に、主担当ができる範囲と確認が必要な範囲を書きます。全部を一人で行う前提を置かず、担当を組み合わせます。

根拠には自分の実測、組織の認定・配置、過去案件で確認された範囲などを使います。自分のラボがUbuntuのコンテナだけなら、Windows実ホストや業務DBの移行まで経験済みとは書きません。[育成システム](../../server-engineer/README.md)の記録は能力確認の参考であり、案件権限の証明とは分けます。

### 2. 不足を四つの種類に分ける

| 不足 | 例 | 埋め方 |
| --- | --- | --- |
| 能力 | 対象OSの復元を説明できない | 検証・経験者の担当・範囲縮小を検討 |
| 権限 | 対象への接続や変更許可がない | 正式な権限申請と承認者の確認 |
| 情報 | 現行構成や停止影響が分からない | 読み取り調査の範囲を別途合意 |
| 時間・人員 | 検証と作業窓に対応できる人がいない | 日程変更、作業分割、支援者を確認 |

不足があることだけを理由に無理に断る必要はありません。ただし、埋める担当・方法・期限がない不足を「何とかする」で引き受けません。

### 3. 既存資料の再利用範囲を確認する

[serverの構築案件パック](https://github.com/ns7jp/server/tree/main/docs/build-package)には要件、設計、パラメータ、構築、試験、引き渡しの見本があります。受付時には「使える項目」と「対象案件では不足する項目」を書きます。

例えば単一VMの監視基盤は、複数拠点の冗長化、24時間有人監視、別組織の認証基盤まで含む見本ではありません。コードや手順書が存在することを、その案件での適合確認に置き換えません。

## PJ00-C3 受ける・調査する・断る判断と次の期限を合意

### 判断を三つから選ぶ

| 判断 | 選ぶ条件 | 依頼者へ伝える内容 | 後続 |
| --- | --- | --- | --- |
| 受ける | 対応範囲と責任が明確で、詳細化へ進める | ここから要件・見積を合意する範囲 | PJ01へ |
| 調査する | 判断に必要な情報だけが不足し、調査が許可されている | 調査対象、操作区分、成果物、担当、期限 | 調査後に再判定 |
| 断る・他担当へ渡す | 能力・権限・資源などの不足を解消できない | 対応できない範囲と理由、可能な代替 | 受付を閉じるか正式に移管 |

ここで「受ける」は、案件を詳細化する意思決定です。価格、納期、契約、本番操作の最終承諾を省略する意味ではありません。正式な権限や契約上の扱いは組織の担当者が決めます。

### 曖昧な依頼への返し方

架空例: 「来週までにサーバーをいい感じにしてほしい」という相談。

> 対象と完了条件を確かめてから作業範囲を決めます。利用者、対象サーバー、困っている現象、停止可能時間、完成を確認する担当を整理します。まず現状確認の範囲をまとめ、確認結果を提示する期限を決めます。

「調査する」を選ぶときも、調査の名目で無制限に変更しません。「設定表示だけ」「ログのこの期間だけ」など、調査の対象と操作区分を受付票に残します。

### 対応できない依頼への返し方

架空例: 業務データの移行について、主担当に復元経験も本番権限もない。

> 現在の担当範囲では、本番データ移行と障害時の復元責任を引き受けられません。現状資料の整理と検証環境での再現準備は担当できます。移行を担当する技術者と変更責任者の確認後に、分担を決める必要があります。

断る理由は依頼者の能力や意図の推測ではなく、担当範囲・確認できた事実・不足条件で説明します。代替を提示する場合も、別担当者の稼働や納期を本人の確認なしに約束しません。

## 受付漏れを防ぐ毎日の扱い

依頼が複数経路から来た場合も、案件IDを一つ決めて関連する受付を結びます。重複案件を勝手に削除せず、どちらが正本かを残します。

受付後は必ず「現在の判断」「待っている相手」「次にすること」「次の期限」を一行で表示します。期限が未定なら`NOT SET`とし、期限を決める作業自体へ担当と確認日を付けます。期限を超えた場合、元の期限を消さず遅延理由を追記します。

保留案件も[日々の運営](../operations.md)で見直します。返事がないことを承認や取消とみなしません。依頼者へ連絡する実際の操作は、案件主担当が許可された経路で行います。

## 架空例 DEMO-A

| 欄 | 演習用の記入例 |
| --- | --- |
| 種別 | training。以下は架空で、実依頼ではない |
| 目的 | 研修担当が監視の画面とログを確認できるUbuntu VMを一台用意する |
| 対象 | 研修専用VM、ダミーデータ、隔離された管理ネットワーク |
| 対象外候補 | 業務データ、インターネット公開、24時間有人対応 |
| 担当の不足 | 受領者、停止許容時間、復元先容量が未確認 |
| 判断案 | 調査する。必要情報の確認範囲を受付票へ記入 |
| 合意・実施 | NOT RUN。実際の合意や成功を意味しない |

この例を自分の案件や学習台帳へコピーして、受注・実行・承認済みにしません。自分が確認した記録だけを提出します。

## 合格・中止・やり直し

- [ ] C1: 目的、依頼窓口、対象、情報区分、原文への参照がある。
- [ ] C2: 担当可能範囲と不足が工程別に記載され、埋め方がある。
- [ ] C3: 判断、理由、判断者、次の担当・期限について実際の確認記録がある。
- [ ] sponsorの承認は、最新の受付票と条件記録を対象としている。

対象所有者が不明、無許可の変更を求められた、機微情報の保存先が未確認、対応不能なのに全責任を求められた場合は進行を止めます。確認事項を明確にして保留または辞退を判断します。

受付内容が変わったら旧票を消さず版を上げ、変わった理由と再判断を残します。[ツール操作](../tracker-guide.md)で再記録した工程と後続承認の扱いを確認します。変更を採用した場合は影響する受付条件を実際に再確認し、後続工程の条件も新しい前提で再実施・再記録します。以前のPASSと承認をそのまま流用しません。

| よくある失敗 | 修正する行動 |
| --- | --- |
| 「了解しました」を本番着手の承諾にしてしまう | 何を了承したか、調査か構築かを明示する |
| 分からない欄を想像で埋める | 未確認とし、確認者と期限を付ける |
| 担当不可を伝えず連絡を止める | できない範囲と理由、代替の可否を説明する |
| 学習実績を業務経験の代わりに扱う | 対象環境、支援量、実際の役割を分ける |

PJ00が有効に承認されたら、[PJ01](01-scope-estimate.md)で対象・除外・受入条件・工数の幅を具体化します。
