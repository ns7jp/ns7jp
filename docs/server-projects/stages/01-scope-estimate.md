# PJ01 要件・見積の合意 — 何をどこまで、どの前提で進めるかを揃える

[案件運用の入口](../README.md) / [前: 受付](00-intake.md) / [見積様式](../templates/scope-estimate.md) / [次: 設計・実行計画](02-design-plan.md)

この工程では、依頼を実行可能な範囲へ分け、作業量・待ち時間・担当者の余力をもとに進め方を合意します。見積は根拠のある予測です。前提が変わると予測も変わるため、数字だけでなく条件と見直す時点を残します。

ここで示す数値は架空の工数例です。価格設定、契約解釈、税務・法務の判断は扱いません。金額・単価・支払条件は組織の担当者が正式な様式で確認し、この教材の金額欄は空欄にしてあります。

## PJ01-C1 対象・対象外・前提・受入条件を合意

### 1. 依頼を観測できる要件へ変える

受付票の目的から、利用者ができるようになることを一つずつ書きます。「速い」「安全」「止まらない」だけでは受入確認ができません。誰が、どの対象で、どの条件のとき、何を見て判断するかを加えます。

[既存の要件定義書](https://github.com/ns7jp/server/blob/main/docs/build-package/00-requirements.md)を参考にしますが、FR/NFRや過去の試験番号を無条件に採用しません。案件内では`REQ-001`などのIDを使い、「案件ID＋要件ID」で識別します。PJ番号は工程の判定、REQ番号は個々の要件であり役割が違います。

| 依頼の表現 | 具体化する内容 | 不明なとき |
| --- | --- | --- |
| 画面を見たい | 利用者、画面、接続元、認証方式、期待する操作 | 画面と利用者を確認する |
| 止まったら戻したい | 対象データ、復元先、許容時間、戻せる時点、確認方法 | 目標値を未設定にして確認 |
| 容量に余裕がほしい | 初期量、増加量、保持期間、試験・復元時の同時使用量 | 実測・見込みの根拠を集める |
| 運用できるようにしたい | 誰が何時に何を確認し、誰へ連絡するか | 運用受領者と対応範囲を決める |

### 2. 対象・対象外・前提を分ける

対象には提供する成果物と作業を、対象外には提供しない機能・時間帯・環境を記載します。前提は相手や他部署が用意する条件です。「先方対応」とだけ書かず、何を・誰が・いつまでに用意するかを残します。

対象外の例は、24時間有人対応、業務データ移行、冗長化、外部公開、追加サーバーです。対象外とすること自体を依頼者・案件責任者に確認します。相手が必要としているものを主担当だけで除外して合意済みにしません。

### 3. 受入条件を先に書く

[要件対応表](../templates/requirements-trace.md)へ、最低限「測定対象」「条件」「期待値」「確認者」を記入します。実施結果はまだ`NOT RUN`です。

架空例: `DEMO-A / REQ-001`「承認された管理端末から、認証後に研修用ダッシュボードを開ける」。受入では、指定管理端末からの成功と、認証なしでの拒否を確認する、と定義します。

数値目標が未確認なら、主担当が測りやすい値を勝手に採用しません。「計画値」「本人の希望」「責任者と合意した値」を分けて記録します。測定条件を伴わない性能値や復旧秒数を他案件から流用しません。

## PJ01-C2 作業分解・見積幅・依存・納期と費用の前提を整理

### 1. 成果物からWBSを作る

WBSは、必要な作業を抜けなく小さく分けた一覧です。「構築一式」ではなく、担当と完了の証拠を付けられる単位にします。初学者は半日〜1日程度で結果を確認できる大きさから始め、調査で分からない作業は先に調査タスクを置きます。

見落としやすいのは、アクセス申請、レビュー対応、検証環境の準備、バックアップ・復元試験、作業リハーサル、受領者の操作、初期保守、文書修正、片付けです。コマンドを実行する時間だけを見積もりません。

### 2. 三点の幅と根拠を付ける

各作業に、順調な場合のO、通常想定のM、不明点や手戻りを含むPを付けます。いずれも**作業する人の工数**です。確率や保証を意味しません。Pを超える可能性がある未調査事項は別に残します。

以下は架空例DEMO-Aの工数です。実案件の見積根拠や学習者の実績ではありません。

| WBS | 作業・完了の目印 | O時間 | M時間 | P時間 | 先行作業 |
| --- | --- | ---: | ---: | ---: | --- |
| WBS-001 | 接続・権限準備の完了確認 | 1 | 2 | 4 | 受付 |
| WBS-002 | 要件と受入条件の合意版 | 2 | 4 | 6 | WBS-001 |
| WBS-003 | 設計・試験・戻し計画のレビュー | 3 | 5 | 8 | WBS-002 |
| WBS-004 | 検証環境の構築 | 2 | 4 | 8 | WBS-003 |
| WBS-005 | 必須試験と別対象への復元確認 | 3 | 5 | 10 | WBS-004 |
| WBS-006 | 変更承認、対象作業、事後確認 | 2 | 3 | 5 | WBS-005 |
| WBS-007 | 受領者の操作と引き渡し | 2 | 3 | 5 | WBS-006 |
| WBS-008 | 初期保守の確認・終結記録 | 2 | 4 | 8 | WBS-007 |
| 合計 | 同じ担当が順に行う工数の例 | 17 | 30 | 54 | 待ち時間は別 |

WBSの根拠には、既存手順の適用範囲、実測した準備時間、初めて試す部分、レビュー回数の想定を残します。裏付けがない精密な小数より、「どこが不確かか」を説明できる幅を優先します。

### 3. 工数と日程を分ける

8時間の作業があっても、作業者の空きが1日2時間なら1日では終わりません。承認・調達・変更窓を待つ時間も別に足します。複数担当の工数合計を、そのまま経過日数に変換しません。

架空例: 週12時間を配分でき、定常対応3時間と調整1時間を見込むなら、案件作業へ使えるのは週8時間です。Mの30時間だけでも約4週の枠が必要です。承認待ち、指定された変更日、受領者の都合は別に考慮します。これは納期の約束ではありません。

| 日程へ反映するもの | 記録の仕方 |
| --- | --- |
| 先行作業 | 完了を待つWBS-ID、待つ理由 |
| 他者への依頼 | 相手、依頼日、回答期限、未回答時の調整先 |
| 担当者の余力 | 既存案件・定常対応を引いた実行可能時間 |
| 変更窓 | 対象側が変更を受け入れられる日時 |
| 手戻り | 何の不確かさに対して、どこで見直すか |

依存先が未確定なら、確定納期ではなく条件付きの候補として示します。遅延時に他案件の約束を勝手に動かさず、[日々の運営](../operations.md)で案件責任者に優先順位の判断を求めます。

### 4. 技術的な容量を見積もる

工数の容量と、サーバーのCPU・メモリ・ストレージ容量を分けます。ストレージは稼働データだけでなく、ログ保持、バックアップ、別対象への復元、更新時の一時領域を含めて見積もります。

架空例の考え方: `必要量 = 初期データ + 増加見込み × 保持期間 + 同時に保持するバックアップ + 復元先 + 一時領域 + 合意した余裕`。圧縮率や増加量を未実測で固定せず、根拠・単位・時点を付けます。空き容量が足りないのに「復元できる計画」としません。

### 5. 費用の前提と追加時の扱いを揃える

工数、外部サービス、ライセンス、調達、保守期間など、費用に関わる範囲を担当者へ渡します。金額・単価・請求条件は正式な権限を持つ担当者が確認し、合意した見積書の参照を残します。

追加サーバー、追加データ移行、休日作業、対象OS変更などの変更が出たら、工数・日程・費用への影響を提示し、採否と追加負担の合意を得るまで追加範囲を実施しません。「軽微だから無料」「あとで請求できる」と主担当が推定しません。

## PJ01-C3 役割・変更扱い・連絡と合意版を確定

役割は、作業する人と判断する人を分けます。一人の名前が複数役割に入る場合も、どの判断をどの立場で行ったかを明記します。工程確認は共通仕様どおり、案件主担当と異なる確認者が行います。

| 決めること | 最低限残す内容 |
| --- | --- |
| 作業と確認 | 主担当、技術確認者、変更責任者、受領者、運用受領者 |
| 連絡 | 通常連絡先、緊急時の経路、対応時間、代理担当 |
| 変更依頼 | 誰が受け、誰が影響を見積もり、誰が採否を決めるか |
| 合意版 | 版番号、日時、対象範囲、参照資料、確認者と確認記録 |
| 有効条件 | 前提が変わったらどの項目を再合意するか |

口頭合意があった場合も、内容を確認可能な記録へまとめ、組織の手順で相手の確認を取ります。返事がないことを合意とみなしません。台帳のPASSは契約成立や追加費用の承諾を生成するものではありません。

変更提案は[変更・障害対応](../change-incident.md)へ記録します。提案段階と採用後の計画変更を分け、採用時は要件・WBS・日程・費用前提・試験をまとめて更新します。

## 合格条件と止める条件

- [ ] C1: 対象・対象外・前提・受入条件を関係者が実際に確認した。
- [ ] C2: 工数の幅、根拠、依存、担当者の余力、技術容量、費用の前提がある。
- [ ] C3: 役割、連絡、変更手順、合意版とsponsorの実確認記録がある。
- [ ] 金額が必要な実案件では正式見積の参照と有効な確認を示し、教材の空欄を合意済みにしていない。

受入条件がない、必須の資源・権限がない、期限までに検証を入れる余地がない、復元先容量が足りない、追加負担の扱いが未合意の場合は、対象範囲を変えるか保留にします。主担当だけで試験や復元を省いて納期を合わせません。

## よくある失敗と見積のやり直し

| 失敗 | 修正 |
| --- | --- |
| 構築時間だけを見積もる | 調査・レビュー・復元・引き渡し・初期保守をWBSへ加える |
| 作業者を増やせば必ず半分になると考える | 分担可能な作業と依存して順に行う作業を分ける |
| 前提の回答待ちを自分の遅さと混同する | 作業残時間と外部待ち時間を別に記録する |
| 変更依頼を相談のまま実施する | 影響提示と採否・負担の合意を確認する |
| 期限を上書きして遅延を消す | 元期限、現在期限、超過、理由、判断者を履歴へ残す |

見積が外れたら、旧見積を保存したまま実績と差分を記録し、残作業を再見積もりします。使った時間を理由なく残時間から引かず、未完了の成果物を見て判断します。合意が変わったらPJ01を再記録し、後続工程の再確認へつなぎます。

## 合意変更後に再確認する範囲

採用した変更で範囲・前提・日程が変わった場合は、影響工程を再実施・再点検し、新しい条件記録とレビューを取得します。旧条件のPASSを参照するだけで承認を復活させません。提案を受け取っただけの状態と、採用して計画を変えた状態は分けます。

合意版を確定したら、[PJ02](02-design-plan.md)で要件を具体的な構成・手順・試験へ対応付けます。
