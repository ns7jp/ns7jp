# 案件運用の共通仕様

[案件運用の入口](README.md)

この仕組みは小規模サーバー案件の仕事を分解し、記録と判断を次の担当へ渡すためのものです。育成台帳のSE番号と、案件のPJ番号は別です。学習修了から実案件の受注・本番権限・検収を推定しません。

## 工程と記録

工程定義の正本は [workflow.json](workflow.json) です。PJ00〜PJ07、各3条件の24条件を定義します。各工程の条件を満たし、責任を持つ人の確認記録を付けて次へ進みます。PJ03は本番変更を始める前の関門です。

| ID | 工程 | 確認者の役割 |
| --- | --- | --- |
| PJ00 | 受付・担当可否 | sponsor（案件責任者） |
| PJ01 | 要件・見積の合意 | sponsor |
| PJ02 | 設計・実行計画 | technical（技術確認者） |
| PJ03 | 検証完了・本番変更の承認 | change（変更責任者） |
| PJ04 | 本番作業・結果確認 | change |
| PJ05 | 検収・引き渡し | customer（受領者） |
| PJ06 | 初期保守・運用移管 | operations（運用受領者） |
| PJ07 | 終結・振り返り | sponsor |

実案件は所属組織が許可した場所で管理します。この公開リポジトリへ顧客情報・実構成・生ログを置きません。教材内の例はすべて架空です。CLIはローカルの `.local/server-projects/<project>/` へ保存し、ネットワーク送信やサーバー操作を行いません。

## 判定の原則

- 案件は `training`（架空演習）または `work`（許可された実案件）で作成し、後から入れ替えません。新規案件の工程はすべて `NOT RUN`。例示から実績を生成しません。
- 条件記録は `PASS / FAIL / BLOCKED`。証跡ファイルを複製し、SHA-256、対象、実施日時、支援・確認内容を残します。最新の記録を判定に使い、過去の失敗を削除しません。
- 全条件がPASSなら `READY FOR REVIEW`。案件主担当と異なる確認者による、その工程の最新証跡に結び付いた承認があり、先行工程も有効なPASSのときに工程PASSになります。
- 確認者のIDと役割は申告記録です。本人認証、代理権確認、顧客の契約承諾、本番実行許可をCLIが発行するものではありません。
- 条件の再記録で当該工程と後続工程の旧承認を失効させ、再確認を求めます。変更提案の採否待ちと、採用した変更による見直しを区別します。
- 採用変更を明示的に `invalidate` した場合は、指定工程以降の全条件に、その変更後の新しい確認記録を必要とします。旧PASSだけの再承認は認めません。影響がない条件でも、再確認した根拠を新たに記録します。
- 保留・再開・取消は理由と日時を追記します。取消は成功完了ではありません。期限変更は元の期限・旧期限・新期限・理由を残し、超過を消しません。
- 作業一覧は依存関係、担当、見積・残時間、期限、状態、阻害理由を管理します。複数案件の表示は優先度・期限・作業中件数・残作業量を示します。自動で他者の仕事や約束を変更しません。
- 優先度変更は `reprioritize` で理由を追記します。順序の変更だけでは工程承認を失効させません。担当作業の変更は `task-reassign` で旧・新担当を残し、該当工程以降の承認を失効させます。DOINGとDONEはいずれも依存作業のDONEを必要とします。
- 範囲から外す未完作業は `task-withdraw` で別の確認者によるsponsor判断と証跡を記録し、`WITHDRAWN` にします。DONEの実績は取り下げられません。非WITHDRAWNの依存先がある間は拒否し、当該工程以降の全条件に新しい確認記録を求めます。取り下げは作業成功に数えません。
- ファイル・台帳の整合を検査することと、本番の成功、検収、入金を確認することは別です。

具体的なCLIの引数・制限は [ツール操作](tracker-guide.md) を正本とします。承認経路・変更依頼・障害対応・週次配分は [日々の運営](operations.md) と工程手順で補います。
