# 追加依頼・計画変更・障害を扱う

[案件運用の入口](README.md) / [変更票](templates/change-request.md) / [障害票](templates/incident.md)

予定外のことが起きたときも、受付、影響確認、判断、実行、結果確認という流れを残します。変更提案が届いたこと、採用されたこと、実施が承認されたこと、実施結果が合格したことは別の出来事です。

## まず種類を分ける

| 種類 | 見分け方 | 最初にすること |
| --- | --- | --- |
| 質問 | 現在の合意内容を確認したい | 正本の版と該当箇所を示す。不明なら調査担当を決める |
| 不適合 | すでに合意した受入条件を満たさない | 該当REQ/TESTと実出力を確認し、修正・再試験を計画 |
| 追加・変更要求 | 合意した範囲、条件、対象、期限が変わる | CHG票を起票し、影響を見積もる |
| 障害 | 利用者影響やサービス停止が起きている | 影響と責任者を確認し、合意した障害対応を開始 |
| 改善案 | 今すぐ合意を変えるとは決まっていない | 採否待ち欄へ置き、担当判断まで実施しない |

「バグか追加か」を言葉だけで決めず、合意済みの要件と受入条件へ戻ります。合意が曖昧なら、その曖昧さを記録して判断者へ渡します。

## 変更要求の一巡

1. CHG-001のような案件内IDを付け、提案者、受領日時、目的、変更したい内容、希望期限を記録する。状態は `PROPOSED`。
2. 現行の要件・設計・対象版と比較し、変わる成果物と試験を列挙する。状態は `ANALYZING`。
3. 工数幅、納期、停止、費用確認、データ、運用、他案件への影響を整理する。小さい変更でも戻し方を確認する。
4. 『採用する／条件を変えて採用する／保留する／採用しない』の選択肢を責任者へ渡す。返答期限まで `AWAITING DECISION` とする。
5. 採用判断の根拠と対象版を保存する。採用なら `ACCEPTED`、不採用なら `REJECTED`、判断待ちなら `DEFERRED`。口頭判断は、内容と確認者を記録して組織の方法で確認する。
6. 採用した変更で戻るべき最初の工程を決める。要件変更はPJ01、設計変更はPJ02、試験結果や作業窓の変更は少なくともPJ03から再確認する。影響が受付の担当範囲へ及ぶならPJ00へ戻る。
7. CLIの `invalidate --from PJxx` を変更票の証跡付きで記録し、該当工程以降の古い承認を失効させる。指定工程以降の全条件に、変更後の新しい確認記録を付ける。影響なしと判断する条件にも、そう判断した根拠を新たに残す。旧PASSだけの再承認は拒否される。
8. 必要な承認後に実施し、変更票を `IMPLEMENTED` とする。受入条件の再試験と結果確認後に `VERIFIED` とする。実施しただけでVERIFIEDへ進めない。

上の変更票状態は様式の手動運用です。CLIは変更の採否ワークフローを自動実行せず、採用後の見直し・再記録・承認の失効を扱います。保留案を採用済みと入力しないでください。

範囲縮小で不要になった未完作業は `task-withdraw` で扱います。別の確認者のsponsor判断と変更の証跡が必要です。旧状態と残時間を残し、WITHDRAWNへ変更します。依存先が残れば拒否されるため、関係する作業を逆順に見直します。これはDONEの代わりに成功を記録する操作ではなく、当該工程以降の新しい条件確認も必要になります。

## 変更の例

架空のDEMO-Aで『監視VM1台』の合意後に『DBも同じVMへ追加したい』と依頼された場合、単にコンテナを一つ増やす作業にはしません。

- メモリーとディスクの容量、監視とDBの停止影響、バックアップ対象を確認する。
- DBの利用者・権限・保存データ・復元条件・運用担当を要件へ追加する必要があるか整理する。
- DES、設定値、構築手順、必須試験、引き渡し説明の変更を列挙する。
- 元の納期でできる範囲、別納期で追加する案、別案件に分ける案を出す。
- 採用されるまでは現在の合意範囲を変更しない。採用後はPJ01以降を再確認する。

この例に採用や成功の実績はありません。見積時間・金額・納期は実際の調査と担当者の判断で記入します。

## 障害時の最初の動き

障害票へ、案件/サービスID、検知日時、利用者への影響、現在分かる範囲、直前の変更、調査担当、連絡担当を記入します。複数人が同じ設定を同時に変えないよう、指揮をする人と操作する人を分けて明示します。少人数で兼務する場合も、誰が判断を担うか残します。

組織の重大度・連絡規則が優先です。次の例は分類の練習用です。

| 分類の例 | 状況 | 判断・連絡 |
| --- | --- | --- |
| 重大 | 広範な利用不能、データ損失の疑い、安全な復旧経路が不明 | 指定責任者へ即時連絡。変更を増やす前に操作範囲を合意 |
| 高 | 一部利用者が主要機能を使えない、代替手段が限定 | 影響拡大の監視、復旧案、次回報告時刻を決める |
| 通常 | 利用可能な代替があり、影響が限定 | 調査・対処の担当と期限を割り当てる |

何分以内に通知・復旧するかは、合意した対応時間帯・SLA・当番体制から決めます。この教材の時間例を契約上の約束に置き換えません。

## 復旧へ進める順序

1. **事実を保存**: 発生・検知時刻、エラー、メトリクス、変更履歴を記録する。秘密値を含む原本は許可された場所へ残す。
2. **範囲を絞る**: 全体か一部か、直前に変化した層はどこか、正常な比較対象はあるかを確認する。
3. **仮説を一つ選ぶ**: 観測事実、想定原因、確認操作、想定出力を分ける。未確認の推測を原因確定と書かない。
4. **戻し・代替を判断**: 戻す版、データ整合、必要時間、停止範囲、再度失敗したときの連絡先を確認する。
5. **認められた範囲で操作**: 対象と時刻、操作担当、実出力を残す。未知の破壊的操作をその場で追加しない。
6. **利用者視点で再確認**: プロセス起動だけで復旧とせず、合意した応答・認証・データ・通知などを確認する。
7. **監視と連絡**: 回復した範囲、未確認事項、再発監視、次の更新時刻を共有する。送信した事実は実際の記録で残す。

本番変更中に失敗した場合は [PJ04](stages/04-execution.md)の中止閾値と戻し手順に従います。緊急変更の承認経路が事前にない場合、CLIのレビュー欄を埋めて権限ができたことにはできません。指定責任者へ判断を求めます。

## 復旧後を取りこぼさない

復旧確認と、原因解明と、再発防止の完了は別です。障害票は各日時を分けます。再発防止は担当・期限・確認方法を付け、必要なら新しい変更票へつなぎます。

振り返りでは、人を責める説明より、検知、手順、権限、設計、判断にどの条件が不足していたかを調べます。『注意する』で終えず、たとえば『切戻し試験をPJ03の対象版へ結び付ける』のように検査可能な改善へ変えます。

障害中に止めた別案件の約束も確認します。再開条件、変更後の担当、更新した期限を残し、黙って遅延を他案件へ移しません。
