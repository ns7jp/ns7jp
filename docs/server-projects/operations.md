# 日々の案件運営

[案件運用の入口](README.md)

案件をさばくとは、受付数を増やすことではありません。約束した成果へ向けて、いま誰が何を判断・実行すべきかを見えるようにし、完了まで残さず扱うことです。まず一人の主担当と確認者がいる小規模案件を想定します。

## 入口を一つ決める

依頼は社内チケット、許可された案件表など、決めた窓口へ集めます。チャットや口頭で来た依頼も、担当者が受付票へ戻します。受付した時点では納期や受注を確約しません。

受付に必要な最小情報は、案件ID、依頼日時、目的、窓口、対象、希望期限と理由、影響、主担当候補、次の確認日時です。分からない値を推測せず、質問の担当と期限を付けます。同じ依頼の重複は元IDへ結び、件数を水増ししません。

業務原本がすでにある場合は、CLIを別の正本にしない運用を選べます。CLIには演習だけを入れ、社内チケットの項目へ本手順を対応させます。二重管理するなら、どちらが正本で、誰がどの時点に同期するかを先に決めます。

## 朝15分の確認

1. 利用者影響のある障害と、実行中の本番変更を確認する。対応責任者が決まっていなければ、通常の構築より先に連絡経路を確定する。
2. 今日の約束、超過した期限、変更窓、回答期限を読む。合意期限と単なる希望期限を区別する。
3. ブロック中の作業について、依存先・問い合わせ担当・次回確認時刻を見る。
4. 作業中の数を数える。初期の目安は一人2件。新たに始めるなら、どれを終えるか、止めるかを決める。
5. 今日の作業を、実際に使える時間へ割り当てる。作業名だけでなく「どの成果物を何時までにどこまで」を書く。
6. 判断が必要な内容は、事実・選択肢・推奨・判断期限を担当者へ渡す。送信や返答の記録を残す。

15分は会議時間の初期目安です。無理に全案件の経緯を読み上げず、変化・障害・判断に絞ります。

## 優先順位の決め方

CLIの優先度は1が最優先、3が後です。以下は初期の運用案であり、契約SLAや組織の障害区分がある場合はそちらへ対応付けます。

| 優先度 | 判断材料 | 取る行動 |
| --- | --- | --- |
| 1 | 利用者への重大な影響、合意済みの変更窓、他案件を止める依存 | 責任者へ報告し、他の約束への影響も含めて配分を決める |
| 2 | 合意期限が近い通常案件、先行準備が必要な作業 | 期限から逆算して作業枠を確保する |
| 3 | 合意期限まで余裕のある改善、調査候補 | 空き枠や計画した調査枠へ置く |

同じ優先度なら、超過・最も早い合意期限・依存の解消効果を見ます。CLIの並び順は判断材料です。顧客との約束、影響の規模、担当者の能力を自動判定しません。優先度の変更は `reprioritize` で理由を追記し、案件原本へも残します。順序以外の範囲・納期が変わるときは、その合意と見直しを別に行います。

## 週の容量を見積もる

使える時間から休暇・会議・当番など確定した時間を差し引きます。さらに割込み・レビュー・調査の余白を別に取ります。余白の割合を全員一律に固定せず、過去の記録から見直します。

架空例: 週40時間のうち会議・定例8時間、当番・割込み用8時間を確保すると、予定作業へ割り当てる枠は24時間です。A案件12時間、B案件8時間、C案件4時間なら24時間に収まります。これは計画例で、実勤務や実績ではありません。

案件Aの全残作業が30時間でも、翌週の割当を12時間にできます。**残作業の合計をそのまま翌週の約束にしない**ことが大切です。CLIの `board --capacity 24` は残作業量と容量の参考表示です。休暇、作業窓、担当ごとの割当やカレンダーは自動最適化しません。[週次配分票](templates/portfolio-review.md)で翌週の割当を決めます。

## 作業を小さくする

作業は「設計をする」ではなく「REQ-003の通信経路とFWルールをDES-002へ書き、技術確認を依頼する」のように、出口が見える単位にします。目安は1〜4時間程度です。長い作業は調査、作成、試験、確認に分けます。時間幅は自分の実績で調整します。

最低限の作業項目は、ID、属するPJ工程、成果物、担当、予定時間、残時間、期限、前提作業、完了条件です。見積時間と残時間は別です。2時間使ったから残時間を2時間減らすとは限りません。調査で想定が増えたら残時間を増やし、理由を残します。

| 状態 | 意味 | 抜けるために必要なもの |
| --- | --- | --- |
| TODO | まだ着手していない | 前提作業の完了、実行枠 |
| DOING | 現在作業している | 成果物と確認結果 |
| BLOCKED | 依存・判断・環境などで進まない | 阻害理由、解消担当、次回確認 |
| DONE | 決めた作業の出口を満たす | 実際の成果物・確認証跡、残時間0 |
| WITHDRAWN | 合意した範囲変更で不要となった未完作業 | 別の確認者によるsponsor判断、取り下げ証跡、残時間0。実施成功ではない |

DONEは工程PASSでも顧客検収でもありません。作業一覧に載せ忘れた試験は、作業件数がすべてDONEでも必要です。工程の24条件を別に確認します。

担当を変更する場合は、受ける人に内容と期限を確認し、`task-reassign` で旧担当・新担当・理由を残します。該当工程以降の古い承認が失効するため、担当変更の影響も含めて再確認します。CLIが本人への連絡や受領を代行することはありません。

採用した範囲縮小で未完作業が不要になった場合は `task-withdraw` で理由・sponsor確認・証跡を残します。非WITHDRAWNの依存先がある間は取り下げできません。依存先から順に計画を見直し、必要な作業は新しいIDで再編します。DONEの実績を取り下げて消す操作は拒否されます。取り下げ後は該当工程以降の全条件を新たに確認し、範囲縮小を反映した承認を揃えます。

## 止まった作業の扱い

「回答待ち」だけでは誰も動けません。『DNSレコード申請の回答待ち、窓口A、次回確認は9月8日10時、遅れるとPJ03の確認が1日後ろへ移る』まで書きます。日付は案件ごとに実際の値へ置き換えます。

期限を超えたら、元の期限、経過日数、影響、問い合わせ済み日時、次の判断者を残します。新しい期限だけに上書きしません。CLIの `reschedule` は期限変更を追記しますが、相手との再合意を代行しません。合意の記録は受付・変更票へ結びます。

案件全体の作業を止めるなら `hold`、再開条件が整ったら `resume` を記録します。再開時は承認対象版・作業窓・人員・バックアップの有効性を再確認します。古い承認が条件変更で使えなくなったら `invalidate` で必要な工程から見直します。

## 夕方10分と週末30分

夕方は実施内容、実績時間、残時間、想定との差、次回の一手を残します。「進捗80%」より『必須10試験中7件PASS、2件NOT RUN、1件FAIL』の方が判断できます。実際の試験一覧に基づいて数えます。

週末は次を [週次配分票](templates/portfolio-review.md)へ記録します。

- 完了・検収・取消になった案件と、それぞれの根拠。
- 工程待ち、回答待ち、試験失敗など、止まった理由の違い。
- 今週の予定時間・実績時間・残時間。実績未記録を0時間としない。
- 次週の担当別の空き時間、割当、余白。過剰なら範囲・期限・人数を判断者へ相談する。
- 同じ原因の再発と、採用する改善を一つ。案は採否待ち欄に置く。

## 運営の数字を読む

| 指標 | 数え方 | 誤解しやすい点 |
| --- | --- | --- |
| 作業中件数 | DOINGの作業数 | 人数の異なるチームを単純比較しない |
| 滞留時間 | BLOCKEDになった時刻から現在まで | 期限超過と待ち時間は別 |
| 納期差 | 実際の完了日と合意期限の差 | 取消や未完了を完了0日として数えない |
| 工数差 | 記録済み実績と見積の差 | 欠測を0としない。追加範囲を分ける |
| 再作業 | 合意条件の不適合によりやり直した時間 | 承認された追加要求と分ける |

CLIが自動算出しない指標は原本の時系列から集計します。上記を測っていなければ欠測と書きます。件数目標のために承認や試験を省かず、遅れの原因を次の見積と計画へ返します。
