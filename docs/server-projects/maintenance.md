# 案件運用システムを保守する

[案件運用の入口](README.md)

## 導入時の確認

案件責任者と主担当で、対象案件、既存原本との関係、役割、承認経路、記録場所、保守の対応時間帯を合意します。まず架空1案件で入力と報告を試し、実案件の原本を保存できる環境かを確認します。

導入したことを理由に、既存の契約・変更承認・情報管理を置き換えません。実案件では必要な社内レビューを受け、本番操作は承認されたツールと手順で行います。

## 定義を変更するとき

工程と条件の正本は [workflow.json](workflow.json) です。PJ条件を変えるときは、8工程の手順、様式、CLI判定、テスト、例の対応を確認します。CLIは保存した定義との不一致を検出するため、既存案件が突然新条件で合格にならないようにします。

定義に変更がある場合、旧版のリポジトリと台帳を保管し、新版の演習用案件で検証します。この版には既存台帳を自動移行する機能はありません。過去記録を新しい実施として再作成せず、必要な移行は原本を保持する仕様と検査を別途設計します。

## バックアップと復元確認

CLIの台帳と証跡は `.local/server-projects/` 配下です。Gitへ入らないため、GitHubへ教材を保存しても個人台帳のバックアップにはなりません。業務では組織のバックアップと暗号化の手順を使います。

演習データなら、すべての書き込みを終えた状態で、台帳と証跡を一緒に別の許可された場所へコピーします。ロックファイルが残った場合は実行中プロセスを確認し、原因を調べてから扱います。書き込み中のコピーや、証跡だけ・JSONだけのコピーを完全なバックアップとしません。

復元確認は元の台帳へ上書きせず、同じ教材版の別コピーに復元し、`check --project ID` と `report --project ID` を実行します。案件数、イベント数、最新状態、添付の存在とハッシュを照合します。実際に確認した日、対象、版、結果を残します。この手順を文書化しただけでは復元試験済みになりません。

## 定期的な見直し

| 頻度の初期目安 | 確認すること | 根拠 |
| --- | --- | --- |
| 作業日 | 期限、滞留、WIP、次の担当 | 案件ボードと作業原本 |
| 週次 | 容量、工数差、依存、再作業 | 週次配分票 |
| 月次 | 手順の不足、繰り返す障害、外部参照の変化 | 改善候補・公式資料 |
| 教材更新時 | 台帳、リンク、書式、既存育成機能 | ローカル検査とCI |
| 案件終結時 | 移管、保管、アクセス、改善 | 終結票 |

これは運用周期の提案です。OSスケジューラーや通知の定期実行は設定していません。実際の開催・確認がなければ未実施とします。

## 検査コマンド

リポジトリのルートで実行します。台帳の構造、判定、リンクを確認し、サーバー操作は行いません。

```powershell
node scripts/server-projects.mjs check
node --test tests/server-projects.test.mjs
node scripts/check-engineer-links.mjs
node --test tests/server-engineer.test.mjs
```

GitHub ActionsはNode.js 22で案件・育成の検査を行います。既存のdocs-checkでMarkdown、Mermaid、内部リンクと見出しを確認します。外部リンクのチェックは参考扱いです。

## この版の境界

このCLIはローカルで一つの共有ディレクトリを扱います。複数端末間の同期・競合解決、サインイン、電子署名、承認者の本人確認、サーバー実行、メッセージ送信、カレンダー配分、請求・入金確認は実装していません。小さな組織の正式な原本を置き換える前に必要な要件を確認します。

単体テストは合成した入力で判定の失敗条件を確認します。実案件、実顧客、初心者の一巡利用、第三者の受領、長期保守の実績は、それぞれの実施証跡があるまで未確認です。
