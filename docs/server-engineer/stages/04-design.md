# SE04 要件を設計・試験へ落とす

[育成システム](../README.md) / [前段 SE03](03-services.md) / [次段 SE05](05-automation.md) / [評価手順](../assessment.md)

**完成像は「別の人が、何を作り、何を確認すれば受け入れられるか判断できる構築案件一式」です。** SE03で動かした構成を題材に、要件、構成図、設定値、試験、切戻し、引き渡しをつなぎます。文章量ではなく、実環境との一致と判断の再現性を評価します。

目安はW13〜W16です。24週間は学習の計画枠、その後4〜8週間は総合課題の計画枠であり、期間が経過しただけで一人前になる保証ではありません。本段階の提出物は学習成果であり、顧客の承認済み設計や就業経験とは扱いません。

## 開始条件と教材

- SE03が本人以外の評価者の確認を経てPASSである。特に通信制御、DB権限、別DBへの復元の実測記録がある。
- 今回の学習VM、管理端末、ラボネットワーク、戻せる構成版を特定できる。
- 仮想の依頼者役を依頼できる人を決める。依頼できなければ要件は「本人の案・合意待ち」で進め、受領や承認を代筆しない。
- [設計パック](../templates/design-pack.md)、[作業記録](../templates/work-record.md)、[引き渡し記録](../templates/handover.md)を個人記録先に複製する。各欄の未実施を結果で埋めない。

既存の[構築工程の実務ドキュメント](../../learning-plan/03-build-process.md)を記載項目の辞書として使います。[server-monitor構築案件パック](https://github.com/ns7jp/server/tree/44c52e733826b9b5239918c05010b8b68b60346c/docs/build-package)には要件から作業結果報告までの実例があります。実例に書かれたアドレス、時間、担当者、既定値は自分の環境へ採用した値ではありません。参照元のGit SHAと自分が採用・変更した箇所を記録します。

| 週 | 主作業 | 週末に説明すること |
| --- | --- | --- |
| W13 | SE04-C1：依頼を質問と測定できる要件に分解 | 「使いやすい」「止まらない」をどの試験に変えたか |
| W14 | SE04-C2：構成図、通信表、パラメータ、選択理由 | なぜその構成が要件を満たし、どこは満たさないか |
| W15 | SE04-C3：正常・異常・復旧試験と追跡表 | どの要件がどの実測証跡で確認できるか |
| W16 | SE04-C4：変更、切戻し、引き渡しの通し確認 | 途中で止める条件と、前の状態へ戻った証拠 |

## 用語を作業に結び付ける

| 用語 | この課題での意味 | 取り違えを防ぐ問い |
| --- | --- | --- |
| 要件 | 利用者や運用者が必要とする結果 | 「Nginxを使う」は必要な結果か、実現方法か |
| 基本設計 | 要件を実現する構成・役割・境界 | 入口を止めると誰が使えなくなるか |
| 詳細設計 | 実際に設定する名前・値・配置先 | 手順書の値と実機の値は一致するか |
| 非機能要件 | 性能、復旧、権限、保守などの条件 | 何台から、何件、何分測って確認するか |
| 受入条件 | 依頼者が受け取る判断に使う条件 | 誰が、どの証拠を見て、どう判定するか |
| 追跡表 | 要件から設計・試験・証跡をたどる表 | 一つの要件を最後までたどれるか |
| 切戻し | 変更前のサービス状態へ戻す手順 | コードを戻した後のデータと設定は整合するか |

## SE04-C1 要件・対象外・非機能の測定条件を合意用に作る

**目的：** あいまいな依頼を、作業開始前に確認できる条件へ変えます。「速いサーバーを作る」で終わると、作った後に完成を判断できません。

**前提：** SE03の構成と測定できる項目を説明できること。依頼者役に見せる場合も、実際の会社情報や顧客データを使わず架空の業務にします。

**実施手順：**

1. 「学習用の在庫一覧を、ラボ利用者が閲覧し、許可された利用者がサンプル在庫を登録する」という依頼文を1段落で書く。既存3層ラボを使う場合、業務機能は[実装されている一覧・登録API](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/labs/three-tier/ap/app.py)の範囲に合わせる。
2. 利用者、操作、利用時間、保存する情報、許容停止、許容データ損失、運用担当、問い合わせ先、環境制約の9項目を質問票にする。不明な答えは未確認と書き、設計者が顧客の意向を作らない。
3. 機能、通信、権限、性能、復旧、運用に要件ID `REQ-001` から番号を付ける。このIDは案件内のIDで、育成条件ID `SE04-C1` とは役割が異なる。
4. 各要件に「理由」「優先度」「確認方法」「受入条件」「合意状態」を付ける。優先度は必須・希望・対象外を使い、必須が未確定なら作業前に戻る。
5. 対象外を明示する。例えば外部公開、実個人情報、商用可用性保証、決済、多拠点冗長化、クラウド契約はこのローカル学習案件に含めない。
6. 依頼者役に読み上げて解釈の違いを記録し、修正前後を残す。相手の確認がなければ「合意用案」のまま提出する。

次は**設計の記入例**です。目標欄をそのまま実績に写しません。

| 案件内要件 | 目標案 | 測定条件 | 実際の結果の初期値 |
| --- | --- | --- | --- |
| REQ-001 一覧参照 | 既知のサンプル3件を正しく表示 | 指定したラボclientからGET、内容も照合 | NOT RUN |
| REQ-002 権限制御 | 許可された入口は成功、不許可経路は拒否 | 接続元・資格情報・対象ポートを試験ごとに固定 | NOT RUN |
| REQ-003 応答 | 一覧GET 100回のp95が1秒以内 | 単一client・並列数1・データ100件・測定前に5回予熱、失敗数も別集計 | NOT RUN |
| REQ-004 復元 | 宣言したRTO・RPO以内 | 別DB/別VM、障害検知から利用者操作復帰までの時刻を採録 | NOT RUN |

**期待結果：** 必須要件に未定義の合格条件がなく、測れない約束は対象外または再検討になっている。目標は学習ラボの仮説であり、実測によって未達を判定できる。

**失敗・戻し方：** 実装されていない機能を必須にしていたら、依頼者役と範囲を見直す。試験後に目標を緩める場合は、元目標・未達結果・変更理由・変更後の適用日を残し、過去の失敗を合格へ書き換えない。

**提出物：** 要件一覧、質問と回答、対象外一覧、目標と測定条件、合意状態。`SE04-C1` の作業記録から各ファイルへ結ぶ。

**自分の言葉で説明：** 「CPUを2個にする」はなぜ要件ではなく設計になり得るか。p95が目標以内でも失敗要求があれば何が問題か。未確認の要件をどう管理するか。

**補習：** [構築工程の実務ドキュメント](../../learning-plan/03-build-process.md)で工程の違いを読み、SE03の一つの試験を「要件→測定条件→期待結果」に書き直す。説明できるまで要件を増やさない。

## SE04-C2 構成・設定値・技術選択理由を整合させる

**目的：** 図に描いたもの、手順で設定するもの、実際に動くものを一致させます。

**前提：** SE04-C1の必須範囲が定義済みであること。変更を加える前のVM状態と接続経路を採録済みであること。

**実施手順：**

1. 構成図に管理端末、VM、ネットワーク、Web/AP/DB、監視、バックアップ先を載せる。同一VM内のコンテナと別VMを異なる枠で描く。
2. 矢印に接続元・接続先・名前・ポート・方向・用途を付け、通信一覧へ転記する。管理経路と利用者経路を分ける。
3. パラメータ表に設定ファイル、設定項目、採用値、採用理由、取得方法を記載する。秘密値そのものは入れず保管場所と取得担当を書く。
4. 次の5点について「比較した案→選択→理由→弱点→見直す条件」を1段落ずつ書く。単一VMか複数VMか、OS、サービス実行方式、入口と認証、バックアップ方式。
5. 実機の読み取り結果と照合する。OS、NIC、経路、待受、サービス、コンテナ構成、マウント、時刻同期の採録をSE01〜03の手順で行い、差分表へ載せる。
6. 図と表の全ホスト名・ポートを相互確認する。存在しないDNSやゲートウェイを記入例から持ち込まない。

| 確認したい境界 | 図に必要な情報 | 実機で確かめること |
| --- | --- | --- |
| VMとホストPC | 仮想スイッチとNIC接続 | VM識別情報、実IP、到達元 |
| WebからAP | 名前、ポート、使用ネットワーク | 許可経路の成功、入口からの実応答 |
| WebからDB | 直接接続を許可するか | 許可しないなら道具自体の動作を確かめた拒否試験 |
| データとコード | データの所在、バックアップ先 | Gitだけで戻らないものの一覧 |
| 管理と利用 | 管理者権限、一般利用者の範囲 | 許可される操作と拒否される操作 |

**期待結果：** 一つの通信矢印を選ぶと、設定値と実測出力へたどれる。設定差分は修正済み、または理由と対応期限がある。単一ホスト故障で全層が停止するという限界を説明できる。

**失敗・戻し方：** 図を実環境に合わせるだけで済ませず、要件と設計のどちらが誤っていたかを判断する。意図しない公開範囲や管理接続不能が見つかったら追加変更を止め、SE02で記録したコンソール経路と直前設定で戻す。

**提出物：** 構成図、通信表、パラメータ表、5件の選択理由、実機照合結果。参考にした[基本設計](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/build-package/01-basic-design.md)と自作内容を区別する。

**自分の言葉で説明：** 3つのコンテナは3台のサーバーとどこが違うか。バックアップを同じVMだけに保存すると何が守れないか。設定値を変更するとどの資料を更新するか。

**補習：** [SE02](02-network.md)でclientからDBまでを声に出して追い、[SE03](03-services.md)で各層を一つずつ確認する。一枚の図で説明できないなら新しい製品を追加しない。

## SE04-C3 要件ごとに正常・異常・復旧試験と証跡を結ぶ

**目的：** 「動いた」の一言を、第三者が追える試験と証拠に変えます。

**前提：** SE04-C2の設計と対象が一致していること。異常試験の対象は自分の隔離ラボに限定し、変更前設定と中止条件があること。

**実施手順：**

1. 各必須要件に案件内試験ID `TEST-001` から番号を付け、正常・異常・復旧のどれを確かめるか記載する。該当しない種類は「対象外の理由」を書く。
2. 各試験に実行者、実行場所、事前状態、入力、操作、期待出力、合否判定、後処理、証跡先を付ける。HTTPの200だけでなく内容一致と拒否の理由まで定める。
3. 試験前に期待結果を記入する。正常な状態を採録し、障害を一つだけ加え、観測し、戻し、同じ正常試験を再実行する。
4. 失敗したら失敗の試行を保存する。原因、変更箇所、再実行の試行IDを追記し、最新版だけでなく経緯もたどれるようにする。
5. 追跡表の全必須行を点検する。要件→設計項目→試験→実施時刻→証跡ファイル→判定が一周することを確認する。

| 要件 | 正常試験 | 異常試験 | 復旧試験 | 証跡で必要な内容 |
| --- | --- | --- | --- | --- |
| 一覧参照 | 既知データの表示一致 | 検証用AP停止中の利用者影響 | APを戻した後の再参照 | HTTP結果と本文、層別ログ、時刻 |
| 経路制御 | 許可元から成功 | 不許可元から拒否 | 意図的に変更したルールの復帰 | 接続元、診断道具の動作、経路、出口状態 |
| 復元 | バックアップが読める | 別の試験用コピーで不完全バックアップを拒否 | 別DBへ復元して内容照合 | バックアップ時刻、ハッシュ、対象DB、利用者操作 |

**期待結果：** 必須要件が未実施・失敗・成功のどれか明確で、証跡のない成功がない。コンテナ試験とVM試験、静的検査と実行試験を分けて記録している。

**失敗・戻し方：** 道具が見つからないために通信試験が失敗した結果は「拒否成功」にしない。先に道具を直す。復元先を特定できない、バックアップが読めない場合は破壊操作へ進まずBLOCKEDを残す。実験後は対象の正常性を確認し、途中状態を次の試験に持ち込まない。

**提出物：** 試験仕様、追跡表、正常・異常・復旧それぞれの実行記録、未達一覧。書式は[既存試験項目書](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/build-package/06-test-specification.md)も参照するが、過去の著者結果を自身の試行へ写さない。

**自分の言葉で説明：** 合格条件を実施後に決めるとなぜ問題か。疎通不能と権限制御の成功はどう違うか。件数が同じだけでデータ復元完了といえるか。

**補習：** SE03の別DB復元を1件選び、他人が追える粒度で試験を書き直す。証跡を閉じて期待結果を説明し、再度開いて一致を確かめる。

## SE04-C4 変更・切戻し・引き渡し手順を第三者が追える形にする

**目的：** 成功する手順に加えて、失敗したときに止まり、戻し、事情を伝えられる手順を作ります。

**前提：** SE04-C3の現行版が試験済みであること。変更は例として入口設定の小さな変更1件を選び、データ形式を変える大規模移行は初回に選ばない。

**実施手順：**

1. 変更票に目的、対象、現在の版、変更する版、差分、影響時間、担当、開始条件、確認者を書く。
2. 作業を「変更前確認→保存→構文確認→適用→利用者試験→運用確認」に分解する。各行に実行場所、期待結果、中止条件、戻す手順番号を付ける。
3. 切戻しの時間上限を宣言する。「エラー時」だけでなく、接続不能、想定外の対象、必須試験の失敗、終了予定までに戻せない見込みを具体化する。
4. 自分で一度通常変更を実施し、もう一度は決めた時点で切戻す。旧版への復帰後に利用者操作と保存データを照合する。再起動やDB操作が必要なら別作業として影響と復旧準備を明記する。
5. 引き渡し資料に起動・停止、確認場所、バックアップと復元、よくある異常、連絡内容、既知の制限、運用担当・期限をまとめる。認証情報は資料本文に書かない。
6. 本人以外の人に、資料だけで「次にどの確認を行うか」を追ってもらう。読み手が質問した箇所を欠陥として記録して直す。本段階は机上確認でもよいが、SE07の実操作による受領とは区別する。

**期待結果：** 第三者が対象・手順・中止・復旧を迷わず特定でき、切戻した後の正常性に実測記録がある。機器名や版が仮記入のまま残っていない。

**失敗・戻し方：** 読み手が止まったら口頭で補い、その内容を資料へ反映する。書いていなかった操作は記録する。切戻し失敗は手順が未完成の証拠として残し、旧状態を再構成できるまで変更練習を増やさない。

**提出物：** 変更票、通常変更と切戻しのログ、引き渡し資料、机上確認の質問と修正。参考は[変更・切戻し計画](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/build-package/08-change-rollback-plan.md)。

**自分の言葉で説明：** 作業を開始しない条件、途中で止める条件、切戻しが完了した条件をそれぞれ挙げる。作業担当と受入判断者の責任は何が違うか。

**補習：** 5行だけの変更手順を作り、1行ずつ「この行が失敗したら」を追う。[引き渡し記録](../templates/handover.md)の未確認欄を埋められる証拠から揃える。

## 段階を閉じる

4条件の作業記録を個人台帳へ添付し、[評価手順](../assessment.md)でレビューを受けます。文書だけ整い実機試験がなければSE04-C3は未実施のままです。レビュー指摘には対象要件、修正、再試験、残課題を返し、本人以外の評価記録を得てから[SE05](05-automation.md)へ進みます。
