# SE02 通信経路を設計して調べる — 「つながらない」を分解する

[育成システムの入口](../README.md) / [評価手順](../assessment.md) / [前: Linux](01-linux.md) / [次: Web・AP・DB](03-services.md)

ネットワークは、相手の住所を調べ、どの出口から送るか決め、相手の受付へ届ける仕組みです。名前解決、経路、待受、ファイアウォール、アプリの応答は別々に失敗します。目的は、観測から範囲を絞り、根拠なしに設定を変えないことです。

前提はSE01合格、専用Ubuntu VMと管理端末、コンソール経由の復旧方法、正常時のIP表です。コマンドは指定がない限りUbuntuのBashで実行します。Windows管理端末では同等の確認に`Get-NetIPConfiguration`、`Resolve-DnsName`、`Test-NetConnection`を使い、OSを記録します。[既存W5〜W8](../../learning-plan/02-curriculum.md)を週別の補助教材として使います。**この教材の実機試験は未実施です。**

| 条件 | 成功の目印 | 必要な証跡 |
| --- | --- | --- |
| SE02-C1 | IP・サブネット・経路を図と実測で対応付ける | IP表、図、routeの実出力 |
| SE02-C2 | 名前解決の成功と失敗を切り分ける | 問い合わせ先、応答、OS側解決との比較 |
| SE02-C3 | SSHとFirewallの許可・拒否・復旧経路を試験する | 許可元と拒否元からの実接続、FW、コンソール |
| SE02-C4 | 未知の通信障害を観測から特定して復旧する | 支援なしの調査過程、原因、再確認、評価者記録 |

## SE02-C1 IP・サブネット・経路を図と実測で対応付ける

1. 管理端末、VMのNAT側NIC、VMの学習ネットワーク側NICを描きます。「管理端末→VM」「VM→パッケージ取得先」の2経路を別の矢印にします。サブネットは同じネットワークの範囲、ゲートウェイは範囲外へ出る出口です。
2. VMで次を確認します。`ip route get`は経路選択を表示するコマンドで、実際に相手へ通信成功した証拠ではありません。

   ```bash
   ip -brief link
   ip -brief address
   ip route show table main
   ip route get 1.1.1.1
   ```

3. 管理端末の学習側IPを、実際の出力から作業メモへ転記し、VMで`ip route get 管理端末の実IP`を実行します。文字列を実IPへ置換する前に実行しません。
4. 各経路の`dev`と`src`を図へ書き込みます。NAT側と学習側の両方へ不要なdefault routeを書かず、設計と実測の差を調べます。
5. [既存のネットワーク実機検証 NW-01〜NW-04](https://github.com/ns7jp/server/blob/main/docs/build-package/09-network-validation-procedure.md)に沿って結果票を作ります。例示の`192.0.2.0/24`は教材用であり、自分の実IPに置換します。全文を一度に実行せず、現在用意した対象だけを確認します。

| 観測 | 言えること | まだ言えないこと |
| --- | --- | --- |
| NICがUP | そのインターフェースが動作状態 | 相手アプリへ届くこと |
| IPとプレフィックスが一致 | OS設定が構成表と一致 | DNSが正しいこと |
| routeに出口がある | OSがその経路を選択する | Firewallが許可すること |
| pingが返る | ICMP往復が成功 | HTTPやSSHの成功 |

失敗時はインターフェースの追加前後、IP重複、NATとホストオンリーの役割を確認します。routeの一括削除やネットワークの全面再作成は行わず、[初期構築設計](../../learning-plan/05-phase1-exercise-design.md)の対象を限定した設定・復旧へ戻ります。

## SE02-C2 名前解決の成功と失敗を切り分ける

DNSは名前に対応するIPなどを問い合わせる仕組みです。OSの名前解決には`/etc/hosts`なども関わるので、`dig`のDNS応答と`getent`のOS側の解決結果は、同じになるとは限りません。

1. 先に利用している名前解決の設定を確認します。コマンド不足は`BLOCKED`として、必要パッケージを別の準備作業で導入します。

   ```bash
   command -v dig getent resolvectl
   resolvectl status
   getent hosts localhost
   ```

2. インターネット向けDNS問い合わせを許可した学習環境では、文書用ドメイン`example.com`の名前解決を試します。閉域環境では管理者・評価者が用意した学習FQDNへ置き換えます。公開WebサイトへのHTTP接続はこの試験に不要です。

   ```bash
   dig +time=2 +tries=1 example.com A
   getent ahostsv4 example.com
   dig +time=2 +tries=1 se02-missing.invalid A
   getent ahostsv4 se02-missing.invalid
   printf 'OS側名前解決の終了コード=%s\n' "$?"
   ```

3. `dig`では`status`、ANSWER、SERVERを記録します。成功時は期待する名前の応答、存在しない名前では通常`NXDOMAIN`を観測します。`dig`の終了コードだけでレコードの存在を判定しません。
4. timeout、NXDOMAIN、SERVFAILを区別します。timeoutは応答が得られないこと、NXDOMAINは名前が存在しないというDNSの応答、SERVFAILはサーバーが処理できなかった応答です。全てを「ネットが切れた」とまとめません。
5. 管理端末でも同じ名前を問い合わせ、VMとDNS参照先・応答が異なるか確認します。異なる場合、split DNSなどの意図した設計か、設定誤りかを説明します。

`.invalid`を存在しない名前として扱わず独自の応答を返すネットワークでは、実際の応答を残し、ローカルのDNS管理方針を確認します。教材の期待値に合わせるために出力を加工しません。会社のDNSレコードやPC全体のDNSをこの練習のために変更しません。

**戻し方:** この節のコマンドは問い合わせと設定表示だけです。変更が必要になった場合は、変更前設定と対象を記録し、別の変更作業として実施します。

## SE02-C3 SSHとFirewallの許可・拒否・復旧経路を試験する

ファイアウォールは、送信元・宛先・ポートなどの条件に基づき通信を通す仕組みです。「ルールが書いてある」と「その送信元から接続できる／拒否される」は別々に確認します。

1. [Phase 1設計のT-09/T-13と検証用セグメント](../../learning-plan/05-phase1-exercise-design.md)で、許可元と拒否元を明確にします。拒否元は自分が管理するラボ内の検証端末です。第三者のホストへの接続試験は行いません。
2. 管理端末からの正常なSSH接続を維持し、VMコンソールからも一般ユーザーで入れることを確認します。
3. VMで待受とFWを採録します。

   ```bash
   sudo ss -lntp
   sudo ufw status verbose
   sudo ufw status numbered
   sudo sshd -t
   ```

   `sshd -t`が出力なし・終了コード0であれば構文検査成功です。それだけで別端末からの認証成功にはなりません。既存の`LIMIT 22/tcp`は試行頻度の制限であり、管理元CIDR以外を拒否することの代わりにはなりません。

4. 許可元から正しい鍵を使って接続し、VMの利用者・ホスト名を確認します。拒否元からはその同じVMのSSHへ1回だけ試し、時間上限を設けて結果を記録します。
5. 拒否の理由を、送信元、FW条件、VM側の待受、許可元の接続成功と突き合わせます。名前を間違えた、鍵が違う、コマンドが無い、という失敗はFW拒否試験の合格ではありません。
6. 必要であれば[ネットワーク検証 NW-07](https://github.com/ns7jp/server/blob/main/docs/build-package/09-network-validation-procedure.md)の上限付きパケット観測を使います。本文や認証内容を出す`-A`や`-X`は使わず、対象NIC・対象ポート・最大20パケット・15秒以内に限定します。
7. 検証用に追加した接続経路を、元のPhase 1手順に従って戻し、通常の許可元から再接続します。

拒否元を用意できない場合、その試験は`BLOCKED`です。コンテナ間の遮断や「ルールを見た」だけで、VMのFWによる送信元拒否を満たしたとはしません。ルールの変更が必要なら、既存の許可接続とコンソールを残して、対象1規則の追加・確認・復旧を計画します。

## SE02-C4 未知の通信障害を観測から特定して復旧する

この条件は`independent`が必要です。手順付きの故障演習を終えただけでは合格にしません。最初に次の練習を行い、評価では別セッションに評価者が選んだ、本人が原因を事前に知らない対象限定の障害を使います。

### 小さなHTTPサーバーで正常状態を用意する

`python3`が導入された学習VMを使います。専用一時フォルダ内のダミー本文だけを公開し、個人文書やリポジトリ全体を公開しません。まずVM内のloopbackだけで観測に慣れます。

端末A:

```bash
SE02_HTTP="$(mktemp -d /tmp/se02-http.XXXXXX)"
printf 'SE02 network practice\n' > "$SE02_HTTP/index.html"
python3 -m http.server 18082 --bind 127.0.0.1 --directory "$SE02_HTTP"
```

端末B:

```bash
ss -lnt 'sport = :18082'
curl --fail --show-error --max-time 5 http://127.0.0.1:18082/
```

期待結果はloopbackの待受と、用意した本文です。端末Aで`Ctrl-C`を押した後に同じ確認を行い、待受の消失と接続エラーを記録します。端末Aで同じ起動コマンドを実行し直すと、同じ本文へ戻ることを確認します。これは原因既知の練習です。

評価では、必要に応じて同じダミーサービスを**学習専用NICの実IPだけ**にbindし、管理端末→VMの通常経路を正常確認してから開始します。公開IPや`0.0.0.0`へ無条件に広げません。評価者はサービスの対象・復旧方法を把握し、SSHやOSの起動経路を壊さない範囲を選びます。

### 調査の順番

| 順番 | 自分が確かめること | 調査記録に残すもの |
| --- | --- | --- |
| 1 | どこから何へ接続したか | 実行端末、名前/IP、ポート、時刻、エラー全文 |
| 2 | 名前と経路が妥当か | getent/dig、route、名前を使う接続とIP指定接続の差 |
| 3 | 宛先が待ち受けているか | ss、サービスを起動した端末の状態とログ |
| 4 | 通信がどこまで届くか | 許可元・対象側の記録、必要時の限定capture |
| 5 | どの仮説を支持／反証したか | 次の操作を選ぶ理由、予想する変化 |
| 6 | 最小の変更で戻ったか | 変更内容、同一確認の再実行、影響範囲 |

再起動を繰り返す前に、少なくとも状態・ログ・経路を保存します。対象の識別に自信がない、復旧経路が失われた、学習範囲外へ影響する場合は中止し、理由を報告します。原因を当てる速さより、根拠と停止判断を優先します。

評価者がいない場合や、AIから具体的な修復指示を受けた場合も練習は続けられますが、この条件の独立評価は未完了です。[評価手順](../assessment.md)へ支援量を正直に記録します。

### Dockerラボを補習に使う場合

[二セグメント障害ラボ](https://github.com/ns7jp/server/tree/main/labs/network-troubleshooting)には、LinuxのDocker Engine/Composeで動く既存キットがあります。Dockerの基本起動・停止を[SE03-C1](03-services.md)で学んでから補習に戻れます。専用Docker環境で`server`直下から実行します。

```bash
cd labs/network-troubleshooting
docker compose config --quiet
bash run-drill.sh
docker compose down
```

実行前にREADMEとスクリプトの対象ネットワークを確認します。既存ラボと同名のネットワークを共用しません。これはコンテナのネットワーク障害を扱い、VMのNIC・外部DNS・UFWの合格証跡には置き換えません。自動で故障を注入・復旧するキットの実行は、独立した未知障害の解決とも分けます。

## 提出と再試験

- [ ] C1: 構成図と実際のIP/routeの対応、経路選択と到達成功の区別。
- [ ] C2: 正常な名前、存在しない名前、問い合わせ先、OS側の名前解決の比較。
- [ ] C3: 許可元・拒否元の試験と、FW以外の失敗ではない根拠、復旧経路。
- [ ] C4: 正常時・障害時・復旧後の出力、仮説と反証、本人の判断と評価者の観察。
- [ ] 原本を保存し、公開する写しのIP・MAC・アカウントを必要な範囲でマスク。
- [ ] [台帳](../tracker-guide.md)へ環境、支援量、UTC日時、Git SHA、試行を追記。

| 説明問題 | 解答の観点 | 補習 |
| --- | --- | --- |
| ping成功でWeb正常と言えない理由は | ICMPとTCP/HTTPは別。待受・認証・アプリの確認が必要 | C1の「まだ言えないこと」を説明 |
| NXDOMAINとtimeoutは何が違うか | 前者は名前不存在という応答、後者は応答が得られない | C2の実出力を比較 |
| 接続拒否を見たらFWが効いていると言えるか | listener不在や認証失敗などを分ける必要がある | C3の根拠を見直す |
| コンテナの通信断を直したらVM通信も合格か | 対象と経路が異なるため別の試験が必要 | C4の環境境界を図示 |

自己説明が難しければ、[一次切り分け記録の記入例](https://github.com/ns7jp/server/blob/main/docs/evidence/templates/troubleshooting-worklog-example.md)を読んでから、別のポート・別のダミー本文で同じ観測を練習します。記入例の原因や数値を、自分が観測した事実へ転記しないでください。
