# SE06 監視・復旧・継続運用

[育成システム](../README.md) / [前段 SE05](05-automation.md) / [次段 SE07](07-capstone.md) / [評価手順](../assessment.md)

**完成像は「利用者の異常を見つけ、根拠から切り分け、戻ったことを確かめ、翌日以降も追えること」です。** サービス起動直後の成功に、検知・対応・復元・再起動・複数日の観測を加えます。

目安はW21〜W24です。W21で監視、W22で障害対応、W23で復元、W24を中心に7日間の観測を行います。観測期間は実際の暦日が必要です。教材、CI、ログの雛形を生成しても7日間稼働した実績にはなりません。

## 開始条件と使う環境

- SE05がPASSで、自動化から作った学習VM、試験済みの構成、切戻し手順がある。
- 監視対象VMと別の管理端末を使える。可能なら監視データの採録先も対象VMの外に置く。同一VM内の監視がホスト停止時に一緒に止まる限界を記録する。
- 通知試験先はローカル受信器か明示的に用意した演習用の宛先で、実業務の通知先を含まない。標準課題では人への外部送信を必要としない。
- 学習データのバックアップを読み取れる。復元先は別VM、別DBまたは別名volumeとして新設し、元の対象を維持できる。
- 作業記録、[障害記録](../templates/incident.md)、[週次振り返り](../templates/weekly-review.md)を用意する。

既存の[監視ランブック索引](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/runbooks/README.md)、[バックアップ・復旧設計](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/backup-restore.md)、[日次点検スクリプト](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/scripts/ops/daily-check.sh)を使います。後者の`SKIP`は確認済みを意味しません。必要な項目がSKIPなら本段階では未確認として扱います。

[恒久ホスト演習設計](../../learning-plan/13-persistent-host-exercise-design.md)には再起動、24時間後、72時間後の確認の考え方があります。本系列ではその観測の考え方をローカルVMへ適用します。VPS契約、ドメイン購入、クラウド配備はこの必修段階に含めません。

## 運用で分ける4種類の時刻

| 時刻 | 意味 | 記録の根拠 |
| --- | --- | --- |
| 障害発生 | サービスに影響が出始めた時刻 | 評価者の注入記録、利用者試験、ログ |
| 検知 | 監視または人が異常を認識した時刻 | 発火記録、受信記録、本人の観測 |
| 暫定復旧 | 利用者が使える状態へ戻った時刻 | 正常な業務操作と依存先の確認 |
| 完了 | 根本対応・残課題・引き継ぎが整理された時刻 | 障害報告と評価者の確認 |

計測にはタイムゾーン付き時刻を使い、複数端末の時刻同期を先に確認します。発生時刻が不明なら不明と書き、検知時刻からの復旧時間と発生からの停止時間を混同しません。RTOは許容する復旧時間の目標、RPOは許容するデータ損失の時間幅の目標として事前宣言し、実際の所要時間・失われたデータを別欄に記録します。

## SE06-C1 利用者視点の監視と隔離した通知先で検知を確認する

**目的：** プロセスの存在と、利用者が目的を達成できることを分けて監視します。アラートを設定しただけでなく受信まで確かめます。

**前提：** 監視対象の正常値、入口、依存先、通知経路が構成図にある。テスト用の受信先と変更前設定を確認していること。

**実施手順：**

1. 監視設計表を作り、「利用者ができないこと」から必要な監視を選ぶ。最低限、利用者のHTTP応答と内容、依存先、ホスト容量、監視の欠測、バックアップ鮮度を扱う。
2. 各項目に採録元、周期、しきい値、継続時間、通知先、最初の確認、復旧確認を付ける。[既存ルール](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/deploy/prometheus/rules.yml)の数値を採用する場合は、対象の負荷と検知時間に合う理由を説明する。
3. 正常状態でダッシュボード・ログ・利用者操作を確認する。3層ラボでは`/web-healthz`、`/healthz`、`/readyz`と在庫一覧の役割が違うため、必要なものを個別に確認する。
4. ローカル通知受信器を設定する。既存の[webhook-sink構成](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/compose.e2e.yaml)と[E2Eの通知検査の説明](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/e2e-validation.md)を参照し、学習用設定でルーティングとFIRING・RESOLVED受信を採録する。受信器を起動しただけではアラートの配送設定は完成しない。
5. まず試験用アラートで配送だけを確認する。次に対象を特定したラボサービス一つを停止する演習で、利用者の異常→監視の発火→受信→サービス復帰→解消通知を順に記録する。配送試験の成功と実症状からの検知成功を別々に判定する。
6. 監視収集や通知先自身が停止したときに、誰がどの経路で欠測へ気付くかを確認する。対象と同じVMに受信器も置く場合は、ホスト停止の外部検知まで達成したとは書かない。

| 監視対象 | 正常時の期待 | 異常で確認すること |
| --- | --- | --- |
| 利用者の一覧参照 | HTTP成功と内容一致 | プロセスが生きていてもDB依存で失敗すること |
| DB依存 | readyz成功、必要なクエリ成功 | 通信失敗とDB停止を区別できる観測があること |
| ホスト容量 | 事前に決めた上限より余裕 | 専用の小さな試験領域か模擬値でしきい値を越えた時の処理 |
| 監視の継続 | 最終サンプルが所定時間内 | データが来ない状態を正常値ゼロにしないこと |
| 通知経路 | FIRINGとRESOLVEDを受信 | 送出失敗・受信器停止を記録できること |

**期待結果：** 利用者の症状から通知受信までの実測時刻があり、復旧解消まで確認できる。ローカル受信はローカル受信の実績として表し、Slackやメールの実配信へ読み替えない。

**失敗・戻し方：** 通知が来なければ、ルール評価、発火状態、ルーティング、送出、到達、受信記録を順に調べる。外部の人が受け取る設定を発見したら試験を中断し、ローカル宛先へ直してから再開する。演習後は注入した停止や試験用ルールを解除し、正常性と通知収束を確認する。

**提出物：** 監視設計表、ルールの対象版、正常値、配送単体試験、実症状からの検知・解消、監視の限界。

**自分の言葉で説明：** アラートが来ない理由を三つ挙げる。HTTP200と業務成功はどう違うか。監視自体が止まった場合に誰が気付くか。

**補習：** [Zabbix監視演習設計](../../learning-plan/09-zabbix-monitoring-exercise-design.md)の項目・トリガー・通知の分解と比較し、製品名を外して「測定→判定→配送→対応」を説明する。通知先を増やす前に1経路を通す。

## SE06-C2 障害の検知・切分け・連絡・復旧を時系列で記録する

**目的：** 思い付いた再起動を重ねず、証拠から仮説を絞り、止める判断も含めて対応します。本条件は`independent`必須です。

**前提：** SE06-C1の検知、復旧経路、データ保全がある。評価者と演習時間、影響範囲、中止条件を共有する。本人の端末や業務ネットワークに影響する障害は選ばない。

**実施手順：**

1. 演習前に正常状態と復旧目標を採録する。練習では[service-down](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/runbooks/service-down.md)等のランブックを読み、期待する復旧条件を説明する。
2. 評価用試行では、評価者が安全に戻せるラボ内の障害を一つ選ぶ。本人には利用者の症状、対象範囲、時間制限だけを渡し、原因や次のコマンドを教えない。教わった場合は支援付き練習へ切り替えて記録する。
3. 検知時刻と利用者影響を記録し、初報をローカル文書として作る。内容は分かっている影響、未確認、担当、次の確認、次回報告予定。人への外部送信を自動的に行わない。
4. 観測→仮説→次の検査→結果→仮説の更新を1行ずつ記録する。入口、AP、DB、名前解決、通信、資源のどこまで確認済みかを図に書き込む。
5. 復旧操作の直前に対象、期待する変化、失敗時の戻し方を述べる。事前の時間・影響・データ保全の中止条件に達したら作業を止め、状態を残してエスカレーション用の報告を作る。
6. 利用者操作、依存先、データ、監視、解消通知のうち今回の必須項目を確認して暫定復旧を判定する。ログのエラーが消えただけで終了しない。
7. 評価者の実際の注入内容と自分の推定を照合する。検知まで、調査、復旧、復旧確認の所要時間を分け、原因・寄与要因・再発防止・担当・期限を障害記録に残す。

**期待結果：** 原因判断が少なくとも二つの異なる観測で説明でき、復旧後の利用者確認がある。判断できない範囲を認めて止めるべき場面では止められる。操作が速いことだけで評価しない。

**失敗・戻し方：** 原因不明の変更を重ねたら、最後に把握できていた状態と変更一覧を整理する。データ破損や対象外への影響が疑われたら即時中断し、復旧責任者役へ情報を渡す。中断した試行は消さず、その判断の妥当性と技術上の未達を別々に評価する。

**提出物：** 障害タイムライン、観測と仮説、初報・経過・復旧報告の下書き、実測時間、正常復帰の証拠、評価者の観察記録。

**自分の言葉で説明：** 原因と症状は何が違ったか。最初の仮説を捨てた証拠は何か。どの条件で自分の担当範囲を越えると判断するか。

**補習：** [SE02](02-network.md)または[SE03](03-services.md)へ戻り、一つの原因に対して二つの観測を取る。[連絡例](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/incident-comms.md)は文章の材料として使い、架空の時刻や実施していない送信を転記しない。

## SE06-C3 別対象への復元で復旧時間とデータ損失を測る

**目的：** バックアップのファイルがあることから、別の対象で利用者が再び使えることへ進みます。

**前提：** 元データを維持できる別の復元先、バックアップ時刻と取得対象一覧、必要なコード・秘密値・ロール等の復元手段があること。必要容量とバックアップの読み取り可否を確認していること。

**実施手順：**

1. 要件からRTO・RPOの目標と起点・終点を宣言する。「復元コマンドの秒数」と「障害検知から利用者復帰まで」は別に測る。
2. 元データに識別できるサンプルを用意する。項目、件数、決めた順序で出力した内容ハッシュを保存してからバックアップを取る。取得時刻とバックアップのSHA-256を採録する。
3. バックアップ後に一意なサンプルを追加し、その登録時刻とIDを記録する。後で何が戻らないかを照合する材料にする。サンプル以外は使わない。
4. 復元先の名前、VM識別情報、DBまたはvolume名、既存データがないことを確認する。名前を確認できない場合は止める。
5. 監視基盤なら[別名volumeへの復元スクリプト](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/scripts/ops/restore-volumes.sh)の対象検証を読み、既定の既存volume拒否を維持する。新しい復元先を使い、`--force`で確認を省略しない。
6. DBならSE03で作った別DBへの論理復元手順を使う。必要なロール、権限、データ、シーケンスを照合する。`pg_dump`はDB単位で、ロール等のクラスタ全体の情報は別管理が必要である。[PostgreSQL 16公式：SQL Dump](https://www.postgresql.org/docs/16/backup-dump.html)
7. 復元先のアプリだけを復元DBへ向け、一覧、登録、権限、監視を確認する。件数と内容ハッシュの一致、バックアップ後サンプルの有無、利用者復帰時刻を採録する。
8. 元データが変わっていないことも確認する。実際に失われるIDと件数、最後に復元できた更新時刻、観測できる損失時間幅を記録する。時刻を持たないデータしかなく時間幅を測れない場合はRPO実測を未確認とし、次回の測定設計を直す。

既存[3層ラボB-3](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/labs/three-tier/README.md)は使い捨てラボの元DB内でテーブルを消して戻す演習です。そのままでは本条件の「別対象への復元」になりません。手順を読む教材として使い、元DBを維持した別DB・別VMでの試行を別に採録します。

**期待結果：** 復元先で利用者操作が通り、元データは維持され、目標と実績を比較できる。目標未達なら未達理由と改善案がある。同一VM内の別volume試験を別ホストの復旧実績へ読み替えない。

**失敗・戻し方：** チェックサム不一致、容量不足、権限不足、復元先誤指定を発見したら適用前に停止する。途中復元に失敗した領域は未完成として隔離し、元環境に接続し直す判断を記録する。確認前にバックアップ世代を削除しない。

**提出物：** バックアップ対象表、元/先の識別、バックアップとデータのハッシュ、復元ログ、RTO/RPOの目標・実測・限界、元環境の不変確認。

**自分の言葉で説明：** バックアップ成功から利用者復帰までに何が必要か。RPOが0と主張するにはどの証拠が必要か。バックアップ後の1件が戻らない理由は何か。

**補習：** [SE03](03-services.md)のDB復元と[Pythonバックアップキット](../../learning-plan/python-ops-kit/README.md)を使い、ダミーファイルまたは小さなDBで往復し、内容の照合方法から見直す。

## SE06-C4 再起動と7日間の観測で永続性と欠測を記録する

**目的：** 手動で起動した直後だけ動く構成を見つけ、観測が抜けた事実も含めて運用記録を維持します。

**前提：** SE06-C1〜C3の正常状態とバックアップがあり、VM再起動を行ってよい学習時間、コンソール接続、復旧手順がある。ホストPCや共有ホストは再起動対象にしない。

**実施手順：**

1. 観測開始前に、開始日時、終了予定、毎日の観測予定時刻、許容ずれ、採録担当、採録先、必須項目、停止・延長条件を決める。例えば毎日20時±30分という計画を本人の生活に合わせて選ぶ。
2. 再起動前のVM識別、OS起動時刻、サービス、マウント、待受、時刻同期、バックアップタイマー、利用者応答、直近データを採録する。自動起動の設定があるかを読み取り、設定の存在と実挙動を区別する。
3. 学習VMだけを予定した手順で再起動する。本書は再起動の実行指示をホストPCへ送る仕組みを持たない。実行する本人が対象を確認する。
4. 再起動後、手動でサービスを起こす前にコンソールと管理端末から状態を採録する。OSの新しい起動時刻、SSH、ディスクの永続マウント、サービス自動起動、利用者操作、監視復帰、バックアップの次回予定を照合する。
5. 再起動直後、開始から24時間後、72時間後、7日目の確認を計画に含め、毎日少なくとも1回観測する。自動採録を使う場合は初回に手動の読み取りと一致を確かめ、採録先が対象VMだけに依存するかを記録する。
6. 毎日、下表の行を追加する。通常の状態変化と異常、手動変更、バックアップの最終成功、実際の観測期間を記録する。CPUやディスクの値を前日からコピーしない。
7. 抜けた観測は「欠測」とし、予定時刻、気付いた時刻、理由、確認できない期間、次の確認を残す。後日の正常性を過去の正常性へさかのぼって適用しない。
8. 終了時に欠測・異常・変更・期限超過をまとめ、必須観測が不足したら追試を計画する。元の終了予定、遅延日数、延長理由を保存する。未観測期間は埋まったことにしない。

「7日間の観測」は、D1〜D7の実日付と、開始から終了までの実経過時間を両方記録します。7回の採録を同日にまとめても充当できません。24時間・72時間の点は実経過時間で確認し、日付だけで済ませません。7日目が開始から144時間なら、その時間をそのまま書き、168時間連続稼働と表現しません。7×24時間を要件にした場合は168時間時点の追加観測も行います。

**期待結果：** 再起動前後の比較で永続性が確認でき、異なる7暦日に観測記録がある。欠測がある場合も記録の正直さは評価するが、必要な稼働確認が揃ったことにはしない。必須観測と不足分の追試が揃うまでこの条件を自己判断でPASSにしない。

**失敗・戻し方：** 再起動後に起動しない場合、手動で直す前の状態を記録し、依存、設定、ログを調べる。手動起動だけで復帰したら自動起動の試験はFAILのまま改善後に再試行する。観測器が止まった場合は監視欠測として残す。

**提出物：** 再起動前後の生ログ、7日間の表、24/72時間の根拠、欠測・延長の履歴、バックアップ成功記録、再発防止と担当・期限。

**自分の言葉で説明：** 日次点検が7回成功したら7日間ずっと正常だったといえるか。再起動後に手動起動した場合に何が未達か。観測を忘れた日をどう扱うか。

**補習：** [SE01](01-linux.md)のサービス・永続マウントへ戻る。[週次振り返り](../templates/weekly-review.md)で観測時刻・採録経路を見直し、無理のない追加観測を設定する。

## 段階を閉じる

検知、切分け、別対象への復元、再起動・複数日観測をそれぞれ記録し、[評価手順](../assessment.md)でレビューを受けます。7日間の実観測や評価者が未実施なら、この教材が完成していても学習者のSE06は未完了です。人による確認後に[総合課題 SE07](07-capstone.md)へ進みます。
