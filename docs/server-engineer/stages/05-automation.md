# SE05 再現できる構築と変更

[育成システム](../README.md) / [前段 SE04](04-design.md) / [次段 SE06](06-operations.md) / [評価手順](../assessment.md)

**完成像は「空の学習VMに、対象版を説明して同じ構成を作り、変更に失敗しても元へ戻せること」です。** コマンドの連続実行を自動化しただけでは完成にしません。対象の限定、失敗停止、秘密値の分離、2回目の挙動、実サービス、別VMの再構築まで確かめます。

目安はW17〜W20です。W17でGit、W18で安全なスクリプト、W19で構成管理、W20で再構築と切戻しを扱います。学習期間を短縮したい場合も、実施記録と人による評価を省略しません。

## 開始条件と教材

- SE04がPASSで、要件・構成図・パラメータ・試験・切戻しの対応が取れている。
- 管理端末と対象VMが別で、対象VMのコンソールから復旧できる。学習VMの識別情報、OS、IP、管理ユーザー、許可した操作を記録する。
- 現用とは別に、新規OSの検証VMを1台用意できる。単一PCでも別VMでよい。会社のホストや共有サーバーを対象にしない。
- 作業用Gitブランチと非公開の個人記録先がある。[作業記録](../templates/work-record.md)に実行場所・対象・Git SHA・セッション・支援量を記入する。

本書のコマンドは学習者が前提を確認して使う手順例です。教材を作成しただけで、ユーザーのVMへ適用したという意味にはなりません。

## 考え方

**手順の自動化**は、命令を順番に実行することです。**構成管理**は、必要な状態を宣言し、現在との差を埋めることです。**冪等性（べきとうせい）**は、同じ入力を繰り返しても目的の状態が崩れない性質です。「2回目に変更ゼロ」は有用な観測ですが、サービスが正しく動くことや、すべての異常に安全であることまでは証明しません。

Ansibleのcheck modeは変更の予測で、未対応モジュールや前の処理結果に依存するタスクでは十分な確認になりません。`check_mode: false` のタスクはcheck実行中にも実変更を行い得ます。diffには秘密情報が出る可能性があるため、実行前に対象タスクと出力範囲を確認します。[Ansible公式：check modeとdiff mode](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_checkmode.html)

## SE05-C1 Gitの差分・レビュー・対象版を追跡する

**目的：** 「昨日動いたもの」を特定のファイル集合とコミットへ結び、レビュー対象と配置対象を一致させます。

**前提：** Gitの取得先が自分の学習用リポジトリであり、既存の未コミット変更を把握していること。公開用ソースと秘密値・個人台帳を分けていること。

**実施手順：**

1. リポジトリのルートで次の読み取りを行い、remote、作業ブランチ、開始時SHA、未コミット差分を作業記録に残す。認証情報を含むremote URLは記録前に伏せる。

   ```bash
   git status --short
   git branch --show-current
   git rev-parse HEAD
   git diff --stat
   git diff --check
   ```

2. SE04の変更票1件につき作業ブランチを作り、変更対象を限定する。OS設定の変更と説明の修正を理由なく混在させない。
3. 変更前後を読んで「何が変わるか」「どの要件を満たすか」「戻す版」を書く。設定の値が変わる場合はパラメータ表と試験期待値も更新する。
4. ステージした差分を見直す。鍵、パスワード、トークン、実接続情報、個人台帳、採録した生ログが混入していないことを確認する。`.gitignore`へ追加しただけでは既に追跡されたファイルは除外されないため、追跡状態も確かめる。
5. コミット後のSHA、変更理由、実行予定試験、結果の記録先をレビュー資料へ書く。練習ではローカル差分を第三者に見せてもよい。公開PRを作る場合は送信先と公開範囲を確認する。
6. レビュー指摘を修正し、配置対象をその修正後SHAへ固定する。ブランチ名だけでなく最終SHAを記録し、配置後の実ファイルとの対応を確かめる。

**期待結果：** 試験記録から配置版へ、配置版からレビュー差分へたどれる。未コミットの変更を含めた実行はその旨と差分を記録し、コミットSHAだけで再現可能と主張しない。

**失敗・戻し方：** 他人の未コミット変更を発見したら保全して対象を分ける。間違ったコミットを共有した場合は履歴を強制的に書き換えず、修正・取消のコミットで経緯を残す。秘密値を誤って公開した場合は単にファイルを消して完了とせず、公開先の範囲と失効・再発行の必要性を担当者へ伝える。

**提出物：** 変更票、差分、変更前後SHA、レビュー指摘と対応、配置版確認。生の秘密値は提出しない。

**自分の言葉で説明：** `main`とコミットSHAを記録する違いは何か。レビュー後にファイルを1行変えたら、何を再確認するか。戻すコードに対してDBが新しい形式なら何が問題か。

**補習：** 学習用テキスト1ファイルで変更→差分→コミット→取消変更の流れを説明し、SE04の変更票へ対応付ける。Git操作が不明なままサーバー設定の大量変更を扱わない。

## SE05-C2 自動化の事前確認・失敗停止・秘密値分離を試験する

**目的：** 自動化が想定外の対象を変更したり、失敗を成功として後続処理へ流したりしないことを確かめます。

**前提：** 検証用の小さなダミーファイルだけを置く専用ディレクトリがある。バックアップ元と復元先は別で、パスの実体・容量・権限を確認済みであること。

**実施手順：**

1. [Pythonキットのroutine設定](../../learning-plan/python-ops-kit/linux/routine/routine.yaml)と[処理本体](../../learning-plan/python-ops-kit/linux/routine/routine.py)を読む。教材既定のcleanup対象をそのまま使わず、対象VM内の今回作った専用ダミーディレクトリ1か所へ限定する。root、home、`/tmp`全体、実ログ保存先を実削除練習の対象にしない。
2. 仕様に入力、対象範囲、変更内容、成功・失敗の終了コード、ログ、同時実行、再実行、dry-runの定義を書く。ファイル名に空白がある入力も含める。
3. 適用フラグなしで動かし、候補の表示と実ファイル不変を前後の一覧・ハッシュで照合する。dry-runという表示だけで安全だったと判断しない。
4. ダミーデータで、入力不足、存在しない対象、権限不足、不正な設定、二重起動、容量不足を模擬する。容量不足は小さく容量を制限した専用試験領域やテスト用応答で再現し、OSディスクを埋めない。
5. 失敗ケースごとに終了コードとログを採録し、失敗した処理の後に成功記録や世代削除が走らないことを確認する。不十分なら学習用コピーを修正して再試験する。
6. 秘密値は環境に適した別の保管先から渡し、ソース、CLI引数の記録、標準出力、例外、差分に出ないことをダミーの識別文字列で試験する。実パスワードを漏らして検査しない。
7. 初回の適用は専用ダミーデータに限る。生成物を別の専用復元先へ戻し、内容が一致することを確認する。運用データへ広げる前に対象指定と戻し方を再レビューする。

| ケース | 事前に書く期待結果 | 採録するもの |
| --- | --- | --- |
| dry-run | 候補だけ表示、対象は不変 | 前後一覧・ハッシュ・終了コード |
| 対象不正 | 変更前に停止、対象を特定できるエラー | エラーと変更がなかった証拠 |
| 途中失敗 | 後続の危険な処理へ進まない | 時系列ログ、途中生成物、再実行結果 |
| 再実行 | 仕様どおり成功、重複・欠落なし | 1回目と2回目の状態比較 |
| 秘密値 | ダミー秘密の文字列がログに出ない | 検査した出力範囲と結果 |

**期待結果：** 正常系だけでなく拒否・途中失敗も期待どおりで、実データへ触れずに検証できている。既存キットに必要なガードがなければ、その不足をFAILまたは改修課題として扱っている。

**失敗・戻し方：** 想定外の対象を列挙したら適用へ進まない。対象識別、パスの解決、シンボリックリンク、権限を確認する。失敗時に残った一時ファイルは専用試験領域内であることを確認してから個別に処理する。失敗ログを削除してやり直さない。

**提出物：** 自動化仕様、学習用差分、上表の実行記録、ダミーデータ復元一致、秘密値検査結果、未対応条件。

**自分の言葉で説明：** 終了コード0とバックアップ成功はどう違うか。dry-runの後に対象が変わった場合はどうするか。`set -e`だけで失敗処理が十分といえるか。

**補習：** [シェルスクリプト演習](../../learning-plan/06-shell-scripting-exercise-design.md)の引数・終了ステータス・エラー処理へ戻り、ファイル1個で成功と失敗を再現する。自動削除やスケジューラ登録を先に増やさない。

## SE05-C3 Ansibleを2回適用し冪等性と実サービスを試験する

**目的：** 構成管理が1回目に必要な変更を行い、2回目に不要な変更を起こさず、ホストが使えることを確認します。

**前提：** 学習用Ubuntu VM、別のLinux管理端末または適切に用意した管理環境、SSH公開鍵、sudo権限、コンソール復旧経路がある。管理端末上のAnsible導入は参照版の[配置手順](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/deployment-ansible.md)に合わせる。基盤用`foundation.yml`と監視一式用`site.yml`は別の成果物であると理解する。

**実施手順：**

1. 最初は[foundation.yml](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/ansible/playbooks/foundation.yml)の`common`と`docker`の範囲を選ぶ。監視サービスまで確認する場合は続けて`site.yml`へ進むが、実行した範囲を分けて記録する。
2. [foundation inventory例](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/ansible/inventory/foundation.local.yml.example)を追跡対象外のローカル設定へ複製し、実VMのIP、接続ユーザー、管理者公開鍵へ置き換える。説明用アドレス`192.0.2.20`や鍵の`AAAA...`を残さない。
3. 変数の既定値と上書きを読む。特に[foundationのgroup_vars](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/ansible/inventory/group_vars/foundation/main.yml)では管理者sudo設定がパスワード不要になっている。採用理由、鍵の保管と失効方法、適用範囲を説明して記録する。
4. 接続先を一覧で確認し、構文検査を行う。以下は管理端末の`server/ansible`を実行場所とし、inventory内の対象名を`ans-01`にした場合の例である。

   ```bash
   ansible-inventory -i inventory/foundation.local.yml --graph
   ansible-playbook -i inventory/foundation.local.yml playbooks/foundation.yml --list-hosts --limit ans-01
   ansible-playbook -i inventory/foundation.local.yml playbooks/foundation.yml --syntax-check
   ```

5. タスクのcheck mode挙動と秘密を含むdiff出力の扱いを確認し、対象1台へcheckを行う。初期のUbuntu管理ユーザーがsudoのパスワードを必要とする場合は、`--ask-become-pass`のプロンプトで、inventoryの現在の`ansible_user`に対応するsudoパスワードを入力する。これから作る管理者のパスワードやSSH鍵のパスフレーズとは別である。秘密値をコマンド引数、inventory、作業ログに書かない。現在の接続ユーザーにパスワード不要sudoが設定されていることを確認できた場合は、このオプションを省略できる。予測できない項目はリストへ残す。checkが通らない理由を把握せず実適用で解決しようとしない。

   ```bash
   ansible-playbook -i inventory/foundation.local.yml playbooks/foundation.yml --check --limit ans-01 --ask-become-pass
   ```

6. 対象、SSH復旧経路、変更内容、保存済み状態が一致したら、同じinventory・同じSHAで実適用する。直後に新しいSSH接続を開いて管理経路が保たれていることを確かめる。最初の接続は確認終了まで保持する。

   ```bash
   ansible-playbook -i inventory/foundation.local.yml playbooks/foundation.yml --limit ans-01 --ask-become-pass
   ```

7. 同じコマンドを2回目として実行し、全ログとPLAY RECAPを保存する。`failed=0`、`unreachable=0`、2回目の`changed=0`を期待する。変更が残る場合はタスク名・理由・影響を分析し、検証だけのタスクの誤検知でも無視せず定義を修正して再試験する。
8. 対象VMでOS、管理ユーザー、sudo、SSH、Firewall、Docker daemon、意図した待受を実機試験する。`site.yml`まで構築した場合はその受入手順で利用者の入口、認証、監視の実応答も確認する。`foundation.yml`だけで監視アプリが構築されたとは扱わない。

**期待結果：** 2回の適用ログと実機の受入結果が揃う。構文検査、check mode、実適用、サービス受入の四つを別々に判定できる。

**失敗・戻し方：** 誤対象、SSH不能、権限不備があれば後続を止める。コンソールから直前の設定を戻し、接続回復を記録する。想定外に複数ホストが表示されたらinventoryを直すまで実適用しない。`ignore_errors`や常時`changed_when: false`を足して表示上の成功にしない。

**提出物：** 秘密を除いた対象構成、SHA、構文・check結果、初回・2回目の全ログと終了コード、実機受入、例外一覧。

**自分の言葉で説明：** inventoryとは何か。`changed=0`なのにHTTPが失敗するとき何を調べるか。CIの構文検査とVMへの適用結果はなぜ別か。

**補習：** 変更が残るタスクを一つに絞り、現在値・期待値・変更前後を比較する。[基盤案件パックの試験仕様](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/docs/build-package-ansible/06-test-specification.md)へ戻る。

## SE05-C4 新規VMをコードから再構築し旧版への切戻しを試す

**目的：** 特定のVMや記憶の中に残る手作業に依存せず、対象版から環境を再現します。本条件は`independent`必須です。公式資料と自作手順書は参照できますが、AIや他人から次の操作指示を受けた試行は練習として記録し、自力の試行を別に行います。

**前提：** SE05-C1〜C3の記録がある。新規OS VMが既存アプリや設定をコピーした完成イメージではないことを説明できる。初回試行Aの正常な版・バックアップ・秘密値の復元先を確保する。

**実施手順：**

1. 再構築対象を記録する。VM UUID等の識別情報、新しい仮想ディスク、OS導入時刻、ソフト導入前の状態を採録する。VM名を変えただけの既存VMは使わない。
2. 管理端末でGitから採用SHAを取得し、管理用設定と秘密値を別の正規経路から与える。配置した内容を記録する。秘密値そのものを証跡に入れない。
3. 自作手順とコードで基盤・選択したサービスを構築する。手動で補った操作があれば理由とコマンドを記録し、恒久的に必要ならコードか前提手順に取り込む。
4. SE04の必須試験を再実行し、初回環境との機能・権限・設定差分を照合する。ホスト名やIPのように変更が必要な値と、不意に変わった値を分ける。
5. 小さな変更版Bを適用して受入する。その後、変更票に従って既知の正常版Aへ戻す。秘密値・volume・データ形式をGitの切替だけで戻せると仮定しない。
6. 旧版Aに戻ったファイル・稼働版・利用者操作・データ・監視を確認し、切戻しに要した時間を実測する。戻す対象は今回の新規VMだけに限定する。
7. 構築時間を、OS準備、依存取得、適用、試験、復旧の区間に分ける。待ち時間や失敗修正も消さない。別日再構築はSE07でさらに行う。

**期待結果：** 新規VM上で必須試験が通り、旧版へ戻した後も利用者操作が成功する。再現に必要な入力と手順が資料にあり、本人が判断した根拠を説明できる。

**失敗・戻し方：** 説明できない手動設定に依存したら、その箇所を練習へ戻す。切戻し中にデータ互換性の問題を見つけた場合は変更を重ねず、保全したデータと設計を照合して復旧計画を作り直す。障害VMとログを確認前に削除しない。

**提出物：** 新規性の証拠、初期状態、環境Aとの差分、構築全ログ、必須試験、B→A切戻しの実測、参照資料、受けた支援の記録。

**自分の言葉で説明：** Gitに置くものと置かないものは何か。VMのコピーによる復帰と新規構築の実証はどう違うか。自動化が途中で止まった時にどこから再開できるか。

**補習：** 再現できなかった操作を1件だけSE04の設計・手順・試験へ戻し、SE05-C3で2回適用を確認する。その後、新しい試行IDでSE05-C4を行う。

## 段階を閉じる

自動化の成功ログだけでなく、対象の実応答、失敗時の停止、切戻し後の状態を[レビュー記録](../templates/review.md)へ結びます。4条件の最新版の試行が揃ったら[評価手順](../assessment.md)へ進みます。本人以外の評価後に[SE06](06-operations.md)を始めます。
