# SE07 条件変更から引き渡しまで

[育成システム](../README.md) / [前段 SE06](06-operations.md) / [評価手順](../assessment.md) / [設計パック](../templates/design-pack.md)

**総合課題では、合意用の要件から新規VMを構築し、別日に条件を変えて再構築し、未知障害に対応し、別の人へ引き渡します。** ここまでの教材で覚えた操作を、条件を見て自分で選び直せるかを確かめます。

24週間の学習を終えた後、4〜8週間を計画の目安にします。これは習熟速度や職務能力を保証する期間ではありません。確認するのは、合意した小規模Linuxサーバーの範囲で、要件確認・設計・構築・試験・復旧・引き渡しを自分で進め、担当範囲を越えるときに止めて相談できる力です。雇用上の資格、すべてのサーバー技術の習得、商用本番運用の認定ではありません。

## 誰が何をするか

| 役割 | 実際に行うこと | 代わりに行ってはいけないこと |
| --- | --- | --- |
| 学習者 | 設計判断、構築、検査、調査、記録、説明 | 評価者の観察や受領を代筆する |
| 評価者 | 課題条件の確認、独立試行の観察、未知障害の選定・注入・保全、評価記録 | 答えを教えながら自力試行として合格にする |
| 引き渡しを受ける人 | 手順書を使った実操作、質問、残課題の確認、受領状態の記録 | 資料を開いただけで操作完了とする |

引き渡しを受ける人は本人以外の実在する人が必要です。評価者と同じ人が兼ねてもかまいませんが、初見で読んだ範囲、事前に知っていた範囲、与えた補足を記録します。評価者や受領者を確保できない場合は、資料と練習を先に進め、人の実施が必要な条件をBLOCKEDまたは未実施で残します。AIは人の観察者や受領者として署名しません。

## 開始条件

- SE00〜SE06が本人以外の評価を経てPASSである。SE06の複数日観測の不足や未実測を持ち越して完了扱いにしない。
- 新規OSから作るローカル学習VMと、別の管理端末を使える。OSの導入とコンソール復旧に必要な手順を持っている。
- 実個人情報や会社データを含まないサンプルを使い、既存サービスへ影響しないラボネットワークを用意できる。
- ソース、非公開設定、秘密値、バックアップ、評価記録を分けて保存できる。
- 必須条件、測定目標、時間枠、停止条件、評価者、受領者、評価日時を事前に記録する。新しいクラウド契約、外部公開、有料サービス利用は必須にしない。

4条件とも`independent`が必要です。公式資料と自作手順書は参照できます。AIによる次のコマンドの指示、他人の逐次操作指導を受けたら、その試行は`ai`または`guided`として練習記録に残します。指示を隠さず、習熟後に別の新規試行で独立して実施します。

## 課題：小規模な在庫受付サービスを構築する

**依頼文：**「研修用の備品を扱う担当者が、在庫一覧を確認し、受け付けたサンプル品を追加できるようにしてください。利用できるのは隔離したラボの許可済み利用者です。障害に気付き、データを別の環境へ戻し、次の担当者が手順書を読んで点検できる状態で引き渡してください。」

標準ルートは、[既存3層ラボ](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/labs/three-tier/README.md)を、新規Linux VM上にSE05の[Ansible基盤](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/ansible/playbooks/foundation.yml)から載せる構成です。業務機能を一から開発する課題ではありません。提供済みの[AP実装](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/labs/three-tier/ap/app.py)は次の範囲です。

| 実装済みの機能 | 課題で使う操作 | その機能だけでは確認できないもの |
| --- | --- | --- |
| `GET /` | 在庫のHTML一覧表示 | 更新・削除用GUI、利用者管理 |
| `GET /api/items` | ID・SKU・名称・数量の照合 | 企業向けの検索・承認業務 |
| `POST /api/items` | JSONでSKU・名称・数量を登録 | GUI登録フォーム、監査証跡、二重受付の業務制御 |
| `GET /api/items/count` | 件数の照合 | 内容が正しいこと、復元の完全性 |
| `/web-healthz`、`/healthz`、`/readyz` | Web生存、AP生存、DB依存を分けて観測 | すべての利用者操作が成功すること |

提供コードにない機能を実装済みとして設計書へ書きません。削除、受注、決済、SSO、複数拠点への自動切替を要件へ足す必要はありません。

一方、[既定のCompose構成](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/labs/three-tier/compose.yaml)は隔離された学習用です。固定のラボ用パスワード、TLS・利用者認証なし、`POSTGRES_USER=app`による初期管理ロールを含みます。これをそのまま最小権限の完成構成と扱ってはいけません。SE03で実施した認証付き入口、TLS、秘密値分離、DB管理用とアプリ用ロールの分離を、自分の構成へ組み合わせるところも課題に含めます。流用元の設定を読んで、実際に追加・変更し、許可と拒否を試験します。

入口の作り方、接続元、ラボ用の信頼経路はSE03で使った方式を採用してよいものとします。3層ラボ自体にはホスト向け公開ポートがありません。入口を追加する場合は通信表に載せ、ラボ内の意図した接続元だけに限定し、設定したことと実際に到達制御できることを別に確認します。

既にSE03〜06を[server監視基盤](https://github.com/ns7jp/server/blob/44c52e733826b9b5239918c05010b8b68b60346c/README.md)で統一した学習者は、評価者と事前に「運用担当者向け監視Webサービス」を代替案件にしてもかまいません。その場合も要件→試験の表を事前に作り、監視・閲覧・通知・別対象復元など実装にある業務操作へ置き換えます。在庫登録APIや業務DBがあるとは書かず、機能・データ・権限の評価範囲を明示します。

## 必須要件と受入試験

以下を案件内IDとして設計パックに採用し、採用する構成に合わせて測定条件を確定します。育成条件ID `SE07-C1` 等と混同しません。

| 案件内ID | 必須要件 | 受入で残す証拠 |
| --- | --- | --- |
| CAP-REQ-01 | 新規OSのVMから対象版を構築する | VM識別情報、OS導入時刻、導入前状態、教材とアプリのSHA、適用ログ |
| CAP-REQ-02 | 許可した利用者が在庫を一覧・登録できる | 既知のSKUの一覧一致、JSON登録、登録後照合、入力不足の拒否 |
| CAP-REQ-03 | 入口の認証・TLSと接続元制御が機能する | 許可時成功、不正資格情報拒否、不許可経路拒否、証明書の名前・信頼・期限 |
| CAP-REQ-04 | APとDBの権限を限定する | アプリ権限で必要操作成功、管理操作拒否、Web→DB直接接続拒否 |
| CAP-REQ-05 | 事前に決めた応答目標を満たす | 条件を固定した応答時間の生データ、失敗数、集計方法 |
| CAP-REQ-06 | 障害を検知し演習用宛先へ通知する | 実症状→発火→受信→復帰→解消の時刻、外部送信の有無 |
| CAP-REQ-07 | 別対象にデータを復元し利用者操作へ戻せる | バックアップ、元/先の識別、内容一致、損失データ、復旧時間 |
| CAP-REQ-08 | 再起動後に必要なサービスと設定が戻る | OS起動時刻、永続マウント、SSH、利用者応答、監視・バックアップ予定 |
| CAP-REQ-09 | 別の人が手順書で点検と指定操作を行える | 相手の実操作ログ、質問、受領または保留、残課題 |

アプリ権限の拒否試験は専用の検証DBで行い、本番や既存データを削除して確かめません。管理操作の実行が拒否された理由を確認し、構文誤りや道具不足による失敗を権限制御の成功へ読み替えないでください。

## 目標値を先に決め、実績は後から測る

初回計画に使える**目標例**を示します。能力の認定基準になる共通の保証値ではなく、評価者と合意するラボの仮条件です。データ数やPCの性能に合わなければ、開始前に理由を付けて変更します。

| 項目 | 目標例・条件 | 実測値の初期状態 |
| --- | --- | --- |
| 一覧応答 | 単一client、並列数1、サンプル100件、予熱5回の後GET100回、p95 1秒以内、失敗0件 | NOT RUN |
| 障害検知 | 対象サービス障害から演習用受信先での検知まで3分以内 | NOT RUN |
| 復旧 | 検知から利用者の一覧・登録再開まで60分以内 | NOT RUN |
| データ損失 | RPO 24時間以内を例とし、バックアップ周期・最終復元点を測る | NOT RUN |
| 再起動後復帰 | VM再起動開始から、手動起動なしで利用者操作が戻るまで10分以内 | NOT RUN |

応答時間は成功要求の時間と失敗数を分けて集計し、測定場所、OS、VM資源、並列数、データ数、期間、p95の計算方法を残します。少数回の計測や低負荷試験から商用負荷時の性能を断定しません。

RTO・RPOは目標です。実測欄には実際の復旧所要時間、戻った最終更新、戻らなかったIDと件数、確認できた損失時間幅を記載します。バックアップ後に追加したデータの時刻を取っていなければ、推測で損失時間を埋めません。未達後に目標を変更しても元の未達を保存し、変更した目標に対して新しい試行を行います。

## 4〜8週間の進行例

| 期間の目安 | 行うこと | 次へ進める条件 |
| --- | --- | --- |
| 第1週 | 要件確認、設計、試験計画、評価者との条件確認 | 必須範囲、目標、停止条件が確定 |
| 第2〜3週 | 初回の新規構築とSE07-C1 | 必須試験と本人説明が揃う |
| 第3〜5週 | 別日・別セッション・条件変更でSE07-C2 | 新規性、変更への対応、再受入が揃う |
| 第4〜6週 | 評価者が選んだ未知障害でSE07-C3 | 調査・復旧・中止判断の記録が揃う |
| 第5〜8週 | 第三者の実操作とSE07-C4、指摘修正、再評価 | 受領状態、残課題、評価者の記録が揃う |

予定より時間が必要なら、理由と元の期限を残して計画を更新します。期間内に終わらせるために失敗や支援量を隠したり、未実施を埋めたりしません。

## SE07-C1 要件から新規VMへ自力で構築し全必須試験を通す

**目的：** 要件から必要な操作を自分で選び、初期状態から受入まで一つの案件として完了します。

**前提：** 開始条件と案件要件が確定しており、評価者が独立試行の開始時点と参照可能資料を確認している。SE05で作った完成VMをそのまま提出せず、新規OS VMを使う。

**実施手順：**

1. 試行AのセッションIDと開始時刻を記録する。VM UUID等、ディスクの新規性、OS導入時刻、Dockerやアプリが未導入である状態を採録する。OSイメージには既習のアプリを含めない。
2. 要件ごとに設計、設定値、試験、証跡先を用意する。単一VM内の3層構成であること、単一VM停止で全層が影響を受けることを依頼者役へ説明する。
3. 採用するリポジトリのSHAを固定し、SE05の基盤から構築する。秘密値は専用の保管先から渡し、Gitや採録ログに入らないことを確認する。
4. SE03の認証・TLS・権限の成果物を取り込み、流用した既定値との違いを記録する。DB管理ロールをAPが使っていないことを、設定と必要操作・管理操作の試験で確かめる。
5. CAP-REQ-01〜09のうち引き渡し実施前にできる必須試験をすべて行う。引き渡し用資料も作成し、実際の第三者受領はSE07-C4で実施する。未実施のC4をこの時点で受領済みにしない。
6. バックアップを別DB/別VMへ復元し、元データの保全、内容一致、更新後サンプルの損失、利用者操作復帰を確認する。既存B-3スクリプトの元DB内復元だけで充当しない。
7. 再起動後の状態を手動起動前に観測する。初回適用と2回目適用、利用者試験、監視、復元、再起動を別々の結果にする。
8. 評価者に構成を説明し、任意に選ばれた要件から証跡へたどる。未達を直した場合は新しい試行または再試行として追加し、旧結果を保存する。

**期待結果：** C1で実施する全必須試験が成功し、構成と判断を自分で説明できる。C4の第三者実施など後続条件は別に未実施で管理し、総合完了を先取りしない。

**失敗・戻し方：** 不明な設定のまま進めない。影響がラボ外へ広がる、秘密値が露出する、復元元を破壊する可能性がある場合は止める。支援が必要なら練習へ切り替え、支援履歴と未達を残し、改めて新規VMで独立試行を行う。

**提出物：** [設計パック](../templates/design-pack.md)、新規VMの初期状態、構築ログ、対象版、全必須試験の追跡表、バックアップ・復元と再起動結果、支援記録、本人説明。

**自分の言葉で説明：** 任意の1要件について、なぜこの設計か、何を測ったか、何がまだ保証できないかを3分で話す。コマンドの名前だけで説明しない。

**補習：** 失敗が要件ならSE04、再現性ならSE05、検知・復元ならSE06へ戻す。補習を終えた証拠と次の独立試行を別に残す。

## SE07-C2 別日・別セッションに条件を変えた新規VMを再構築する

**目的：** 一度できた設定を繰り返すだけでなく、変わった要件を見て必要な差分を判断します。

**前提：** C1の試行Aが記録済みで、評価者が結果を確認している。別の新規OS VMを用意し、試行Aとは異なるUTC日付とセッションIDで試行Bを行う。日本時間の表示だけで日付条件を判断しない。

**変更条件の選び方：** 評価者と事前に決めた安全な範囲から、評価者が試行B用に少なくとも2項目を提示します。単なるホスト名変更だけで終わらないよう、通信または運用条件を必ず1項目含めます。

| 変更例 | 学習者が判断し直す範囲 | 再試験するもの |
| --- | --- | --- |
| ラボネットワークの別サブネット、管理接続元変更 | IP表、経路、DNS/名前、Firewall、inventory | 許可・拒否・管理復旧経路 |
| VMのメモリを利用可能範囲内で減らす | 資源割当、ワーカー数、監視、性能目標との整合 | 応答時間、失敗数、メモリ、復旧 |
| バックアップ先を別の新規VMへ変える | 保存先、権限、転送経路、容量、復元手順 | バックアップと別対象復元、損失時間 |
| 許可利用者・管理者を学習用の別アカウントへ変える | 認証情報の正規取得、権限、失効、資料 | 新アカウント成功、旧アクセスの扱い、運用操作 |

**実施手順：**

1. 試行Bの条件書、開始時刻、UTC日付、セッションID、新規VM識別情報、OS初期状態を採録する。試行Aの完成VMの名前変更、ディスク複製、完成後スナップショットの復元は新規構築として認めない。
2. 条件の差分を要件→設計→設定値→試験→引き渡しに反映する。変更されない要件も受入に必要なものは再試験対象にする。
3. 自作手順と公式資料を使い、構築を実施する。新しい環境でハードコード値や未文書化の依存が見つかったら、根拠を記録して修正する。
4. C1と同じ必須試験と変更条件の追加試験を行う。初回・2回目適用、許可・拒否、性能、別対象復元、再起動を試行B自身の証跡で確認する。
5. 初回と2回目の設定・時間・失敗・データの違いを比較する。短時間になった場合も測定範囲が同じか確かめる。差分を隠すために目標を後付け変更しない。
6. 小さな設定変更と切戻しを試行Bの環境でも行い、変更前の利用者操作が戻ることを確認する。

**期待結果：** 別UTC日付・別セッション・別新規VMで、変更された条件を満たし、同じ必須機能を再現できる。既存の完成環境を利用しただけの結果と区別できる。

**失敗・戻し方：** 旧IPや旧権限を使い続けたら、変更影響の分析へ戻る。VM再作成を理由に試行Aを消さない。独立性が保てなくなった場合は支援付き練習を追加し、改めて別の試行で評価する。

**提出物：** 条件変更書、A/B比較、新規VMの証拠、UTC日時・セッション、構築・試験・切戻し、支援記録、変更した設計と引き渡し資料。

**自分の言葉で説明：** 変更条件のうち影響が最も広かったものは何か。IPを変えるとどの資料と試験が変わるか。以前の実測を今回の結果へ流用できない理由は何か。

**補習：** SE04の追跡表で変更から影響先をたどり、SE05で値を外出しする方法を練習する。条件を満たす新しい独立試行を計画する。

## SE07-C3 評価者が選んだ未知障害を復旧し中止判断を説明する

**目的：** 原因が書かれた演習の再生を越え、症状と証拠から調査順序を決められることを確認します。

**前提：** 評価者が実際に参加し、正常状態、戻す手順、データ保全、演習対象、制限時間を確認済みである。学習者は正常性を検査できるが、注入原因と操作を事前に知らない。

**評価者の準備：**

1. 学習者の既実施シナリオを確認し、既習領域内で本人に原因を教えていない障害を一つ選ぶ。通信、サービス依存、設定、権限などから、対象ラボだけで安全に戻せるものを選ぶ。
2. 注入する設定、正しい復旧状態、復旧手順、最大影響、中止時刻を学習者に見えない評価者記録へ保存する。実データの削除、OSディスクの枯渇、ホストPCの停止、秘密値の漏えいは使わない。
3. 正常状態の証拠を取った後に注入し、本人には「利用者症状」「対象範囲」「制限時間」「中止条件」を提示する。原因名、次のコマンド、正しい仮説は提示しない。

既存の`run-drill.sh`を本人が読み、既知の障害を決まった順に実行してPASS出力を見るだけでは、この条件を満たしません。AIが障害を選んだ文章だけを生成しても、評価者の実注入・観察の代わりにはなりません。

**学習者の実施手順：**

1. 検知と利用者影響を確認し、[障害記録](../templates/incident.md)に初報の下書きを残す。確認済みと推定を分ける。
2. 変更履歴と正常状態を読み、入口→依存先の順に観測する。毎回、今の仮説、検査で区別できること、実際の結果、次の判断を記録する。
3. 原因が一つに絞れたら、対象と影響、戻す方法を説明して限定した復旧操作を行う。原因が不明なまま全サービスを何度も再起動しない。
4. 原因と影響を説明できない、データ保全が不確か、対象外への影響がある、残り時間で戻せないと判断したら止める。状況、実施済み操作、証拠、残る仮説、必要な支援をエスカレーション用の文書にまとめる。
5. 利用者操作、依存先、データ、監視、通知収束を確認して復旧を判定する。復旧した時刻と終了判断の根拠を残す。
6. 演習後に評価者が注入内容を開示し、推定原因と照合する。復旧成否、調査の妥当性、危険な操作の有無、中止判断、説明を別々にレビューする。

**期待結果：** 原因を証拠から説明して復旧でき、危険な状況では中止できる。適切に中止した判断は評価するが、復旧を実証していない試行をこの条件全体のPASSにしない。必要な補習後に別の未知障害で再試行する。

**失敗・戻し方：** 評価者は中止条件に達したら演習を止め、自身が用意した復旧手順でラボを戻す。本人が復旧したことにはしない。ヒントを与えたら、その時刻と支援量を記録し、独立評価とは分ける。

**提出物：** 本人の全タイムライン、検査・仮説・出力、初報/復旧報告下書き、実測時間、中止基準と判断、評価者の注入・観察記録。公開する場合は内部アドレスや秘密を除いた写しを作る。

**自分の言葉で説明：** 最初に疑った原因と実際の原因は同じだったか。誤った仮説をどの証拠で捨てたか。残り時間が半分なら判断をどう変えるか。

**補習：** SE02・SE03の切分けとSE06のタイムラインを練習し直す。評価者が別の原因を選ぶ次回まで、復旧できなかった記録を保持する。

## SE07-C4 別の人が手順書で操作し受領・残課題を記録する

**目的：** 自分が分かる資料から、次の担当者が実際に操作できる資料へ仕上げます。

**前提：** C1〜C3の最終構成が正常で、引き渡す版が固定されている。本人以外の受領者が参加し、操作する学習VM、許可された権限、止める条件を確認している。

**実施手順：**

1. [引き渡し記録](../templates/handover.md)に構成、目的、版、接続経路、権限取得経路、日次点検、バックアップ、復元、停止・起動、異常時連絡、既知の制限、残課題をまとめる。秘密値は本文へ書かない。
2. 受領者へ資料を渡し、最初に対象と期待結果を読み上げてもらう。学習者は横から次のコマンドを指示せず、受領者が資料を読んで選ぶ様子を観察する。
3. 受領者が実際に、対象の確認、ログイン、日次点検、サンプル一覧照合、許可されたサンプル登録を行う。監視基盤を代替案件にした場合は、合意済みの閲覧と監視確認の操作を使う。
4. さらに影響を限定した操作を一つ選ぶ。例えば別の復元先にあるデータの確認、または検証用サービス1件の計画停止と再開を、対象・影響・戻し方が書かれた手順で実施する。受領者が操作に不安を感じたらその場で中止して資料を直す。
5. 受領者が迷った箇所、質問、誤解、必要だった補足を記録する。口頭で助けた内容は資料へ反映し、該当箇所をもう一度受領者が操作する。
6. 受領者本人が「受領」「条件付き受領」「受領保留」のいずれかと理由を記録する。条件付きなら残課題、担当、期限、影響、完了確認者を明示する。必須条件が未達なら総合完了には進めない。
7. 引き渡し後に最終構成の正常性を確認し、公開可能な成果と非公開の生記録を分ける。学習環境、支援、検証範囲、未実施を残した成果説明を作る。

**期待結果：** 別の人が資料から実操作でき、受領状態と残課題が本人の記録で確認できる。資料の存在や感想だけを、引き渡し完了の証拠にしない。

**失敗・戻し方：** 操作中に想定外の対象やエラーが出たら中断し、資料の欠陥か環境差かを分ける。元の正常性を確認してから修正版を再試験する。受領者が参加していない場合は日付・氏名・受領を架空で埋めない。

**提出物：** 引き渡し資料、受領者の実操作ログ、質問と改善、再試行、受領状態、残課題台帳、最終正常性、公開用の成果説明。

**自分の言葉で説明：** 次の人が困った箇所はどこだったか。相手が理解していると思い込んでいた前提は何か。残課題を誰がいつ確認するか。

**補習：** SE04-C4の机上確認へ戻り、質問された箇所を具体的な対象・期待結果・中止条件へ書き直す。同じ箇所を再操作してもらって確認する。

## 最終レビューと能力の表し方

4条件の最新試行と、人による観察・受領の記録を[評価手順](../assessment.md)へ渡します。台帳で`READY FOR REVIEW`になっても、学習者の能力が自動で認定されたわけではありません。判定は証跡の内容と実際の観察を確認した人が行います。再試行や構成変更があれば古い評価を使い回さず、対応する新しい試行のレビューを受けます。

提出時には次の5点を1ページで説明します。

1. **担当できた範囲：** 例として、小規模なLinux VM、ラボ内Web/AP/DB、構成管理、監視、別対象への復元、手順書の引き渡し。
2. **実行環境と条件：** OS・VM資源・ネットワーク・ソフト版・Git SHA・データ量・測定条件・実施日。
3. **自力で判断したこと：** 技術選択、条件変更、障害切分け、中止判断と、それぞれの根拠。
4. **実測と評価：** 宣言した目標、実際の結果、失敗・再試行、支援量、評価者・受領者の確認範囲。
5. **今後の担当外：** 商用負荷、実顧客データ、組織の変更承認、クラウド運用、冗長化など、今回実証していないこと。

合格後も、業務の規模や製品が変われば必要な試験とレビューを追加します。職務経歴書等へ記載する際は「個人学習・検証環境で実施」と明記し、就業経験や本番運用実績に置き換えません。
