# GitHubへの統合仕様

[入口](README.md) / [能力設計](design.md) / [調査根拠](sources.md)

## 何を統合するか

このフォルダは既存の育成体系に接続する設計文書とテンプレートです。BR/BX対応のCLIや自動昇級処理は未実装です。本章は文書の構成、記録の境界、将来自動化する際の契約を定義します。

基本方針は、育成の正本を`ns7jp/ns7jp`に、動かすラボを`ns7jp/server`に置く既存構成を維持することです。SEの32条件、PJの24条件、serverのLevelを改番しません。上位能力BRは見取り図として追加し、発展課題BXの記録から、根拠のある説明を作れるようにします。

## 文書の配置と接続

育成入口のREADMEとリポジトリのREADMEから、このフォルダへ案内します。SEの評価要約と学習時間の注記も整合させます。

| ファイル | 役割 |
| --- | --- |
| README.md | 読む順序、既存SEとの関係、最初の行動 |
| design.md | BR0〜BR6の能力設計と専門分岐 |
| practice.md | BX01〜BX12、48必須条件と評価方法 |
| action-plan.md | 最初の2週間、24週、配属後の計画 |
| templates.md | 本人の試行とレビューを記録する9種類の枠 |
| sources.md | 確認日・調査SHA・出典・境界 |
| implementation-contract.md | 本仕様と将来自動化する場合の契約 |
| validation.md | 文書検査の記録と未実施範囲 |

実行ラボと過去の実測は引き続き[server](https://github.com/ns7jp/server)を参照します。追加カードは演習設計であり、新規ラボの動作実績ではありません。server側や公開サイトからの追加案内は、文書統合後の別変更として扱います。

## 正本と記録の関係

| 情報 | 正本 | BR/BX側の扱い |
| --- | --- | --- |
| 基本能力とSE条件 | 既存`curriculum.json`とSE評価仕様 | 参照する。新規の評価JSONへ32条件を複製しない |
| 本人のSE試行と人の評価 | 既存ローカルSE台帳 | learner ID、試行ID、版、レビュー参照を使う |
| 案件の工程・承認・検収 | 既存PJ台帳 | 案件と本人の役割を参照。技能PASSと業務承認を結合しない |
| 発展課題の内容 | このフォルダのBX課題定義 | 定義版と適用日、変更理由を持たせる |
| 発展課題の本人記録 | 初期は非公開のMarkdown記録 | 条件別の結果、実測、支援量、人の確認を残す |
| 公開表示 | 秘匿化した成果の説明 | 生ログ・顧客情報・承認者の個人情報を含めない |

既存CLIの`--criterion`へBRやBXを入力しない。初期段階は[記入テンプレート](templates.md)を本人の非公開領域へコピーして使う。SEの証跡ファイルを新記録へコピーする代わりに、試行IDと保存先を参照する。

## 自動化する場合のデータ契約案

これは将来実装時の項目仕様です。存在しないCLIコマンドを本設計に掲載しません。

| 項目 | 内容・制約 |
| --- | --- |
| definitionVersion | BR/BXの評価定義の版。後から変更して過去の合格を作らない |
| learnerId / attemptId | 学習者識別子と一試行の一意ID。実名公開を必須にしない |
| exerciseId / criterion | BX01〜BX12とカードの必須条件1〜4 |
| performedAt / recordedAt | 実際の実施時刻と登録時刻。タイムゾーン付き |
| environment / target | desk、container、vm、physical、cloud等と具体的な対象・制約 |
| revision / versions | 40桁Git SHA、OS・依存関係・設定差分の版 |
| assistance | guided、ai、independent。実際に受けた支援を記録 |
| expected / actual | 事前の受入条件、実際の出力・測定結果 |
| result | PASS、FAIL、NOT RUN、BLOCKED。必須条件をNAで免除しない |
| evidenceRefs | 非公開証跡の参照とハッシュ、公開版の有無、マスク範囲 |
| relatedSE / relatedPJ | 元記録のIDと版。参照だけで追加条件を充足させない |
| review | 対象試行、文書/実技の範囲、実在の評価者ID、日時、判断、理由 |
| invalidation | 対象・版・要件の変更に伴う再確認範囲。履歴を消さない |

ハッシュはファイルの同一性の確認であり、内容の事実性や実施者の認証ではありません。評価者名の入力も、本人確認や熟練認定を自動保証しません。

状態表示は「未実施」「実施中」「再提出」「評価待ち」「演習条件確認済み」「条件変更で再確認」を区別します。実務で任せる範囲の判断は別項目とし、演習が完了したという理由だけで業務権限や技能称号を更新しません。

## 現在の変更と後続作業

| 単位 | 変更内容 | 確認するもの |
| --- | --- | --- |
| 1 文書整合 | 週10/15時間、SE07-C2要約と詳細の差を整理 | 正本・詳細・要約が同じ意図を表す |
| 2 橋渡し文書 | BR見取り図、BX課題、記入枠、既存入口とのリンク | ID、相互リンク、実装/実測/未実施の表記 |

今回の変更は1と2を対象とする。3以降のユーザー実施や評価者観察を、コード検査の成功で済ませない。CLIを増やす前にMarkdown運用で負担と不足を確認する。

## 受入条件

- すべてのBRが既存SEまたはBXの実在する定義へつながる。
- 12枚のBXカードすべてに前提、操作順、必須条件、失敗時の補習、証拠、評価範囲がある。
- 基本課程の条件・番号を変更しない。SEとPJに同じ名前の新しい台帳を作らない。
- 学習者の初期状態は未確認・未実施である。資料生成でPASSを作らない。
- 過去のFAIL、旧期限、支援量、欠測、評価者不在を消さない。
- 正常系だけでなく否定条件、復元後の利用者操作、他者による再現を評価できる。
- 既存の文書・リンク・定義検査を適切な環境で実施し、成功した検査名と対象版を残す。
- 公開後は実際のページでリンクと表示を確認し、CIの成功だけで利用者の到達を推定しない。

## 自動化を追加した場合に必要な検査例

単なる文書追加のために大きなテスト群を増やす必要はありません。状態管理を実装する場合は、誤った合格を防ぐ振る舞いを検査します。

| 入力状況 | 必要な結果 |
| --- | --- |
| 全記録が未実施 | 合格・熟練表示を出さない |
| 1条件FAIL、他3条件PASS | 課題を合格にしない |
| 机上説明だけで実行必須条件を提出 | 環境条件を満たさないと表示 |
| 独力条件の試行がai/guided | 練習記録を残し、独力確認は未充足 |
| 実技必須課題に文書レビューだけ添付 | 実技観察を確認済みにしない |
| 新しい試行や構成へ変更 | 古いレビューを自動で流用しない |
| 未知のBX ID、証跡欠落、別学習者の承認 | 入力を拒否または明示的に未充足とする |
| 全演習条件が確認済み | 実務権限・雇用上の経験を自動付与しない |

## 教材の保守

月1回を点検の目安に、リンク切れ、対応OS/製品版、変更された実習の期待値、本人・評価者の詰まりを確認します。この文書はスケジュールの提案であり、自動実行や通知を登録したものではありません。

定義変更時は理由、影響する条件、旧記録の再評価要否を記録します。旧版の実施結果は残し、現在の条件を満たすかは別に確認します。読者から得た意見は採否待ちに置き、担当者が採用した変更だけを正本へ反映します。
