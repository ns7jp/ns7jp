# 発展課題カード：中級から熟練への12の橋

[入口](README.md) / [能力設計](design.md) / [実行計画](action-plan.md) / [記入テンプレート](templates.md)

作成日：2026-09-06 / 状態：文書化済み・実技未評価。全課題の本人実施は NOT RUN、人の評価は未実施です。

BR4はBX01〜04、BR5はBX05〜08、BR6はBX09〜12を使用します。BRは能力を説明する見取り図です。新しい段階PASSの台帳を作らず、SEとBXの根拠を集約し「この対象・条件の演習で相当する能力を確認」と記録します。説明を読むこと、支援付き練習、設計準備は並行できます。

課題には練習段階と評価段階があります。練習ではAI・講師の支援を使い、その支援量を残します。評価では公式文書と自作手順書を参照しながら、本人が次の操作と判断を選びます。原因・コマンドの答えを与えられた試行は独力評価へ転記しません。人の評価は文書レビューか実技観察かを分け、最新の試行ID・対象・版へ結び付けます。

各カードの4条件はすべて必須です。FAIL、NOT RUN、BLOCKED、欠測で確認できない条件は合格へ集計しません。環境の都合で実施できない場合はBLOCKEDと理由を残し、同じ能力を実際に観察できる代替環境を計画します。必須条件をNAへ変更して完了させません。機能追加などの任意観点に限り、理由と評価者の確認を付けて対象外とできます。

これらは本計画の発展演習基準です。全課題が確認できても、実務の経験・権限・継続成果は別に確認します。

**能力を確認したと記載する前提：** BR4はSE00〜SE07の必要条件と人の評価、BX01〜04の全条件を確認します。BR5はその根拠にBX05〜08、BR6はさらにBX09〜12を加えます。既存SEの判定は変更せず、参照した試行・版・人の評価を記録します。前提が不足していても、発展課題の練習記録は保持できます。

**人が確認する範囲：** 対象領域の構築・運用・復旧または設計判断を評価できる本人以外の人と、観察範囲を決めます。BX01〜04・06〜08は実技、BX09は他者による再現、BX10はレビューと指導後の本人理解、BX12は標準の利用と改善結果を確認します。BX05は設計書と本人の判断説明、BX11は比較資料と関係者との判断過程を観察します。BX05・11を机上演習で行った場合、合意は演習内の意思決定と明記し、本番稼働・実組織の決裁にしません。生ログや資料を読んだだけのレビューは、実技観察や他者実行の代替になりません。

## 12の発展課題

### BX01: 再構築とドリフトを制御する

**段階:** BR4。**前提・入力・環境:** SE00〜07の基礎構築と確認方法を説明できる。入力は構成コミット、OS/依存版、通信表、検証用データ。隔離した既存環境と空の別環境を用意する。秘密情報は公開ファイルへ入れない。

**実行順:**

1. 構成から「変更してよい設定」「保持するデータ」「秘密情報」を分け、両環境の識別情報を記録する。
2. 空環境に構築し、外部クライアントから正常操作・認証拒否・通信拒否を検証する。
3. 構築処理を再実行し、不必要な再起動・変更・データ削除がないか確認する。
4. 許可した検証設定を一つずらしてドリフトを検出する。意図した変更かを判定して修正し、再検証する。

**全必須の合格条件:** (1) 元環境への非公開の手作業に依存せず別環境が成立する。(2) 正常・拒否の期待結果が一致する。(3) 再実行後も検証データと必要な設定が保持される。(4) 仕込んだ差分を検出し、設定変更の採否と是正後の状態を説明できる。

**不合格例と補習:** 起動確認だけ、差分を無条件上書き、再実行でデータ初期化。構成処理とデータ操作を分離し、差分一つだけの小さな試験からやり直す。

**証拠:** コミット、環境情報、初回/再実行ログ、差分、利用者操作結果、データ比較、判定。**職場での境界:** 自動化の演習合格は本番への自動適用権限を意味しない。構成ドリフトにも緊急変更など理由があり、正しい状態の決裁者を確認する。

### BX02: 複数台と依存故障を扱う

**段階:** BR4。**前提・入力・環境:** IP、DNS、待受ポート、サービスログを読める。隔離環境の独立したOSを持つVMまたはホストを2台以上使い、Web・アプリ・DBの層を分け、少なくとも一つの層間通信をOS境界の外へ通す。検証用データを使い、入力は通信許可表と利用者操作一覧。同じ物理ホスト上のVMでも複数OSの練習はできるが、物理故障への冗長化は未検証とする。

**実行順:**

1. 正常時の名前解決、接続経路、認証、データ更新を確認して基準値を保存する。
2. 許可する接続と拒否する接続を送信元ごとに試験する。
3. DBなど一つの依存先を停止し、利用者への症状、タイムアウト、エラー、各層のログを観測する。
4. 依存先を復旧し、再接続・重複処理・データ整合を確認して依存関係図を改訂する。

**全必須の合格条件:** (1) 2台以上のOS境界をまたぐ経路で、許可/拒否が通信表と一致する。(2) どの層が故障し、どこに症状が出たか時系列で説明できる。(3) 復旧後に参照・更新が成功し、意図しない重複がない。(4) 同一ホスト・DNS・認証など共通原因となる依存先を明示する。

**不合格例と補習:** すべてのポートを許可して解決、3台起動だけで終了。二層構成へ縮め、送信元・宛先・ポート単位で接続と拒否を確認する。

**証拠:** 通信表、構成図、正常/拒否テスト、停止/復旧時刻、各層ログ、データ確認。**職場での境界:** 故障注入は許可された検証対象に限る。共有DNSや認証基盤を実習目的で止めない。

### BX03: 別環境へ復元して利用を再開する

**段階:** BR4。**前提・入力・環境:** 対象データとバックアップ方式を説明できる。入力は演習用RTO/RPO、保護対象、バックアップ世代、データ照合方法。元環境と隔離された復旧先を使う。

**実行順:**

1. 元環境が使えない前提で、バックアップ・鍵・資格情報・手順を取得できるか確認する。
2. 最新の復元可能時点と期待データを記録し、復旧開始時刻を採る。
3. 新環境に復元し、内容と整合性、認証、参照、更新を確認する。
4. 業務確認完了時刻を採り、実測時間とデータ損失範囲を目標と比較する。

**全必須の合格条件:** (1) 元サービスに依存せず必要な復旧資材を取得できる。(2) 復旧先でデータの意味と整合性が期待通りである。(3) 利用者操作が成功する。(4) 演習目標を満たし、開始/終了の定義と実測値が揃う。目標未達はFAILとして改善する。

**不合格例と補習:** バックアップ成功のみ、同一環境へ戻すだけ、件数だけ一致して内容未確認。小さな既知データで内容照合し、復旧資材の不足を埋めて再実施する。

**証拠:** バックアップ識別子、復元時点、実行ログ、データ照合、業務確認、実測、目標比較。**職場での境界:** 本番への上書き復元や実データ持出しを演習として行わない。ラボ値は本番のRTO/RPO保証に転記しない。

### BX04: 負荷・容量・欠測を継続して観測する

**段階:** BR4。**前提・入力・環境:** HTTPの成功/失敗、CPU、メモリ、ディスクの意味を説明できる。隔離したサービスと負荷発生器を使う。入力はリクエスト内容、データ量、段階別負荷、試験時間、停止条件、成功率/遅延の演習目標。

**実行順:**

1. 試験前に測定点、採取間隔、分母、エラー定義、p95の対象となる要求、ウォームアップの扱いを固定する。
2. 通常負荷から段階的に増やし、要求数、成功率、エラー数、p95、CPU/メモリ/ディスク、キューなどを同じ時間軸で採る。
3. 停止条件に到達する前に止め、負荷を下げて回復を確認する。負荷発生器自身が飽和していないかも確認する。
4. 観測を意図的に短時間止めて欠測を識別できるか確認する。別日にも同条件で再測定し、期間を事前に決めた日常観測（初回計画の例は7日）と合わせて、データ増加・ディスク残量・ログ量の変化を記録する。負荷試験・通常観測・停止期間・欠測を分け、容量判断を残す。

**全必須の合格条件:** (1) 別日の測定を含め、負荷条件・測定窓・総要求数・成功/失敗・p95の対象が再現できる。(2) 遅延やエラーの変化を資源の飽和と対応づけ、未確定の原因は推測とする。(3) 事前に決めた観測期間のデータ増加と容量変化を示し、欠測を正常値やゼロへ補完せず判定不能区間として扱う。(4) 停止基準を守り、負荷終了後の利用者操作と資源回復を確認する。

**不合格例と補習:** p95だけ報告して大量のエラーを隠す、集計済みp95の単純平均、試験負荷不明、欠測を稼働扱い。まず一定負荷で生の要求結果と集計を照合し、成功率と遅延を同時に読む。

**証拠:** 負荷設定、実行日時、環境、測定値、エラー内訳、p95算出対象、欠測区間、停止理由、容量判断。**職場での境界:** 承認のない負荷試験を本番・外部サービスへ向けない。短時間ラボの限界値を本番容量や長期稼働率として提示しない。

### BX05: 要件を複数案の設計比較へ変える

**段階:** BR5。**前提・入力・環境:** BR4相当の構築・観測・復旧の制約を説明できる。入力は利用者、業務時間、データ、RTO/RPO、予算、納期、運用人数。実情報がない数値は演習用仮定として記録する。

**実行順:**

1. 要件、制約、仮定、未決事項を分け、要件ごとに検査方法を置く。
2. 単一構成と冗長構成など、実行可能な少なくとも二案を同じ軸で比較する。
3. 費用、共通故障、復旧、運用負荷、移行しやすさを検討し、重要な不確実性を小さな検証で確かめる。
4. 採否理由、残余リスク、未決事項、再検討条件を設計判断記録にまとめる。

**全必須の合格条件:** (1) 重要要件に根拠と検査方法がある。(2) 比較案の条件が揃う。(3) 採用・不採用理由が要件に結び付く。(4) 未確認・残余リスク・決裁者の判断事項が明示される。

**不合格例と補習:** 製品名や高可用性という言葉で採用を決める、比較案の費用範囲が異なる。利用者の一操作と一つの故障を起点に、運用まで含む小さな二案を比較し直す。

**証拠:** 要件表、二案の構成図、比較表、検証結果、設計判断、レビュー範囲。**職場での境界:** 技術者は事業上の損失許容や予算を代理で決裁しない。演習上の仮定承認と実際の承認を区別する。

### BX06: データの整合性を守って移行する

**段階:** BR5。**前提・入力・環境:** BX03の復元と整合性確認ができる。旧/新の隔離環境、既知の更新履歴を持つ検証データを用意する。入力は切替手順、停止可能時間、切戻し期限、整合性基準。

**実行順:**

1. 書込元を時系列で一つに定める。演習では旧新への二重書込を禁止し、どの時点で書込を止めるかと切戻せる最終期限を固定する。
2. コピーと差分適用をリハーサルし、件数・キー・重要項目・関連整合性・業務操作を照合する。
3. 旧側の書込を止めて最終同期し、合格を確認して接続先を切替える。新側の書込開始が切戻しに及ぼす影響を確認する。
4. 期限内の切戻しを試し、期限後は再同期/前進復旧など別計画が必要な理由を記録する。完了後に旧側を誤って使えない状態にする。

**全必須の合格条件:** (1) 各時点の唯一の書込元が確認できる。(2) 移行前後で定義したデータ整合性と業務操作が一致する。(3) 切戻し期限と不可逆点を区別し、期限内の切戻しを実証する。(4) 停止時間、更新の欠落/重複、旧側への残存アクセスを確認する。

**不合格例と補習:** DNSを戻せばいつでも切戻せると思う、新側に書かれたデータを無視して旧側へ戻す。少量データに連番の更新を入れ、書込停止→最終同期→切替の一本の経路を再演する。

**証拠:** 移行時系列、書込元/拒否の確認、同期ログ、整合性比較、切戻し記録、停止時間、残課題。**職場での境界:** 実データの消失や書込停止を伴う切替は承認された計画と権限の範囲で行う。本番で二重書込が必要なら、別途その整合性設計と検証を要する。

### BX07: 未知の複合障害を連携して解く

**段階:** BR5。**前提・入力・環境:** 単一原因の切分けと復旧ができる。隔離環境を使い、評価者が許可された故障候補から二つを選ぶ。実施者には原因を知らせない。連絡・記録・復旧の役割を決める。

**実行順:**

1. 初期症状だけを受け取り、利用者影響と停止/相談条件を確認する。
2. 役割を分け、仮説・観測・反証を記録する。同時変更が衝突しないよう変更担当と記録を一元化する。
3. 復旧を優先して必要な措置を実施し、利用者操作とデータを確認する。原因が未確定なら未確定のまま伝える。
4. 原因開示後に時系列を照合し、検知、切分け、連絡、復旧の改善点を選ぶ。

**全必須の合格条件:** (1) 原因を知らない初回試行の証拠がある。(2) 影響と事実/仮説が分離され、同時変更が統制される。(3) 中断/相談条件を守り、復旧後確認が完了する。(4) 他者との役割分担と情報共有の実行記録がある。

**不合格例と補習:** 原因を知っている再演を未知障害と呼ぶ、全員が別々の設定を直す、一人演習を連携実績にする。単一障害で連絡と変更の担当分離から練習する。

**証拠:** 原因開示時点、症状、時系列、仮説と観測、担当記録、復旧後確認、振返り。**職場での境界:** 演習の統括経験を本番重大障害の指揮実績にしない。本番では既定の指揮系統とエスカレーションを守る。

### BX08: 権限・更新・廃止を一周する

**段階:** BR5。**前提・入力・環境:** 権限、更新、バックアップの基本を説明できる。隔離サービス、複数の検証利用者、資産一覧を使う。入力は役割別権限、更新計画、保存/削除方針、廃止範囲。

**実行順:**

1. 利用者を追加し、役割ごとに必要な操作と禁止する操作を試す。
2. 権限を変更/失効し、既存セッションやトークンなど残るアクセスも確認する。
3. 更新を適用して正常性を検査し、失敗を想定した復旧も演習する。
4. 対象を廃止し、入口、アカウント、秘密情報、監視、バックアップ、課金対象資源の処理結果を資産一覧と照合する。

**全必須の合格条件:** (1) 役割別の許可/拒否が一致する。(2) 失効後に残るアクセスの扱いを確認する。(3) 更新後と復旧後に利用者操作が成功する。(4) 廃止範囲の残存物が確認され、保存するデータは理由と期限が残る。

**不合格例と補習:** 管理者権限で全部通す、VM削除だけで廃止扱い。利用者一人と資産一覧一枚から始め、追加→利用→失効→撤去を追跡する。

**証拠:** 権限表、許可/拒否結果、失効確認、更新/復旧ログ、資産照合、残存物の処理記録。**職場での境界:** 職場の保存義務や調査対象を演習判断で消さない。クラウド実行なしの場合、課金確認は理由付きNAとし、実際の撤去実績にしない。

### BX09: 他者が使える標準を作る

**段階:** BR6。**前提・入力・環境:** BR4〜BR5で再現できた構成や手順がある。元の作成者以外の実施者と、異なる入力の隔離環境を用意する。入力は利用対象、適用条件、除外条件、保守担当。

**実行順:**

1. 共通化する範囲と変更可能な入力、非対応条件、例外の申請方法を固定する。
2. 手順/設定モジュール/検査を版付きで渡し、別の人に異なる入力で実行してもらう。
3. 作成者の口頭補完が必要だった箇所、誤解、失敗を記録して改訂する。
4. 再実施し、成功率、質問箇所、手戻りなど事前に選んだ指標で改訂の効果を観測する。

**全必須の合格条件:** (1) 適用/非対応/例外/保守が定義される。(2) 別の人が異なる入力で実際に利用する。(3) 再利用結果を基に標準が改訂される。(4) 改訂後の再実行と効果観測がある。

**不合格例と補習:** テンプレートを公開して利用実績とする、作者自身の再実行だけ。小さな確認手順一つを別の人に渡し、質問と再試行を記録する。

**証拠:** 標準の版、実施者と入力、利用ログ、質問/手戻り、改訂差分、効果比較。**職場での境界:** 個人の標準案を全社標準として適用しない。他者がいなければ標準作成までの部分到達とし、他者利用はNOT RUN。

### BX10: 設計レビューを育成につなげる

**段階:** BR6。**前提・入力・環境:** 他者の要求・設計・検証記録と、レビュー協力への合意がある。演習用題材でもよい。入力はレビュー範囲、重要度基準、学習者の現在地。

**実行順:**

1. 要求と証拠を読み、事実の誤り、リスク、好みの違いを分ける。
2. 指摘ごとに対象、影響、根拠、確認方法を付け、優先度を決めて説明する。
3. 学習者本人に修正案を考え、説明・実行してもらう。分からない理由を確認して教材や課題を調整する。
4. 修正後を確認し、似た別条件でも本人が判断できるかを観測する。

**全必須の合格条件:** (1) 指摘は要求と根拠に対応する。(2) 採否理由と重大な未解決事項が記録される。(3) 学習者本人の説明・修正・実行がある。(4) 別条件での理解確認と指導方法の改善がある。

**不合格例と補習:** 全部書き直して渡す、言い方だけ整える、感謝されたので理解したと判断する。一つの通信許可ルールなど狭い題材で「理由を説明→本人が変更→別条件で確認」を行う。

**証拠:** レビュー対象版、指摘、根拠、採否、本人の説明、実行結果、別条件の確認、指導改訂。**職場での境界:** レビュー参加は最終承認者への就任を意味しない。機密設計や個人評価を無断で公開せず、AI代行の回答を学習者本人の理解記録にしない。

### BX11: 信頼性・費用・納期の判断を導く

**段階:** BR6。**前提・入力・環境:** SLI/SLO、復旧、費用範囲、運用負荷を説明できる。入力は現行構成、測定結果、予算/納期/人員の変更、意思決定者。演習なら関係者役を担う協力者を用意する。

**実行順:**

1. 変更された制約と影響する要求を特定し、測定値・見積・仮定・欠測を区別する。
2. 継続、縮小、延期、段階導入などの案を同じ費用・信頼性・運用負荷の軸で比較する。
3. 関係者に選択肢と残余リスクを説明し、決める事項を権限者へ渡して合意と例外条件を記録する。
4. 選ばれた案の検証可能な部分を演習し、見込みと結果の差を観測して判断を更新する。

**全必須の合格条件:** (1) 数値の出所と測定範囲が明確である。(2) 複数案が同じ軸で比較される。(3) 他者との説明・調整・意思決定の記録がある。(4) 検証結果と差分を基に判断の維持/更新を説明できる。

**不合格例と補習:** 信頼性目標を独断で下げる、最安値だけで比較、架空の関係者合意を作る。制約を一つ変えた二案比較から始め、提案と決裁を別欄にする。

**証拠:** SLI/SLO範囲、測定/費用前提、比較案、合意または演習役の判断記録、検証、更新理由。**職場での境界:** 事業リスク、予算、納期の最終決裁は権限者が行う。演習上の合意は組織承認や実務調整実績として表記しない。

### BX12: 運用実績から標準を改訂する

**段階:** BR6。**前提・入力・環境:** 実際に記録したラボ運用または公開可能な業務の障害・手戻り・負荷がある。元データがなければ先に観測する。入力は改善前の証拠、対象標準、協力者、観測方法。

**実行順:**

1. 事実と推測を分け、利用者影響・再発頻度・作業負担などから改善対象を選ぶ。
2. 改善仮説、期待する変化、副作用、確認期間、担当、期限を決める。
3. 手順・設定・監視・運用開始前レビューを改訂し、別の人に適用してもらう。
4. 比較可能な条件で改善後を観測し、再発・手戻り・負担・見逃しなどを比較する。採用継続、再改訂、撤回のいずれかを記録する。

**全必須の合格条件:** (1) 改善前の実測または実行証拠がある。(2) 他者による改訂標準の適用が確認できる。(3) 改善後の効果と副作用を観測する。(4) 結果に基づく標準の採否・版・次回見直し条件を残す。

**不合格例と補習:** 実装したから効果ありとする、欠測期間を再発ゼロと扱う、架空の事故で改善実績を作る。小さな手戻り一つを実測し、一変更だけ施して同条件で再確認する。

**証拠:** 改善前記録、仮説、変更、他者適用、観測窓と欠測、効果/副作用、採否、改訂版。**職場での境界:** 他部署へ影響する標準の改訂・展開には、その組織の権限と変更手続きを使う。ラボ運用の改善はラボ実績として示す。
