## 計画の前提

主軸はLinux、基準は週10時間です。既存のSE育成体系を合否の正本にします。旧24週教材には週15時間の計画もありますが、本案は同じ量を24週で消化すると約束するものではありません。旧教材は各SE条件の学習・補習素材として選びます。

24週×10時間＝240時間を基本課程の計画枠とし、総合課題に4〜8週・40〜80時間を別枠で置きます。準備、補習、評価者待ちなどによって延長します。BR4以降はBXの課題ごとの見積を立て、月数で熟練到達を決めません。

| 週に使える時間 | 同じ240時間の演習枠を確保する算術上の目安 | 調整方法 |
| --- | --- | --- |
| 5時間 | 約48週 | 同じ課題を分割し、復旧確認などの必須条件を省かない |
| 10時間 | 約24週 | 下表を基準に、不合格条件は復習して再提出する |
| 15時間 | 約16週 | 実演・復習・記録へ配分。別日課題や実観測日数は短縮しない |

これは工数の割算で、学習効率の保証ではありません。総合課題、休止、レビュー待ち、環境準備を含む実際の完了日は別に計画します。

## 最初の2週間

開始前に全教材を読破しません。準備未完ならSE00を進め、環境が使える人だけ最小サービスへ進みます。すでに手元にあるVM・資格情報を本設計が確認したわけではないため、実行前に本人が用途と対象を確認します。

| 回 | 実施する一つの仕事 | 終了時に残すもの |
| --- | --- | --- |
| 1 | 実行場所、VM、再作成経路、秘密値の保管を整理 | 環境票と現在地診断。未確認は未確認のまま |
| 2 | 専用Ubuntu環境で既存の前提診断を行う | コマンド、出力、FAIL/WARNの理由と次の行動 |
| 3 | app/nginxの役割と通信方向を読む | 手描きの構成図、期待HTTPコード |
| 4 | 既存ガイドの設定準備・最小起動・応答確認 | 2サービスの状態、認証あり/なしの実結果 |
| 5 | 予想と結果の違いを整理し、翌日に説明 | 30秒説明、説明できなかった一項目 |
| 6 | 計画停止・再開と応答再確認 | 停止中/再開後の出力。自動復旧試験とは別 |
| 7 | OS利用者・権限・サービスとログを観測 | SE01の最初の不足条件の記録 |
| 8 | 名前解決・経路・待受・HTTPをつなぐ | 症状、仮説、識別に使った観測 |
| 9 | 手順への依存を減らした再試行 | 支援量、版、対象、以前との違い |
| 10 | 週次レビュー、次のSE条件を一つ決める | 続行/補習/評価待ちと理由 |

1回60〜90分を目安に、残りは調査・記録・復習へ配分します。初回環境構築が長引いた場合、表の回数を実施済みとして進めず、その地点から続けます。

## 最小構成の実施カード

**目的：** app/nginxの2サービスについて、応答、認証、計画停止と再開を自分の出力で説明する。

**実行場所：** 破棄できる専用Ubuntu 24.04環境のBash、`ns7jp/server`のルート。Windows PowerShellへそのまま貼り付けない。既存サービスとComposeプロジェクト名が衝突する環境では実施しない。

**前提：** [現在の初心者ガイド](https://github.com/ns7jp/server/blob/main/docs/beginner-learning-guide.md)の実行場所・ツール導入・秘密値準備を先に完了する。今回確認した版は `d0a69321ffb3248c8e953d75bea5ff9512c1b838`。異なる版なら設定・期待値を照合する。ここは既存手順の要点であり、秘密値の生成手順を省略して起動できるという意味ではない。

**手順1：** `pwd`、`git rev-parse HEAD`、前提診断の出力を保存する。

**手順2：** `.env`と秘密値の準備・Git除外を、既存ガイドの順で確認する。値そのものを公開ログへ出さない。

**手順3：** 以下を一行ずつ実行し、各結果を確かめる。最初の構成検証が失敗したら起動へ進まない。

```bash
docker compose config --quiet
docker compose up -d --build app nginx
docker compose ps --all app nginx
```

appは起動しhealthy、nginxは起動状態であることを確認する。nginxにhealthcheck定義がなければhealthy表示を合格条件に足さない。

**手順4：** 同じUbuntuから次を実施する。最後は対話でパスワードを入力する。正しいユーザー名は使用する`.env`と照合する。以下の`monitor`は確認版の既定値。

```bash
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/healthz
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/metrics
curl -sS --user monitor -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/stats
```

| 観測 | 期待 | 判断 |
| --- | --- | --- |
| `/healthz` | 200 | このhealth応答を確認した |
| 認証なし`/` | 401 | 認証で制限されている |
| 認証なし`/metrics` | 401 | metricsも保護されている |
| 正しい認証の`/api/stats` | 200 | 認証後のAPI応答を確認した |
| 000、接続失敗 | HTTP応答に到達していない | curlのエラーと終了コード、経路・待受を調べる |
| 502 | nginxから上流への接続などを調べる | app状態とnginx/appログを照合する |

`/healthz`の200だけでは、認証、DB、監視収集、通知、復元、OS全体の正常性を保証しない。

**手順5：** 検証用2サービスを計画停止し、状態を確認する。停止後のcurlは到達失敗を想定し、状態コードだけでなくエラーと終了コードを記録する。

```bash
docker compose stop app nginx
docker compose ps --all app nginx
```

再開は既存ガイドに沿って行い、healthyを待って手順4の4項目を再確認する。

```bash
docker compose up -d app nginx
docker compose ps --all app nginx
```

終了は同じ専用プロジェクトで `docker compose down` を使う。初回演習の片付けでvolume削除を追加しない。停止・再開・終了とデータ削除は別の操作として理解する。[Docker stop仕様](https://docs.docker.com/reference/cli/docker/compose/stop/)

**提出：** 対象とSHA、前後の状態、4つのHTTP結果、停止と再開の結果、秘密値を含まないログ、30秒の説明、まだ試験していない範囲。**完了：** これらを既存入門ガイドに照合して記録した時点。D-1、自動復旧、全監視の実測やBR3到達へ拡大しない。

## 基本課程の24週計画

下表は時間の割り振りです。各行の短い完了欄が既存の4条件を置き換えるものではなく、[SE00〜SE07の正本](https://github.com/ns7jp/ns7jp/blob/b3dd74756c53b6eeebb38c5fc65b16a7d27f8824/docs/server-engineer/curriculum.json)と詳細課題をすべて確認します。

| 週 | SEとの対応 | 中心課題 | 完了時の証拠 |
| --- | --- | --- | --- |
| 開始前 | SE00 | 対象、VM再作成、予想と事実、説明 | 環境票、出力、翌日の説明 |
| W1〜2 | SE01 | 新規Linux、利用者・権限、必要ツール | 新規性、許可/拒否、設定の理由 |
| W3〜4 | SE01 | サービス、ログ、追加ディスク、再起動 | 正常/異常、永続化、再起動後の結果 |
| W5〜6 | SE02 | IP、経路、名前解決、通信図 | 正常と失敗を分ける観測 |
| W7〜8 | SE02 | SSH、FW、未知の通信障害 | 許可/拒否、戻し方、仮説の変化 |
| W9〜10 | SE03 | app/nginx、HTTP、認証、TLS | 応答と証明書の確認、認証拒否 |

| W15〜16 | SE04 | 詳細設定、変更、復旧、引き渡し設計 | パラメータ、試験仕様、レビュー修正 |
| W17〜18 | SE05 | Git、Ansible、失敗停止、再適用 | 差分、実適用、再実行の検証 |

SE07-C2は詳細本文に従い、**変更を2項目以上、うち1項目は通信または運用条件**にする。別の新規VM、別セッション、別UTC日付も確認する。調査時に評価要約へ残っていた変更1項目の記述は、[既存の評価手順](../assessment.md)でも詳細本文に合わせた。

## BR4以降の進め方

| 段階 | 基本順序 | 同時に進められるもの | 次段階の条件 |
| --- | --- | --- | --- |
| BR4 | BX01再構築→BX02依存障害→BX03別環境復元 | BX04の観測を先に始め、試験中の期間は明記 | BX01〜04の必須条件と人の確認がそろう |
| BR5 | BX05方式比較→BX06移行 | BX07障害連携、BX08権限・更新を別セッションで実施 | BX05〜08の判断、実技、関係者との確認がそろう |
| BR6 | BX09他者再現→BX10レビュー・育成 | BX11複数案件の判断、BX12効果観測 | BX09〜12の演習評価。実務の熟練判断は別途 |

発展課題の説明や設計案を読むことは、前段階の合格待ちでも進められます。正式な技能評価の順序と、読書や支援付き練習の順序を混同しません。第三者不在でも準備・自己練習を続け、人の実施が必要な条件は待機として残します。

課題ごとに「準備・実行・計測・記録・再試験・評価待ち」を分けて見積もります。BX04やBX12の観測期間を見積工数だけで埋めず、実際に観測できた期間と欠測を報告します。

## 毎週の運用

週10時間の例は、資料と説明2時間、実演4時間、条件変更と切り分け2時間、記録とレビュー2時間です。仕事と同じく、一つの課題を受け入れ条件まで持っていく時間を確保します。

1回90分なら、前回の説明10分、今回の予想10分、実行40分、確認20分、片付け・次の課題10分に分けます。安全な停止・保存が終わらなければ、時間枠を理由に必要作業を打ち切りません。

翌日、7日後、28日後に短い再説明と条件変更を試します。この間隔は運用上の目安です。間違えたら教材の該当箇所を読み、別の試行として再確認します。

詰まったら、対象・直前の変更・期待・実結果を保存し、仮説を二つ挙げ、両者を見分ける観測を一つ選びます。約30分調べても仮説を更新できない場合は相談材料を作る目安にします。これは障害対応の中止期限ではありません。同じ失敗が続けば、より小さな構成に戻す、公式資料へ戻る、評価者へ質問する、のいずれかを選びます。

## 職場への30・60・90日接続

[既存の職場接続](https://github.com/ns7jp/ns7jp/blob/b3dd74756c53b6eeebb38c5fc65b16a7d27f8824/docs/server-engineer/workplace.md)を使い、以下を担当範囲の確認材料にする。日数経過だけで権限を増やさない。

| 時期の目安 | 担当の広げ方 | 合意・観察するもの |
| --- | --- | --- |
| 1〜30日 | 既存構成・運用・連絡経路を理解し、指導下で一部分を実施 | 対象・権限・変更窓・相談条件、本人が担当した範囲 |
| 31〜60日 | 合意した小変更を設計から結果報告まで担当 | 事前レビュー、影響範囲、切戻し、他者確認 |
| 61〜90日 | 限定した案件を一周し、改善案を根拠付きで提出 | 受入、引き渡し、障害/残課題、次に任せる範囲 |

上司・リーダー等が実際の環境で担当を決める。顧客情報や社内ログは会社の保管経路に残し、公開ポートフォリオへ無断で移さない。公開可能な説明は実施範囲と一般化した学びに限定する。

## 学習が進んでいるか測る

追う指標は、実施条件数と評価済み条件数を分けた進捗、1週間後に説明できた項目、条件変更で起きた誤り、復旧後確認の抜け、他者が詰まった箇所、観測の欠測です。コード行数や連続学習日数だけを主指標にしません。

初期値は未確認です。4週ごとに、本人の説明・提出の品質・補習にかかる時間を見て計画を調整します。教材自体の分かりにくさも記録し、本人の能力不足と即断しません。新しい改善案は採否待ちに置き、今の必須課題が完了したらいったん区切ります。
